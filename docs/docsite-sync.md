# How The In-Product Manual Stays In Sync With docs/USER-MANUAL.md

The operator console's `/help` screen (backed by `GET /api/public/manual`)
never reads `docs/USER-MANUAL.md` at runtime and never parses markdown at
runtime. It reads one pre-rendered, pre-sanitized artifact,
`civiccast/docsite/manual.json`, that ships inside the installed `civiccast`
package payload — the same way `USER-MANUAL.pdf` and `USER-MANUAL.docx` are
rendered as release artifacts, not generated on demand. The Markdown is the
current manual source. Every PDF, DOCX, and in-product copy distributed with a
release must be rendered from that same source revision and bound by its render
manifest; an older generated copy is not an exception or current guidance.
Candidate PDF/DOCX renders are staged under
`artifacts/release-preparation/manual/`.

## The pipeline

1. `docs/USER-MANUAL.md` is the single source of truth (per `CLAUDE.md`).
2. `scripts/render_docsite_manual.py` renders it to HTML with the same
   `pandoc` binary `scripts/render_user_manual.py` already requires for the
   PDF/DOCX artifacts (one rendering engine, not two), then:
   - embeds every local image (currently the two architecture diagrams,
     referenced relative to `docs/`) as a base64 `data:` URI
     (`civiccast/docsite/render.py::embed_local_images`) — a relative path
     doesn't resolve to anything once this HTML is served from
     `manual.json` with no filesystem underneath it, so embedding once at
     render time keeps the manual fully self-contained and working with no
     internet connection,
   - sanitizes the HTML through an allowlist parser
     (`civiccast/docsite/render.py::sanitize_html`) so no raw-HTML block in
     the source and no future pandoc extension can smuggle a `<script>` or
     an event-handler attribute into the operator console,
   - extracts a flat table of contents from every `id`-bearing heading
     (`civiccast/docsite/render.py::extract_toc`) — every `##`/`###`/`####`
     heading in the manual gets one, whether from an explicit `{#anchor}`
     tag or pandoc's own GitHub-style auto-slug,
   - writes both as `civiccast/docsite/manual.json`, plus a companion hash
     manifest `civiccast/docsite/manual.render.json` recording the
     newline-normalized SHA-256 of `docs/USER-MANUAL.md` and the SHA-256 of
     the JSON artifact itself. The release render manifest binds its PDF and
     DOCX to that same current-source hash; candidate files and their manifest
     are staged together under `artifacts/release-preparation/manual/`.
3. `civiccast/docsite/manual.json` is committed to the repository, like the
   PDF/DOCX. It is **not** regenerated by the installer or at process
   startup.
4. `pyproject.toml`'s `[tool.hatch.build.targets.wheel.force-include]`
   ships `civiccast/docsite/manual.json` inside the wheel — the same
   force-include mechanism that already ships
   `civiccast/records/fixtures/*.ttf` — so it rides along in the installer
   payload with zero packaging-script changes and works fully offline.
5. `civiccast/docsite/service.py::load_manual()` reads and
   pydantic-validates that one file at request time (cached, keyed on the
   file's own mtime so a live dev server picks up a re-render without a
   restart). It never touches `docs/` or `pandoc` at runtime.

## The drift gate

`scripts/render_docsite_manual.py --check-current` (wired into
`.github/workflows/ci-docs.yml`, right next to the candidate
`render_user_manual.py --check-current` step) fails the build if:

- `docs/USER-MANUAL.md` changed since `civiccast/docsite/manual.json` was
  last rendered (source hash mismatch), or
- `civiccast/docsite/manual.json` was hand-edited or only partially
  regenerated (its own recorded hash mismatch).

This does not require byte-identical HTML across different `pandoc` patch
versions: attribute ordering or slug details can differ, and `ci-docs.yml`
does not pin a `pandoc` version. That renderer variation does not permit a
release to carry forward a PDF/DOCX or in-product manual from an older source
revision. Before release, render every distributed format from the current
`docs/USER-MANUAL.md` and verify each format's source-bound manifest. **After
editing `docs/USER-MANUAL.md`, render both the in-product artifact and the
candidate PDFs/DOCX:**

```sh
# Refresh the tracked PDF, DOCX, and render manifest under docs/.
uv run python scripts/render_user_manual.py --out-dir docs

# Render release-candidate PDF/DOCX and manifest to the default
# artifacts/release-preparation/manual/ directory.
uv run python scripts/render_user_manual.py

# Refresh the in-product HTML and source-hash manifest.
uv run python scripts/render_docsite_manual.py
```

Commit the resulting tracked `docs/USER-MANUAL.pdf`, `docs/USER-MANUAL.docx`,
`docs/USER-MANUAL.render.json`, `civiccast/docsite/manual.json`, and
`civiccast/docsite/manual.render.json` alongside the Markdown edit. The release
must include its candidate PDF/DOCX and matching manifest from that same source
revision; do not label an older tracked or attached render current.

## Why not parse markdown (or read the .md file) at runtime

- **Offline help.** The in-product manual and its embedded images are bundled
  with the application, so operators can open help without an internet
  connection. This is separate from setup acquisition: setup may download
  components and models unless the station uses the complete offline kit.
  `civiccast/app.py`'s `lan_only_station` handling limits runtime documentation
  routes; it does not describe or prove the installer's download behavior. A
  build-time artifact has no runtime dependency on `docs/` being present in the
  installed payload.
- **No new pinned runtime dependency.** The native app's dependency surface
  is deliberately narrow (see `pyproject.toml`'s `dependencies` comments).
  `pandoc` is already a required build/CI tool for the PDF/DOCX pipeline;
  reusing it at build time avoids adding a markdown-parsing library
  (`markdown`, `mistune`, `markdown-it-py`, ...) to the shipped runtime.
- **One rendering engine.** Using `pandoc` for both the PDF/DOCX and the
  in-product HTML means there is exactly one markdown-syntax interpretation
  to reason about across every rendered artifact.
