# v1.4 Restore, Update, And Beta Walkthrough Proof

This is the v1.4 operations-hardening protocol for beta stations. It turns the
current restore and update surfaces into explicit proof steps without claiming a
full disaster-recovery product before it exists.

## Restore Proof Target

The v1.4 restore target is an isolated station profile. Do not restore over the
active meeting station during beta proof.

The proof scope is:

- Database state: schedules, assets, caption review, summaries, signed records,
  subscribers, provider proof state, and operator state.
- Media artifacts: uploaded files, generated packages, private rehearsal proof,
  and signed-record artifacts.
- Configuration: station setup, storage paths, backup destination, provider
  credential handles, and non-secret setup state.
- Redaction boundary: secrets are not printed in proof files, support bundles,
  or operator-visible evidence.

## Restore Rehearsal Steps

1. Finish durable storage setup and run **Verify backup** in Setup.
2. Open **System Health** and confirm restore status is not blocked by backup.
3. Run **Restore rehearsal**.
4. Confirm the API reports the isolated target profile and the DB/media/config
   restore plan.
5. Keep the proof summary with release evidence for the tested version.
6. Before any public claim, repeat the proof against a station profile populated
   with representative database rows, media files, provider proof records, and
   signed records.

The current product rehearsal writes a proof payload to backup storage, copies
it into an isolated restore workspace, verifies checksum stability, cleans up
temporary files, and records the result. That is a beta restore proof for the
backup destination and plan, not a full disaster-recovery guarantee.

## Update And Rollback Steps

1. Confirm no meeting is in progress and backup status is ready.
2. Choose or build the rollback artifact before applying an update.
3. Apply the update only inside a maintenance window with the operator console
   closed.
4. Run database migrations and startup checks before reopening the console.
5. Run **Safe to broadcast** and a private rehearsal after the update.
6. If post-update proof fails, reinstall the rollback artifact and rerun **Safe
   to broadcast**.
7. Keep the rollback artifact available until the next successful meeting proof.

The System Health update panel exposes these steps and whether a rollback
artifact path is configured. A beta update is blocked when backup is not ready.

## Observed Walkthrough Protocol

v1.4 needs two observed walkthroughs before release promotion:

- Non-technical operator: first setup, backup verification, restore rehearsal,
  private rehearsal, live-room preflight, records review, and publish handoff.
- Technical admin: installer acquisition, storage setup, provider proof,
  support bundle, restore/update status, rollback artifact selection, and
  evidence collection.

Record for each walkthrough:

- Tester role, date, CivicCast version, OS, and install artifact.
- Actions completed without help.
- Actions completed only after help.
- Exact wording or screen that caused hesitation.
- Any support bundle generated.
- Product fix, documentation fix, or regression test created from each issue.

Do not promote v1.4 as walkthrough-complete until both observed sessions are
recorded or a human release owner explicitly accepts that blocker.
