## What this candidate is

Two shipped-product bugs found by Gate A on the beta.3/beta.4 line -- both
fixed here, pending tonight's run proving it:

1. **The GStreamer playout worker died before it could ever run, on every
   machine without a system-wide GStreamer install already on `PATH`.**
   The control-plane child process's environment is built by composing
   several env dicts together, and the one carrying the bundled
   GStreamer `bin` directory prepend was merged UNDER the supervisor's
   stock `PATH` rather than over it, so that prepend was discarded on
   every station. Without it, `gi` cannot `LoadLibrary` on
   `gstreamer-1.0-0.dll` (the per-process `os.add_dll_directory` list
   does not help here -- Win32's bare-name search only honors `PATH`),
   the `gi.overrides.Gst` import fails with `TypeError: must be an
   interface`, and the worker exits at import before it can do anything
   else (#154). Every customer box and every sandbox run hit this; only a
   dev box with GStreamer already installed system-wide was masked from
   it. Proof: Gate A evidence `20260903-225553Z` on kit `9479c56` shows
   the worker start and stay alive after the fix, against the import-time
   crash in evidence `20260903-195625Z` on the same kit line before it.
   Two secondary bugs were also found and fixed, but neither could matter
   until the import-time crash above was fixed: a module-identity mismatch
   between `worker.py`'s by-path import and `engine.py`'s package-form
   import that made engine dispatch miss on every program leg once the
   worker did start (#153), and a hardware-decoder rank policy that missed
   the `d3d12` factory family, so `decodebin` autoplugged a GPU decoder
   that cannot actually decode on a VM/sandbox/WARP adapter and stalled
   the pipeline ~10s after `PLAYING` (also #154). See the `[Unreleased]`
   section of `CHANGELOG.md` for the full account of all three.
2. **The packaged `tsp.exe` shipped without the data files TSDuck resolves
   relative to its own directory on Windows, so Gate A's TSDuck capture
   itself could not measure the product engine even after the worker fixes
   above landed** (#156, open as of this draft -- see
   "In flight" below).

**Resolved (T4 passed; T6 did not -- on the relaunch-count rule, not on
liveness).** `v1.0.0-beta.4` is the first CivicCast release whose Gate A run
measured real MPEG-TS packets from the GStreamer default engine, not the
ffmpeg fallback -- superseding beta.3's `PASS_PRODUCT_ENGINE` grade, which
was a grader false pass already retracted in
`v1.0.0-beta.3-verification.md` (the capture tool bug that produced it is
fixed in #145; the retraction is not new). Gate A run `33837269907` against
kit `4b30c99`, clean lane:

```
T4_RESULT=PASS_PRODUCT_ENGINE; tsp exited 0 over 1233 analysed packets
with 0 invalid syncs / transport errors / discontinuities
```

**Do not read this as "the soak passed."** The separate 120-minute engine
soak (kit `4b30c99`, T6) ran the same healthy engine for two continuous
hours and still returned `T6_RESULT=FAIL` -- see "120-minute engine soak"
below for the real numbers and why a FAIL there does not contradict the T4
PASS above. Nothing in this document claims the soak passed; see "Claims

## 120-minute engine soak

**2026-09-04, sandbox, lane PR #155 T6, kit `4b30c99`.** Three channels
(`public`, `education`, `government`) ran on the GStreamer default engine,
each playing three real LPM sample clips scheduled as premieres, for 120
continuous minutes. 22 scheduling beats x 3 channels = 66 samples; every one
of the 66 was measured `ON_AIR` with a passing TSDuck capture (minimum 1357
packets per 8-second capture window). Worker RSS stayed flat across the
whole run, roughly 445-566 MB, no leak trend.

Lane verdict, as the harness wrote it:

```
T6_RESULT=FAIL reason=soak-public relaunches=8 (>3); soak-education
relaunches=6 (>3); soak-government relaunches=7 (>3) beats=22
failed_beats=0
```

**The FAIL is the relaunch-count rule, not liveness.** `failed_beats=0`: no
sample, on any channel, at any beat, was ever off-air or failed its TSDuck
capture. What tripped the T6 verdict is a separate counted-relaunch budget
(`>3` relaunches per channel over the run): each channel restarted 6-8
times over the 120-minute run, more than T6's `>3` budget. Each restart is
a short on-air blip (the gap between the old worker's last frame and the
new worker reaching `PLAYING`), not an outage the operator has to
intervene in. Evidence:
`C:\Users\scott\Desktop\CIVICCAST-EVIDENCE\soak-120-4b30c99-20260904`.

**Correction (2026-09-05): the root-cause explanation below was wrong and
is retracted.** This document previously said the playout worker exits
cleanly at the end of every source plan
(`civiccast/egress/source_plan.py`'s `max_segments=8`), roughly every
10-15 minutes under continuous back-to-back premieres, and credited
beta.5's #162 (seamless plan rollover) with removing the blip and the
relaunch count. That was inferred from worker pid changes across
scheduling beats, never verified against the worker's own logs, and it is
wrong: this soak's `gst-worker.stderr.log` for all three channels contains
only

```
CTRL stall: no output for 10s — quitting for daemon restart
```

lines -- 7/9/10 occurrences across education/government/public -- and no
EOS or plan-end exit anywhere. A beta.5 retest soak (kit `e502074`,
2026-09-05) shows the same pattern: 8/8/7 stall lines, again no plan-end
exit. The plans actually running were 28-38 minutes long while restarts
came 1-25 minutes apart, which is inconsistent with a plan-boundary cause.

Two contributing issues were found in the sandbox soaks, both dated
2026-09-05:

- **(a) Sandbox-specific output stalls.** The software-encoded channels
  see periodic output stalls in the GPU-less Windows Sandbox test
  environment while the source preparer conforms clips synchronously on
  the same box. Whether this reproduces on real station hardware (an R7
  with an iGPU, where operators have reported no such issue) is not
  established.
- **(b) A real product bug: the restart-handling automation pass
  crashed.** Every restart's channel-automation pass then raised
  `UnicodeEncodeError: 'charmap' codec can't encode character '\ufffd' in
  position 118` -- the worker's stall message folds a `\ufffd` replacement
  character into `last_error`, and writing that value out under the
  process's `cp1252` console/client encoding failed, skipping channel
  supervision for that channel until the next tick. Fixed in beta.5 by
  #169 (merged); #167, an earlier attempt at the same fix (ASCII-fold
  only, not the underlying state-write encoding), is closed, superseded
  by #169.

**#162's seamless plan rollover is a real improvement for genuine
plan-boundary transitions, but it was never exercised by either soak --
no plan boundary was ever reached -- and it is not what fixes the
restarts measured here.** Evidence:
`C:\Users\scott\Desktop\CIVICCAST-EVIDENCE\soak-120-4b30c99-20260904`
(beta.4) and
`C:\Users\scott\Desktop\CIVICCAST-EVIDENCE\soak-120-e502074-20260905`
(beta.5 retest); see "Known issues in beta.4" below.

**Update (2026-09-05, real tester hardware): (a) and (b) above are not
what operators actually experience.** Measured on real station hardware,
the restarts operators see -- a brief on-air blip every 10-25 minutes on a
multi-channel, CPU-only station running with live captions on -- are
driven by the live caption tap, not by a sandbox artifact or the encoding
bug above. `civiccast/captions/tap_worker.py` transcribes every `ON_AIR`
channel in-process on CPU; with three channels captioning at once it
exceeds its own settled-segment backlog limit roughly every 30 seconds
(`CRITICAL civiccast.captions.tap_worker: Caption tap overload for
channel <id>: N settled segments exceeds the maximum 2 ...`) and never
backs off, driving the control-plane process to ~2.5 CPU cores and
starving the GStreamer playout workers -- each worker's own 10-second
stall watchdog then fires and exits, which the daemon relaunches. Fixed
in beta.5: #169 (the state-write `UnicodeEncodeError` above, a real bug
but not this driver). The caption-tap overload fix itself has no merged
PR yet (PR pending). **Workaround for beta.4 operators: none in the
product.** `CIVICCAST_CAPTION_TAP` is the only switch for the live
caption tap, and a native station's control-plane process hardcodes it
to `inline` unconditionally (`civiccast/native/station_runtime.py:1361`)
-- there is no per-channel or operator-console setting to turn live
captioning off on a beta.4 station.

## Known issues in beta.4

1. **Each channel's playout worker restarts periodically under continuous
   premiere scheduling, causing a short on-air blip.** This is what the
   120-minute engine soak above measured as `T6_RESULT=FAIL` on the
   relaunch-count rule (`failed_beats=0` -- no sample ever failed or went
   off-air; the harness counts relaunches, not outages). This section
   previously attributed the restarts to the worker exiting at the end of
   its source plan (`max_segments=8`) every 10-15 minutes and credited
   beta.5's #162 with fixing it; that explanation was an unverified
   inference and is retracted -- see "120-minute engine soak" above for
   what the worker's own logs actually show. Contributing issues found in
   the sandbox soaks, 2026-09-05: **(a)** periodic output stalls specific
   to the GPU-less Windows Sandbox test environment, not established to
   reproduce on real station hardware; and **(b)** a `UnicodeEncodeError`
   in the channel-automation pass on every restart, which skipped channel
   supervision for that channel -- a real product bug, fixed in beta.5 by
   #169 (#167, an earlier attempt, is closed/superseded). #162's seamless
   plan rollover is a genuine improvement for plan-boundary transitions
   but does not address either issue above.
   **What operators actually see, measured on real tester hardware
   (2026-09-05): a brief on-air blip every 10-25 minutes on a
   multi-channel, CPU-only station with live captions on**, driven by the
   live caption tap (`civiccast/captions/tap_worker.py`) transcribing
   every `ON_AIR` channel in-process on CPU. On three simultaneous
   channels it exceeds its own backlog limit every ~30 seconds (`CRITICAL
   civiccast.captions.tap_worker: Caption tap overload for channel <id>:
   N settled segments exceeds the maximum 2 ...`), never backs off, and
   drives the control-plane process to ~2.5 CPU cores, starving the
   GStreamer playout workers -- their 10-second stall watchdog then
   exits, which the daemon relaunches. Fixed in beta.5: #169 (the
   encoding crash above). The caption-tap overload fix itself has no
   merged PR yet (PR pending). **Workaround for beta.4: none in the
   product** -- `CIVICCAST_CAPTION_TAP` is hardcoded to `inline` on every
   native station (`civiccast/native/station_runtime.py:1361`), with no
   per-channel or operator-console setting to disable it.
2. **TSDuck data files now shipped with the packaged `tsp.exe`** (#156).
   Previously `tsp.exe` had its plugin DLLs but not the `.names`/`.xml` data
   files TSDuck resolves relative to its own directory on Windows, so even
   a healthy engine's TS capture failed with errors like `file not found:
   tsduck.hfbands.xml`. Fixed by shipping the ~1 MB of missing data files in
   the server pack; this is what makes the T4 `PASS_PRODUCT_ENGINE` result
   above possible at all.
3. **Upgrade over a running beta.3 station fixed** (#159). Before the fix,
   the upgrade's provision step unconditionally start/stopped a PostgreSQL
   cluster that the freshly started station service already owned and had
   running -- the provision step's own start/stop, colliding with the
   service's already-live instance of the same cluster, failed the install
   outright and forced a crash recovery of the database on the next
   successful start. The fix has the provision step recognize a cluster the
   running station already owns and migrate it in place instead of
   restarting it out from under the live service.

## Claims and wording check

No sentence in this document, the release notes, `CHANGELOG.md`, or
`README.md`'s engine bullet may say the 120-minute engine soak "passed."
The accurate framing, used throughout: **the engine stayed live and on-air
for the full 2 hours (`failed_beats=0` across 66 samples); the T6 lane
itself failed, on the relaunch-count rule, not on liveness or packet
quality.** "Passed" and "soak passed" are reserved for a future run under a
budget sized for continuous-premiere density, or after the restart driver
measured on real tester hardware (the live caption tap's CPU overload,
2026-09-05 above; fix PR pending) is confirmed cleared under a longer or
hardware-matched retest. The automation `UnicodeEncodeError` found in the
sandbox soaks is a real, separate bug, fixed in beta.5 by #169 (#167,
superseded). Beta.5's #162 seamless plan rollover is unrelated to this
particular relaunch count -- it addresses genuine plan-boundary
transitions, which neither soak ever reached.

## Scope

This verification covers the Gate A station-acceptance lanes (clean
install, cross-version upgrade, download-only, and -- new this candidate --
the T4 product-engine measurement) and the publish-time asset integrity
checks above. It does not itself constitute field proof across many
machines, live external provider delivery, physical SDI/DeckLink capture,
real cable-operator headends, or unattended multi-day station operation --
see "What's proven in this candidate" and "Honestly scoped" in
