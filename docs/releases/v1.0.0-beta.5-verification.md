## What this candidate is

Three kinds of change since `v1.0.0-beta.4` (source SHA
`c27c6e70200406b51558ee1ef6b3a95ee4dc4426`):

1. **Headline: beta.4's soak restarts diagnosed correctly, and the real bug
   fixed (#167).** beta.4's own 120-minute engine soak (recorded in
   [`v1.0.0-beta.4-verification.md`](v1.0.0-beta.4-verification.md)) proved
   the GStreamer playout engine itself was healthy for two full hours
   (`failed_beats=0`) but failed Gate A's T6 lane on a relaunch-count rule.
   That document originally attributed the restarts to the worker exiting
   at the end of every source plan (`max_segments=8`) every 10-15 minutes
   and credited this candidate's #162 (below) with the fix -- **that
   explanation was wrong and has been retracted** (corrected 2026-09-05 in
   `v1.0.0-beta.4-verification.md` and the beta.4 release notes). It was
   inferred from worker pid changes, never from the worker's own logs.

   Reading the actual `gst-worker.stderr.log` from the beta.4 soak (kit
   `4b30c99`) and a beta.5 retest soak (kit `e502074`) shows only `CTRL
   stall: no output for 10s — quitting for daemon restart` lines in both
   runs (beta.4: 7/9/10 occurrences across education/government/public;
   beta.5: 8/8/7) -- no EOS or plan-end exit in either. Plans actually ran
   28-38 minutes while restarts came 1-25 minutes apart, ruling out a
   plan-boundary cause. Two real causes, both found 2026-09-05: **(a)**
   periodic output stalls specific to the software-encoded channels in the
   GPU-less Windows Sandbox test environment (while the source preparer
   conforms clips synchronously on the same box), not established to
   reproduce on real station hardware (an R7 with an iGPU, where operators
   have reported no such issue); and **(b)** a real product bug -- every
   restart's channel-automation pass raised `UnicodeEncodeError: 'charmap'
   codec can't encode character '\ufffd' in position 118` (the worker's
   stall message folds a `\ufffd` replacement character into `last_error`,
   and writing it out under the process's `cp1252` client encoding
   failed), skipping channel supervision for that channel. **Fixed in this
   candidate by #167**: an ASCII-safe child-log tail so a non-ASCII byte in
   the worker's stderr can no longer reach `last_error` in a form that
   breaks the write; a `client_encoding` fix for the underlying database
   write path is a tracked follow-up.

   **#162, below, is a real improvement for genuine plan-boundary
   transitions, but it was never exercised by either soak and is not what
   fixes the beta.4 restarts.** Evidence:
   `C:\Users\scott\Desktop\CIVICCAST-EVIDENCE\soak-120-4b30c99-20260904`
   (beta.4) and
   `C:\Users\scott\Desktop\CIVICCAST-EVIDENCE\soak-120-e502074-20260905`
   (beta.5 retest).

2. **Also in this candidate: seamless source-plan rollover for genuine
   plan-boundary transitions (#162).** Independent of the diagnosis above,
   the playout worker genuinely does exit cleanly at the end of every
   source plan (`civiccast/egress/source_plan.py`'s `max_segments=8`
   bounds how many segments one worker process plans before it exits by
   design), which can happen under continuous back-to-back premieres.
   #162 fixes that at the root: `ChannelAutomationService._check_plan_rollover` (new in
   `civiccast/egress/automation.py`) watches the projected wall-clock end of
   the plan a channel is actively airing and, within 30 seconds of that end,
   re-fetches the schedule through the same `source_plan_provider` already
   in use. Because `build_source_plan_from_schedule` always resumes the
   currently-airing item and windows forward from "now," a later fetch
   naturally reaches further once more has been published -- that recompute
   *is* the rollover. If the fresh plan extends further, the existing
   `"reload"` command (the same one `_check_slate_replan` already uses for
   the slate-to-program transition) is enqueued; `GstPlayoutStrategy.reload_content`
   rebuilds the program leg in place and switches both video and audio onto
   the new leg's first buffer at the outgoing clip's end -- EOS is dropped on
   the outgoing selector pads, running-time is rebased, and the new leg is
   held prerolled so the switch has nothing left to wait on. The channel's
   `state` row never leaves `ON_AIR` during the swap; only a `TRANSITIONING`
   *proof event* is recorded, matching the existing slate-to-program
   transition's own behavior. If the schedule genuinely has nothing further
   published, this is a deliberate no-op and the plan is left to reach its
   natural end -- closing that residual gap (seamlessly swapping onto
   slate/filler *before* genuine schedule exhaustion) is a separate,
   smaller follow-on, not part of this fix. The FFmpeg-concat engine
   (`supports_content_reload = False`) still benefits from the same
   `"reload"` command: `_request_reload` marks the channel `TRANSITIONING`
   and defers to the existing graceful pending-reload handoff rather than
   force-killing the worker, so the restart that does happen there is no
   worse than before.

   Proven on HALO with the bundled GStreamer: the rollover engine test suite
   passed 5/5, TSDuck showed 0 discontinuities and 0 PCR/PTS leaps across the
   monitored rollovers. **Known residual, carried forward as a known issue
   below:** if the next leg is not ready before the outgoing clip ends, the
   output freezes until it is ready or the existing 10-second stall watchdog
   restarts the channel -- the immediate-switch (non-rollover) path is
   unchanged by this fix.

3. **Gate A harness fixes -- the independent post-upgrade schema proof now
   actually executes (#158, #160, #161, #163).** Four bugs in the harness
   itself, found in sequence as each one was fixed and the next one surfaced
   underneath it, all on the cross-version-upgrade lane's post-upgrade
   `psql` schema proof (a check that runs independently of the product's own
   health endpoint, so a product-side false pass can't hide a database left
   mid-migration):
   - **#158 -- `tsp.exe`'s exit code came back `null` on Windows PowerShell
     5.1.** `Start-Process -PassThru` + `Wait-Process -Id` leaves
     `$proc.ExitCode` null unless the process handle was touched first (a
     PS 5.1 quirk); Gate A run `33826665417` on kit `4b30c99` captured a
     full, healthy TSDuck engine report (1229 packets, 0 invalid syncs, 0
     transport errors, AVC 720p + AAC on PID 65/66) yet still judged T4
     fail-exit- on the null exit code alone. Fixed by caching
     `$proc.Handle` and waiting on the object; contract test added.
   - **#160 -- the schema proof read the installer's `DatabaseUrl` from the
     wrong registry key.** The installer records it under
     `HKLM\Software\CivicCast\Native`; the harness read
     `HKLM\SOFTWARE\CivicCast` and judged every upgrade run that reached
     this check `<no-database-url>` -- first seen on Gate A run
     `33857982657` (kit `c27c6e7`), where install/activation/health all
     independently passed. Harness-only; a contract test now pins the key
     against the NSIS source so the two can't drift apart silently again.
   - **#161 -- the proof's SQL argument to `psql` was not quoted.**
     `Start-Process -ArgumentList` does not quote its elements, so the SQL
     statement reached `psql` split across nine separate arguments: `psql`
     warned `extra command-line argument ... ignored`, ran a bare `SELECT`,
     exited `0` with no rows, and the upgrade lane judged
     `<no-alembic-version-row>` (Gate A run `33870994702`, kit `c27c6e7`,
     install/activation/health all independently passing). Fixed by
     quoting the SQL argument and treating an exit-0 result carrying those
     warnings as a failed proof rather than a silent pass; contract test
     added.
   - **#163 -- the proof's single `UNION ALL` query failed as a whole when
     only one of the two possible namespaces has an `alembic_version`
     table.** The product keeps its version table in the `civiccast`
     schema, not `public`; querying both in one statement fails outright
     when `public.alembic_version` does not exist at all (Gate A run
     `33885550628`, kit `c27c6e7`, recorded `<psql-failed>` with `relation
     "public.alembic_version" does not exist` while
     install/activation/health/DB-at-head all independently passed). Fixed
     by running one statement per namespace and falling through cleanly on
     "does not exist"; contract test added.

   Each of these bugs sat *underneath* the one fixed before it -- fixing
   #158 exposed #160, fixing #160 exposed #161, fixing #161 exposed #163.
   Tonight's Gate A run is the first whose cross-version-upgrade lane can
   actually reach a real, independent `psql`-read verdict on the
   post-upgrade schema instead of failing inside the proof harness itself
   before it ever produced one.

   ready before the outgoing clip ends, the output freezes until it becomes
   ready or the existing 10-second stall watchdog restarts the channel. The
   immediate-switch (non-rollover) path is unchanged. Not yet scheduled;
   tracked as a follow-on to #162.
2. **Gate A harness self-test lane still to add** (batch 27). The four
   independent-proof bugs above (#158, #160, #161, #163) were each found by
   a real Gate A run failing in a new way, one at a time, rather than by a
   test that exercises the harness's own proof logic in isolation. A
   self-test lane for the harness itself (so a fifth latent bug in the same
   proof path is caught before a live run, not after) is queued as batch 27
   and is not part of this candidate.

## Scope

This verification covers the Gate A station-acceptance lanes (clean
install, cross-version upgrade, download-only), the T4 product-engine
measurement carried forward unchanged from beta.4 (this candidate does not
touch the GStreamer engine's decode/PATH/module-identity fixes), the new T6
rollover retest above, and -- once filled in -- the publish-time asset
integrity checks. It does not itself constitute field proof across many
machines, live external provider delivery, physical SDI/DeckLink capture,
real cable-operator headends, or unattended multi-day station operation --
see "What's proven in this candidate" and "Honestly scoped" in
[README.md](../../README.md) for what has and has not been proven.
