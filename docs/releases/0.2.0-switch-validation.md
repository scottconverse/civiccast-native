# 0.2.0 — Does the automatic CDN surge switch actually work?

**Status:** measured result (0.2.0 Deliverable 2). Lab/software validation on one
machine, against an **in-process stub CDN edge** — no real CDN and no station
hardware exist yet. Pairs with
[0.2.0 — direct-delivery ceiling](0.2.0-direct-delivery-ceiling.md), which
establishes *why* a surge switch is needed.

---

## Bottom line

The [direct-delivery ceiling](0.2.0-direct-delivery-ceiling.md) showed a single
station tops out around **216 HD viewers** on a 1 Gbps link — a hot meeting can
draw far more. 0.2.0's answer is an **automatic surge switch**: serve locally by
default, and when the crowd crosses a threshold, hand viewers off to a CDN.

This validation proves the switch **works end-to-end** in the lab, and it caught
and fixed a real bug that would have broken it in the field:

- Under a rising crowd, the station **detects the surge and switches to the CDN**,
  and viewers who follow the switch keep playing with **zero stalls**.
- The switch **holds** while the crowd stays large, and **releases back to local
  — deleting what it uploaded — when the audience leaves**, so an idle station
  pays nothing for the CDN.
- The bug we caught: once viewers moved to the CDN, the station **stopped
  refreshing the CDN copy**, which would have frozen every CDN viewer within
  seconds. Fixed, with a test that fails if it ever regresses.

**What is *not* claimed here:** that a real CDN holds *thousands* of concurrent
viewers. That is a beta-time measurement (it needs a real CDN and real
bandwidth) and is deliberately not fabricated from a loopback stub. What the lab
proves is that the station-side switch — the part CivicCast controls — is
correct; the CDN's fan-out capacity is the CDN vendor's documented job.

## For station operators

Your station serves meetings straight from its own PC — simple, free, no cloud
bill. That's fine for a routine meeting. But when a contentious item packs the
room (and the livestream), one building's internet can't feed everyone.

The **surge switch** handles that automatically. It's **off unless you turn it
on**, and when on:

1. Normal nights: everything is served locally. Nothing touches a CDN, so there
   is no cost.
2. When the live audience grows past a threshold you set, the station quietly
   starts publishing the stream to your CDN and, after a short buffer, sends
   viewers there — so the crowd is served by the CDN's big network, not your
   doorway.
3. When the crowd thins out, it switches back to local and **removes the stream
   from the CDN**, so you stop paying for it.

The one thing we had to get exactly right — and did — is that viewers don't
**freeze** at the moment of the switch. In testing, a simulated crowd rode the
switch from local to CDN and back with **no stalls at all**.

The honest caveat: we proved the *station's* half against a stand-in CDN on one
computer. Proving that a real CDN then holds thousands of viewers is what the
**beta test** with a real station and a real CDN is for — the tools to measure
it ship here, but the number is not invented in the lab.

## For IT / engineering

### What was validated, and what wasn't

| Claim | How | Result |
|---|---|---|
| Switch **engages** past the concurrent-viewer threshold | ramp emulated viewers past it | ✅ `local → warming → cdn` |
| Viewers **ride the switch without stalling** | switch-aware viewers follow `/current`, measure stalls through the transition | ✅ **0 stalls / 500 fetches** (25 viewers) |
| Switch **holds fresh** under sustained load | keep polling post-switch, watch the CDN manifest advance | ✅ CDN keeps syncing |
| Switch **releases + evicts** when the crowd leaves | drain to a below-release trickle | ✅ back to `local`, CDN objects deleted |
| Real CDN holds **thousands** of viewers | — | ⛔ **beta-time** — needs real CDN + bandwidth; not claimed from a stub |

### The harness

`civiccast/load/switch_lab.py` stands up the **real** serving + switch path and
drives emulated viewers through it:

- a rolling `RollingStation` (from `civiccast/load/lab.py`) writes the local live
  window on the real cadence;
- the real `civiccast.stream.media_router.live_router` serves it (and carries the
  local-manifest load-signal hook);
- the real `/api/public/live/current` resolution endpoint hands each viewer the
  local URL, or the CDN URL once switched;
- a real `SurgeSwitchService` drives a real `LiveCDNPublisher`;
- an **HTTP-served lab CDN edge** (`_LabCDNAdapter` + a `StaticFiles` mount) so an
  in-process viewer can actually fetch the "CDN" — the shipped stub adapter
  returns `file://` URLs an ASGI client can't GET.

Emulated viewers are **switch-aware**: each cycle they re-resolve `/current` and
follow whatever URL they're handed. A `ManualClock` drives the whole ramp
(threshold crossing, delay buffer, load-monitor window), so the result is
deterministic and reproducible rather than wall-clock flaky.

Runnable:

```bash
python -m civiccast.load.switch_lab --viewers 25 --threshold 10 --cycles 20
#   viewers           : 25
#   switched to CDN   : True
#   final state       : cdn
#   segment fetches   : 500 (local 50 / cdn 450)
#   stalls            : 0 (0.00%)
#   state timeline    : local warming cdn cdn cdn cdn ...
```

Exit code is non-zero if it fails to switch or any viewer stalls, so it doubles
as a CI gate.

### The bug the validation caught

The load signal that drives the switch (`observe → tick → publisher.sync`) was
fired **only** on the local-manifest poll (`media_router`). The moment the switch
flips, viewers follow the CDN URL and **stop polling the local manifest** — so
the switch stopped being driven, the publisher stopped syncing, and the CDN
window **froze**. Every CDN viewer would then stall as soon as it drained the
last-synced window.

Reproduced deterministically before the fix: **64 stalls / 80 fetches**, timeline
stuck on `cdn`.

**Fix:** also observe at `/api/public/live/current` — the one touchpoint every
viewer polls to (re)discover the stream in *both* local and CDN states. That
keeps the switch driven after the flip (CDN stays fresh) **and** keeps the load
signal alive, so the switch can hold under sustained load and release cleanly
when the audience actually leaves. `tests/load/test_switch_lab.py` locks in all
four behaviors; the freshness test is RED before the fix.

### Honest limitations — and why the switch stays OFF by default

An independent adversarial review of this deliverable confirmed the *mechanism*
is sound (no double-count, thread-safe, correct guards, clean eviction) but
raised three production-fidelity gaps the loopback lab cannot exhibit. They are
the reason the surge switch ships **off by default and must not be enabled
against real traffic yet** — the client-side piece (#3) is a hard prerequisite,
not a nicety.

1. **Real-CDN fan-out is unmeasured.** A loopback stub cannot exhibit a real
   CDN's concurrent-viewer capacity or edge latency. The "holds thousands" claim
   is validated at beta against a real CDN; the harness already accepts any
   manifest URL, so the same ramp points at a real edge with no code change.
2. **The release path can evict under an active audience — the key risk.** The
   switch measures load from requests the origin sees, and a real CDN hides the
   audience it is serving. With the shipped once-fetch client (#3), the origin's
   count reflects only *new joiners* in the last few seconds — **not** the crowd
   already watching via the CDN. So if joins merely slow for a moment during a
   long meeting, the origin reads near-zero load, crosses the release threshold,
   returns to local, and **`evict_all()` deletes the CDN manifest + segments out
   from under viewers still watching that URL.** The harness cannot reproduce
   this (its emulated viewers re-poll `/current` every cycle, an accurate count).
   This is why enabling the switch is gated on the client re-resolve (#3); until
   then the origin-side estimate is unsafe for the *release* decision.
3. **Client swap signal — the prerequisite for enabling.** The harness models the
   intended player: one that periodically re-resolves `/current` and follows the
   switch. The shipped public portal fetches `/current` **once** on mount, so
   real existing viewers neither swap to the CDN nor keep the origin's load count
   honest. The periodic `/current` re-poll + player source-swap is the remaining
   **client-side** piece (tracked in the Deliverable 2 issue) and is a
   **prerequisite for turning the surge switch on** — the *backend* is proven to
   support it here, but the loop is not closed without it.
4. ~~**CDN edge caching is untested.**~~ **Closed by the cache-contract lab
   below (Tier A).** The CDN adapters now upload the right `Cache-Control`
   headers, and a caching-edge simulator proves the contract they rely on. A
   real vendor edge is still Tier B (see below).

## Cache-contract lab (Tier A)

**Status:** measured result, same lab / same machine. Closes limitation #4
above. This does **not** replace a real CDN edge (Tier B, beta-time) — it
proves the *contract* the adapters and any correctly-configured edge must
honor.

### The gap this closes

`civiccast.stream.cdn.cache_control()` tells the adapters what `Cache-Control`
to upload: `max-age=1` for the manifest (it churns every ~2s and a stale copy
can name an already-evicted segment), `public, max-age=31536000, immutable`
for segments (immutable once written — this is where the CDN offload actually
comes from). But the switch-validation harness's lab edge was a bare
`StaticFiles` mount, which caches **nothing** — it could exercise the publish
path but never the *edge's* behavior, so it could not tell a correctly-capped
manifest header apart from no header at all.

### The simulator

`civiccast/load/cache_edge.py`'s `CachingEdgeASGI` is a from-scratch ASGI
proxy that wraps an origin app and does what a real edge does with
`Cache-Control`: cache a `200` per path for the max-age (or forever, for
`immutable`) the *origin* sent, serve hits without touching the origin, and
refetch once stale. `build_switch_lab(..., cache_edge=True)` mounts it in
front of the existing `/cdn-edge` `StaticFiles` mount (now wrapped to emit the
real `cache_control()` headers), so `simulate_switch` viewers fetch **through**
the edge exactly as they would through a real CDN.

### What it proves

| Claim | How | Result |
|---|---|---|
| Manifest freshness is **bounded**, not unbounded | `max-age=1`, sync every 0.4s, drove `ManualClock` over 10 cycles, compared served vs. true media-sequence | ✅ lag stayed within `ceil(max_age / sync_interval) = 3` segments every cycle (observed lags up to 3, never more) |
| Segment caching is **immutable** | 10 fetches of the same segment key | ✅ exactly **1** origin fetch, 9 edge hits |
| Origin load scales with **time, not viewers** | 30 emulated viewers × 8 cycles, each fetching the manifest *and every segment it names* through the edge, post-switch | ✅ **6** origin manifest fetches for 180 CDN-state viewer polls (174 edge hits, 96.7% offload); **11** origin segment fetches for 1,069 segment reads (99.0% offload) — origin segment fetches equaled exactly the 11 distinct segments actually requested |
| Release + eviction still clean with the edge in front | full engage → release → evict cycle (`threshold=4`) through the edge | ✅ **0 stalls** in both phases (36 + 10 fetches), CDN dir and manifest fully emptied on release — no regression from the non-edge harness |

### The falsification — the RED that makes this load-bearing

`CachingEdgeASGI(..., default_ttl_seconds=60)` simulates exactly the
pre-`cache_control()` world: a provider edge applying its own default TTL
because the origin sent no `Cache-Control` at all. Against a real rolling
station (`window=3`), fetching once, rolling the station 6 times (evicting
every segment from that first fetch off disk), then re-fetching 10 seconds
later (well inside the simulated 60s TTL):

- the edge served the **exact same stale manifest** — media-sequence
  unchanged despite the station having genuinely moved on;
- fetching a segment that manifest named **404'd** — the true origin had
  already deleted it.

That is the classic live-HLS-over-CDN stall, reproduced deterministically. If
the simulator could not produce this failure, it could not be trusted to prove
the fix either.

### Honest limits

This is a software model of edge caching *semantics* — no geo-distribution, no
capacity/LRU eviction, no purge API, one process on one machine. It proves
that the headers the adapters send are correct and that a *correctly behaving*
edge would do the right thing with them. It cannot prove a specific vendor's
edge (BunnyCDN, Cloudflare) actually honors `Cache-Control` the way this
simulator or the HTTP spec says — that is Tier B, and needs a real CDN
account, same as the thousand-viewer fan-out claim above.
