## One-paragraph summary

3.1 has two distinct caption items that are easy to conflate and must not be.
**(1) Archive-import caption *recovery*** is a clean, high-value win: detect and
reuse embedded CEA-608/708 in imported legacy files instead of re-running Whisper
on already-captioned content. The ingest seam for this already exists. **(2)
Native CEA-708 *embedding* into the emitted stream** is a known blocker that no
OSS on the competitive-landscape list fixes — it is a GStreamer-plugin packaging
problem on Ubuntu 24.04 WSL. This note scopes (1) as 3.1 work and tracks (2)
honestly so captions are not oversold in the release.

## Item 1 — Archive-import caption recovery via CCExtractor (3.1, do it)

### Problem

When a station imports legacy/archive content (prior cable broadcasts, historic
council recordings, syndicated programs), those files frequently already carry
broadcaster-approved **CEA-608/708** captions. Today CivicCast's caption path is
faster-whisper-large-v3 (ADR 0002). Re-captioning known-good files is wasteful
and risks *regressing* against a caption track a broadcaster already approved.

### What already exists (the seam)

- `civiccast/captions/external.py` — `ExternalCaptionIngestRequest` already accepts
  an external caption payload in `cea-608-708`, `srt`, or `webvtt` form, parses it
  to `CaptionCue`s, and routes it into the caption **review queue**
  (`CaptionReviewStore`). Its declared boundary is
  `external-caption-appliance-to-review-queue-no-hardware-control`.
- So CivicCast can already *receive* recovered captions into the human review
  workflow. What is missing is the upstream tool that *extracts* CEA-608/708 from
  a container file and posts it to that contract.

### Proposed design

- Add **CCExtractor** as an **operator-installed subprocess** in the asset-import
  path (alongside the existing `ffprobe` ingest probe in `civiccast/assets/`).
- On import: probe for embedded CEA-608/708. If present, run CCExtractor →
  normalize its output → submit through the existing
  `ExternalCaptionIngestRequest` contract (`appliance_id="ccextractor"`,
  `protocol="cea-608-708"`) so recovered captions land in the review queue exactly
  like any other external caption source.
- **Fall through to Whisper only when no embedded captions are found.** Never
  silently overwrite a recovered broadcaster track; the operator reviews/chooses.
- Surface provenance in the review item: `source=ccextractor` vs
  `source=faster-whisper`, so the operator sees which track is which.

### License posture

- CCExtractor is **GPL-2.0** → **subprocess only, never linked**. CivicCast invokes
  the binary; the installer extracts/downloads it; nothing GPL is imported into the
  Apache tree. Same posture as the bundled ffmpeg/GStreamer runtimes.

### Acceptance criteria

- Importing a file with embedded CEA-608/708 produces a review-queue caption track
  recovered by CCExtractor, with `source=ccextractor` provenance, and **no Whisper
  pass runs** for that file.
- Importing a file with **no** embedded captions runs the existing Whisper path
  unchanged.
- CCExtractor absence is fail-soft: import still succeeds; the operator is told
  recovery was unavailable and Whisper is offered.
- Evidence names: input file, detected caption standard, extracted cue count,
  cue count landed in the review queue.

### Non-goals

- Not an *embedding* path (see Item 2). Recovery feeds the review/authoring side,
  not the emitted stream.
- No claim of FCC Part 79 compliance.

## Item 2 — Native CEA-708 embedding blocker (3.1, track honestly — do not imply solved)

### The blocker

Per the 3.0.0-beta1 CHANGELOG and ADR 0018, putting captions **into the emitted
linear stream** is the GStreamer engine's job — **no ffmpeg build encodes 608/708
from text.** The intended GStreamer graph requires `tttocea608`, `ccconverter`,
`cccombiner`, and `h264ccinserter`. Ubuntu 24.04 WSL currently provides
`ccconverter` and `cccombiner` **but not `tttocea608` or `h264ccinserter`**, so the
live sidecar-to-emitted-stream caption proof remains **blocked**. Embedding is
opt-in via `CIVICCAST_EGRESS_EMBED_CAPTIONS` and **off by default**.

Per ADR 0018, `caption_status` stays **`not-verified`** until emitted-stream
decode-back passes (CivicCast reads CEA-608 back via ffmpeg `readeia608`); the
default ffmpeg engine ships the caption *sidecar* and fails closed.

### Why this matters for the 3.1 theme

"Operator confidence" can read as "captions are done." They are not, for the
*emitted-stream* surface. CCExtractor (Item 1) improves **import**; it does
**nothing** for **embedding**. If both are bundled under one "captions" headline,
a station could reasonably assume on-air embedded captions work. They must not.

### What 3.1 should actually do here

- **Do not** claim native CEA-708 embedding in 3.1 release notes. Keep it opt-in
  and off by default; keep `caption_status` honest per ADR 0018.
- **Resolve it as a packaging task, not an OSS-reuse task:** source/build the
  missing `gst-plugins` (`tttocea608`, `h264ccinserter`) for the Ubuntu 24.04 WSL
  runtime, or document the supported runtime where the full graph is available,
  then run the decode-back proof. Track as its own item with an owner.
- **Operator-facing copy** must distinguish *reviewed/recovered captions* (Item 1,
  authoring side) from *emitted-stream captions* (Item 2, still not-verified), per
  ADR 0018 compliance.

### Acceptance criteria (for whenever embedding is unblocked — likely beyond 3.1)

- The GStreamer embedding graph builds on the supported runtime with all four
  plugins present.
- Emitted-stream **decode-back** passes: decoded cue count matches expected within
  timing tolerance, and only then does `caption_status` flip to `on` for that
  output (ADR 0018).
