# CivicCast 3.3 To 4.0 Sprint List And Implementation Plan

Date: 2026-07-02

Status: SUPERSEDED -- historical planning reference from the pre-reset 3.x/4.0-rc ladder, abandoned by the 2026-07-06 version reset. The current release line is v1.0.0-rc18.

This document is the durable 3.3-to-4.0 worklist. It captures every item currently known to be buildable in software, documentation, local test harnesses, virtual devices, local CI, local VM clean installs, generated fixtures, downloaded test software, or API/spec-based simulation.

The only work intentionally excluded from this list is validation that requires a third-party physical facility, cable headend, station operators, app-store approval, or accounts and systems outside local control. Anything that can be built, simulated, documented, packaged, tested, or verified locally belongs here.

## Operating Rule

Do not defer software-doable work out of this plan. If a later review discovers a missing local implementation, local test, documentation, simulator, fixture, migration tool, QA artifact, or packaging task, add it to this document and assign it to a stage before claiming 4.0 completion.

Each implementation slice must leave the repo in a reviewable state. Use local-only work unless explicitly told otherwise. For each slice, run the relevant local tests plus GauntletGate Lite, fix open findings to zero, and commit locally. At each stage boundary, run GauntletGate All across the full repo and all relevant components, fix findings to zero, update docs and evidence, then commit locally.

## Installer Strategy

The installer is not a one-time Stage 1 task. Stage 1 builds the installer substrate and the clean-machine gate: clean VM reset, Windows installer automation, WSL/runtime bootstrap, first launch, health checks, repair/uninstall/reinstall basics, log capture, and support-bundle capture.

After Stage 1, every stage must update the installer, bootstrap scripts, packaged runtime, first-run defaults, docs, and clean-machine checks whenever that stage adds new services, adapters, migrations, fixtures, lab tooling, runtime dependencies, configuration, or user-facing workflows. No feature is considered complete if it only works from a developer checkout and is not reachable from the installed product when it should be.

Stage 7 builds and verifies the final 4.0 release installer. The final gate must re-run clean install, upgrade, repair, uninstall, reinstall, first-run, app launch, health checks, support bundle generation, and packaged-workflow verification using the final installer artifact.

## Seven-Stage Implementation Plan

The stages below are not permission to leave work incomplete. They are the order of attack. Stage 7, 4.0, is complete only when all 31 items are implemented, documented, locally verified, and covered by the final gate.

### Stage 1 - 3.3: Install, First Run, Local Gate Foundation

Stage 1 makes the product installable, recoverable, and testable on demand. It closes the highest-friction beta risks first: installer behavior, first-run setup, local CI, and repeatable clean-machine verification. This stage establishes the installer substrate and clean-machine gate; it does not freeze the installer for the rest of the roadmap.

Primary scope:

- Item 1: installer, clean install, repair, update, uninstall, retry, interrupted install, WSL/runtime recovery, logs, app launch, clean VM checks.
- Item 2: first-admin, first-station setup, station profile defaults, storage, timezone, roles, and dashboard readiness.
- Item 27 baseline: secret handling, installer log redaction, credential boundaries, role defaults, and audit basics needed by setup.
- Item 29 baseline: local runner that can execute unit tests, integration tests, installer build, clean VM install, artifact collection, and GauntletGate lanes.
- Item 30 baseline: install, repair, uninstall, first-run, troubleshooting, and local-runner docs.
- Item 31 baseline: typed config validation, error taxonomy, logging conventions, and cleanup of stale setup code.

Exit criteria:

- Clean Windows VM install passes from a fresh machine state.
- Repair, reinstall, uninstall, and upgrade paths have automated or documented local verification.
- First-admin and first-station setup complete without manual database or shell intervention.
- Local runner can produce a stage report with all required artifacts.
- Later-stage installer update requirements are documented in the local runner and stage templates.
- GauntletGate Lite passes after each slice and GauntletGate All passes at stage end with zero open findings.

## Final 4.0 Definition Of Done

4.0 is done only when:

1. Every one of the 31 items has code or a documented non-code artifact where code is not the right output.
2. Every software-doable path has local tests, fixtures, simulators, generated media, VM checks, or documented local verification.
3. Required checks are not skipped. A skipped required check is a failed release gate unless an equivalent enabled substrate proves the same capability in the same report.
4. The local runner can reproduce the full verification path.
5. GauntletGate All passes on the full repo and all relevant components with zero open findings.
6. The docs accurately describe what is implemented.
7. The release can be installed and used from a clean Windows machine without hidden local developer steps.
