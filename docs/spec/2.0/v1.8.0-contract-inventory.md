# CivicCast v1.8.0 Contract Inventory

Status: active v1.8.0 stage artifact
Created: 2026-05-31
Stage: `stage/1.8.0-parity-architecture`
Baseline: v1.7.3

## Purpose

This inventory records the contracts CivicCast already has and the contracts
that must become canonical before the 2.0 parity work fans out into native TV,
mobile, CG, contributor, gated-playback, analytics, relay, and facility
integration work.

The rule for public repo-facing language is the same as the release plan: do
not name specific incumbent vendors unless Scott explicitly approves that for a
document. Use industry-standard or feature-specific language in public docs.

## Current Contract Surfaces

### Channel Platform

Source:

- `civiccast/cable/channel.py`
- `civiccast/cable/router.py`
- `civiccast/apps/portal-operator/src/screens/ChannelOpsScreen.tsx`

Existing value:

- `ChannelProfile`, `ChannelOutput`, `ChannelBranding`, `PlayoutBlock`,
  `ChannelNowNext`, `ChannelProofLog`, `ChannelPlayoutPlan`, `CtvFeed`, and
  `CtvFeedItem` already describe a three-channel software lineup, playout
  proof, output targets, and a connected-TV feed.
- The staff channel operations screen already consumes the generated API
  contracts for profile, playout plan, and CTV feed review.

Gap:

- The channel model is still a v1.6 feature surface, not the universal app
  platform contract.
- `OutputKind` is limited to `hls`, `rtmp`, `srt`, and `ndi-plan`; it does not
  yet describe native TV/mobile app targets, app-store packaging surfaces,
  analytics targets, or facility-control outputs.
- `CtvFeedItem` is useful but too narrow to serve as the shared feed for Roku,
  tvOS, Fire TV, Android TV, Android mobile, iOS/iPadOS, Web/PWA, CG, and EPG
  export.

Decision:

- Reuse `ChannelProfile` concepts, but introduce a canonical app-platform
  projection instead of letting every app consume the staff channel model
  directly.

### Live State And Ingest

Source:

- `civiccast/live/models.py`
- `civiccast/live/router.py`
- `civiccast/live/preflight.py`
- `civiccast/apps/portal-operator/src/types/live.ts`
- `civiccast/apps/portal-public/src/App.tsx`

Existing value:

- Live sessions have explicit states: `idle`, `preflight`, `on_air`, `ending`,
  and `recorded`.
- Live sources already model `rtmp`, `rtsp`, `ndi`, and `srt`.
- Recording targets already separate `archive`, `live_file`, and
  `broadcast_master`.
- The staff API exposes generated TypeScript types for sessions, sources,
  targets, and preflight.
- Public live status exists as a resident-safe projection.

Gap:

- Public live status is a local router model and is mirrored manually in the
  public portal TypeScript app.
- The public model does not yet include playback tracks, caption tracks, audio
  tracks, DVR/window policy, stream health, or app-platform fallback behavior.
- Live ingest and relay readiness are not part of the shared app contract.

Decision:

- Keep the staff live-session state machine internal to operator workflows.
- Create a canonical `LiveState` projection for all public apps and CG surfaces.

### VOD, Catalog, And Public Playback

Source:

- `civiccast/vod/models.py`
- `civiccast/vod/router.py`
- `civiccast/schedule/models.py`
- `civiccast/apps/portal-public/src/App.tsx`
- `civiccast/apps/portal-operator/src/types/asset.ts`

Existing value:

- `AssetMetadata` and `AssetEmbedResponse` provide public VOD metadata and
  HLS/embed URLs.
- The schedule module has richer staff asset records, chapters, retention
  policy, metadata updates, and upload responses.
- The operator app consumes generated OpenAPI types for asset rows and metadata
  edits.

Gap:

- VOD has at least two asset metadata shapes: one in `civiccast/vod/models.py`
  and one in `civiccast/schedule/models.py`.
- The public portal hand-writes `AssetMetadata`.
- Catalog concepts required for parity are missing or incomplete: series,
  topics, smart playlists, thumbnails, multiple caption tracks, multiple audio
  tracks, chapter markers, playback policy, and privacy-safe analytics hooks.

Decision:

- Do not expose staff `Asset` rows to apps.
- Add canonical app-facing catalog contracts that can adapt from existing VOD,
  schedule, publish, captions, and podcast data.

### Schedule, EPG, And Now/Next

Source:

- `civiccast/schedule/models.py`
- `civiccast/schedule/router.py`
- `civiccast/cable/channel.py`
- `civiccast/apps/portal-operator/src/types/schedule.ts`
- `civiccast/apps/portal-public/src/App.tsx`

Existing value:

- Schedule items already model `premiere`, `embargo`, `scheduled`,
  `cancelled`, and `published`.
- Conflict handling and schedule list surfaces exist.
- Channel playout blocks already use schedule data as one source.

Gap:

- The public portal hand-writes its schedule item shape.
- There is no canonical EPG export contract.
- Now/next for linear channels and coming-up data for public apps are related
  but not yet represented by one shared model.

Decision:

- Build `ScheduleFeedItem` and `NowNextState` as app-facing projections fed by
  schedule and channel playout data.

### Captions, Audio Tracks, And Chapters

Source:

- `civiccast/captions/models.py`
- `civiccast/captions/review_router.py`
- `civiccast/apps/portal-public/src/HlsPlayer.tsx`
- `civiccast/podcast/models.py`
- `civiccast/schedule/models.py`

Existing value:

- Caption cue and review contracts exist.
- Public HLS playback can discover and switch HLS subtitle tracks.
- Podcast chapters and schedule chapters exist.

Gap:

- Public apps do not receive a canonical list of caption tracks.
- Audio tracks are not represented as first-class public playback metadata.
- Chapters exist in more than one module but are not app-platform canonical.
- External caption-source integration is not represented yet.

Decision:

- Add canonical `CaptionTrack`, `AudioTrack`, and `ChapterMarker` models before
  native apps are built out.

### Publish, Records, And Public-Record Guardrails

Source:

- `civiccast/publish/models.py`
- `civiccast/records/`
- `civiccast/apps/portal-operator/src/types/publish.ts`

Existing value:

- Publish surfaces include canonical, archive, reach, record, and audience
  destinations.
- Publish approval, override, audit, retry, and dashboard contracts exist.
- Public-record status is already visible in publish state.

Gap:

- App playback and gating policy do not yet consume a shared public-record
  guardrail model.
- Publish state is operator-centered and not yet projected as public catalog
  availability for every app.

Decision:

- Introduce a canonical `PlaybackPolicy` model that includes access tier,
  preroll rules, public-record constraints, and publish availability.

### CG And Bulletin Board

Source:

- `civiccast/cg/models.py`
- `civiccast/cg/router.py`
- `civiccast/apps/portal-public/src/App.tsx`

Existing value:

- Idle page and emergency overlay contracts exist.
- Public portal can render the between-stream and emergency state surfaces.

Gap:

- Multi-zone layout, ticker/news zone, dynamic feeds, sponsor/logo zones,
  optional audio zones, bulletin submissions, approval queue, and HLS-rendered
  CG output are not yet modeled.

Decision:

- Add `CgFeedSnapshot`, `CgTemplate`, `CgZone`, and `BulletinSubmission`
  contracts in v1.8.0 so the v1.8.3 CG implementation lands on shared
  platform shapes.

### Contributor, Viewer, And Operator Identity

Source:

- `civiccast/auth/models.py`
- `civiccast/auth/roles.py`
- `civiccast/subscribe/models.py`
- `civiccast/installer/models.py`

Existing value:

- Operator identity and staff roles exist.
- Subscription records and public subscription responses exist.
- First-admin setup and station auth contracts exist.

Gap:

- Viewer accounts and contributor accounts are not separate product roles yet.
- Contributor submission, agreement logging, review status, and notifications
  are not modeled.
- Gated playback needs a viewer-facing identity and entitlement model distinct
  from operator credentials.

Decision:

- Keep staff identity separate.
- Add canonical viewer and contributor identity projections, but defer full
  auth implementation to the relevant later stages.

### Installer And Station Configuration

Source:

- `civiccast/installer/models.py`
- `civiccast/apps/installer/src/types.ts`
- `civiccast/apps/installer/src/api.ts`

Existing value:

- Installer and first-run contracts are deep: deployment profiles, safe-to-
  broadcast, station setup, health, backup/restore, update/rollback, provider
  readiness, package verification, and beta handoff.

Gap:

- Station setup does not yet produce the canonical app-platform configuration
  needed by native TV/mobile/PWA apps.
- Branded versus unbranded app-build settings are not first-class shared data.

Decision:

- Add `StationAppConfig` and `AppBuildProfile` contracts that installer,
  operator UI, and app shells can all consume.

### Frontend Client Contracts

Source:

- `civiccast/apps/portal-operator/src/types/api.generated.ts`
- `civiccast/apps/portal-public/src/App.tsx`
- `civiccast/apps/portal-public/src/HlsPlayer.tsx`
- `civiccast/apps/installer/src/types.ts`
- `civiccast/apps/ctv-reference/`

Existing value:

- The operator portal uses generated OpenAPI contracts plus thin UI aliases.
- The public portal and installer have useful local TypeScript shapes.
- A CTV reference surface already exists.

Gap:

- Public portal shapes are hand-written and can drift from backend Pydantic
  models.
- Native app shells do not yet share one generated or versioned contract
  package.

Decision:

- Add a shared app-platform contract package and contract tests. App shells
  should consume that package instead of copying shape definitions.

## Canonical Contract Set For v1.8.0

The next v1.8.0 implementation slices should establish these public,
app-facing contracts:

- `StationAppConfig`: station name, branding, default channel, enabled
  surfaces, app build profile, analytics policy, support links, and emergency
  status URL.
- `AppBuildProfile`: unbranded or branded app target metadata, including app
  name, icon references, splash references, platform targets, and store
  readiness flags.
- `ChannelPublicConfig`: channel identity, branding, outputs, programming
  rules, fallback behavior, public schedule links, CG feed link, and app
  availability.
- `LiveState`: resident-safe live status, playback URL, health, fallback,
  caption tracks, audio tracks, DVR/window policy, and proof boundary.
- `VodCatalogItem`: app-safe VOD item with series/topics/playlists, poster and
  thumbnail references, captions, audio tracks, chapters, publish state,
  public-record metadata, and playback policy.
- `VodCatalogResponse`: paginated and facet-ready VOD catalog response for Web,
  native TV, mobile, and CG reuse.
- `ScheduleFeedItem`: public schedule and EPG projection with now/next
  suitability.
- `NowNextState`: current and next linear-channel item, fallback state, and
  generated-at metadata.
- `CaptionTrack`: label, language, URL, kind, default status, and source
  confidence/proof.
- `AudioTrack`: label, language, kind, default status, and URL.
- `ChapterMarker`: title, time range, source, and moderation state.
- `PlaybackPolicy`: access tier, public-record guardrail, preroll policy,
  entitlement requirement, and downstream client instructions.
- `AnalyticsEvent`: privacy-safe app event model covering playback start,
  heartbeat, completion, errors, search, schedule browse, and subscription
  actions.
- `CgFeedSnapshot`: multi-zone bulletin-board state for portal, HLS render,
  and facility overlay adapters.
- `ContributorSubmission`: upload, agreement, review, scheduling handoff, and
  producer-notification state.
- `FacilityIntegrationTarget`: software-visible output/control target for AV
  router, caption encoder, relay, overlay, and future hardware adapters.

## Reuse And Replacement Rules

- Reuse existing Pydantic validation style, `extra="forbid"`, explicit literal
  states, and generated OpenAPI client flow.
- Reuse existing channel, live, schedule, publish, captions, podcast,
  subscription, installer, and auth concepts where they already match product
  meaning.
- Replace duplicated public asset and schedule shapes with app-facing
  projections.
- Do not let native apps consume staff/operator models directly.
- Do not encode platform-specific behavior into one app shell first and backfill
  the other shells later. Shared contract first, shell adapters second.
- Do not make public-record restrictions optional client advice. They must live
  in the server-side policy contract.
