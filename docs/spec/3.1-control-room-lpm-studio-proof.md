# CivicCast 3.1 Control Room Studio Proof

**Status:** Draft for local 3.1 work only  
**Date:** 2026-06-29  
**Scope:** Local development and LPM field proof. Do not merge, tag, or publish
this work into the live beta release stream without a separate release decision.

## Purpose

CivicCast 3.1 will turn the existing control-room foundation into a studio-proof
device-control surface for Longmont Public Media. The goal is not to replace the
3.0.1 beta installer or disturb the beta test that starts tomorrow. This work is
local-only until the project director explicitly authorizes publishing it.

The 3.1 work proves that CivicCast can model, preview, fire, audit, and recover
from real production-control actions against the studio systems LPM uses. The
first lab targets are OBS WebSocket 5.x and vMix. LPM field proof extends that to
their vMix streaming PC, vMix laptop, OBS installations, DeckLink inputs visible
inside vMix, NDI inputs visible inside vMix, the ATEM-upstream-to-vMix workflow,
and PTZ state where available.

The control path stays single-plane. CivicCast owns the operator experience,
database state, credentials, cue validation, audit, support bundles, and proof
language. Device writes go through the existing CivicCast control-room dispatcher
and the TSR sidecar boundary. There must not be a parallel Python device-control
stack that competes with TSR.

## Proof Language

Every device-control claim must carry its proof level. A mocked feature is
documented and may be useful for rehearsal, but it is not release evidence for a
station. A lab-proven feature has passed local OBS/vMix proof on this machine or
another controlled lab host. An LPM field-proven feature has touched the real LPM
equipment and produced saved evidence.

The release notes, operator docs, support handoff, and LPM proof matrix must use
those labels consistently. Nothing mocked is hidden, but nothing mocked is
described as station-ready.

## Feature Flag

The whole 3.1 control-room surface starts behind a feature flag. Stations that do
not use device control should not see the UI and should not pay runtime cost for
state polling, sidecar supervision, or device health checks.

The flag enables the control-room setup UI, live control UI, state/tally service,
sidecar lifecycle checks, credential flows, and support-bundle extensions. The
default posture is off unless this 3.1 work is being tested.

## Device Inventory And Secrets

The runtime source of truth is the existing `control_room` database model, not a
YAML file. A YAML file such as `devices.lpm.yaml` may be used for topology import
and export, but it must never contain plaintext credentials and must not become
the source of truth while the app is running.

Device records store identity, kind, transport, host, port, non-secret options,
capability metadata, version metadata, notes, and a `secret_ref`. Secrets live in
the OS keyring through the existing control-room keyring pattern. The UI and CLI
must support setting, rotating, clearing, and testing credentials without ever
echoing a raw secret into logs, support bundles, API responses, or frontend state.

The adapter layer resolves credentials by asking for credentials for a device. It
must not assume that OBS, vMix, ATEM, PTZ, or future devices all use the same auth
scheme.

## Network Safety

Device adapters refuse unsafe destinations by default. Localhost, configured
trusted LAN ranges, and configured VPN ranges are allowed. Public or otherwise
unexpected destinations require a setup-admin override, a reason, and an audit
row. That override is also visible in the support bundle.

The refusal message should tell the operator what failed and what kind of network
target is allowed. It should not leak credentials or embed full secret-bearing
URLs.

## Modes

Test Mode is the default. It is not a banner alone; it is enforced on the server.
When an operator fires a cue in Test Mode, the result is stamped as test/simulated
and the dispatcher must not pretend that a live device changed state.

On-Air Mode requires an allowed role, explicit confirmation, an active session
lock, a configured safe-state cue, a healthy TSR sidecar, valid credentials when
required, network-safety approval, valid cue payloads, and a current material
state fingerprint. Every Test Mode to On-Air Mode transition and every On-Air
Mode to Test Mode transition is audited.

Idle expiry is a configuration decision. The 3.1 default is thirty minutes unless
LPM chooses a different value during field setup. Expiry returns the session to
Test Mode and writes an audit row.

## Operator Locking

One operator owns Live Fire for a control surface at a time. Other operators can
observe, inspect state, and dry-run cues. A browser refresh or WiFi drop does not
instantly release the lock. The default reconnect grace period is thirty seconds.
During the grace period another operator may request takeover, but takeover is
explicit and audited.

After the grace period, a qualified operator may take over the session. The audit
log must record the old owner, the new owner, the reason if supplied, and whether
the takeover happened during or after the reconnect grace period.

## Channel Scope

Every cue has explicit channel scope. A cue may target one channel, a named set
of channels, all station channels, or a lab/mock target. The UI must show this
scope before Dry Run and before Live Fire. A cue that does not declare scope is
invalid.

This matters because the beta environment includes three concurrent channels.
The operator must never have to infer whether a cue affects public, education,
government, or all channels.

## Cue Versioning And Immutability

Cue definitions are versioned. Once a cue version has been referenced by a fired
action or audit event, that cue version is immutable. Editing the cue creates the
next version. The Proof Log stores `cue_id`, `cue_version`, the redacted action
snapshot, the channel scope, and the material state fingerprint used to approve
or refuse the action.

This prevents an audit row from saying an operator fired "Open Meeting" while the
current editable cue named "Open Meeting" no longer matches what actually ran.

## Safe State

Each live control surface must have a safe-state cue before On-Air Mode is
available. The safe state may be a slate, bars, a "we will be right back" hold,
or another station-approved fallback. Safe-state replacement is locked while any
relevant session is On-Air.

Changing the safe-state cue requires setup-admin permission, an explicit
confirmation, and an audit row that records the old cue version and the new cue
version. Live Fire must expose the safe-state action as a panic/recovery control.

## Cue Failure Policy

Real devices usually cannot be rolled back safely. CivicCast therefore does not
offer a vague "rollback" promise. Each cue declares a failure policy that the
dispatcher enforces if an ordered action fails after earlier actions have already
run.

`stop_and_hold` stops the remaining actions and leaves prior successful actions
as-is. `continue_best_effort` continues actions that are marked safe to continue.
`fire_safe_state` immediately attempts the configured safe-state cue.
`manual_recovery_required` blocks further live cues until a qualified operator
acknowledges the failure and chooses the next step.

The dispatcher must never decide this policy silently at runtime.

## Dry Run And Material State

Dry Run renders the intended change against the current state of the devices it
depends on. It also computes a material-state fingerprint. Live Fire refuses only
when the state material to the cue's actions has changed since the dry run.

The fingerprint must not be global. Audio meter movement, heartbeat timestamps,
or unrelated tally changes must not block a cue. Missing target inputs, changed
program or preview state when the cue depends on it, removed OBS sources, or a
vMix input identity change are material and must invalidate the dry run.

If state changes outside CivicCast, such as an operator clicking directly in
vMix, the UI should mark the dry-run preview stale and explain what changed.

## State And Tally

State is separate from cue firing. The state service normalizes online/offline
status, connection health, program and preview, input/source existence, audio
active where available, PTZ position and preset where available, last update
time, stale-state status, and version/capability metadata.

OBS state comes from obs-websocket 5.x events where appropriate. vMix uses the
HTTP `/api` XML document for rich status and the TCP API/TALLY path where useful
for program and preview. XML polling is not described as a true subscription.

The UI receives state updates through a pinned transport. The preferred 3.1
transport is server-sent events unless implementation review finds an existing
repo WebSocket pattern that is safer to reuse.

## OBS Scope

OBS support is pinned to obs-websocket 5.x. The adapter refuses incompatible
protocol versions with an operator-readable explanation. It supports optional
password auth, request/response correlation, captured fixture tests, and opt-in
live integration tests.

The initial action surface includes scene/source operations that can be proven in
lab and then at LPM. Unsupported OBS actions return an explicit "not exposed in
CivicCast 3.1" response.

## vMix Scope

vMix support uses the HTTP `/api` status and function surface, plus TCP/TALLY
where it is useful for program and preview state. The XML parser is schema-aware:
unit tests fail on required-field drift, while unknown optional elements warn
rather than break production.

The 3.1 vMix cue allowlist is limited to select input, preview/program actions,
cut/fade, overlay in/out, scoped title/text update, read status, and tally/status
proof. Input rename is not in scope. Rename is a destructive configuration
mutation that can confuse local vMix operators and orphan automation tied to
input names.

Also out of scope for 3.1 cues are input delete, global vMix config mutation,
shortcut mutation, recording destination changes, and broad "any vMix function"
access. Unsupported functions return an explicit "not exposed in CivicCast 3.1"
response.

## Dispatcher And Audit

The dispatcher is the only cue execution path. It enforces the feature flag, mode
gate, role and session lock, cue version, max payload size, max actions per cue,
ordered action execution, retry-safety metadata, failure policy, material-state
fingerprint, network safety, credential availability, and audit append.

Audit is immediate, local, append-only, ordered, and redacted. Live cue firing
must not block on an external timestamp authority. Instead, local audit rows are
hash-chained immediately and RFC 3161 binding is applied to session-close exports
or audit batches. This gives tamper-evidence without adding live switching
latency or dependency on a remote TSA during a show.

## TSR Sidecar Lifecycle

The TSR Node sidecar is a supervised runtime dependency. The installer or local
runtime must install sidecar dependencies, pin/check the TSR version, start the
sidecar, health-check it, restart it after a crash, surface "sidecar down" in
the operator UI, and include sidecar logs in the support bundle.

With no healthy sidecar, production control fails closed.

## User Interface

The 3.1 UI includes Device Inventory, credential setup/test, Control Surface
Setup, Cue Builder, Dry Run, Live Fire, Safe State/Panic, Proof Log, and Support
Bundle entry points.

The UI must show Test Mode, On-Air state, lock owner, reconnect grace, stale-state
status, sidecar status, per-device health, cue scope, safe-state availability,
material-state mismatch explanations, test/simulated result stamps, and the proof
level for any device or cue. It must never imply that mocked proof is field proof.

## Support Bundle

The existing support bundle endpoint is extended. The bundle includes CivicCast
version, feature-flag state, device topology without secrets, OBS version and
protocol information, vMix version/API snapshot, TSR sidecar version and log
excerpt, recent cue audit rows, recent mode transitions, state-staleness events,
network-safety refusals, material-state mismatch events, and station clock/NTP
sanity when available.

The bundle excludes raw passwords, recovery codes, bearer tokens, authorization
headers, and any secret-bearing URLs.

## Verification

The first verification layer is fixture and unit coverage for cue versioning,
safe-state locking, failure policies, material-state fingerprints, credential
references, network refusal, unsupported vMix actions, OBS protocol mismatch,
vMix XML drift, sidecar health failure, operator locks, takeover, and payload
limits.

The second layer is local live proof against OBS and vMix: scene or source
control, vMix select/cut/fade/overlay/title/status, remote API disabled failure,
auth and no-auth paths, source removal, sidecar restart, browser reconnect, Test
Mode simulated fire, On-Air fire, safe-state panic, and a burst run of fifty cues
over sixty seconds with no drops, no double-fires, and ordered audit.

The third layer is GauntletGate Lite, Walkthrough, and Full run locally.

The final layer is LPM field proof. The proof matrix records OBS, vMix streaming
PC, vMix laptop, DeckLink inputs visible through vMix, NDI inputs visible through
vMix, ATEM upstream workflow, PTZ state where available, safe-state panic,
support bundle, audit export, concurrent-operator behavior, material-state
invalidation, and sidecar recovery.
