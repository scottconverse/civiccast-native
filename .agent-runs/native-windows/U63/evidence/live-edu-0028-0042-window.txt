# ---- why the boundary answer was EMPTY, not the 23.5 s tail (the branch arithmetic) ----
#
# This is the one part of Defect A that has to be reasoned from the code rather than read off
# a log line, because the automation never prints what its provider answered (it prints only
# the lead line, which here says "no asset duration available for the boundary").
#
# At the 00:28:38.238 tick the automation had:
#     plan_end_at  = the live plan's declared end   = 00:28:38 + 554 s = 00:37:52
#     now          = 00:28:38.238
#     lead         = 690 s
#
# `_check_plan_rollover` dispatches on a three-way branch over the provider's answer. Working
# backward from the printed outcome:
#
#   * The line printed `target=filler` and `force_fallback` was therefore TRUE. The only ways
#     the code reaches `force_fallback = True` are (a) the provider returned `None`/no
#     segments, or (b) `fresh_plan.channel_id != channel_id`.
#   * Branch 2 (`use the answer as-is`) requires `fresh_end <= plan_end_at and
#     fresh_seconds < planned_seconds`. With `fresh_start = max(now, plan_end_at) =
#     plan_end_at = 00:37:52`, `fresh_end <= plan_end_at` forces `fresh_seconds <= 0`.
#     A 23.5 s answer cannot satisfy it: 23.5 s <= 0 is FALSE.
#   * Branch 3 (`extend past the answer`) also needs a non-empty answer.
#   => the answer was EMPTY (branch 1). An empty answer is exactly what the printed lead line
#      says: "no asset duration available for the boundary".
#
# And the 23.5 s cannot be the same answer, because it was MEASURED AT A DIFFERENT TIME:
# the daemon's line is timestamped 00:37:28.275, i.e. 4:50 after the automation tick, against
# a plan whose declared end was ~00:37:52. 00:37:52 - 00:37:28 = 23.5 s. That is the daemon's
# own arithmetic on its own clock, at its own reload, and it matches to the tenth of a second.
#
# So the incident doc's hypothesis ("the automation was handed the 23.5 s tail and chose
# filler") is REFUTED: the automation was handed nothing. It saw an empty boundary answer,
# fell into the filler branch, and the look-ahead (`_warm_upcoming_plan`) was skipped along
# with it -- which is why no warm of the programme happened and the daemon had to do a cold
# 276.9 s conform five minutes later at 00:37:28.
#
# The engine's own changeover is what put the daemon in that position: the plan's declared end
# (~00:37:52) and the item's end (~00:37:51.5) agree, but the engine reached EOS at the
# 00:37:22 changeover and the slate came up at 00:37:25.746 -- ~28-30 s before the declared
# end. The origin of that ~28-30 s base offset is the ONE open sub-piece of A1; the leading
# candidate is the deferred-start anchor rule in `_establish_horizon_from_dispatch`, and it is
# reported as a candidate, not as a finding. See reports/U63.md, work A1.

# ---- the fix (A2), stated against these lines ----
#
# With the candidate bytes, the 00:28:38.238 tick does not stop at the empty answer: the new
# `_resolve_rollover_tail` re-asks the provider at `boundary + tail_seconds + 1.0 s` (the tail
# here being 0.0 s, since the answer was empty), gets the programme that is due where the tail
# ends, and -- only if that answer is strictly longer than the tail -- uses it in place of the
# filler. On this shape it replaces `target=filler` with the programme, and because the plan
# is then non-empty the look-ahead runs in the same tick. The floor that keeps this from
# eating a legitimate short item is `_ROLLOVER_TAIL_FLOOR_SECONDS = 30.0`, which is the
# daemon's own `SCHEDULE_GAP_ABSORB_SECONDS` tail rule, NOT the brief's "(shorter than the
# rollover lead)" wording -- stated loudly in the report as a deliberate divergence.
