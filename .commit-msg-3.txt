fix(release): unblock CI after the beta.3 version bump

Two real CI failures on #139 @ 79e27d1, both caused by the version bump not
having propagated to two more places that check against the LIVE repo state
rather than an isolated fixture:

1. tests/release/test_publish_beta_candidate.py: TAG/VERSION constants were
   still "v1.0.0-beta.2"/"1.0.0-beta.2". publish_beta_candidate.
   verify_version_identity() fail-closed-compares the tag being published
   against the REAL civiccast._native_version.__version__ (not a mock) --
   now 1.0.0-beta.3 -- so every test using the old constants got REFUSED
   with a version-identity mismatch that had nothing to do with what each
   test actually exercises (draft/verify/undraft ordering, gh failure
   cleanup, dry-run artifact shape, release-truth updates). Confirmed the
   fixture manifests these tests build are self-contained tmp-path files,
   not the real docs/releases/release-truth.yaml, so the coordinator's
   "staging entry assumes beta.2" hypothesis was not the actual cause --
   the fail-closed version-identity check was working exactly as designed
   against a stale test fixture. Bumped TAG/VERSION to beta.3 and added a
   comment explaining why these constants must track the real version.
   Not weakened: verify_version_identity's comparison logic is untouched.
   45/45 tests pass.

2. ci-docs.yml "Check tracked USER-MANUAL release artifacts"
   (scripts/render_user_manual.py --out-dir docs --check-current): FAIL -
   Rendered manual manifest source hash is stale. The prior two commits
   edited docs/USER-MANUAL.md's version-bump prose but never re-ran the
   Pandoc render, so the committed docs/USER-MANUAL.pdf/.docx/.render.json
   fell out of sync with the source. Regenerated via
   `uv run python scripts/render_user_manual.py --out-dir docs`; the
   --check-current gate now passes locally. Also re-verified
   scripts/render_docsite_manual.py --check-current and
   scripts/generate-openapi-artifacts.py --check (both already regenerated
   in the prior commits) both still pass clean, since they're the other two
   drift gates in the same CI job.

The claims-evidence verifier failure is expected to clear as a cascade of
(1) per the coordinator's own diagnosis -- it could not be exercised
standalone locally (its CLI requires --artifacts-dir/--producer-results/
--github-sha from a real workflow run), so this is confirmed by re-running
CI, not by a local repro.
