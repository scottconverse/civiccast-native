## What it is for
Lets an operator drive the station's production gear (OBS, vMix, Blackmagic ATEM, HyperDeck, PTZ cameras, CasparCG and similar) during a meeting through a small helper service called the TSR control service. You open a "session" on a control surface, tap a cue to preview ("dry run") what it would send, then confirm to fire it. Sessions are either Test (nothing reaches devices, only an audit row) or On-Air (cues are really sent). The page states that putting the result on the channel is a separate Playout action.

## States
- Loading identity: "Loading…". Identity failed: "Could not load your staff identity. <detail>" (522-526).
- Devices failed: "Could not load devices. <detail>". Surfaces failed: "Could not load surfaces. <detail>". Surface failed: "Could not load this surface. <detail>". Surface loading: "Loading cues for this surface...". No cues: "This surface has no cues yet." (716).
- On-Air blocked: "On-Air Session is blocked until readiness passes. <first blocker: action>" (627-629).
- Mode banners: "ON-AIR MODE - cue actions can be sent to production devices. Safe-state cue: <name or 'not configured'>." / "TEST MODE - device actions are blocked and recorded as test-only audit events." (265-279).
- Program feed banner: "Program feed: <source or 'not bound to a live source yet'>" + "This console produces the source. Taking it to air on a channel is a Playout (S5) action — it is not fired from here." (252-263).
- Audit empty: "No cues fired this session yet. Every cue you fire is logged here for the record." (405-406). Rows show a pill Planned / Fired / Failed, the action word and the device id.
- Result banners: "Test action recorded." / "Cue fired." (741-743); errors "Could not dry run the cue.", "Could not fire the cue.", "Could not open the session." (720-736).
- Not configured: the helper being absent is detected from HTTP 502/503 or text containing "not configured"/"unavailable" (59-63). Server side, with `CIVICCAST_CONTROL_ROOM_TSR_URL` unset the service uses a fail-closed null client; readiness check "TSR control service" is blocked and says to configure that variable (`service.py:559-585`, `app.py:3054-3068`).

## Typical task flows (only what the code supports)
1. Rehearse: choose a surface -> leave "Test Mode" -> "Open Test Session" -> tap a cue (dry run) -> "Test... (needs confirm)" -> "Confirm test action" -> see "Planned" in the audit list -> "End session". No device is touched.
2. Go on-air: wait for readiness to pass -> choose "On-Air Mode" -> pick a safe-state cue -> tick the box -> "Open On-Air Session" -> tap cue, read plan, "Fire... (needs confirm)" -> "Confirm fire". If a fire fails use "Roll back to Safe State". The session expires 30 minutes after opening; open a new one.
3. Check gear: "Probe" each device; re-probe when a chip says "Stale — probe again" (older than 5 minutes, `models.py:108`).
4. Support: support_admin writes a note and presses "Create support bundle".
Not supported here: registering devices/cues (Control Room Setup), force-closing someone else's session (backend allows setup_admin/support_admin; no button), viewing when an On-Air session will expire.

Device kind labels (`control-room-format.ts:6-26`): OBS Studio, vMix, Blackmagic ATEM, HyperDeck, PTZ camera, OSC, TCP device, HTTP device, CasparCG, "GPI (network relay)", "Serial (network relay)". Reachability pill (57-65): Disabled, Reachable, Unreachable, Not probed. Health pill (74-87): Never probed, "Stale — probe again", Healthy, Unreachable. Audit result (89-92): Planned, Fired, Failed. Readiness verdict words come from `readinessLabel()` (`status-language.ts:125`): Ready / Check before meeting / Do not broadcast yet / Not set up yet / Needs IT help. Headline rule (`ControlRoomReadinessPanel.tsx:122-127`): ready and equipment verified -> "Ready"; ready but equipment unverified -> "Check before meeting"; any blocker -> "Do not broadcast yet". The server's checks (`service.py:512-808`): TSR control service, Device inventory, Device profiles, Enabled devices, Device health (warning only), Device target safety, Control surfaces, Timeline cues, Cue action safety, Safe-state cue candidate, Station-device evidence. Only "blocked" checks stop On-Air; the last one is always a warning.

## Help-text findings
- [HELP-01] `BE\control_room\service.py:809` + `ControlRoomReadinessPanel.tsx:122-147` — `station_device_ready` is hard-coded False, so the headline can never read "Ready" and the warning "On-air readiness is confirmed once a check against the room's actual devices passes." is permanent. No screen offers that check. A clerk will wait for something that cannot happen. — Help must say: "This always shows 'Check before meeting'; it means the equipment has not been verified by CivicCast, not that something is broken." Log for coder.
- [HELP-02] `ControlRoomScreen.tsx:326, 725-730` + `service.py:237, 303-313` — an On-Air session silently expires after 30 minutes and the screen never shows the time left. After expiry the session is closed server-side, so both "Panic: Run Safe State" and "Roll back to Safe State" fail with "On-Air Mode expired ...". Council meetings often run longer. — Tell operators to re-open an On-Air session before 30 minutes; coder should show a countdown. (Rollback bypasses expiry only while the session is still open.)
- [HELP-03] `ControlRoomScreen.tsx:322-328` — "Panic: Run Safe State" is disabled until you press "Dry Run Safe State", and any other cue's dry run disables it again. In an emergency the label says "Panic" but needs two presses and has no confirmation. — Explain the order in the button's neighbour text; suggest always dry-running the safe-state cue after opening the session.
- [HELP-04] `ControlRoomScreen.tsx:530-533` — "requires the publish/meeting operator, setup admin, or support admin role" — publish_operator is not a permitted role (`READ_ROLES`, line 50; backend `router.py:78-90`). — "requires the meeting operator, setup admin or support admin role".
- [HELP-05] `BE\control_room\router.py:219-225` shown through `ControlRoomScreen.tsx:687` — 409 text tells the user "A setup admin or support admin can force-close it", but no screen button does that and a refresh loses your own open session id (it is held in page memory, line 433). — Document how a stuck lock is cleared (admin ends the session via API/support) or add a control.
- [HELP-06] `ControlRoomScreen.tsx:560-561` — "TSR control service", "LPM profile coverage", "Safe State", "S5", "Playout (S5)" (260) are unexplained jargon. — Replace "TSR control service" with "the production-control helper" in help text; drop "(S5)".
- [HELP-07] `ControlRoomScreen.tsx:203-206, 214` — "needs confirm" is shown on cue buttons; "Fire..." vs "Test..." wording changes with mode but a first-time user cannot tell a Test session fires nothing until reading the blue banner. — Help should lead with "Test Mode never touches your equipment".
- [HELP-08] `ControlRoomReadinessPanel.tsx:75-77` — for the TSR check the screen replaces the server text with "Open Control Room Setup to start or reconnect the local control service before On-Air use." but the backend action says to set `CIVICCAST_CONTROL_ROOM_TSR_URL` (`service.py:574`). — The setup screen may not start the helper (see `controlroomsetup.md`); verify before publishing the sentence.
