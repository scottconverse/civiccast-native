## What it is for
Lets remote council members, presenters or public commenters join the meeting from a web browser (no install) through a self-hosted VDO.Ninja service. An operator makes a "room" tied to a channel, opens it, creates single-use invite links to send to guests, lets guests in from a waiting room, and puts them "on air". CivicCast itself only manages rooms, invites and the guest list; the video mixing is done by VDO.Ninja plus a compositor (GStreamer or OBS) that must already be set up (`RemoteContributionScreen.tsx:4-12`).

## What the user sees
Top to bottom (`RemoteContributionScreen.tsx:265-445`):
1. Heading "Remote Contribution" and "Bring remote council members, presenters, and public comment onto the channel over the browser via self-hosted VDO.Ninja — no install for the guest." (267-273).
2. Amber alert when opening a room or minting an invite failed with "not configured"/503: "Remote contribution isn’t configured yet. A compositor (the GStreamer wpesrc engine or OBS) plus self-hosted VDO.Ninja and coturn must be commissioned before guests can reach the channel. See the diagnostics drawer for status." (276-286).
3. Two columns. Left card "Rooms" (with a pill "setup admin can create" for setup admins): create form, then a list of rooms with a state pill. Right card titled with the room name, or "Select a room".
4. Right card contents once a room is chosen: state pill + "channel <id> · up to N guests"; "Open room" / "Close room"; "Director view (embed in your switcher)" URL box (only right after opening in this page); "Invite a guest" form; "Guest link for <name> — send this" URL box; "Sent invites (N)" list with "Used"/"Pending"; "Guests (N)" tray.
5. Card "Diagnostics" (support admin only): pills "TURN reachable/unreachable", "VDO up/down", "coturn up/down"; target text; "Test TURN connectivity"; a "How to point this station at coturn" disclosure.
The room detail refreshes every 5 s; diagnostics every 15 s (163, 170).

What "On air" really triggers: `_take_channel_live` calls the same live-takeover service as Channels > "Take live", with operator id `remote-contribution` and reason "remote guest on-air" (`BE\app.py:3094-3104`). That queues a takeover command so the channel switches to its live (compositor) source for up to the takeover default of 3600 s (`egress\takeover_service.py:146`). If the channel is already under takeover it is a silent no-op (`app.py:3099`). The audit row names "remote-contribution", not the person who clicked.

## States
- Loading identity: "Loading…" (244). Not allowed: the "You don’t have access ..." text above.
- Rooms load failure: amber text "Could not load rooms." or the API message (301-303). Create failure: "Could not create the room." (297).
- No rooms: "No contribution rooms yet." + "Contribution rooms let remote presenters send live video into this station from a web browser — no studio visit needed. Create a room above and its invite links appear here." (305-307). (Non-setup-admins do not see the create form, so "Create a room above" does not apply to them.)
- No room selected: "Select a room" / "Choose a room to open it, send guest invites, and run the guest tray." (328-332).
- Guests empty: "No guests connected. Send an invite link to bring one in." (619-621).
- Invite failure: "Could not mint the invite." (384). Guest action failure: "Action failed — please retry." (403) or the API text.
- Diagnostics: loading "Loading diagnostics…"; failure "Could not load diagnostics."; not commissioned: "Remote contribution requires a compositor (the GStreamer engine or OBS) plus self-hosted VDO.Ninja and a reachable TURN server (local coturn, or a documented external one) — guests cannot reach the channel until they are commissioned. <detail>" (773-778). External TURN note: "No local coturn process, but TURN is reachable — expected for a documented external TURN server (see below)." (766-768).

## Typical task flows (only what the code supports)
1. Setup admin creates a room (name + channel id).
2. Meeting operator selects the room -> "Open room" -> copies the director link into the switcher -> "Generate invite link" for each guest -> sends each "Guest link" (valid 4 hours, single use).
3. Guests open the link; each appears under "Guests" as "In waiting room" -> operator clicks "Admit" -> "On air" (first on-air also takes the channel live).
4. During the meeting: "Mute", "Off air", or "Drop" (with confirm).
5. After: "Close room" (with confirm). Nothing here returns the channel to its schedule; use Channels > "Return to schedule" (UNVERIFIED-03).
6. Support admin: "Test TURN connectivity" when guests cannot connect.

## Statuses and words on this screen
Room state (`contribution-format.ts:12-23`): Idle, Open, Live ("the room/channel is broadcasting"; distinct from a guest "On air"), Closing, Closed. Guest state (40-51): Invited, Joining, "In waiting room" (code value `connected`), On air, Muted, Dropped, Ended. Connection quality (60-68): Unknown, Good, Degraded, Poor (advisory only; nothing sets it from this screen). Roles: Council member, Presenter, Public comment. Invite: "Used" / "Pending". Not routed through `status-language.ts`.
