# Live  (nav id: live, section: Run Meeting)
Source files: `SRC\screens\LiveRoomScreen.tsx`, `SRC\types\live.ts`, `SRC\screens\status-language.ts`, `SRC\components\ConfirmDialog.tsx`, `SRC\components\shell\Sidebar.tsx`.
Backend traced: `BE\live\router.py`, `BE\live\store.py`, `BE\live\preflight.py`, `BE\live\source_probe.py`, `BE\live\network_probe.py`, `BE\live\storage_probe.py`, `BE\live\readiness.py`, `BE\live\finalization_worker.py`, `BE\installer\service.py`, `BE\installer\router.py`.
(`SRC` = `civiccast\apps\portal-operator\src`; `BE` = `civiccast`. Route `/live`, `SRC\routes.ts:7`. All facts below were read from code; nothing was run.)

Who can open it: any signed-in operator. The nav entry has no `requiredRoles` (`Sidebar.tsx:121`) and the route has no gate (`App.tsx:265`). It is NOT reachable while the first-setup recovery kit is pending (only Manual is, `Sidebar.tsx:93`). What you can DO depends on role (see table). The UI reads derived roles from `/api/staff/auth/me`; a token with scope `admin` or `operator` expands to all five roles (`BE\auth\roles.py:19-37`).

## What it is for
The "live room" walks one meeting through a fixed sequence: pick a configured meeting source, create a live session, run a server-side checklist ("pre-flight"), then mark the session on air and later end it. Ending it hands the session to a worker that looks for the recording file and turns it into an asset. In the code read, the on-air button changes the live-session record (and what the public "live now" status reports); it does not start or switch the outgoing channel feed (that is Channels, "Take live" or "Start"). See HELP-01 and UNVERIFIED-01.

## What the user sees
Top to bottom (`LiveRoomScreen.tsx:1241-1466`):
1. Header: small caps "Operator live room", heading "Live", text "Run pre-flight and start only after CivicCast verifies the source, storage, and network from the server." (1245-1251). Right side pills: session state ("No session" until a session exists) and, after a pre-flight run, "Pre-flight ready" or "Pre-flight blocked" (1256-1260).
2. Red alert "Live action failed." with the error text and a fixed "Next step." (only when an action failed, 1264, 99-116).
3. "Safe to broadcast: Ready / Check before meeting / Do not broadcast yet" panel with the server's `operator_message` and a "Resident preview" link (118-189).
4. If the identity lacks `meeting_operator`: amber note "Live-room controls require the meeting operator role. Source status and readiness checks remain visible." (1273-1277).
5. One of three bodies (1279-1452):
   - Loading: "Loading live-room configuration..."
   - No sources configured: the "Choose a camera or test source" setup guidance card (837-896).
   - Sources exist: two columns. Left: "On-air preview", "Source switcher" (radio cards + a readiness detail card, optional "Edit meeting source" form), "Remote ingest". Right: "Session controls", "Recording finalization" (only after End), and "Recording targets: N".
6. "Pre-flight checklist" at the bottom of the page, always present (939-1022).

## States
- Load failure (sources or recording targets query failed): whole screen replaced by red alert "Could not load live room." + the API message + "Next step. Confirm the CivicCast server is running and connected to its database, then refresh this screen." (1232-1238, 110-113).
- Loading: "Loading live-room configuration..." (1281).
- No sources: "Choose a camera or test source" with the server's `next_step` and option cards ("Needs IT help" pill when flagged) (858-868, 880). If that guidance call fails: "No meeting source is ready yet. Open Setup and choose a camera or test video." (840-844).
- Safe-to-broadcast loading: "Checking safe-to-broadcast state..." (162). Error: "Broadcast readiness could not be checked. Do not start the stream." + "Retry the check. If it fails again, open System Health and confirm the CivicCast service and database are ready." (143-146).
- Preview: always the placeholder "Source preview unavailable - CivicCast has not verified incoming video or audio from <source>. No simulated preview or audio meter is shown." + "Next step. Connect a real encoder or meeting source and run pre-flight. Start Live Stream remains blocked until a server-side media probe passes." (922-931). There is no code path in this screen that shows live video.
- Ingest plan loading: "Checking ingest paths..." (745). Failed: "Remote ingest status is unavailable. Local encoder sources can still run from this room." (737-739). No paths: pill "No source configured" + "No meeting source is configured for this channel yet. Add a camera, encoder, or sample source above before running pre-flight -- CivicCast has no listener at any default address until you do." (758-764)
- Pre-flight list empty: "Run pre-flight to populate the nine-check contract." (959-961).
- Finalization panel waiting: pill "Waiting" and "The finalization worker picks the recording up within a few seconds of End Live Stream. This panel updates automatically." (246-258). Completed: "Recording saved as asset <id>. Find it in the Assets library." (263-264). Failed: backend `failure_reason` or "Finalization failed." (270). Running: "Attempt N of M. The recording is being checked and packaged." (287-288).

## Typical task flows (only what the code supports)
1. First time, no source: open Live, read the "Choose a camera or test source" card, follow the link to Setup (setup_admin must add a source; source creation is not on this screen).
2. Meeting night: choose Broadcast channel -> pick a source card -> "Check source" until the pill says "Delivering" -> "Create live session" -> "Start pre-flight" -> tick the confirmation box -> "Run pre-flight" -> fix any red item and re-run -> "Start Live Stream" -> later "End Live Stream" and confirm -> watch "Recording finalization".
3. Source address changed: "Edit source" (setup admin) -> Save -> "Check source" again; the old "Delivering" state is cleared by the save.
4. Finalization failed: read the red reason, fix the cause, press "Retry finalization".
Not supported by this screen: starting the encoder, putting the source on the channel feed, seeing video, choosing an existing session after a page reload (HELP-02/03).

## Statuses and words on this screen
Session pill (`types\live.ts:39-48`): Idle, Pre-flight, On air, Ending, Recorded. Source type pills (50-55): RTMP, RTSP, NDI, SRT. Source readiness pill (118-123): "Delivering" (media seen within the TTL), "Needs re-check" (seen, but older than the TTL), "Not answering" (last check failed; reason shown), "Not checked". Age text: "Checked N seconds/minutes/hours/days ago", "Checked just now", "Never checked" (141-155). Relay mode (57-61): "Local encoder", "Cloud relay", "Direct platform". Relay health (63-68): Not configured, Ready, Degraded, Offline. Safe-to-broadcast words: Ready / Check before meeting / Do not broadcast yet (`LiveRoomScreen.tsx:130-134`; shared list `status-language.ts:31-35`). Pre-flight row labels (`types\live.ts:70-80`): Network reachable, Recording storage, AI runtime, Live source, Recording target, Operator confirmation, Syndication, Internet Archive, NAS handoff. Row pill words come from `readinessLabel()` (`status-language.ts:125`); a failed row shows no pill, only a red border plus "Next step." text (998-1014).
What the nine checks really test (`BE\live\preflight.py`): Network = TCP connect to 1.1.1.1:443 then 8.8.8.8:443 (3 s each; `network_probe.py:50-53`), i.e. needs internet. Storage = free space on the `CIVICCAST_UPLOAD_DIR` drive (home drive if unset) must be at least 50 GiB (`preflight.py:195`, `storage_probe.py:40-42`). AI runtime: not required (`not_configured` is acceptable). Live source: the selected source must belong to the session's channel and pass a fresh probe. Recording target: needs a non-rehearsal local target. Operator confirmation: the checkbox. Syndication / Internet Archive / NAS: report provider posture and never block going on air (`preflight.py:144-148`). Required set: network, storage, live source, recording target, operator confirmation (`preflight.py:135-142`).

## Help-text findings
- [HELP-01] `LiveRoomScreen.tsx:1431` — "Residents watching the live stream lose it immediately." — The handler only moves the session to Ending (`router.py:736-773`, `store.py:391-407`); it queues no egress command. Residents' status falls through to the channel's egress state (`router.py:310-321`), so the stream may continue. — Say what really happens: "This marks the meeting as ended and starts saving the recording. It does not stop the channel feed; use Channels for that." (confirm with owner/engineer first).
- [HELP-02] `LiveRoomScreen.tsx:64, 1135-1140, 1431` — fixed session id `council-live-room`; dialog promises "start a new live session to go live again". A second create returns 409 "LiveSession already exists: council-live-room" (`router.py:529-535`) and nothing in the screen lists or reopens an existing session. — Either the product needs a new id per meeting (coder) or help must say "one live session per station until IT resets it".
- [HELP-03] `LiveRoomScreen.tsx:1025` — the session is held only in page memory (`useState(null)`); nothing fetches an existing session on load. After a browser refresh during a meeting the buttons return to "Create live session" and "End Live Stream" is disabled. — Tell operators not to refresh while on air; log as a product defect for the coder.
- [HELP-04] `LiveRoomScreen.tsx:110-113` — every failed action (403 role error, 409 pre-flight block, 409 duplicate) is followed by "Next step. Confirm the CivicCast server is running and connected to its database, then refresh this screen." — Wrong advice for most failures, and "refresh" is exactly what loses the session (HELP-03). — Use "Next step" only for load errors; show the server's own next step for action errors.
- [HELP-05] `LiveRoomScreen.tsx:959-961` — "Run pre-flight to populate the nine-check contract." — Jargon. — "Press Run pre-flight to check the camera, recording drive, internet and your confirmation."
- [HELP-06] `LiveRoomScreen.tsx:1385, 1404` — "Start pre-flight" and "Run pre-flight" read as the same action; the first runs nothing. — Rename "Start pre-flight" to "Begin checklist" or merge; explain order in a one-line note above the buttons.
- [HELP-07] `types\live.ts:98` — "Check the confirmation box below, then select Run pre-flight again." — The box is in the right-hand Session controls, above the checklist, not below it. — "Tick the confirmation box in Session controls".
- [HELP-08] `LiveRoomScreen.tsx:318-322, 1292` — heading "Source switcher" and text about arrow keys. — Selecting a card chooses what pre-flight tests; it switches nothing on air. — Rename "Choose meeting source".
- [HELP-09] `LiveRoomScreen.tsx:907-909, 922` — "On-air preview" with "CivicCast only shows source media here after server-side verification." — No code path ever shows video; the panel is a permanent placeholder. — Remove the panel or label it "No video preview in this version".
- [HELP-10] `types\live.ts:70-71` — "Network reachable" / "Recording storage" — The network check needs internet (1.1.1.1 and 8.8.8.8 on 443) so an offline station cannot go on air; the storage check needs 50 GiB free on the CivicCast data drive, not the recording target drive. — Add both facts to the row text and the manual.
- [HELP-11] `LiveRoomScreen.tsx:130-134, 1266` — "Safe to broadcast" banner is computed from the last System Health rehearsal, not from the pre-flight run on this page (`client.ts:728` sends no flags; `installer\service.py:3668-3674`). It can say "Check before meeting" while pre-flight says "Pre-flight ready". — Add "This banner reflects the last System Health rehearsal" under the title; also the text says "System Health" while the nav item is "Readiness".
- [HELP-12] `LiveRoomScreen.tsx:273-281` — "Retry finalization" is shown to every role but the backend allows only meeting_operator (`router.py:824`). — Gate or explain.
