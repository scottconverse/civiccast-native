## Goal
Starting a channel never runs retention discovery on the automation thread. The start path consults the
most recent retention VERDICT produced in the background, with semantics consistent with the tap worker's.

## Design (coordinator decision - implement this; if the code makes it impossible, write questions\U07.md)
1. One shared verdict source per process: the latest `CaptionRetentionResult` (and its monotonic timestamp)
   from the background sweep. Prefer reusing the tap worker's sweep and its result; if the egress daemon can
   run without a tap worker (check `app.py` / `build_channel_automation` wiring and the `tap_root is None`
   path), the provider must start its own background sweep instead of scanning inline.
2. The egress provider returns immediately:
   - fresh verdict (younger than a bound, default 3 x the tap sweep interval = 180 s) -> return it
     (a refused verdict keeps today's refusal behavior, including `publish_caption_runtime_status(...)`);
   - no verdict yet, or stale -> trigger a background sweep if none is in flight, and return a
     "pending" result that lets the program start while the tap worker's existing pending rules keep
     WAV retention off. Do NOT invent a new refusal. Find the exact `CaptionRetentionResult` fields that
     express "ready, retention pending" today (or the closest existing equivalent) and quote them; if no
     such state exists, STOP and ask in questions\U07.md.
3. Never block the caller on a sweep; never take any daemon lock; thread-safe.
