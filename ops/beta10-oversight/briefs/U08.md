## Why the sweep must get cheap
Live facts (2026-09-24): `C:\ProgramData\CivicCast\data\caption-tap` has 21,153 files (public\processed 15,045).
Every full discovery does `resolve()` + `stat()` + `_wav_duration()` + full-read `_sha256()` per chunk plus a
review-store lookup per row (your U07 report and `tap_worker.py` ~1520-1535 document an N+1 DB pattern and
16.75 s at 13,550 candidates on 2026-09-18). It measured 60.5 s live today. The caption tap already runs it
every 60 s on this station, so the machine is re-hashing ~all recorded audio about once a minute, forever,
which is plausibly part of the disk/CPU pressure that makes cold program conforms take ~270-300 s.

## Goal
Steady-state sweeps cost roughly "stat every file" rather than "read every file", the review lookups are not
N+1, and the start-path verdict is kept fresh in the background whenever the provider exists.

## B. Make it cheap
1. SHA-256 cache: reuse a file's digest when (resolved path, size, mtime_ns) is unchanged since the last sweep.
   In-memory, per policy/process, shared by every caller of the same policy object; bounded (drop entries for
   files that no longer exist on each sweep). Never trust a cached digest when size or mtime changed. If any
   caller relies on the digest to detect tampering of an unchanged-mtime file, say so and STOP (questions\U08.md).
2. `_wav_duration`: same cache key.
3. Review-store lookups: replace the per-row lookup with one batched query if the store API allows it (add a
   batch method to the protocol + both stores if needed, with tests for each store implementation that exists).
   If the N+1 is somewhere you cannot batch safely, report exactly where and why.
4. Measure again on the same synthetic archive: first sweep and second (unchanged) sweep. Quote numbers.

## C. Keep the start-path verdict fresh
`CaptionRetentionVerdictSource` gets a background re-arm: after each sweep, schedule the next one at
`sweep_interval_seconds` (60 s) - a single daemon timer/thread, stoppable, never more than one sweep in flight,
still serialized with the tap's sweep by `_DISCOVERY_LOCK`. Start it lazily on first `__call__` (so building
the provider starts no thread). Tests: after one start, the verdict is refreshed without another start; a
background refusal published within the freshness window gates the NEXT start (returns ready=False); stop()
ends the thread (assert by thread name).
