# Unit U04 - Stuck-pass watchdog: when a channel pass runs too long, log where the automation thread is

First, re-read `C:\Users\scott\Documents\Codex\2026-09-16\re\civiccast-ds-oversight\PROJECT-BRIEF.md` in full.

## Why
U01 established that on 2026-09-24 the single automation thread spent ~446 s inside public's pass
(between 13:30:44,903 and 13:38:10,887) and nobody could tell which call it was stuck in, because the
path logs nothing until it finishes. We are not fixing the stall in this unit. We are making the NEXT
stall name its own cause, so the later decoupling fix is designed against evidence.

Coordinator-checked facts (worktree, 2026-09-24):
- `civiccast/egress/automation.py:582` `run_forever` loops `run_once()` then waits `poll_seconds`.
- `automation.py:631` `run_once` iterates `self._store.list_configs()` and calls
  `self._run_channel_pass(config, channel_id, now)` (line ~654) for each enabled channel, serially.
- The production thread is started by a `ThreadSupervisor` named `civiccast-channel-automation`
  (installed `app.py:1405-1409`; check the worktree `app.py` for the same).

## Goal
A watchdog that, while any single channel pass (`_run_channel_pass`) has been running longer than a
threshold, logs the automation thread's CURRENT Python stack, then keeps logging it periodically until
the pass ends, and logs the pass's total duration when it ends. Zero behavior change otherwise.

## Requirements
1. Threshold default 30 s, repeat interval default 60 s. Env overrides
   `CIVICCAST_AUTOMATION_PASS_WATCHDOG_SECONDS` and `CIVICCAST_AUTOMATION_PASS_WATCHDOG_REPEAT_SECONDS`
   (positive floats; invalid -> warning + default, same pattern as other env readers). A value of `0`
   for the threshold disables the watchdog (state this explicitly in code and test).
2. Mechanism: record (channel_id, start monotonic, thread ident) when a pass starts and clear it when it
   ends (use try/finally so an exception still clears it). A single daemon watchdog thread (started from
   `run_forever`, stopped when `run_forever` exits) wakes periodically, and when the current pass exceeds
   the threshold, formats the automation thread's frame from `sys._current_frames()[ident]` with
   `traceback.format_stack` and logs it at WARNING:
   `"Channel automation pass for <channel> has run <N>s (still running); automation thread stack:\n<stack>"`.
   It must never raise into the loop, never take any daemon lock, never touch the store, and never block
   the automation thread. Keep all shared state for this in one small object with its own tiny lock.
3. When a pass that tripped the watchdog finishes, log at WARNING once:
   `"Channel automation pass for <channel> finished after <N>s (exceeded watchdog <T>s)."`
   Passes under the threshold log nothing new.
4. `run_once` called directly (tests, no `run_forever`) must still work unchanged with no watchdog thread.
5. Do NOT change pass order, threading of the passes, the daemon, locks, or any rollover logic.

## Red, then green
- Tests with a fake daemon/pass that blocks on a `threading.Event`: with threshold 0.2 s and repeat 0.2 s,
  the stack warning appears (assert it contains the name of the blocking function in the fake), repeats,
  and the "finished after" line appears after the event is set. Show these FAIL before the change.
- A pass under the threshold produces no watchdog log lines.
- Threshold `0` disables it; invalid env values warn and use defaults.
- The watchdog thread stops when `run_forever`'s stop_event is set (no thread left alive; assert by name).
- Use short real timeouts but keep each test under ~3 s; no sleeps longer than needed.
