# U14 — question: the restart path cannot reuse a prepared plan

**Status: STOP on F3(b) only.** F1 and F2 are implemented, proven red→green, and committed
(`20a0a695`, `516c2dba`). This file is the brief's own STOP condition for F3(b):

> "If the restart path cannot reuse a prepared plan without re-preparing, STOP and write
> `questions\U14.md` with the smallest change that would let it."

It cannot. Evidence and the smallest change are below.

---

## 1. What F3(b) asked for

When the daemon is about to issue a content reload that will NOT defer (policy returned False)
**and** the channel's state is FALLBACK_SLATE, do not attempt the seamless selector swap; use the
existing restart-reload path **with the plan that was already prepared**, so the preparation
(often 100+ s of conform) is not repeated. Scope strictly FALLBACK_SLATE + non-deferred; ON_AIR
deferred rollovers and operator takeovers unchanged. `should_defer_switch` is not to be changed.

## 2. Trace: what the restart path does today with a prepared plan

The decision point the brief describes is inside `_reload_steps`, at the
`switch_at_end_of_current=should_defer_switch(...)` call (`civiccast/egress/daemon.py:3691`). At
that moment the prepared report is **already in hand** — it was yielded back into the generator at
`daemon.py:3617` and unpacked at `3618-3619` (`prepared_plan_dir = preparation_report.plan_dir`).

OBSERVED, in order:

1. `_reload_steps` arms the seamless reload regardless of `switch_at_end_of_current` — the flag is
   only carried into the request (`daemon.py:3808`) and into `_PendingReloadSettlement`
   (`daemon.py:3812`). The prepared plan dir is recorded on the settlement entry
   (`plan_dir=prepared_plan_dir`, `3812`), which is exactly the object
   `live_prepared_plan_dirs` protects (`3380-3396`).
2. `_fall_back_to_restart_reload` (`daemon.py:4024`) takes **no plan parameter**:
   `def _fall_back_to_restart_reload(self, channel_id: str, *, failure_reason: str | None = None)`.
   It records `_pending_reloads[channel_id] = (state.state, state.current_source_label)`
   (`4040-4043`) and, for FALLBACK_SLATE with a live process, `self._reload_kills.add(channel_id)`
   + `_process_terminate(process)` (`4090-4094`). Nothing about the prepared plan survives here.
3. The worker exit then reaches `_poll_process`, which **discards both** plan owners before
   restarting: `self._discard_pending_reload_settlement(channel_id, reason="worker exited")`
   (`2678`) and `self._discard_active_prepared_plan_dir(channel_id)` (`2679`); the former releases
   `pending.plan_dir` via `_release_prepared_plan_dir` (`3356`). Then it calls
   `self._start(channel_id, previous_state=..., previous_source_label=...)` (`2691-2696`) — no plan.
4. `_start_steps` prepares **unconditionally**: `prepared_plan_dir: Path | None = None` (`1683`),
   then `if self._source_preparer is not None: ... preparation_report = yield
   _PreparationRequest(source_plan, config)` (`1684-1686`). The only thing threaded into `_start`
   today is `resolved_plan=` (`1478`), which skips the **provider**, not the preparer (`1615`);
   its docstring says so explicitly (`1481-1488`).
5. `_poll_preparation`'s fallback call site has the report in scope and drops it:
   `report = pending.future.result()` (`~899`) … `self._fall_back_to_restart_reload(channel_id)`
   (`924`) with no argument.

**Conclusion (OBSERVED): a restart reload re-prepares. The prepared plan is released, then the same
plan is conformed again.**

## 3. The smallest change that would let the restart reuse it

All in `civiccast/egress/daemon.py`; no worker/engine change, no policy change.

1. **`_reload_steps`** — at the `should_defer_switch` result (`3691`): when it is `False` **and**
   `state.state == "FALLBACK_SLATE"`, stop before arming; return an outcome that carries
   `preparation_report` (in scope, `3617-3619`). The existing `return False` shape already routes to
   the restart path — it just loses the plan.
2. **`_poll_preparation`** — at `924`, pass the report that is already in scope:
   `self._fall_back_to_restart_reload(channel_id, prepared_report=report)`.
3. **`_fall_back_to_restart_reload`** — accept `prepared_report: SourcePreparationReport | None =
   None` (default `None` keeps every other call site (`3962`, `3980`, `3996`, `4009`, `4172`)
   byte-identical) and stash it on the daemon keyed by channel.
4. **Lifetime** — the stash must be treated exactly like `_PendingReloadSettlement.plan_dir`: add
   its `plan_dir` to `live_prepared_plan_dirs` (`3380-3396`) so the preparer's GC cannot evict it
   while the restart is in flight, and release it on every path that does **not** consume it
   (operator stop, drain, discard) — otherwise F3(b) turns a re-prepare into a leaked directory.
5. **`_start` / `_start_steps`** — accept `prepared_report=`; when set, skip the
   `yield _PreparationRequest(...)` at `1684-1686` and bind the same two values the yield would have
   produced (`source_plan = preparation_report.source_plan`, `prepared_plan_dir =
   preparation_report.plan_dir`, plus `_record_prepared_loudness`). That is ~5 lines at the seam and
   reuses the existing data flow exactly.

Estimated size: ~40 lines + tests, one file.

## 4. Why this shape and not the alternative

* **Design A (decide before preparing — kill the worker first, then prepare)** is smaller but makes
  the dark gap the whole conform: on the measured evidence above that is ~134 s *plus* worker start,
  worse than today's 269.6 s only in the sense that no seamless attempt is wasted. It makes the
  program's arrival dark for the entire conform, which is the thing F3(b) exists to avoid.
* The shape above keeps the prepare (it is unavoidable — the program must be conformed) and removes
  only the *duplicate* prepare.

## 5. The one decision I should not take alone

The report carries its own `source_plan` (`SourcePreparationReport.source_plan`). On reuse, the
restarted worker would air **the plan that was prepared** even if `_source_plan_provider` would
resolve a different plan at restart time (e.g. the horizon moved to the next program while the
restart was in flight). Options:

* **(a) Use the report's plan** — the plan the operator/automation actually triggered the reload
  for; simplest, and matches "use the plan that was already prepared".
* **(b) Re-resolve and reuse the prepare only if the resolved plan matches** the prepared one,
  otherwise re-prepare — safest against a moved horizon, but re-adds a prepare in exactly the
  late-arrival case and needs a plan-identity comparison that does not exist yet.

I recommend **(a)**, with the state row showing the report's source label, and a follow-up watchlist
item if a moved-horizon case is ever observed in the logs. This is a product/behavior decision about
what the channel shows when the restart runs long — hence this file rather than a unilateral choice.

are unaffected and already committed.
