# U06 — product question: an operator's `stop` does not survive a restart on an `auto_start` channel

**Unit:** U06 (channels must come back by themselves after a service restart / machine reboot)
**Branch (worktree):** `beta10-ds` @ `d8ea37b1`
**Status:** unit otherwise complete (gaps 1–3 implemented, tested, committed, green — see `reports/U06.md`).
STOPPED semantics were **not** changed; this file is the question the brief told me to ask instead.

The brief says: *"Do NOT change STOPPED semantics for a channel an operator stopped: if you cannot
tell an operator stop from a crash-induced one from the stored data, STOP and write
`questions\U06.md`."* I cannot, and here is the evidence.

---

## 1. What is OBSERVED

**(a) Reconciliation itself never touches STOPPED.** Both arms of the sweep share one body
(`civiccast/egress/daemon.py:1086-1157`), and `STOPPED` is not in `_STALE_RECONCILE_STATES`
(`daemon.py:1020-1022`). Pinned by `test_operator_stopped_channel_is_never_recovered` and
`test_operator_stopped_channel_with_a_dead_pid_is_never_recovered`.

**(b) But the PRE-EXISTING `auto_start` policy starts it anyway, on the next pass.** This is not my
code and not part of the sweep:

`civiccast/egress/automation.py:1287-1317` — `_run_channel_pass_body` gates on
`self._daemon.has_live_process(channel_id)`, `config.auto_start`, the retry cooldown, and the
pending-start guard. **It never reads `egress_states`.** An enabled `auto_start` channel with no live
process is started, whatever the persisted row says.

Pinned as the evidence for this question by
`tests/egress/test_daemon_stale_state_recovery.py::test_preexisting_auto_start_still_starts_a_stopped_channel`
(added in `d8ea37b1`):

```
$ python -m pytest tests/egress/test_daemon_stale_state_recovery.py -q -p no:randomly
35 passed in 2.00s
```

That test writes `state=STOPPED, pid=None` for an `auto_start=True` channel, asserts the sweep returns
`[]`, drives ONE `service.run_once(...)`, and asserts `daemon.starts == ["gov"]`. It passes — i.e. the
channel the operator stopped is on air again one pass later.

The sibling DRAINING case was already pinned the same way by an earlier unit
(`test_preexisting_auto_start_still_starts_draining_channel`), so the behavior is long-standing, not a
U06 regression: before U06 the only difference was that the stale row was never cleared first.

**(c) The three writers of a STOPPED row are indistinguishable in the stored data.**

| writer | site | row it writes |
|---|---|---|
| operator `stop` command | `daemon.py:1345` (`_process_command`, action `"stop"`) | `state=STOPPED`, `pid=None`, `updated_at=now`, `last_error=None` |
| worker's clean exit / completed drain / queued terminal command | `daemon.py:2640` (`_poll_process`) | same shape, `last_error=stop_error` (which is `None` unless the slate-EOS relaunch path set it) |
| `drain` with no tracked process | `daemon.py:4092` (`_drain`) | same shape, `last_error=None` |

All three go through `_write_state`, which omits `pid` unless passed, so the persisted row is
byte-identical for an operator stop and a crash/completion stop. **There is no field, flag, or
`last_error` text that separates "the operator turned this off" from "this channel left air by
itself".**

**(d) The command ledger cannot separate them either — through the documented API.** A `stop`
command does carry `issued_by` (`civiccast/egress/models.py:286-302`, table `egress_commands`, rows
persist with `consumed_at`), but the `EgressStore` protocol exposes only
`enqueue_command`, `enqueue_commands`, `peek_pending_commands` and `pop_pending_commands`
(`civiccast/egress/store.py:61-88`) — all pending-only. Nothing can read a *consumed* command, so
"was the last command for this channel a human's stop?" is not answerable today without a new store
method.

**(e) The failure mode this collides with.** Per `PROJECT-BRIEF.md`, channels going dark on their own
is the defect being worked; the operator-stop-doesn't-stick case is the mirror image, and U06's own
goal statement names it: *"without touching any channel an operator deliberately stopped"*. As it
stands, the only way an operator can keep a channel off air across a restart is to clear
`auto_start` on the channel first.

---

## 2. Why this is a product question, not a coder decision

Making the operator's stop stick means choosing what "stopped" **means** across a restart, and that
choice changes station behavior an operator sees:

* Does the operator's stop survive a *service* restart? A *machine* reboot? A crash-restart of the
  worker while the service is up?
* Does U06's "channels must come back by themselves" promise apply to a channel with `auto_start`
  set, if the operator has explicitly stopped it since the last start?
* What re-arms `auto_start` — a manual start, a portal toggle, an explicit "resume automation"?

Every answer needs product intent, and any answer changes a user-visible contract (the operator's
mental model of the Stop button), so I am not picking one.

## 3. Options I can see, with what each costs

**Option A — leave it exactly as it is (what I shipped).** Reconciliation never touches STOPPED; the
pre-existing `auto_start` policy still brings a stopped `auto_start` channel back on the next pass.
Nothing to build. Honest statement: "Stop is a stop of the *current* playout; `auto_start` means the
channel is expected to be on air." Documented in the test above.

**Option B — make the operator's stop durable, by distinguishing its cause.** Smallest version I
would propose: extend the pending-only ledger with one read — e.g. `last_command(channel_id)` over
the durable `egress_commands` rows — and have the sweep write a distinct marker (a new state, or a
`last_error` sentinel such as `"operator stop"`) that the `auto_start` policy then honours. Then
`auto_start` would mean "…unless a human stopped it since". Costs: a new store method (both stores +
the protocol), a new state or sentinel with its own reconciliation rule, and a decision about what
re-arms it (a manual start should, and does — `_start` is reached via an operator `start`
command). Note the ledger rows are durable, so the evidence exists; it is the API and the rule that
are missing.

**Option C — make the sweep clear `auto_start` when it sees a STOPPED row.** I would not do this:
it silently rewrites station configuration from a state row, and it cannot tell the operator's stop
from a completed drain, so a channel that intentionally left air at plan end would stop being
auto-started.

**My recommendation if I had to pick: Option B**, because it keeps both promises without weakening
either — `auto_start` still means "come back by itself" for the crash/reboot case that is the whole
point of U06, while an explicit operator stop becomes durable the way an operator expects. But this
is Scott's call, and it is a behavior change to a user-facing contract, so I stopped here.

## 4. What I did NOT do

* Did not change `_STALE_RECONCILE_STATES`, the sweep body, or the `auto_start` policy for STOPPED
  rows. The only STOPPED-related change in this unit is a test that pins the current behavior
  (`d8ea37b1`).
* Did not add a store method or a marker state.
* Did not touch the live station to observe a real operator stop (Rule 1).
