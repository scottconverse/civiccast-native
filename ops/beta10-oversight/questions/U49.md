### 2b. The prescribed ceiling is a near-no-op on this input

**OBSERVED:** the relay's input (`tap-enc.ts`) already peaks at **−1.1 dBTP** — *below* the
prescribed −1.0 dBTP ceiling. A limiter at that ceiling has, by construction, almost nothing to
reduce. Its measured effect at the relay stage is +0.3 dB of improvement over today (case B/B0 in
§3), all of which comes from clamping the encoder's input, not from gain reduction of the program.

### 2c. No filter in the station's ffmpeg is a *true-peak* limiter

**OBSERVED:** `ffmpeg -h filter=alimiter` on the station binary:

```
   level_in          <double>   set input level (from 0.015625 to 64) (default 1)
   level_out         <double>   set output level (from 0.015625 to 64) (default 1)
   limit             <double>   set limit (from 0.0625 to 1) (default 1)
   attack            <double>   set attack (from 0.1 to 80) (default 5)
   release           <double>   set release (from 1 to 8000) (default 50)
   asc               <boolean>  enable asc (default false)
   asc_level         <double>   set asc level (from 0 to 1) (default 0.5)
   level             <boolean>  auto level (default true)
   latency           <boolean>  compensate delay (default false)
```

**No oversampling option.** `alimiter` is a **sample-domain** limiter. A true-peak limiter can only
be built as a composition, which is what the ride already does (`loudness_ride.py:706-715`:
`aresample→4×, alimiter, aresample→1×`), and the repo's own docstring there records two load-bearing
switches: "`asc=0` keeps the lookahead off and `level=0` is what stops it normalizing the trimmed
signal back up".

**I hit that trap from the other side.** My first A/B ran `alimiter` at its defaults (`level`
defaults to **true**, "auto level … normalizes audio back to 0dB"). Result: the emitted ceiling went
the **wrong way** — concat TPK **+0.3 dBTP** (from −0.8 unfixed) and loudness **−15.1 LUFS** (from
−16.1), an illegal +1.0 LU shift. Only after pinning `level=0` did the limiter behave. **A naive
relay limiter would make both the peak and the loudness worse.**

**Also OBSERVED:** `latency` defaults to **false** — `alimiter` does *not* compensate its lookahead
delay unless told to. Dropped into the live relay as-is it shifts audio against video by its
lookahead. (Read from the filter's option list; I did not measure the A/V offset — see §6.)

### 2d. A pre-encode ceiling cannot bound a post-encode codec overshoot

The brief's acceptance bar is "emitted true peak ≤ +0.1 dBTP". The live event it is aimed at started
from a prepared artifact whose documented guarantee is "no decoded sample above **+0.1 dBFS**"
(`TP_GUARD_MAX_PEAK_DBFS`, `loudness_ride.py:1816`) and reached **+1.16 dBFS** in the emitted
segment after two AAC generations. A ceiling placed *before* an AAC encoder constrains the encoder's
input; it does not constrain what the encoder emits. `avenc_aac`/`-c:a aac` overshoot is
content-dependent, so any fixed pre-encode ceiling leaves a residual — it makes the bar *likely*, not
*guaranteed*, and Work 3's test as literally specified ("asserting emitted true peak ≤ +0.1 dBTP")
is not satisfiable by the mechanism the brief prescribes.

## 4. A finding about the acceptance statistic itself

This is new since my first pass and it **corrects** what I filed earlier. Read it carefully.

The brief's OBSERVED table — and the acceptance statistic — comes from
`scripts/capture_emitted_hls_audio_proof.py`, which **concatenates** the captured segments and runs
`ebur128=peak=true` over the joined window (`:1081-1088`), taking the last `Peak:` line
(`:1012`, `"true_peak_dbfs": last(_LOUDNESS_PEAK_RE)`). The `.ffconcat`/list join is the whole
mechanism.

**OBSERVED — the reported window maximum is not the maximum over the window's segments, in either
direction, and I can show both.**

**(i) Under-report.** `emitted3/education/seg000000598.ts`, measured **alone**:

```
    max |sample| = 1.118059 (0.9693 dBFS) at frame 64735 = 1.3486 s
    samples with |v| > 1.0: 2      # (64735, 0, -1.1181), (64736, 0, -1.0613)
$ ffmpeg -i emitted3/education/seg000000598.ts -vn -af ebur128=peak=true -f null -
    Peak:        1.2 dBFS
```

The same segment as the 117th file of a concat list: the window reports **`Peak: 0.8 dBFS`**, and
`+0.8` is where the window's cumulative maximum sits for every longer prefix I tried:

```
prefix= 60  Peak=-0.0 dBFS      prefix=117  Peak=0.8 dBFS
prefix=116  Peak=-0.0 dBFS      prefix=130  Peak=0.8 dBFS
                                prefix=180  Peak=0.8 dBFS
                                prefix=243  Peak=0.8 dBFS
```

A true-peak estimator cannot report less than the largest sample it decoded (0.97 dBFS), so the
window is not decoding the same signal the member file decodes.

**(ii) Over-report.** Case B2's window reports `Peak: 0.3 dBFS` while every one of its 91 member
segments measures ≤ **−1.5 dBFS** and the window's own decoded samples top out below full scale:

```
$ ffmpeg -i ab2/B2/all.ts -vn -af ebur128=peak=true -f null -
    Peak:        0.3 dBFS
$ where2.py ab2/B2/all.ts
    max |sample| = 0.919989 (-0.7244 dBFS)     samples with |v| > 1.0: 0
```

**(iii) The mechanism, measured.** Re-encoding the same audio into longer joins progressively
changes it. The *same* over-full-scale excursion, decoded four ways:

| joined as | decoded position | max \|sample\| | ebur128 window Peak |
|---|---|---|---|
| `seg000000598.ts` alone | 1.3486 s into the segment | 1.118059 (**+0.97 dBFS**) | **+1.2** |
| `597+598` remuxed | 3.3540 s | 1.109590 (+0.90) | +1.1 |
| `597+598+599` remuxed | 3.3540 s | 1.109590 (+0.90) | +1.1 |
| all 243 segments remuxed | 233.3486 s | 1.068281 (+0.57) | **+0.8** |

The concatenated timeline is shifted ~0.58 s by the 243-segment join, and the excursion's amplitude
falls from +0.97 to +0.57 dBFS along the way. The same is visible in frame counts: the 243-segment
window decodes 23,405,568 frames where the members sum to 23,386,320 — the join both adds and loses
audio.

**INFERRED (and I am labelling this as inference, not measurement):** joining independently encoded
HLS segments produces a stream whose decode is not the concatenation of the members' decodes —
timestamps overlap at the joins, so the AAC overlap-add at each boundary is reconstructed from the
wrong neighbour and the demuxer shifts/drops frames. A "window maximum" measured this way is
therefore a property of the join as much as of the program. **This is why (i) and (ii) point in
opposite directions: it is one mechanism, not two.**

**Consequence for this unit:** the brief's table is a column of such window maxima, so its cells are
not reliable per-segment maxima — some may be join artifacts, and some real events may be damped
below the limit by the join. **Every claim in §1 and §3 above is therefore made on per-segment
measured maxima, not on a window maximum.** I have not modified
`scripts/capture_emitted_hls_audio_proof.py` or `bin\rung_check.py` — the coordinator's tightening of
`rung_check.py` (fresh OK worker receipt + integer cue count for `CAPTION_QUIET`) is untouched.
