## Q1 (headline) — the rule collides with the committed crash-loop escalation ladder

### The rule, verbatim from the brief

> "an ACTIVE channel is never dark while its program is being prepared. On any start/relaunch,
> the daemon starts the worker IMMEDIATELY on the fallback slate … then hands the prepared program
> in with the normal seamless reload when preparation completes."

### What the code does today for the same event

An `ON_AIR` channel whose worker exits non-zero is handled by `_relaunch_after_crash` and the
escalation ladder in `civiccast/egress/daemon.py`. It retries the **program**, advancing
`_restart_streak` (rate-limited by `_PREROLL_TIMEOUT_STREAK_COOLDOWN_S = 60`), and reaches
`FALLBACK_SLATE` only when `streak >= _LIVE_SOURCE_FAILURE_FALLBACK_STREAK`.

OBSERVED, pinned by the repo's own tests:

* `tests/egress/test_daemon_first_output_timeout_relaunch.py:391-421` asserts
  `daemon._restart_streak["gov"] >= 5`, `state == "FALLBACK_SLATE"`, and `reached_at == 405.0`.
* `tests/egress/test_daemon.py:6798`
  `test_repeated_live_source_crash_falls_back_to_slate_instead_of_dead_air_loop` asserts
  `len(started) == n + 1` (one start per retry) and FALLBACK_SLATE only at the end; its docstring
  names the contract it defends: "dead air forever".

So for **the same event** — one non-zero worker exit on an ON_AIR channel — the brief says "air
the slate now" and the committed ladder says "retry the program, air the slate at the fifth
failure, measured at 405 s". Both cannot hold for the same event.

### What this unit did about it, and why

INFERRED (from the code): the two are not actually in conflict about the *goal* — both exist to
prevent dead air — but they disagree about the *first move* after one crash.

This unit implements the rule **only where the finding was measured and where the station runs**:
the asynchronous preparer (`enable_async_preparation()`, which `civiccast/egress/automation.py`
turns on for the station). That is the path on which the reported darkness was observed
(`evidence\public-exit1-1119\`, `evidence\public-exit0-0159\`) and the only path on which
`_start` returns with **nothing on air**. The slate-first branch is guarded on
`self._preparation_executor is not None`; on the synchronous path and everywhere else the ladder
is untouched, and `test_u47_the_synchronous_path_keeps_the_crash_loop_escalation_ladder` pins that
so the scope choice cannot drift silently.

The guard is **a scope choice forced by a conflicting committed contract, not an implementation
limit** — the slate worker is a separate process, so the synchronous path could air one too. That
distinction is written into the `SCOPE` comment in `daemon.py` precisely so a later reader does
not "fix" it by removing the guard.

### The question

**Does "on any start/relaunch" mean the slate-first rule overrides the escalation ladder's
retry-the-program-until-streak-5 semantics — on the synchronous path too, and (if so) does the
ladder survive anywhere?**

The options as I see them:

1. **Stay as implemented.** Rule applies to the asynchronous (station) path; ladder keeps its
   5-retry semantics on the synchronous path. The station is protected; the two contracts are
   still formally contradictory, which is a documentation debt.
2. **Rule wins everywhere.** The slate airs on the first crash-relaunch regardless of executor,
   and the ladder is retired or re-pointed. 22 currently-pinned tests change meaning, including
   the "dead air forever" latch — that latch exists because a source that never comes up used to
   be abandoned silently, so retiring it needs a deliberate answer to "what stops a
   never-playable program from leaving the channel on the slate forever?".
3. **Ladder wins, rule narrowed further.** "Any start/relaunch" is read as "any OPERATOR-initiated
   or scheduled start/relaunch", and crash-relaunches stay wholly with the ladder. This is the
   most conservative reading of both texts and needs no test churn — but it does not fix the
   measured 11:19 darkness, because that darkness was a crash-relaunch.

I did not pick one. Option 1 is what is implemented; options 2 and 3 are the coordinator's call.

## Q2 — the brief's 5 s slate bar is not met on this seat, and the excess is worker bring-up

The brief's acceptance bar, verbatim: "slate output within 5 s of start".

OBSERVED, seven runs of `tests/egress/test_u47_slate_first_real_worker.py` on this seat
(command: `python %TEMP%\u47\run_pytest.py tests/egress/test_u47_slate_first_real_worker.py -q
-p no:randomly -rs -s`), worker-exit → slate output:

```
5.42 / 5.48 / 5.62 / 5.84 / 5.84 / 6.06 / 6.22 s
```

The last run's own breakdown line, verbatim:

```
[u47] slate render (warm, one-off): 0.70s; worker-exit -> slate output: 6.22s (budget 5s;
1.24s to spawn + 4.98s worker startup); slate grew for 3.28s while held; spawns=['program',
'slate', 'program']
```

INFERRED: the excess is the worker process's own bring-up (`python` + `import gi` + `Gst.init` +
graph build + preroll), not the daemon's decision path. The daemon's own share of the window —
deciding, conforming the slate plan, and spawning — is the residue.

**The question:** is the 5 s bar a hard gate on this unit, or a stated intent whose real target is
"not 20–133 s"? The defect being fixed is a preparation-window darkness of 20–133 s; 6.2 s is a
~20× improvement, and the remaining ~5 s is the cost of starting a GStreamer process at all, which
no daemon-side change removes.

I deliberately did **not** assert the 5 s bar: a permanently red test hides the miss instead of
reporting it. The test asserts an 8 s regression ceiling (which catches the failure the test exists
for) and **prints** the 5 s miss. If the bar is a real gate, the fix is not in this unit's scope —
it would be a warm/pre-rendered slate leg (Q3) or a pre-forked worker.

## Q3 — must the slate be conformed before it can air at all?

OBSERVED: on both paths the slate is produced by the ordinary preparation machinery — a plan
resolved from `_fallback_source_provider`, then run through `source_preparer` — before any worker
starts. That is why the slate itself costs a conform (~0.6–1.1 s warm for the single-segment shape
this unit's tests exercise; the field slate shape is not measured here).

INFERRED: a slate leg that is already prepared and cached would remove that share of the window
entirely, and would be the natural way to meet a 5 s bar. Whether the station should keep a
standing, pre-conformed fallback slate (and what invalidates it — config change, slate message
change, loudness change) is a product decision, not a defect fix.

**The question:** should the fallback slate be a pre-prepared, cached, long-lived artifact rather
than something conformed at the moment it is needed?

## Q4 — "any start/relaunch" vs a genuine cold start

The brief says "any start/relaunch"; its own explanation says "an ACTIVE channel is never dark".
Those differ for a channel that is already dark.

Implemented and pinned: an operator start of a STOPPED channel prepares the **program** first, with
no slate leg
(`test_u47_an_operator_start_of_a_stopped_channel_still_prepares_the_program_first`). The channel
is already dark, so there is no airing state to protect, and the first thing it should air is the
program.

**The question:** confirm. If the brief literally wants the slate first even on a cold start, that
is a different change (and it changes what the operator sees on a channel they just started).

## What is NOT in question

* The defect is real and reproduced from the code, not just from the field logs: pre-U47, the
  relaunch resolved and conformed the scheduled program with no encoder running at all. The unit
  tests assert the pre-U47 shape red and the fixed shape green (Rule 3, both quoted in
  `reports\U47.md`).
* A **second** darkness, found by this unit's own test C, is fixed: on the asynchronous path a
  *failed* hand-off preparation reached `_fall_back_to_restart_reload`, which out of a live
  `FALLBACK_SLATE` terminates the slate worker (issue #157) and took an airing channel dark. The
  fix (`_keep_slate_after_failed_hand_off`, reached from both the sync tail and
  `_poll_preparation`) is a defect fix, not a product decision — but it is the reason the async
  and sync failure paths now share one helper.
