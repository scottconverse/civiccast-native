## 2. The question

**How should the rung's −16 ± 1 LUFS / 240 s criterion treat a 240 s window that is dominated
by quiet, non-speech material — where the ride is already at its 18 dB clamp and the ride's own
0.9 LU gate has flagged and passed it on by design?**

Two facts bound the answer, both OBSERVED:

- **The same asset passes elsewhere.** The rung ran a second time at 11:12:12 (same evidence
  directory, `loudness-02.json`) and **PASSed all three channels — public −16.7 LUFS** — while
  the *same* Parks asset was still on air (the only public source between 10:55 and 11:20 in
  `control_plane-app.log`). The criterion samples one 240 s window per channel, so whether this
  asset fails or passes depends on which window the sample lands on, not on the asset.
- This is not a one-window accident. Across the whole 7793 s asset, **762 of 7554** sliding
  240 s windows (**10.1 %**) sit more than 1 LU from −16 — from 3636 s to 5986 s — and the
  global window minimum is **−24.04 LUFS at 5590 s**. The whole program is −16.09 (dev
  −0.09), i.e. in band.
- The **asset-worst** window (5640–5880 s, −21.87 LUFS, dev −5.87) is a genuinely different
  stretch: tilt median **−14.1 dB**, only 2.9 % of frames tilt>0 — strongly non-speech. It
  must **not** be lifted. Any rule change that fixes the rung window by brute force would
  roar this one.

## 3. Options, with my recommendation

1. **Leave it as is.** The rung FAIL stands for windows like this. Cost: an 8 h rung can be
   failed by material no lawful setting of the ride would move, and each one costs an
   investigation.
2. **Treat quiet/non-speech-dominated windows as not loudness-applicable** — the rung scores
   only windows whose source clears some program-loudness floor. Cost: a new threshold to
   tune and defend, and it is exactly the kind of "skip the hard window" predicate that can
   hide a real miss.
3. **Judge the rung over the whole program (or the whole 8 h) rather than one 240 s window** —
   keep 240 s windows as a *reported diagnostic*, not a pass/fail. Cost: a deliberately quiet
   program could then pass while a loud one fails the intent. **This is the one I would pick**:
   it matches what the ride itself already guarantees (whole program within 0.5 LU —
   measured −0.09 here), it removes a statistic the ride was never designed to control at
   45 s resolution, and it keeps the per-window numbers visible in the report for triage.
4. **Make the ride target a 240 s window instead of 45 s** (`RideParams.window_s = 45.0` at
   `loudness_ride.py:326`) so the ride and the criterion measure the same thing. Cost: the ride
   would push quiet stretches much harder and late — pumping and room-tone lift. I have **not**
   measured that, and it is the one option that changes nominal output for every asset, so it
   would need its own full-asset and 7-cell measurements before any decision.

**Explicitly not on the list: raising `g_max_db` (`loudness_ride.py:333`).** The gap here is
18…22 dB; raising the clamp far enough to close a −38 LUFS stretch would amplify room tone and
mic noise by that much. The clamp is doing its job.

The count is a **duration**, so it slides with position (32 → 87 s across ±30 s). **INFERRED, and

window lands on **neither** as the rung computes it: the count says EXCLUDED, the sweep says FAIL,
