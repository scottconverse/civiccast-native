## Q2 (product question: what counts as verified for this change) — is a station/real-model re-measurement wanted?

Every U23 test runs the fake runtime. That proves plumbing, timing, the seam and the queue
arithmetic — it does not prove ASR behaviour, and it cannot produce the number this unit is
justified by. The claim in `reports/U23.md` §7.2 — "a ~16 s stall now costs seconds of
captions instead of 2–8 minutes" — is U22's OBSERVED station measurement plus the code path,
not an end-to-end measurement of this change on air.

**Question:** should a follow-up unit re-measure the live tap (the U22 harness shape) with
`abdfd20d` installed, to confirm that a shared-GPU stall now produces a catch-up WARNING and
continuous captions rather than a 2–8 minute blackout — or is the fake-runtime proof the
accepted bar for this class of change? **Recommendation:** re-measure, because the acceptance
verifier that failed in the first place samples real caption output, and only a station run
closes that loop. Also note it would tell us whether the default budget (3 sheds / 300 s) is
right: U22 saw 19 overloads in 67.5 minutes, which on its face is enough episodes to reach
the ladder.

## Q3 (small, needs a ruling) — the two new env knobs fall back to the DEFAULT on a bad value, which is a mild trap

`_clamped_env_int(name, default, minimum=0)` / `_clamped_env_seconds(name, default,
minimum=1.0)` **discard** an unparseable or below-minimum value, log a WARNING, and use the
default. So `CIVICCAST_CAPTION_TAP_CATCH_UP_SHED_LIMIT=-1` does not mean "catch-up off" — it
means **3**. The documented off-switch is an explicit `0`. This is consistent with every
other tap knob and with the "live captions are best effort and must never hold the control
plane down" posture (the phrase is at `tap_worker.py:455`, inside
`_clamped_env_seconds`, `:446-471`; `_clamped_env_int` is `:484-516`; the design rationale —
"a station that refuses to start over it would be a worse failure" — is at `:416-421`), and
`docs/ops/background-workers.md` now says so in the variable table, so no code change is
proposed.

**Question:** is the fall-back-to-default semantics the intended station-wide convention for
all clampable env knobs, or would you prefer below-minimum values to clamp to the minimum
(where a negative limit would then genuinely mean "off")? **Recommendation:** leave as is —
it is uniform, documented, and a startup refusal on a typo'd optional knob would be worse.
Raised only because a below-minimum value silently becomes the *most permissive useful*
setting rather than the most restrictive one.
