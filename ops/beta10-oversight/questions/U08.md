## 1. Product question: how fresh must tamper-evidence be, and what does the station pay for it?

### What is OBSERVED

* **The digest is a tamper gate.** `civiccast/captions/review_media.py:84`:
  `if _sha256(source) != evidence.source_sha256:` → `CaptionReviewClipError`. `evidence.source_sha256`
  was recorded when the evidence was written (`review_media.py:64` records it on the way in).
* **An operator path depends on it.** `civiccast/captions/review.py:147-178`
  (`require_low_confidence_approval_evidence`, reached from the low-confidence approval route) calls
  `verify_caption_review_audio_evidence_for_cue`. A mismatch blocks the approval — so a cached digest
  would weaken a control a human relies on, which is exactly the case the brief told me to surface.
* **It is also the single most expensive phase of the sweep, twice over.** Measured on the synthetic
  9,996-file archive (`$TEMP\u08\measure.py`, full numbers in `reports\U08.md` §1):
  * 1 review row per evidence file (4,998 rows): evidence verification **7.2 s of a 24.6 s sweep**,
    4,998 fresh reads of 4,998 distinct files.
  * 4 review rows per evidence file (19,992 rows, the live coalescing shape — one ASR window attaches one
    WAV to every cue it produced): evidence verification **16.8 s of a 35.1 s sweep**, i.e. **19,992 reads
    of 4,998 distinct files**.
  * In the live topology the same phase runs over the station's recorded audio every 60 s forever.

### What is IN place because of it

* The cross-sweep `(st_size, st_mtime_ns)` reuse is **not** applied to that read. `retention.py:555`
  `_verify_evidence_once` is a memo scoped to one sweep, keyed on the row's recorded
  `(source_path, source_sha256, source_bytes)`, so `N` rows over one file cost **one** read within a sweep
  and the **next** sweep starts clean. The 19,992 → 4,998 reduction above is that memo; the 4,998 reads
  that remain are fresh reads of the current bytes, every sweep.
* Tests pin the safety half: a row whose recorded digest disagrees is still dropped; a file tampered
  between two rows of the same sweep still fails verification; a tamper performed after one sweep is seen
  by the next sweep even with size and mtime restored.

### The question

**Should a station pay one full read of every retained evidence WAV per sweep interval (currently ~2.4 s of
a ~5–8 s sweep on the 1-row model, and the same 4,998 reads on the 4-row model) to keep the tamper check
answering from the current bytes, or is a bounded-staleness answer acceptable there?**

The options, with my recommendation:

* **(A) Leave it as delivered.** Fresh read per sweep per file; reuse only within a sweep. Cost: the
  residual above. Safety: unchanged from today.
* **(B) Recommended if the cost ever bites: reuse with a *tamper-specific* trust rule** — e.g. key the
  cache on `(size, mtime_ns, inode/ctime_ns)` and keep it per *sweep* only, which the delivered code
  already does — or move the freshness requirement to the *approval* call (`require_low_confidence_
  approval_evidence` already re-verifies at the moment of approval), and let the *retention* sweep reuse
  the digest. That is a real product decision: the sweep's use of the digest is an audit record of what it
  is about to delete, not a gate; the gate is the approval path. Deciding that is above my pay grade
  because it means saying "the sweep may delete a file whose digest it read a sweep ago", which is fine
  only if the file cannot change without changing its mtime (the tap and evidence writer both write once,
  by `os.replace`).
* **(C) Do nothing further** and accept the residual.

I recommend **(A) now, (B) only if the measured live steady state is still a problem** — the live number is
unknown to me because measuring it is prohibited, and the brief's whole premise (60.5 s live discovery) was
dominated by the *chunk* half of the sweep, which this unit already made stat-only.

Nothing here blocks the unit: the delivered code is (A).

## 2. Design decision I did not take: declare the bulk reader on the store protocol?

OBSERVED: `list_with_audio_evidence` exists on both concrete stores —
`PostgresCaptionReviewStore` (`civiccast/captions/persistence.py:237-254`, one `select`) and
`InMemoryCaptionReviewStore` (`civiccast/captions/review.py:285-290`, a per-row dict lookup with no I/O) —
but is **not** declared on the `CaptionReviewStore` protocol (`review.py:181-225`). Retention therefore
reaches it with `getattr` and falls back to per-row `get_audio_evidence` (`retention.py:419-429`).

The brief said to add a batch method "to the protocol + both stores **if needed**". It is not needed by
measurement: the durable store is already one query, and the in-memory store's per-row path measured
0.2–0.7 s of a 7.9–25 s sweep. Declaring it on the protocol is a public-contract change for every other
implementer (including test doubles), so I reported it instead of doing it.

**Do you want the protocol declared in a follow-up unit?** If yes it is a two-line protocol addition plus
tests for any implementer that lacks it — a small, separate, reviewable change rather than an appendix to
this one.
