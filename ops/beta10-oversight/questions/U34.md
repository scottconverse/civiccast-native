## Q1 — `CIVICAST_DEFER_SWITCH_TIMEOUT_S` is a dead knob; a deferred switch that never fires has no operator-reachable bound

**OBSERVED.** At U34 HEAD (`5397c069`), the string occurs **exactly once** in the whole worktree:

```
tests/egress/test_gst_engine_wsl.py:1540:            "CIVICAST_DEFER_SWITCH_TIMEOUT_S": "30",
```

It is set into one test's environment and **read by nothing** — not the engine, not the worker, not
the daemon, not the installer. The engine's only bound on a deferred (boundary-aligned) replacement
that never reaches its boundary is the constructor default:

* `defer_switch_timeout_s: float = 900.0` — `civiccast/egress/gst/engine.py:633`, stored at `:662`;
* armed as a GLib timeout when the deferred mode is chosen — `engine.py:3682`
  (`max(1, int(self.defer_switch_timeout_s)), self._on_defer_switch_timeout, txn_id`);
* its only other appearance is the forced path's log text (`engine.py:4207`).

Nothing in the repo constructs `GstPlayoutEngine` with anything but the default outside tests, so
the 900 s bound is not operator-settable by environment today, and the test above asserts nothing
about the variable it sets.

**Why this matters (OBSERVED, by reading the predicate).** `_force_ready_deferred_switch`
(`engine.py:2954-2961`) accepts a force only when `switch_at_end_of_current` **and** `new_leg_ready`
**and** *not* `old_leg_eos` **and** *not* `commit_in_progress`. The live reload-7 freeze put the
channel in exactly the state where the boundary the deferred switch waits for never arrives — the
outgoing leg's live video branch stopped feeding, so no EOS/boundary was ever produced. Before U34,
in that state the only in-engine bound was 900 s.

**INFERRED, not measured:** on the live box the daemon's own escalation resolved the situation long
before the engine's 900 s timer (U30 §4.4's timeline is 70–100 s of frozen output, with a 30 s
stall escalation before it). I did not watch the 900 s timer expire and do not claim to have. After
U34 the per-stream judge reaches the same `_force_ready_deferred_switch` at its own bound (10 s
default), so the practical exposure is much smaller — but the knob is still dead, and the
constructor-only bound is still 900 s.

**The decision I did not make.** Three honest options:

1. **Wire it** — read `CIVICAST_DEFER_SWITCH_TIMEOUT_S` in `GstPlayoutEngine.__init__` as the
   default for `defer_switch_timeout_s`, make `test_gst_engine_wsl.py:1540` assert it. Blast
   radius: operator-visible timing, alignment with the daemon's escalation ladder, and the two
   governed claims comments that cite the 900 s bound (`docs/claims/claims.yaml:568` and `:1329`),
   plus the doc comments in `engine.py:3378`, `daemon.py:292/4248`, `worker.py:162` and
   `strategy.py:110` that describe the same number. There is also a **duplicate** of the constant
   that has to move with it: `ChannelAutomationService._ROLLOVER_DEFER_SWITCH_TIMEOUT_SECONDS =
   900.0` (`automation.py:1007`), which `tests/egress/test_automation.py:531` pins with an explicit
   equality assertion, and whose comment at `automation.py:997-998` already spells out that it must
   stay consistent with the engine's default. Wiring the knob without moving that pair would make
   two numbers that are documented as one number disagree.
2. **Delete it** — drop the line from the test and record that the deferred bound is
   constructor-only, i.e. not operator-reachable.
3. **Leave it and document it** — state plainly that the bound is fixed at 900 s in this line.

**Recommendation if forced to pick: (1)**, because a 900 s in-engine bound is longer than the
daemon's own escalation, which makes it a lever that is only reachable in a state where the
operator has no other one and the platform has already taken over. But whether that number should
be operator-visible, and what it should default to relative to the daemon's ladder, is the owner's
call — not a coder's, and not inside U34's three items.
