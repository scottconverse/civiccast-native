## 1. The "+2.2 dBFS tail window" does not exist — it is a seek artifact, not an emitted peak

The brief asks me to *"find out whether [the 4d36 tail window's +2.2 dBFS] survives `TP=-1.5`, and if not,
why"*. OBSERVED — it never existed as an emitted peak. Three independent measurements of the same
artifact:

- Seek-free ground truth for that window (4d36, `-ss` nowhere, whole-file streamed decode → raw f32le slice
  → `ebur128=peak=true`): **TP = −0.7 dBTP**, slice sample peak **−1.0415 dBFS**, `over_full_scale = 0`.
- The harness's input-seek convention (`-ss` *before* `-i`, which is the production probe's convention)
  reports **+2.2** for the same window. The output-seek convention (`-ss` *after* `-i`) reports −0.0 —
  because it reports the *program's* global peak, not the window's (see below), so it is not corroboration.
- The emitted program's own seek-free true peak on that LRA=11 cell is **−0.0 dBTP** with sample peak
  −0.129 dBFS and `over_full_scale = 0` — i.e. all of its overshoot is inter-sample, which no +2.2 dBTP
  sample-domain excursion could be.

**INFERRED, mechanism.** `-ss` before `-i` starts decoding mid-GOP with no AAC warm-up; the decoder's
priming transient lands in the first frames of the filtergraph, and `ebur128`'s peak hold reports it. It is
a property of the measurement, not of the file. Nothing to fix in the conform.

**The same investigation did settle the seek question generally**, which matters because the harness called
output-seek "exact" and "the one that decides it". OBSERVED — against the seek-free truth, input-seek
reproduces integrated loudness **and LRA to the digit on all 3 arbitrated windows** (e.g. 4d36 LRA=11
720+240 s: truth I=−18.3 LRA=6.4; input-seek I=−18.3 LRA=6.4; output-seek I=−17.0 LRA=5.6), and input-seek
*never* matches truth's true peak. Output-seek matches truth's integrated loudness on **0 of 3** — its I is
cumulative from file start (4d36 output-seek I = −17.0 = that program's own whole-program I; `astats`
counted 57,601,024 samples in the output-seek run vs 11,521,024 in the input-seek run for a 240 s window).
So in the appended table every per-window I/LRA comes from input-seek, and **every true-peak verdict is a
seek-free verdict** (whole-program, no `-ss` at all, plus an f32 sample-domain pass).

**Consequence for the verdict.** 4d36 still fails, at every LRA, and its true peak still exceeds the −1.0
dBTP ceiling — but for the real reason: whole-program seek-free TP is −0.0 / −0.2 / +0.0 dBTP at LRA 11 / 7
/ 5, while the loudnorm limiter's own PCM output honours `TP=-1.5` (filter PCM reads −1.4/−1.5 dBTP). The
≈ +1.2…+1.3 dB is AAC 192 kbps true-peak overshoot, identical in single-pass and two-pass, on material
with zero samples over full scale in the sample domain. It is an encoder property, not a two-pass defect
and not an LRA-selection problem.
