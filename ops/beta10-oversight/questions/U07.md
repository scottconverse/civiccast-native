## 2. Why this is a product question, not a coder decision

Unblocking the stall requires the provider to answer a start when it has **no** verdict. The only
faithful label for that answer is missing from the type, and the two ways to proceed differ in
station-visible safety:

* **The `ready` contract becomes ambiguous.** Today `ready=True` means "the retention policy ran and
  cleared this station". If the provider returns `ready=True` with no verdict, `ready=True` also means
  "nothing was checked". The daemon cannot tell them apart and never re-checks (1c), so the ambiguity
  is terminal for that broadcast.
* **It changes when the one remaining real refusal is applied.** `caption-storage-volumes-diverge` is
  the *only* remaining refusal in this policy (the volume-relative space caps were removed by owner
  decision 2026-09-20 — `retention.py:143-150`) and it is a misconfiguration guard, not a space panic.
  On a cold start the first verdict cannot be in hand (the sweep takes ~60 s on this archive), so under
  a plain-"ready" rule a diverging-volume station's **first start after boot would air the scheduled
  program instead of being refused to the fallback slate** — a fail-open change to a gate that is
  fail-closed today. Whether that trade is acceptable is your call, not mine.

## 3. Options I can see, with what each costs

**Option A — return a plain optimistic `ready=True` when there is no fresh verdict.**
`CaptionRetentionResult(ready=True, refusal_reason=None, requires_fallback_slate=False)`, unchanged
type, provider returns inside the bound. Cheapest. Cost: exactly the ambiguity and the cold-start
divergence bypass in §2. The pending state stays invisible to the daemon, any log line, and the
operator sidecar.

**Option B — keep the cheap divergence check synchronous; background only the heavy half.**
The provider still runs the divergence check inline (three syscalls, §1e) and returns the same refusal
it does today when the volumes diverge; it then consults the shared verdict for the discovery half and
returns optimistic-`ready=True` when there is none. Today's fail-closed gate is preserved exactly, the
60 s of discovery never runs on the automation thread, and no type changes. Cost: a small,
well-tested refactor of `enforce_discovered` so the cheap check is a separate method (call it from
`enforce_discovered` so there is one implementation), plus the note that the provider then is not
literally "return the last verdict" — it is "cheap check + last verdict".

**Option C — make "pending" expressible: add a field to `CaptionRetentionResult`.**
E.g. `verdict_pending: bool = False` (defaulted, so every existing constructor and the VOD job keep
working), the provider returns `ready=True, verdict_pending=True`, the daemon keeps starting the
program on `ready=True`, and the pending state becomes observable — loggable, and publishable to the
existing operator sidecar (which today has no pending state either: `CaptionRuntimeState` is
`within-capacity | overloaded | storage-refused | paused | disabled`,
`civiccast/captions/live_sidecar.py:23-29`). Cost: a type change to a dataclass consumed by both
`egress/daemon.py` and `captions/vod_job.py` (which reads `.ready` — `vod_job.py:643,752-763`), plus a
new sidecar state if you want it operator-visible.

**My recommendation if I had to pick: Option B, with Option C if you also want the pending state to be
observable.** B strictly dominates A — it fixes the stall identically while changing no fail-closed
behavior — and it is the smallest change that satisfies the Goal as written ("Starting a channel never
runs retention *discovery* on the automation thread"; a two-`stat()` divergence check is not
discovery).
