# CivicCast playout: prior art and fixes for the defects seen live on 2026-09-24

Research date: 2026-09-24. Scope: primary sources only (GStreamer / gst-plugins-rs source on the 1.28 and main branches, FFmpeg source and docs, project LICENSE files read through the GitHub API or raw files, Microsoft Learn). Anything I worked out myself rather than read in a source is labeled **(inference)**. Nothing in the repo or on the running station was touched.

License key: **SHIP** means it fits CivicCast policy (OSI-permissive, or LGPL/MPL used as a runtime dependency). **IDEAS ONLY** means GPL/AGPL, so study it but never ship it.

## 2. Per-defect findings

### 2.1 Defect 1: A/V desync after a leg switch (video ~109 s behind audio)

**Facts from sources**

- `gst_pad_set_offset` changes a pad's running time. Downstream sinks synchronize on running time, so an offset that puts buffers ahead of the pipeline's current running time makes a clock-synced sink **wait** (backpressure). An offset behind it makes the buffers late. See the [Synchronisation design doc](https://gstreamer.freedesktop.org/documentation/additional/design/synchronisation.html) and [Pipeline manipulation](https://gstreamer.freedesktop.org/documentation/application-development/advanced/pipeline-manipulation.html).
- **`concat` handles one stream only.** The concat source says it keeps "the running time continuous" by adjusting segment base per input ([gstconcat.c, 1.28](https://github.com/GStreamer/gstreamer/blob/1.28/subprojects/gstreamer/plugins/elements/gstconcat.c)). Sebastian Dröge's write-up says multi-track gapless concatenation needs "multiple concat elements and the streamsynchronizer element … to keep everything synchronized" ([coaxion.net 2014](https://coaxion.net/blog/2014/08/concatenate-multiple-streams-gaplessly-with-gstreamer/)). If one filler item's audio and video lengths differ, each per-stream concat moves forward by a different amount, and that difference **accumulates**. `streamsynchronizer` fills the shorter stream with GAP so both move forward together (gst-plugins-base `gststreamsynchronizer.c`). concat also has an `adjust-base` property meant for use with streamsynchronizer.
- **input-selector in 1.28 commits a switch lazily.** MR 10507 ("two-phase sinkpad switch", commit `dd0c2e3eba`, 2025-12-14, in the 1.28 branch) made `active-pad` a *pending* value that is only committed when a buffer or event is next processed ([commit list](https://github.com/GStreamer/gstreamer/commits/1.28/subprojects/gstreamer/plugins/elements/gstinputselector.c), [1.28 release notes](https://gstreamer.freedesktop.org/releases/1.28/)). Follow-up fixes from MR 11928 ("Add 2 more calls to check for active pad switch", "Hold active-pad during allocation query", 2026-06-24) are on **main but not on the 1.28 branch** (checked against the GitHub mirror commit history).
- **FFmpeg interleaving:** the muxer waits for at least one packet per stream and buffers up to `max_interleave_delta` (default 10 s) before writing anyway ([formats.texi](https://github.com/FFmpeg/FFmpeg/blob/master/doc/formats.texi)). The HLS muxer cuts a segment "on the next key frame after this time has passed" ([muxers.texi, hls_time](https://github.com/FFmpeg/FFmpeg/blob/master/doc/muxers.texi)). When video lags, the video timeline stalls, so no cut is possible and the playlist freezes. Once more than 10 s is buffered, packets are written with the skew baked into the segments. That matches what we saw: a ~30 s freeze, then segments with video far behind audio.

**Hypotheses for the 109 s (inference, to confirm in logs)**
1. A slate/filler item whose video stream is ~109 s shorter than its audio (a still image or short loop with a long bed). Per-stream concat without a streamsynchronizer turns that straight into a permanent 109 s skew. This fits "video behind audio" and "never re-converged".
2. The offset was built from per-stream ends ("max of observed outgoing ends") that were measured on the leg side (stream time / segment position) instead of the output-side running time. That puts one stream's offset ahead of the clock.
3. Given the 1.28 lazy commit, a switch that commits on audio before video can make the two streams switch at different buffers (lower likelihood).

**What to do (R2)**
- Take the offset from one source: output-side running time. Use pad probes on the selector src pads (or encoder sink pads) that record the end running time of the last buffer on each stream, and use max(video_end, audio_end), or the clock's running time if that is larger. Apply the **same** value to every src pad of the new leg. Log it with the pipeline running time at apply time. An offset more than ~1 frame ahead of "now" should be treated as a defect.
- Multi-segment legs: add `streamsynchronizer` after the concats (set concat `adjust-base=false`, as the concat docs suggest), or guarantee equal A/V duration at conform (`-af apad -shortest`, or trim audio to the video duration).
- Watchdog: compare the running time of the latest buffer at the video and audio encoder sink pads. This is cheap and catches any future cause.
- Defensive option: `livesync` (gst-plugins-rs, MPL-2.0) on each branch before the encoders repeats the last frame or inserts silence over gaps and drops late buffers ([docs](https://gstreamer.freedesktop.org/documentation/livesync/index.html)). It keeps the encoders and mux fed, which turns a mux stall into a visible freeze that the watchdog can catch. It does not fix a real skew.

### 2.2 Defect 2: input-selector / live leg teardown deadlocks

**Source-verified mechanism (GStreamer 1.28 branch, `gstinputselector.c`)**
- The chain function takes `active_sinkpad_lock` (a `GRWLock`) in **reader** mode and holds it **across `gst_pad_push()` downstream** (reader lock taken near the top of chain, `gst_pad_push (sel->srcpad, buf)` called inside it, reader unlock only after the push returns).
- `gst_input_selector_release_pad()` takes the same lock in **writer** mode (`g_rw_lock_writer_lock (&sel->active_sinkpad_lock)`), then calls `gst_pad_set_active(pad, FALSE)`, which also needs the pad's stream lock.
- `get_property("active-pad")` takes the lock in **reader** mode.
- The header comment says writer mode is "limited to `maybe_commit_active_pad ()`", but `release_pad` and `reset` also take it as writer in 1.28 ([gstinputselector.h](https://github.com/GStreamer/gstreamer/blob/1.28/subprojects/gstreamer/plugins/elements/gstinputselector.h)).
- **Consequence (inference from the code):** `release_request_pad` cannot return while *any* selector pad is inside a downstream push. If downstream is blocked, the release blocks for as long as that lasts. Downstream can block because a queue is full because the sink is waiting on a future-offset buffer (defect 1), or because the encoder is starved of CPU (defect 4). On Windows, GLib's GRWLock is built on SRWLOCK. A pending exclusive waiter usually makes new shared acquirers queue behind it, so a concurrent `get_property("active-pad")` wedges too. That matches both reported symptoms. **Defects 1, 2 and 4 feed each other.**
- With the default `sync-streams=TRUE`, inactive pads **wait** inside the selector (`gst_input_selector_wait_running_time`, either a cond-wait or a `gst_clock_id_wait` in `sync-mode=clock`). `release_pad` sets `being_released` and broadcasts to wake them, which is correct. The blocking-push case above is not covered.
- This code is new (two-phase switch, Dec 2025) and follow-up concurrency fixes landed on main in June 2026 without a backport. Expect other edge cases in 1.28.x.

**Patterns**
- R1 teardown order: switch first. Then **block or drain the old leg upstream of the selector**, with a BLOCK probe on the leg's src pads (or EOS into the leg and wait for it on the selector pad via a probe). Set the leg bin to NULL, then release the selector pad from a non-streaming thread with a timeout. Never run a release from a pad-probe callback or a streaming thread.
- `sync-streams=false` removes inactive-pad waiting (inactive pads return OK or NOT_LINKED immediately, depending on `always-ok`). CivicCast already holds the prerolled leg with its own probes, so the selector's syncing isn't needed **(inference)**.
- Alternatives:
  - `fallbackswitch`: inactive pads "Dropping … on inactive pad"; `release_pad` = pad-local `flush_start` then deactivate ([source](https://github.com/GStreamer/gst-plugins-rs/blob/main/utils/fallbackswitch/src/fallbackswitch/imp.rs); [docs](https://gstreamer.freedesktop.org/documentation/fallbackswitch/fallbackswitch.html)). It schedules per-pad clock waits in running time, so it expects inputs timed against the pipeline clock. Our file legs need correct offsets for this (they need them anyway).
  - `fallbacksrc` (the same plugin) is built for live sources with restarts. It now supports multiple streams and encoded passthrough ([GStreamer Conference 2025 slides, Centricular](https://indico.freedesktop.org/event/11/contributions/518/attachments/303/396/fallbacksrc-2025.pdf)). It is a source, not a playlist switcher.
  - Inter-pipeline: `intersink`/`intersrc` (gst-plugins-rs `rsinter`, MPL-2.0, built on the `StreamProducer` API, "for transferring data between pipelines … in the same process"; 1.28 adds `event-types` on intersrc). `intervideosink/src` + `interaudiosink/src` (gst-plugins-bad, LGPL) re-timestamp independently on the consumer side, so A/V lock across them is approximate **(inference, known behavior)**. Prefer rsinter for A/V.
  - `gst-interpipe` (RidgeRun): **LGPL-2.1** ([COPYING](https://github.com/RidgeRun/gst-interpipe/blob/master/COPYING)), so shippable as a runtime dependency. It is **not** in the official Windows binaries, so we would have to build and maintain a Windows DLL. Prefer rsinter, which already ships.
  - `uriplaylistbin` (gst-plugins-rs, MPL-2.0): a gapless URI playlist built on uridecodebin3 ([docs](https://gstreamer.freedesktop.org/documentation/uriplaylistbin/index.html)). It could replace the hand-built concat slate/filler legs. It does not help schedule-time switching.
  - `playbin3`/`uridecodebin3` gapless and `instant-uri` design ([playback-gapless](https://gstreamer.freedesktop.org/documentation/additional/design/playback-gapless.html)): useful reference for preroll-then-swap with blocked pads.
- Availability: the cerbero 1.28 `gst-plugins-rs.recipe` includes `fallbackswitch`, `livesync`, `togglerecord`, `uriplaylistbin`, `hlssink3`, `rsinter`, `rsaudiofx`, `rsclosedcaption`, `hlsmultivariantsink`, `gopbuffer`, `streamgrouper` ([recipe](https://github.com/GStreamer/cerbero/blob/1.28/recipes/gst-plugins-rs.recipe)). Confirm on the station build with `gst-inspect-1.0 fallbackswitch`.
- Worth filing upstream: "input-selector 1.28: `release_pad` writer-locks `active_sinkpad_lock`, which chain holds across `gst_pad_push`; release blocks while downstream is blocked". Ask for the MR 11928 fixes to be backported to 1.28.

### 2.3 Defect 3: FFmpeg HLS relay locking the stream set

- The FFmpeg HLS muxer cuts only on a keyframe after `hls_time`. `split_by_time` allows non-keyframe cuts (not wanted here). `temp_file` and `independent_segments` are available ([muxers.texi](https://github.com/FFmpeg/FFmpeg/blob/master/doc/muxers.texi)).
- The UDP input has `fifo_size`, `overrun_nonfatal`, `buffer_size` and `timeout` options ([protocols.texi](https://github.com/FFmpeg/FFmpeg/blob/master/doc/protocols.texi)). Loopback UDP can drop under CPU starvation, and a probe that starts while a PID is momentarily silent sees only one stream **(inference)**.
- **Better architecture (R5):** end the GStreamer pipeline in `hlssink3` (gst-plugins-rs, **MPL-2.0**, [docs](https://gstreamer.freedesktop.org/documentation/hlssink3/index.html)). It is feature-equivalent to hlssink2, sends force-keyframe requests upstream so cuts land on target boundaries, posts `hls-segment-added` messages, and 1.28 added single-file byte-range mode. `hlscmafsink` gives CMAF/fMP4, and `hlssink2` (gst-plugins-good, LGPL) is the conservative option. The stream set is whatever pads are linked, so it can never "lock" to audio-only. This also removes a process, a probe, and the UDP hop.
- If we keep FFmpeg: keep the explicit `-map`; send from `mpegtsmux alignment=7` (1316-byte datagrams); add `?fifo_size=…&overrun_nonfatal=1`; watch playlist mtime (restart if older than 3 × hls_time). Do **not** set `max_interleave_delta=0`: it waits forever for a missing stream and turns a lag into a hard freeze.
- SRT (libsrt **MPL-2.0**, verified) and RIST (librist **BSD-2-Clause**, verified COPYING) are for lossy networks. On loopback they add nothing over removing the hop. Keep them for off-box contribution feeds.

### 2.4 Defect 4: CPU contention (encoders and conforms starving caption ASR)

**Hardware encode, license facts (all verified from source)**
- GStreamer `nvcodec` plugin: `GST_PLUGIN_DEFINE(... nvcodec, ..., "LGPL", ...)` in gst-plugins-bad `sys/nvcodec/plugin.c` (that file carries a BSD-2 header, Ericsson 2017). The bundled `nvEncodeAPI.h` carries NVIDIA's MIT-style notice ("This copyright notice applies to this header file only … Permission is hereby granted, free of charge"). At runtime it `LoadLibrary`s `nvEncodeAPI64.dll` / `nvcuda.dll` from the installed NVIDIA driver, so nothing NVIDIA-proprietary is shipped. Elements include `nvh264enc` (CUDA), `nvd3d11h264enc`, `nvautogpuh264enc` ([plugin docs](https://gstreamer.freedesktop.org/documentation/nvcodec/index.html)). 1.28 added `emit-frame-stats` and interlace fixes ([1.28 notes](https://gstreamer.freedesktop.org/releases/1.28/)).
- FFmpeg: `nvenc_deps="ffnvcodec"`, `nvenc_deps_any="libdl LoadLibrary"`. nvenc and ffnvcodec are in `HWACCEL_AUTODETECT_LIBRARY_LIST`, **not** in any nonfree list (nonfree is only `cuda_nvcc`, `cuda_sdk`, `decklink`, `libfdk_aac`, `libmpeghdec`) ([configure](https://github.com/FFmpeg/FFmpeg/blob/master/configure)). nv-codec-headers are MIT ([nvEncodeAPI.h](https://github.com/FFmpeg/nv-codec-headers/blob/master/include/ffnvcodec/nvEncodeAPI.h)). `h264_nvenc` is therefore fine in an LGPL build. Avoid `--enable-cuda-nvcc` / `--enable-libnpp` (nonfree), `--enable-gpl` (x264) and `--enable-nonfree`.
- `d3d12h264enc` (gst-plugins-bad `sys/d3d12`, LGPL) uses the OS D3D12 Video Encode API and has **`cc-insert`**, `rate-control`, `gop-size`, `bitrate` ([docs](https://gstreamer.freedesktop.org/documentation/d3d12/d3d12h264enc.html)). It is vendor-neutral, so it works if CivicCast ever targets AMD iGPUs **(inference: needs a driver that exposes D3D12 H.264 encode; test on Blackwell)**.
- `mfh264enc` (Media Foundation, LGPL plugin) has `adapter-luid`, `d3d11-aware`, `low-latency`. It uses the vendor hardware MFT when one is present.
- `qsvh264enc` (Intel, uses libvpl, **MIT** verified) and `amfh264enc` (AMD; AMF SDK headers **MIT**, verified LICENSE.txt) are also LGPL plugins. Relevant only on those GPUs.
- GeForce NVENC session limit: raised to **8 concurrent sessions** in early 2024 ([Tom's Hardware](https://www.tomshardware.com/news/nvidia-increases-concurrent-nvenc-sessions-on-consumer-gpus), [VideoCardz](https://videocardz.com/newz/nvdia-geforce-gpus-now-support-up-to-8-concurrent-nvenc-encoding-sessions)). 3 live encoders plus up to 5 conforms fit. Enforce a session budget in the conform scheduler.
- Captions with hardware encode: `h264ccinserter` works on any H.264 bitstream, so the current caption path is unaffected. `d3d12h264enc cc-insert` and FFmpeg `h264_nvenc` A/53 CC are alternatives.
- Patents are separate from copyright licenses. Cisco's openh264 binary carries Cisco's AVC patent coverage; hardware encoders do not bring that same arrangement. Flagged as an owner/legal question (§5), not a license blocker.

**Keeping ASR responsive (R7)**
- faster-whisper: `cpu_threads` maps to CT2 `intra_threads` and "A non zero value overrides the OMP_NUM_THREADS environment variable". `num_workers` maps to `inter_threads` ([transcribe.py](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)). CT2 intra-op threading is OpenMP, controllable with `OMP_*` ([CTranslate2 parallel docs](https://opennmt.net/CTranslate2/parallel.html)). Feature extraction and Silero VAD run on the CPU even with `device="cuda"`, so the ASR worker still needs CPU time slices.
- CT2's pool threads can't be deprioritized individually, but **process priority class applies to every thread in the process**. So: ASR in its own process at `ABOVE_NORMAL_PRIORITY_CLASS`. Conform ffmpeg launched with `subprocess.BELOW_NORMAL_PRIORITY_CLASS` (or `IDLE_PRIORITY_CLASS`), `-threads 4`, and assigned to a **Job Object** with `JOB_OBJECT_CPU_RATE_CONTROL_ENABLE | HARD_CAP` and `CpuRate = pct × 100` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information)). Optionally tag conforms **EcoQoS** via `SetProcessInformation(ProcessPowerThrottling, EXECUTION_SPEED)` ([QoS doc](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)). The docs list EcoQoS as always selecting the most efficient frequency. The effect on a non-hybrid 16-core desktop part is untested **(inference)**. CPU Sets (`SetProcessDefaultCpuSets`) can reserve 2–4 cores for ASR as a soft reservation.
- GStreamer playout workers (the real-time path) should stay at NORMAL or ABOVE_NORMAL, never below ASR's batch-y conform peers.

### 2.5 Defect 5: preparation cost

- **Prior art:** ffplayout's current design links libav through `ffmpeg-next` and runs its own in-process decode → process → encode pipeline with a single continuous encoder, so there is no pre-conform of the library. For hardware encode, "NVENC accepts `yuv420p` directly" ([developer.md](https://github.com/ffplayout/ffplayout/blob/main/docs/developer.md)) (GPL-3.0, ideas only). CasparCG and Liquidsoap also decode on the fly (GPL, ideas only).
- CivicCast's leg already decodes, then runs videoconvert/videoscale/videorate/capsfilter, then re-encodes live. The conform's video re-encode is therefore a **redundant generation** **(inference from the described pipeline)**. What a conform really needs to guarantee is: decodable, CFR-convertible, loudness-correct, and equal A/V duration (see 2.1).
- **R8 tiers:**
  1. *Remux*: H.264 (any resolution the leg can scale) + audio. `ffmpeg -c:v copy`, audio two-pass loudnorm to AAC, `-af apad` + trim to the video duration, mux to TS. Cost is audio analysis plus a copy.
  2. *Hardware transcode*: odd codec, VFR, interlaced. `-hwaccel d3d11va` (or cuda) decode + `h264_nvenc`/`h264_mf` encode inside the capped job object.
  3. *Software transcode*: last resort (openh264).
- Cache key: (content hash of source, conform-profile version, loudness target). Warm the cache in the background under the job-object cap.
- Alternative: skip pre-conform entirely and do loudness live (R9/`audioloudnorm`). Not recommended as the primary path, because live dynamic normalization is exactly what misses (2.6).

### 2.6 Defect 6: live loudness

- FFmpeg `loudnorm`: "Support for both single pass (livestreams, files) and double pass (files) modes." In dynamic mode it upsamples to 192 kHz. `linear=true` requires `measured_I/LRA/TP/thresh` and "will revert to dynamic" if its conditions aren't met, meaning target LRA is below source LRA or the gain would push true peak above TP ([filters.texi](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi)). Two-pass: pass 1 `loudnorm=I=-16:TP=-1.5:LRA=11:print_format=json`, pass 2 feeds the measured values with `linear=true`. Log whether pass 2 actually stayed linear (the JSON `normalization_type`). Content with high LRA silently falls back to dynamic unless the LRA target is raised.
- gst-plugins-rs `audioloudnorm` (audiofx, **MPL-2.0**): "Audio processing part … ported from ffmpeg/libavfilter/af_loudnorm.c … generously relicensed to MPL-2.0". Caps are fixed at **192 000 Hz F64**, with a 3 s gain lookahead (it reports +3 s latency in live mode) and a 10 ms limiter lookahead ([imp.rs](https://github.com/GStreamer/gst-plugins-rs/blob/main/audio/audiofx/src/audioloudnorm/imp.rs)). It is the **same dynamic algorithm** as today's single pass, so it will not fix the content-dependent miss. It costs resampling to and from 192k per channel.
- `ebur128level` (same plugin; uses the `ebur128` crate v0.1.10, **MIT** verified) supports momentary, short-term, global (integrated), LRA and sample/true peak with histogram mode. Use it for live monitoring and alarms (R9).
- Measurement caveat (inference): a 4-minute window reading −18.1 LUFS is not necessarily a program-integrated failure. Decide whether the SLO is per-program integrated or rolling short-term, and alarm on the one we mean.

## 4. Do NOT adopt

| Item | Why |
|---|---|
| x264 / `x264enc`, FFmpeg `--enable-gpl` builds, BtbN "gpl" builds (the ones ffplayout's docs point Windows users to) | GPL, excluded by policy. Make sure the bundled FFmpeg is an LGPL build (`ffmpeg -version` must not show `--enable-gpl`/`--enable-nonfree`). |
| FFmpeg `--enable-nonfree`, `--enable-cuda-nvcc`, `--enable-libnpp`, `libfdk_aac` | Listed nonfree in FFmpeg configure, so the binary becomes non-redistributable. NVENC does **not** need any of these. |
| ffplayout, CasparCG, Liquidsoap, OBS code or binaries | GPL-2/3. Ideas only. |
| `audioloudnorm` as "the fix" for defect 6 | Same algorithm as the failing single-pass mode (a port of af_loudnorm dynamic). It adds 192 kHz F64 resampling and 3 s latency per channel. Monitoring (`ebur128level`) plus two-pass prep is the fix. |
| `max_interleave_delta=0` on the relay | Makes FFmpeg wait forever for a missing stream, turning a lag into an outage. |
| `hls_flags split_by_time` | Non-keyframe segment starts break some players. The real problem is video lag, not the cut rule. |
| intervideosink/src + interaudiosink/src for A/V program paths | Each side re-times independently, so A/V lock across them is approximate (inference). Fine for monitoring or preview, not for program. Use rsinter. |
| Relying on 1.28 input-selector for hot teardown without the R1 ordering | The lock design shown in §2.2. Upstream follow-ups are not in 1.28. |
| Any CC-BY-NC Whisper fine-tunes or models needing per-deployment registration | Policy. The current faster-whisper/CT2 plus OpenAI Whisper weights (MIT) are fine. Re-check any new model card. |
