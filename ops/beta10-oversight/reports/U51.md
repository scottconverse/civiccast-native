### 1.1 Item 2 — the design, and why this one

**OBSERVED** at `civiccast/egress/sinks.py`: the HLS sink now carries two names —
`manifest_name = "playlist.m3u8"` (L297, the file players poll) and
`mux_playlist_name = "playlist.mux.m3u8"` (L304, private to the muxer);
`manifest_target()` (L312) returns the advertised path and `connect_target()` (L317) now returns the
**staging** path, which is what `container_args()` (L362) hands ffmpeg as its output. Segments are
unchanged: `segment_seconds = 2` (L291), `playlist_size = 6` (L292),
`-hls_flags delete_segments+append_list+program_date_time+independent_segments`.

The relay therefore no longer lets ffmpeg publish what viewers read. `_ManifestPublisher`
(`civiccast/egress/hls_relay.py:1032`) is a daemon thread named
`hls-manifest-publish:<channel dir>` (L1109) that polls the staging playlist's
`(st_mtime_ns, st_size)` every `_MANIFEST_PUBLISH_INTERVAL_S = 0.25` (L747) and republishes the
advertised file **on change, not on a timer**, by an in-place rewrite (`r+b`, write, `truncate()`);
`_replace_manifest` (L1190) — the pre-U51 temp-file-then-`Path.replace` shape — survives only as a
fallback when in-place cannot work. It never raises, never un-publishes, and warns once per failure
episode rather than per tick. `close()` (L1115) sets an `Event` and joins for
`_MANIFEST_PUBLISH_JOIN_S = 2.0` (L753), then abandons the daemon thread with a warning rather than
blocking a relay restart. It is constructed in `_start_relay_locked` **only after a child really
exists** (L1588) so a degraded start leaves no publisher, and it is closed in `_terminate_relay`
(L1789) **after** the child is dead — the reverse order would leave the last window the muxer wrote
unpublished.

Why this and not the brief's other two candidates is argued from measurements in §3: a relay-side
watchdog cannot see this failure (§3.4 — the child exits `0` with **zero** error lines), and
`delete_segments` behaviour is a real but *different* leak (§3.5). In-place rewrite is the only lever
that removes the rename-from-the-publish-path entirely; §3.3 measures the one thing that could go
wrong with it (a torn read) and shows it does not happen with `r+b` while it does with `wb`.

### 1.2 Item 1 — the design, and what it reverses

`_clear_hls_window` (`civiccast/egress/hls_relay.py:363`) is called from `_start_relay_locked`
(L1514), **after** `output_args()` has created the directory and **before** the child exists, so no
handle but ours can be in play. It globs `seg*.ts`, `*.tmp`, `manifest_name`, `mux_playlist_name`
inside `Path(manifest_target()).parent`, `unlink()`s each file, tolerates `FileNotFoundError` as
"already gone" and any other `OSError` as "locked by a reader" (logged, never fatal), and returns.
It is deliberately at the **spawn** and not at `apply` — `apply` is idempotent and re-entered for a
live relay, and a wipe there would delete the window a running channel is serving.

**INFERRED:** item 1 reverses U21's restart-continuity guarantee — with `append_list` the next child used
to continue the predecessor's playlist and sequence, and now there is a 2–4 s window at each relay
(re)start where the advertised playlist is empty before the first staging publish lands. That is a
product-visible behaviour change at every restart; it is stated in `INSTALL-NOTE.md` §2.5 and is the
main reason installing this candidate is a decision, not a formality.

## 3. Item 2 investigation — what ffmpeg's hls muxer actually does here

The brief asked a question before it asked for a fix: *on Windows, when the rename/replace of
`playlist.m3u8` (or a segment delete) hits a sharing violation, does ffmpeg retry, block, or error
out?* All of the following was measured with the station ffmpeg against **replay scratch directories**
under `%TEMP%\u51\`, never against the station.

### 3.1 The muxer's publish path is a rename, and a held handle denies it

**OBSERVED** (`%TEMP%\u51\m2-ffmpeg-reader\`, summarised in `m2.rerun.log`):

```
in-place writes: 47 ok / 0 blocked
rename-over:     1 ok / 46 blocked
first error seen: rename: PermissionError: [WinError 5] Access is denied:
  '…\m2-ffmpeg-reader\playlist.m3u8.new' -> '…\m2-ffmpeg-reader\playlist.m3u8'
```

**OBSERVED:** an in-place write into the held file succeeds every time; the temp-then-rename publish
succeeds **once** in 47 attempts. ffmpeg does **not** retry in any useful sense and does **not** block
forever on the rename — it fails the operation and moves on.

### 3.2 What that failure looks like from outside: a silent freeze

**OBSERVED** (`%TEMP%\u51\e1-playlist-holder\result.json`, printed by `replay_facts.py`) — a real ffmpeg
reader holding the advertised playlist, versus an identical run with no holder:

```

    samples=40 span=0.0..19.53s
    playlist updates total=9
    longest update gap=2.01s (16.02..18.03)
    segs at end=7 last=['seg000000008.ts']
--- e1-playlist-holder (hold_target=playlist)
    samples=64 span=0.0..31.56s
    holding samples=46
    playlist updates total=5

    segs at end=7 last=['seg000000014.ts']
```

The advertised manifest stops updating for **15.54 s** while the muxer keeps segmenting (7 segments on
disk, mtimes advancing every ~2 s through the held window). **OBSERVED** on the same muxer's stderr

**INFERRED:** this is exactly the 10:36 incident's shape — a coder holding the live playlists froze
the advertised window on all three channels, with nothing in the relay's own log to say why.

### 3.3 The chosen mechanism, measured: in-place rewrite does not tear

`%TEMP%\u51\m5-torn\`: one writer republishing every 0.25 s while two readers hammer the file, counting
reads that return an empty or short buffer. **OBSERVED** (`result-rplusb.json` / `result-wb.json`):

```
variant r+b : writes={'n': 80, 'blocked': 0}  reads={'A': 144542, 'B': 145966, 'torn': 0}
variant wb  : writes={'n': 80, 'blocked': 0}  reads={'A': 137566, 'B': 137413, 'torn': 32}
torn_samples (wb): ["'' (len 0)", "'' (len 0)", "'' (len 0)", …]
```

`r+b` + write + `truncate()`: **0 torn reads in 290,508**. `wb` (open-and-truncate): **32 torn reads in
275,011**, every one an empty file. **INFERRED:** the in-place rewrite must be `r+b`, not `wb` — a
reader that arrives between `wb`'s truncate and its write sees an empty manifest, which is a *player*
failure, and the fix would have traded a frozen window for a broken one.

### 3.4 Why not a relay-side watchdog

**OBSERVED** (`%TEMP%\u51\m4-restart-hold\result.json`): a **fresh** ffmpeg child pointed at a directory
that already held a reader's handle froze for the whole window —

```
before: {'size': 629, 'mtime': 1790457314.598, 'entries': 6, 'last': ['seg000000009.ts']}
while held: samples=22 updates=1
after release: samples=8 updates=[23.02, 24.02, 26.02, 28.02, 30.02]
child_alive_at_release=False exit=0   stderr error lines=0
```

The child was **alive and healthy** the entire time, exited `0`, and produced **no** error line; the
instant the handle closed, publishing resumed at the normal 2 s cadence. **INFERRED:** a watchdog
watching the child's liveness or its stderr cannot see this failure at all — it would have to watch the
*advertised manifest's* staleness, which the publisher makes structurally unnecessary. This is the
measurement that ruled the brief's second candidate out, rather than a preference.

### 3.5 The segment-delete half, which is a different (real) leak

**OBSERVED** (`%TEMP%\u51\m3-segment-holder\result.json`): with a reader holding one *segment*,
ffmpeg's `delete_segments` fails exactly **once** —

```
[hls muxer @ …] failed to delete old segment …\m3-segment-holder/seg000000000.ts: Permission denied
```

— and the playlist **keeps advancing** (`updates total=20`, longest gap `2.52 s`, `updates inside that
window=16`, final `seg000000019.ts`). So a held segment does **not** stall publishing; it leaks the
held file, which stays on disk (the directory still holds **8** `seg*.ts`, including the held
`seg000000000.ts`). **INFERRED:** the leak the brief asked about for item 1 and the stall it asked about
for item 2 are the same root cause (a held handle on Windows) with two different symptoms; item 1's wipe
is what reclaims the fossil at the next start, and this run is the evidence that the wipe is the right
place for it.

### 3.6 The staging write itself is atomic

**OBSERVED** (`%TEMP%\u51\m6-staging\result.json`): 8,160 samples over 14.0 s of a real muxer writing
`playlist.mux.m3u8`, watching for a reader ever seeing a shrinking or absent staging file:

```
distinct_file_ids=7   runs=7   runs_with_a_shrink_under_one_id=0   shrink_observations=0
absent_runs_after_first_publish=0   tmp_names_seen=['playlist.mux.m3u8.tmp']   ffmpeg_exit=0
```

Seven distinct file identities for seven updates, no shrink, no absence after the first publish.
**INFERRED:** the staging file is safe for the publisher to diff by `(mtime, size)` — it is never
observed in a half-written state — and the fix does not need to read the staging file atomically.

**OBSERVED** (`%TEMP%\u51\c1-candidate-replay\result.json`; the script builds the muxer argv from

## 9. Doubts, gaps, and things a reviewer should attack

1. **The wipe changes viewer-visible behaviour at every restart** (§1.2). A 2–4 s window with no
   segments after a relay restart is a real regression in continuity for a viewer watching through it.
   The trade is deliberate (fossils vs a short gap) and it is the owner's call, not mine.
2. **A held segment still leaks until the next start** (§3.5). `_clear_hls_window` reclaims it at the
   next relay (re)start, and only then; a reader holding a segment for the life of a channel leaves it
   there. Fixing that inside a running session would mean retrying the delete, which is a different
   change with its own blast radius.
3. **75 leaked publisher daemon threads** in the hang dump (§6.2). They come from test-built
   supervisors, and the production path closes its publisher in `_terminate_relay`, but I have not
   proven that every test teardown path does, and 75 daemon threads inside one pytest worker is a smell.
4. **The `pcrextract` gap is unfixed and out of scope** (§6.1). A real-ffmpeg continuity check in this
   repo cannot reach `PASS` on this seat until the payload ships the plugin (or the tool falls back to
   another PCR source). It makes one test permanently red and it will keep confusing future sessions
   unless it is named somewhere durable.
5. **`government` and `public` reporting identical first-segment indices** in both censuses (§5). Not
   investigated; not load-bearing; noted so a later session does not read it as a typo in this report.
6. **The publisher's polling interval is a fixed 0.25 s** and the test suite builds publishers in
   several places; I did not audit every construction site for whether 0.25 s is right for it.
7. **One U51 test failed once, in the 39-minute whole-egress run, and passes in every shorter run**
   (§6.3). `test_stopping_the_channel_stops_publishing` — a teardown-shaped test — is the most likely
   place for a timing race to hide, and "it passes when I run it" is not an explanation. Until it is
   either reproduced under load or explained, the honest position is that this file has one unproven
   flake.
