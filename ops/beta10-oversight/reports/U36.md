### 1.3 Why a late horizon produces a clean exit instead of a graceful switch

**OBSERVED**, three code facts compound:

1. `automation.py:2628-2645` (and the same shape at `cli.py:1150-1168`) builds the
   production provider with **`max_segments=1`** whenever the GStreamer engine is selected,
   plus `max_segment_seconds=1800` and `gap_absorb_seconds=SCHEDULE_GAP_ABSORB_SECONDS`:
   ```python
   max_segments=1 if gstreamer_engine_selected() else 8,
   ```
   An automation plan on the station's engine is therefore **always a single segment**.
   Nothing in the pipeline follows the installed leg, so when that one leg ends, the
   *pipeline* ends.
2. `engine.py`'s deferred switch (`switch_at_end_of_current=True`) fires at the OUTGOING
   leg's own EOS, keyed on the **audio** end (`CTRL reload: outgoing EOS observed
   stream=audio (1/2 stream(s))`, `rebase-reference … ends=[video=…, audio=…]`,
   `switch_running_time=<audio end>` — **OBSERVED** in `gst-worker.stderr.log`). The engine
   is faithful to the media: it hands over when the media ends.
3. The daemon's rollover is *driven by the recorded horizon*, not by the media: it dispatches
   when the schedule is extended or the lead timer fires (`trigger_at = max(last_segment_start_at,
   plan_end_at − _rollover_lead_seconds())`, automation.py:1973-1990). With the horizon a few
   seconds past the real end, the outgoing leg EOSes **before** the rollover's plan is ready
   to take over.

### 1.6 Root cause, in one sentence (corrected)

**The daemon's rollover horizon is computed from the schedule clock (`starts_at` of a re-served
rotation item) while the engine's leg starts at the `ON_AIR` instant; the two disagree by a few
seconds, so on the relaunch path `elapsed_seconds = current_time − item.scheduled_at` still reads

program.**

The brief's version of this sentence ("the plan's program end runs past the real media end") is
correct about the *symptom* and **wrong about the cause**: the media is not shorter than the rows.

## 2. The fix that was asked for, and why it is inert here

### 2.1 What was implemented

Commit `b0f2e49c` — `fix(u36): cap a plan segment by the media's real playable length`:

- `source_plan.py` gains an optional `media_duration_resolver` seam (default
  `civiccast.stream._ffmpeg.probe_media_duration_seconds`), consulted once per segment at
  `~source_plan.py:975-978`:
  ```python
  inpoint = asset.trim_in_seconds
  outpoint = asset.trim_out_seconds
  media_end = media_duration_resolver(media_path) if media_duration_resolver is not None else None
  duration = _segment_duration(
      item, asset, inpoint=inpoint, outpoint=outpoint, media_end=media_end
  )
  ```
- `_playable_duration` applies `if media_end is not None: end = media_end if end is None else min(end, media_end)`.
- `_segment_duration` therefore returns `min(slot, playable, media_end)` — a segment can never be
  planned past its media's real measured end.

Commits `773234bb` (red), `14da353f` (real-ffmpeg reproduction), `61d8c6d7` (format-only), all
local to the worktree, none staged, none pushed.

### 2.2 Why it does not fix the observed incident

The cap only bites when the row-derived playable duration **exceeds** the media. Per §4 that never
happens on this station: 0 of 539. For the incident's own numbers (`elapsed_seconds ≈ 664.4`,
`duration = min(slot 667, playable 667, media_end 667.100) = 667`), `elapsed_seconds >= duration`
is still False, so `_segment_from_item` still returns a ~2.6 s segment. **The cap changes nothing
for the sliver.** INFERRED from the arithmetic and confirmed by the measured absence of any
overrunning row.

The cap remains a correct *class-level guard* — if a station's rows ever did overstate their media,
it would prevent exactly the past-EOF artifact §1.4 measures. Whether to keep it is question 1 in
`questions\U36.md`.

### 2.3 The relaunch rule, decided from the code (work item 3, second half)

**OBSERVED** by reading the paths, not by a run:

- When the planner's durations are truthful and the item is genuinely exhausted,
  `_segment_from_item` returns `None` (source_plan.py:898-902).
- The plan builder then produces no segments from that item, and `_plan_from` yields `[]` for it;
  the U26 gap-absorb window (`SCHEDULE_GAP_ABSORB_SECONDS = 30.0`, source_plan.py:106, consumed by
  `_gap_absorb_candidate_index`) resolves the **next** item starting at/after `current_time` within
  that window, at its own elapsed 0. So the "next program, not the remainder" rule is already the

- `daemon._avoid_schedule_tail_plan` (`daemon.py:4333-4386`, `_SCHEDULE_TAIL_FLOOR_SECONDS = 30.0`)
  would convert a sub-30 s tail into "start the next program", but it is called only under

  horizon-bound rollovers and never runs on the relaunch path at all**. That is the missing guard
  for this defect; adding it is a product decision (question 3), not implemented.

**On the observed data the exhaustion branch does not fire at the relaunch instant**: 664.4 < 667.
That is precisely why the fix in §2.1 is inert and why the correction in §1.6 matters.

### 12.2 Decision 2 (Q3) — the 30 s schedule tail floor, at both sites

**Where it applies** (line numbers at HEAD `c3df08c7`, verified by grep this session):

| **site 2(ii)** | `civiccast/egress/daemon.py:4658` | inside `_start_steps` (`:1787`)'s call path — the **relaunch** path |

Both sites call the same resolver; the floor is applied once, in the resolver, so the two paths

**The proof sentence the coordinator asked for** — quoted verbatim from the resolver's docstring
(`daemon.py:4419-4426`), which is the claim the code below it implements:

> "So resolve the schedule where that tail ENDS instead -- the next item -- and use it when it is
> a strict improvement. […] It cannot skip a program that genuinely has more than the floor
> left: the body returns `source_plan` unchanged (identity, not a copy) before any boundary call
> whenever the tail is at or above `_SCHEDULE_TAIL_FLOOR_SECONDS`, and even below the floor the
> replacement is only taken when the plan due where the tail ends is STRICTLY longer than the
> tail it replaces. A tail of 30s or more is therefore never even measured against the schedule,
> and a shorter one is only ever exchanged for more media than it had."

**OBSERVED**, the guard itself, `daemon.py:4459-4461`:

```python
        tail_seconds = sum(segment.duration_seconds for segment in source_plan.segments)
        if tail_seconds <= 0.0 or tail_seconds >= _SCHEDULE_TAIL_FLOOR_SECONDS:
            return _TailFloorOutcome(source_plan, False)
```

`_TailFloorOutcome(source_plan, False)` carries the *same list object* it was handed, and every
other early return at `:4458`, `:4476`, `:4478`, `:4487`, `:4490` does the same — so the
"unchanged" half of the sentence is structural, not a convention. The "strictly longer" half is
the comparison that decides whether `slate` is used; there is no branch that swaps a >= 30 s tail
for a shorter one, and no branch that swaps any tail for something that is not strictly longer.

**Why "slate only if there is no next program" is safe**: when the boundary provider answers with
nothing, the resolver returns the *unchanged* plan rather than an empty one — so a channel with
no next program keeps airing the tail it has, and a channel whose next program genuinely starts
later is not forced to slate. The slate is only reached through the retry-exhausted path in
§13.7, at the boundary.

**Asked:** *"A reload that fails before commit must keep the current leg (slate) playing, never exit

### 18.1 The code path, named from the log (OBSERVED)

`evidence\education-exit1-1451\gst-worker.stdout.log`, lines 2649-2650 (verbatim, truncated at the
right for width):

```
2649 CTRL reload aborted: new program errored before commit (source=decodebin14): gst-stream-error-quark: GStreamer encountered a general stream error. (1)
2650 WORKER_RESULT {'error': (gerror=GLib.Error('GStreamer encountered a general stream error.', 'gst-stream-error-quark', 1), debug='../gst/playback/gstdecodebin2.c(4755): gst_decode_bin_expose (): /GstPipeline:civiccast-playout/GstDecodeBin:decodebin14:\nall stre…
```

Line 2649 is the **contained** abort (the ENG-009 branch prints this and calls
`_abort_pending_reload("error")`). The very next line is the worker's `WORKER_RESULT` carrying that
**same** `decodebin14` GError — exit 1 on a channel that was still producing output.

The named path: `_abort_pending_reload` clears `self._pending_reload` the instant it rejects the new
leg, while that leg's disposal runs on a daemon thread started by `_start_aborted_leg_retirement`. In
that window `_belongs_to_pending_reload` (slot already cleared) and `_belongs_to_retiring_reload` (an
abort never had a commit) both early-out, so the aborted leg's **own** second bus ERROR matched no
containment branch and fell through to the fatal tail — `self._error = message.parse_error()` +
`self._loop.quit()` → worker exit.

### 18.2 The fix

Commit `703f9f29`, `civiccast/egress/gst/engine.py` (+76, one file):
- new `self._abort_retire_legs: list[dict]` in `__init__` — the attribution record
  (`{"thread", "elements", "retired"}`), pruned per abort in `_start_aborted_leg_retirement`;
- `_belongs_to_aborted_leg(src)` — walks the parent chain against each record's elements; a leg whose
  retirement failed is deliberately kept attributed (it is still in the pipeline);
- a new containment branch in `_on_bus` immediately **before** the fatal tail, printing
  `CTRL reload: contained error from an already-aborted reload leg (source=…): …`;

Containing these errors costs no airtime: before the abort's holds are lifted the leg is DROP-fenced
at its own src pads by `_detach_leg_from_selectors`, so nothing it emits can reach the selector or
the mux.
