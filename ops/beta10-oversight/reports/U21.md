## 2. Cause of the skipped self-heal (00:53 / 00:56)

**OBSERVED, from HEAD source.** The daemon logs the intent *before* the gate that can refuse it:

```python
# civiccast/egress/daemon.py:2790-2796   (stalled-but-readable window branch)
if not was_already_flagged_dead:
    _LOG.error(
        "HLS relay child for channel %s is still running but its live window "
        "has not advanced; residents are getting a frozen stream. Attempting "
        "a bounded relay self-heal.", channel_id)
...
# civiccast/egress/daemon.py:2806
producing = channel_id in self._on_air_confirmed_at
maybe_heal(channel_id, now=now, producing=producing, startup_grace_s=...)
```

and the callee then refuses on that argument:

```python
# civiccast/egress/hls_relay.py:1044-1045
if not producing:
    return False
```

`producing` is the daemon's **on-air-evidence latch**, not process liveness. The latch is set on the
first tick that observes real on-air evidence (`daemon.py:3035-3039`) and **popped** at three
places:

- `daemon.py:2174` — "This IS a fresh spawn -- any on-air evidence latched for a PREVIOUS worker no
  longer describes this one." (the relaunch path),
- `daemon.py:3076` — process exit,
- `daemon.py:4797` — operator stop.

So the sequence at 00:53 was: the 00:51:26 worker exit popped the latch; the replacement (U14
slate→program) worker had not yet produced on-air evidence; the relay's window was stalled and
logged "Attempting a bounded relay self-heal"; `maybe_self_heal_stalled` returned `False` at
`hls_relay.py:1045`; **no relay restart**. The same reasoning explains the second line at 00:56: the
flag `_hls_relay_dead[channel_id]` is set to `bool(stalled)` on every non-`None` poll
(`daemon.py:2787`) and to `False` again the moment a poll is *not* stalled, so one continuous
episode logs the ERROR once per stall re-entry — the two lines are not two independent attempts.

The design is not wrong — a STARTING/no-source channel must never be restarted from there
(`daemon.py:2797-2802`) — but it left the one state the live incident was actually in (a worker
that had restarted, a relay that had not, and therefore no latch) with no net at all. B1 closes it
by removing the dependency: the relay is rebound by the worker's own (re)start, before any
self-heal question arises.

## 3. Task B — fixes, red then green

### 3.1 B1 `0d8b410a` — rebind the relay to every new worker session

`HlsRelaySupervisor.apply(config, *, new_session=False)` tears the channel's relay child(ren) down
before walking the sinks when `new_session` is true, so the child serving the new session was
spawned **for** it. The replacement binds the same deterministic port (`hls_relay_uri_for`, a
pure function of the sink URI), so the `udpsink` host/port already in the engine graph stays valid
— asserted in the new test. `_start_steps` decides `worker_already_live = existing_process is not
None and _process_poll(existing_process) is None` **before** calling `apply`, and passes
`new_session=not worker_already_live`: first start, crash relaunch, the U16 output-desync guard
restart and the U14 slate→program restart all rebind; the in-place reload path
(`_request_reload` → `apply` with the default) keeps one continuous mux.

*Red, with both source files reverted:* 3 supervisor tests fail with
`TypeError: apply() got an unexpected keyword argument 'new_session'`; the daemon test fails at
`assert len(relay_calls) == 2` (`relay_procs` len 1, `worker_procs` len 2 — the relaunched worker
inherited the old relay). *Green:* 3 passed + 1 passed, and the two pre-existing supervisor tests
(`test_start_leaves_the_playlist_alone_while_the_hls_relay_is_still_alive`,
`test_apply_is_idempotent_for_an_unchanged_sink`) stay green.

**Two deliberate deviations from the brief's "prefer", recorded in the commit:**

- The relay is still **spawned at `apply` time** (during prep, ~75 s before the worker) rather than
  "right when the new worker is launched". `apply`'s documented degradation contract requires the
  spawn result **synchronously**: a sink whose relay could not start is returned UNCHANGED (still
  `hls`), and that decision is made inside `apply`. Deferring the spawn would re-open that
  contract. Consequence: OVERSIGHT-LOG 23:42:35's watchlist item ("spawn/re-arm the relay when the
  worker starts") is **partly** addressed — the *rebind* is now tied to the worker session, but a
  first-start relay is still spawned at prep time and can still sit ~75 s before its input has
  data. That startup window is unchanged by this unit.
- `_discard_stale_hls_playlists` stays conditioned on `hls_relay_was_alive` (read before the
  teardown). The rebind does not make the on-disk window stale: the replacement continues it via
  `delete_segments+append_list`, so a crash relaunch must not drop residents' manifest.

### 3.2 B2 `e21da49c` — the output A/V guard also judges `FALLBACK_SLATE`

The U16 guard gated on `state.state != "ON_AIR"`, so a channel airing a fallback slate was never
measured — the one state where the guard is the only net, because a slate leg is written by the
same mux, the same `udpsink` and the same long-lived relay child as a program leg. The gate is now
`state.state not in {"ON_AIR", "FALLBACK_SLATE"}`. Every other gate is untouched: STARTING has no
output; TRANSITIONING is where the U16 rebase legitimately moves the streams against each other;
DRAINING is deliberately leaving air; a `None` probe still never restarts anything; a pid change
still resets the streak; the 3-consecutive-probe / 3-per-rolling-hour / 600 s-cadence budget is
unchanged.

The restart still rides the ordinary crashed-encoder relaunch
(`_restart_desynced_output` → `_process_terminate_bounded`, no `_reload_kills` entry →
`_poll_process` sees a real non-zero exit → `_relaunch_after_crash` → `_begin_relaunch` → `_start`),
which **is** the B1 path, so the replacement worker gets a relay bound to its session. Test 3
proves that: after a slate-desync restart the relay is respawned on the same argv/UDP port and the
old child is terminated.

*Red, `-k "fallback_slate_output or slate_restart_rebinds"` with `civiccast/egress/daemon.py`
reverted to HEAD:* `assert probe.calls == 2, "a slate output was not measured at all"` →
`assert 0 == 2`; and `assert fixture.workers[0].terminated, "the slate desync did not restart the
worker"` → `assert False`; `2 failed, 15 deselected in 1.39s`. *Green:* `17 passed in 1.76s` for the
whole file (the negative test passes on both trees — that is the point: it pins what did **not**
change).

**Can a guard restart reuse the prepared plan instead of re-preparing? No — and that has a cost.**
`_begin_relaunch` calls `_start` with no `resolved_plan`, and `_start_steps` only skips the
`source_plan_provider` call when one is passed (`elif resolved_plan is not None`, `daemon.py:1828`);
the only caller that passes one is the slate-EOS relaunch, which already holds the plan it is
airing. Reuse here is not a smaller version of the same change: a worker that desynced on a program
leg may be relaunching minutes later onto a program whose window has moved on, and `_start`'s
readiness/fallback ladder would then be entered with a plan the current resolution never validated.
So the guard restart is **cold-prepared and the channel is dark for that preparation** — bounded,
and already paid by every crash relaunch; the alternative it replaces is a permanently desynced
output that only an operator restart clears (which is what the live 00:52:31 guard restart cost,
and did not fix).

### 3.3 B3 `54eb629d` — bounded retry on a Windows sharing violation

`load_caption_cues_from_timed_text` now reads through `_read_timed_text`, retrying a
`PermissionError` up to `_ACTIVE_VTT_READ_ATTEMPTS` (3) total attempts with
`_ACTIVE_VTT_READ_BACKOFF_SECONDS` (0.05 s) between them — the brief's "a few times with a short
sleep, bounded, e.g. 3 × 50 ms". Worst-case added wait 2 × 50 ms. The writer is the caption tap's

degraded to an empty cue list ("no cues readable" and "no cues" must not be the same answer — the
decode-back proof acts on the difference). Only `PermissionError` is retried.

*Red:* the tests import the new private constants, so reverting the module fails at collection

`assert len(attempts) == _ACTIVE_VTT_READ_ATTEMPTS` → `assert 1 == 3`; `2 failed, 9 passed in 11.28s`.
*Green, whole file:* `11 passed in 9.17s`.

### 4.1 The coordinator's item-1 test, answered — REFUTED at the live magnitudes

`questions\U21-coordinator-note.md` asks: *"Test explicitly whether an input PTS jump (worker

The mechanism as stated is **not** what the relay does: a one-sided 0.710 s video jump does not

A jump of the size that *does* engage a correction (≥20 s one-sided) leaves ≈**half** the jump, not
the whole jump. So the item-1 hypothesis is refuted at the live magnitudes and the ≈half-jump
residual only appears well above them.

### 4.2 What the live slate-entry evidence actually shows — and what it does not decide

From OVERSIGHT-LOG line 119 (education, 00:49:12 program→`FALLBACK_SLATE`): the U16 start
diagnostics are **symmetric** at the measured boundary — ends v=4113.212 a=4113.922, switch
4113.922 to **both** pads, both selector-first-buffer `running_time 4113.922`, `pts 0.700`,
`pipeline_running_time=none` (the normal observed-ends branch). The only asymmetry is the
**0.710 s outgoing-pad gap applied to video only** — and that exact shape, with a fresh relay, is
`V071`: clean at 0.019 s over 15 segments after the jump.

So no slate-leg timestamp asymmetry capable of birthing a permanent offset was found at the
boundary I could measure. The offset that then appeared (+19.75 s on the wire at 00:50:28) is not
reproduced by any shape I ran, and the growth to +31.8 s coincides with the **00:51:26 worker
restart with the relay kept** — precisely the round-5 P3 class B1 cures. B1 alone does not cure a
desync *born on the slate* without a worker restart, which is exactly why B2 exists as the net.

### 4.3 Exclusions, stated so the next unit does not re-run them

- The engine's muxer-output → wire boundary was **not** separately instrumented. Everything I
  measured is downstream of the UDP port; a per-stream timestamp asymmetry introduced *inside* the
  engine's muxer and invisible at its own diagnostics is **not** excluded by this unit.
- No bespoke two-leg packaged-GStreamer experiment was run (PyGObject is absent from this

### 4.4 Coordinator item 2 — why a freshly restarted relay can sit without writing

Live case (OVERSIGHT-LOG line 122): the 01:04:34 self-heal **did** restart the relay (new pid
23120) and it wrote nothing until the 01:06 full channel restart (fresh at 01:06:32, a-v 0.005).

Round 5 P4 is the closest replay of that shape and it **did** write within one segment (new pid
35608 wrote `seg000000029` onward, `r5.out:39-48`): the replacement binds the same deterministic
port, `append_list` continues the index, stale old-session segments are never deleted, and
`analyzeduration`/`probesize` delayed nothing beyond the first segment. So none of probe timing, a
stale playlist, or stale segments explains the live freeze; the remaining reading — **INFERRED** —
is that the restarted child's **input** was not delivering data (the engine's `udpsink` for that
channel was not feeding the port at that moment, e.g. because the reload had left the graph's
sender bound to a session that was no longer producing to it), which is a different defect from the
one this unit fixes and is not reproducible in the harness, where the source is under my control.

What B1 changes for that case: the child is now replaced by the worker's own start, not by a
self-heal that may be declined — so the 01:04-class "restart the relay while the engine is mid-reload"
window is no longer reachable through the self-heal path.
