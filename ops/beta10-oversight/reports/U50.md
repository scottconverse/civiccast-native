## 2. What was actually wrong (the defect, and the fix)

*Delivered in `7c90396e`; this half is the part that turned the live run green.*

**OBSERVED** (the delivered code path, `scripts/verify_beta10_live_hls_media.py`), the pre-fix decode loop walked
the window in order and copied each segment immediately before decoding it. `_snapshot_segment` retries 20 × 0.1 s
and then gives up ("copy race"). The live-HLS directory keeps only ~7 live segments (see §4), so the 5 newest
window members — the `from_live` tail — were the ones the relay deleted while the loop was still decoding the 25
older keeper copies. The result was that **five segments could not be read, and the deciding rule
(`unverified_count > 0 → UNVERIFIED`) then marked the entire 60 s span UNVERIFIED even though 25 of 30 segments
had decoded with cues.** That is exactly what verify #9 shows (13 / 7 / 10 cues on public / government /
education, status UNVERIFIED on all three).

The fix **captures first, decodes second**: every finished segment in the span is plain-copied into private
scratch (`scratch/caption/`) *before any of them is decoded*, in the order that matters most first — volatile
(`live`) before `keep`, newest mtime first within each group. If a live file rotates away between the listing and
the copy, the keeper's copy **of the same name** is used as a stand-in (same finished segment the relay
published), and the record says so. Each per-segment record now carries `captured_from` (`live` | `keep`) as
**provenance**, and each entry of `caption_window.segments` carries its own `source`, so a consumer can see which
of its inputs were still on air and could rotate away mid-run.

The deciding rule is unchanged: `unverified_count > 0 → UNVERIFIED`, else `cue_count > 0 → PASS`, else `FAIL`.
No product code, no threshold, and no rung verdict rule was touched.

## 8. Doubts

- **Two live points is thin evidence for a race.** The mechanism is proven at the unit level with a stub that
  unlinks the tail on the first decode, and the pre-fix failure reproduced *today* against the exact pre-fix
  bytes (Rule 3 RED), so I believe the mechanism; but verify-09 → verify-10 is a two-sample live comparison and
  the failure it fixed was timing-dependent. The rung's remaining verifies (#11 onward, every 10 min until
  ≈21:31) are the real test, and I will not be watching them — they should be checked in the morning; anything
  other than `source: keep` + `decode-back PASS` on all three channels would falsify this fix.
- **The keeper is a workaround, not a fix.** It exists because the live directory holds ~14 s and the caption
  window wants 60 s. If the caption window is meant to be a real 60 s window of *live* audio, the product needs
  to keep more segments (or the window rule needs to be honest about what the relay retains). That is a product
  question, not a measurement question — see §4's backlog item; the keeper should be treated as scaffolding to be
  deleted once the window has a real source.
- **The keeper reads the same directory the relay writes**, four times a second per channel, on the station's
  disk. It never holds a handle and never opens the playlist, and the rung's three channels were never DARK while
  it ran, but a copier on the live path is a risk that should not become permanent. Its cost is unmeasured.
- **The `UNVERIFIED` channel status will keep being printed for caption-clean runs**, because `audio_window`
  wants 120 s of decoded audio and the live directory has ~14 s. Anyone reading the evidence cold will keep
  seeing "UNVERIFIED" next to a passing caption verdict. That is a readability trap that belongs in the same
  backlog conversation as the fossil cleanup — the same 14-second window causes both.
