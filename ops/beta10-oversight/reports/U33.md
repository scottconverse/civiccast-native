## 0. Verdict in one paragraph

**OBSERVED.** The live path is not GPU-bound. With the tap's three channel threads in flight,
*every* stage inflates — including stages that never touch the GPU — because the three channel
threads contend for the GIL. The single largest stage is `ct2_generate` (65.3% of instrumented
stage time at concurrency 3), which is real model work and is **not** cuttable without changing
the model or the window geometry, both of which the coordinator ruled out. The one genuinely
wasteful stage is `decode_audio`: the tap writes each 16 kHz chunk to a temporary WAV and
faster-whisper decodes it straight back to the samples the process just had. That is
**OBSERVED** at 49.7 ms/window serial and 98.2 ms/window at concurrency 3, and cutting it is a
measured **1.097x**. It is shipped (commit `dc6f6dae`). It meets the brief's **p95 ≤ 2.5 s** bar
(2095.8 ms) and **does not** meet the **median ≤ 0.8 s** bar (1609.4 ms, 2.01x over). Nothing that
respects the coordinator's two constraints reaches the median bar; only the batched design does
(p50 706.6 ms) and it costs measurable word loss (WER mean 0.0066, max 0.125), which the brief
forbids. That is written up in `questions/U33.md` Q1, not decided here.

What it does, in order:

   function (`import numpy as np`, `runtime.py:1047`; `runtime.py` has no module-scope numpy
   import), because numpy ships with the optional caption runtime and is not declared in
   `pyproject.toml` — the same lazy-import rule `_load_whisper_model_class` already follows for
   faster-whisper.
2. **`_chunk_audio_source(self, chunk: AudioChunk) -> Iterator[Any]`** (`runtime.py:919`, a context

   and keeps the temporary-WAV round trip for anything else (a different rate needs the resampler)
   and for `live=False` (batch/VOD, no real-time cadence).
3. **`_transcribe_source(self, source: Any, *, initial_prompt: str | None)`** (`runtime.py:940`) —

**Why the passthrough is safe (OBSERVED, `faster_whisper/transcribe.py:386-387` and `875-876`).**
`decode_audio` short-circuits on an ndarray input; the station's chunk is already 16 kHz mono s16le,
so the samples the decoder would have produced are the samples the station already holds. The
committed diff makes that explicit in the helper's docstring rather than leaving it as folklore.

**What must not change (OBSERVED).** `word_timestamps=True` on the live path is load-bearing.
`CaptionStabilizer` (`stabilize.py:35`) is constructed `live=True` at `tap_worker.py:2408`;
`observe()` routes to `_observe_live_words` only when `live and hypothesis.words is not None`
(`stabilize.py:85`), and `compatible()` (`stabilize.py:153-161`) plus the confirmation rule
`len(previous.votes) >= stable_windows` (`stabilize.py:216`) both need the word spans. Dropping
`word_timestamps` to save the 13.6–28.5 ms alignment stage would silently disable stabilisation.
Both the commit message and the tests state this.

## 11. Doubts

1. **The target may be unreachable under the stated constraints.** `ct2_generate` alone is
   1027.2 ms/window at concurrency 3 — more than the 800 ms median budget — and it is model work.
   If the coordinator's two constraints are firm, I do not think the median bar is reachable by
   tuning this path, and I would rather say that plainly than ship a number that looks adjacent to
   the target. (`questions/U33.md` Q3.)
2. **The `array` gain came out smaller in `b9` than the profiler predicted.** The profiler said the
   decode stage is 49.7 ms/window serial and 98.2 ms at concurrency 3; the shipped lever measured
   1.097x on the round wall. **INFERRED:** deleting 98 ms of a 1879.9 ms median should be ~1.05x on
   latency alone, and contention effects on the surviving stages could plausibly absorb part of it —
   but I did not decompose the post-change profile, so I cannot say the gain equals the deleted
   stage. I report the measured 1.097x and not a story about it.
3. **`mirror` was faster than `live` (1.061x) despite being the same code path with knobs inert.**
   `mirror_mismatch_rounds` is empty, so the outputs are identical, which means the 6% is
   measurement or implementation difference — a Python-level reimplementation versus the station's
   own function. **INFERRED:** this puts a ~6% noise/implementation floor under every arm-to-arm
   comparison here, and it means the 1.097x `array` gain is ~1.6x the control's own deviation. I
   would want a repeat run before treating any single-digit-percent arm difference as real.
4. **The corpus is 39 windows of English speech from one source family.** Detection agreed on every
   window and no window tripped the temperature ladder. The ladder being dead on this corpus is not
   evidence that it is dead on the station's real feed.
5. **`b9.py`'s docstring carries figures its own JSON contradicts** (§3.4). I caught it by reading
   both. Anyone reading only the docstring would quote numbers that are wrong; I flag it here
   because it is the exact failure mode this program keeps finding.
