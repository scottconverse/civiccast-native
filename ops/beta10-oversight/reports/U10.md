## B. Mechanism from code

### What counts as a "settled segment"

`tap_worker.py:1814-1826`:

```python
def _settled_segments(self, channel_dir: Path) -> list[tuple[int, Path]]:
    """Numbered segments with a newer sibling (ffmpeg moved past them)."""
    numbered = [...all files matching _SEGMENT_RE...]
    numbered.sort()
    # GStreamer publishes through ``.wav.partial -> .wav`` atomically, so
    # every visible WAV is complete. Legacy FFmpeg segment output writes the
    # highest WAV in place; preserve its one-file settling guard.
    return numbered if self._atomic_segments else numbered[:-1]
```

A settled segment is a numbered `chunk-NNNNNN.wav` in `<tap_root>/<channel>/`. On the GStreamer engine
(`_atomic_segments` true) every visible WAV counts, because the writer renames `.wav.partial → .wav`
atomically. **The count is a count of files sitting in a directory — it is a proxy for "how far behind
is ASR", not a measure of ASR error.**

### The max-2 backlog gate

`tap_worker.py:1000-1042` (the scan pass, one channel at a time):

```python
with self._phase_timing.phase("scan_settle_and_backlog_gate", channel=channel_id):
    segments = self._settled_segments(channel_dir)
if not segments:
    continue
channels.append(channel_id)
if self._channel_has_inflight(channel_id):
    # Preserve per-channel ordering ... The current batch owns its paths; new
    # arrivals remain queued for the next scan after it ends.
    continue
inflight_names = self._inflight_names(channel_id)
queued_segments = [item for item in segments if item[1].name not in inflight_names]
if not queued_segments:
    continue
if self._backoff.is_paused(channel_id):
    ...
    dropped += self._drain_paused_channel(channel_id, channel_dir, queued_segments)
    continue
if len(queued_segments) > self._max_backlog_segments:
    self._record_discarded_batch(..., outcome="overloaded", reason="max-backlog-exceeded", ...)
    self._invalidate_inflight_for_overload(channel_id)
    dropped += self._fail_closed_overload(channel_id, channel_dir, queued_segments)
    overloaded_channels.append(channel_id)
    continue
```

with `self._max_backlog_segments = max_backlog_segments` (`tap_worker.py:556`), default `2`.

Three things follow directly:

1. **A segment being transcribed is not backlog.** The in-flight batch's own files are subtracted, and
   while a batch is in flight the channel is skipped entirely (`_channel_has_inflight`). So the gate
   measures *segments that arrived while the current batch was running*.
2. **`>` not `>=`** — the trip threshold is 3.
3. **It is a single-sample test.** One scan seeing 3 trips it. There is no "over the limit for K
   consecutive scans" smoothing, no hysteresis, and no severity scaling.

### Cadence and the implied tolerance

`tap_worker.py:269,272` — `segment_seconds = 5.0`, `poll_seconds = 2.0` (both env-overridable).
Producer side `civiccast/captions/tap.py:58-63` passes `-segment_time 5.0` to ffmpeg.

The channel emits one 5 s WAV every 5 s; the scan runs every 2 s. A batch submitted at `t` blocks the
gate for that channel until it finishes; segments arriving during it queue. To avoid 3 queued
segments, the batch must finish before the *third* segment lands, i.e. within roughly **13 s**
(3 × 5 s minus the 2 s scan granularity). **The gate tolerates a batch of up to ~13 s. Every batch
longer than ~13 s costs a 120 s caption outage.** That ratio — 13 s of overrun → 120 s of silence — is
the whole defect in one line.

### Pause lengths and escalation

`tap_backoff.py:68,73`:

```python

```

`tap_backoff.py:173-190` `record_overload`: `delay = min(base * 2 ** (consecutive_overloads - 1), max)`.

`_fail_closed_overload` (`tap_worker.py:1473-1516`) does three things on every trip:

## D. Why the verifier PASS does not refute this

This is the part I would act on first, because it is a **measurement** problem, not a code problem.

`_fail_closed_overload` calls `self._clear_channel_captions(channel_id)`, which calls
`publisher.reset()`, which in `live_sidecar.py:41` is `self.publish([])` — an empty WebVTT written to
`active.vtt`. The tap then produces nothing for 120 s.

So during a pause: no new cues are produced for ~120 s. Cues already inserted into the emitted TS
persist for their display duration and then scroll off (INFERRED — I traced the sidecar reset, not the
whole feed→`h264ccinserter` path). After roughly 5–15 s, the emitted output has no captions for the
remaining ~105–115 s.

The coordinator's verifier ran ~2 minutes around 18:12 and decoded captions from the emitted TS on all
three channels — while three pauses were firing inside that window. **The most likely explanation is
that the check asks "are captions present in this sample?" rather than "are captions present in every
second of this sample?", and the pause is intermittent enough to slip through.** With 182 outages a
day, a check that samples presence rather than continuity will pass essentially always.

This matters directly for the acceptance rung: *"captions present in the emitted output THROUGHOUT
30 min / 2 h / 4 h / 8 h runs."* Per-channel, public was paused 21.5% of the 11:39–18:42 window,
education 20.1%, government 10.4%. The measured station-wide trip rate in that window is
79 events / 7.06 h = **11.2 trips per hour**, so a 30-minute run should be expected to contain on the
order of **5 caption gaps** (0.55 per 30 min per channel). **The current verifier cannot see them, and
no duration rung should be believed until it can.** The check needs to be per-second, not per-sample.

## C. Recommendations, ranked

All are proposals. **Nothing below was implemented.** Line numbers are worktree `tap_worker.py` /
`tap_backoff.py`.

### 1. Clear stale tap segments on worker construction, not only on explicit START — HIGHEST CONFIDENCE

**Evidence: OBSERVED** (the 17:17:41/43 trip with `oldest_q_age` 50–56 s on a fresh service start, and
the code comment at `tap_worker.py:883-890` naming this gap).

**Change:** at tap-worker construction / first scan, discard every numbered WAV already present in each
`<tap_root>/<channel>/` before the gate is evaluated. The stated blocker — "file mtime cannot establish
which process produced a chunk" — does not need to be solved: at construction there is no live writer
for this session yet, so *every* file present is stale by definition. That is the same argument the
existing `_discard_settled_segments` docstring already makes for the START path
(`tap_worker.py:1337-1341`), and reusing it costs one call site.

**Smallest form:** in `run_once`, before the backlog gate, discard any segment whose mtime predates
worker construction. Fixes a guaranteed 120 s caption outage on every service restart — including the
one at the start of an acceptance run.

### 2. Stop treating a 1-segment overshoot as grounds for a 120 s outage — HIGHEST IMPACT

**Evidence: OBSERVED** — 128 of 182 trips (70%) fire at exactly 3 segments against a max of 2.

**Change, in order of preference:**

- **(a) Raise the gate and require persistence.** Make the trip require the backlog to exceed the limit
  on *K consecutive scans* rather than one, and/or raise `max_backlog_segments` from 2 to ~6 (≈30 s of
  tolerance against the measured 19 s worst-case tail). At 6, the observed tail would no longer trip
  the gate at all, while a genuine ASR collapse (the case the gate exists for) still would.
- **(b) Make the pause proportional.** `_fail_closed_overload` currently opens a 120 s window for a
  1-segment overshoot and the same 120 s for a 9-segment one. The 900 s rung measured today (2×)
  came from repeated mild overshoots, not from a station in real trouble.

I would do (a) — it is a constant and a counter, not a policy rewrite, and it keeps
`tap_backoff.py`'s intent intact.

**What (a) risks, stated plainly:** a higher gate tolerates more backlog, so a genuinely
under-provisioned station spends longer accumulating before shedding. The measured data says this
station is at ~50% ASR duty with `p50` backlog age 1.3 s, so it has the headroom — but that is an
inference about *this* station, not a general truth, and the constant should be justified against a
worst-case measurement rather than the median.

### 3. Do not blank the captions on a transient overshoot

**Evidence: OBSERVED** (`tap_worker.py:1479` → `publisher.reset()` → empty `active.vtt`).

Clearing the sidecar is defensible when the tap is genuinely abandoning a session. For a one-scan
overshoot it throws away the stabilizer's context and the on-screen caption state to recover from a
condition that self-corrects on the next scan. A gentler first response — shed the oldest queued
segments down to the limit and continue, escalating to a real pause only if the overshoot persists —
would keep captions flowing through exactly the transient the gate is misfiring on.

**This is a product decision about which behaviour the station should prefer**, so it belongs to Scott,
not to me. Note it interacts with the spec's operator-approval and refusal-on-uncertainty
non-negotiables: the current fail-closed behaviour is arguably the conservative reading, and changing
it needs an explicit call.

### 4. Reduce the CPU contention that produces the tail (larger change, no code surgery)

The measured contention sources are software encoders: `openh264enc` × 3 playout channels and a
`-threads 8` foreground conform. Options worth measuring, in increasing blast radius: cap concurrent
foreground conforms station-wide; prefer hardware encode for playout if the Blackwell box can
(`station_box_profile.py:389` already maps `nvenc → nvh264enc`, so the plumbing exists); or schedule
conforms away from acceptance runs. **I would not start here** — recommendation 2 makes the gate
robust to the tail regardless of its cause, which is the more durable fix.

### 5. Also worth a look (cheap, independent)

- `egress.daemon` re-logs `state -> ON_AIR` every ~2 s indefinitely — 19,586 lines in 7 h, ~90% of the
  log. It costs log I/O and buries the signal that U10 had to dig through. Emit on change only.

## What a live test would need to show

For recommendation 2, the claim to prove is *"the pause rate collapses without the gate going blind"*,
and it needs both halves:

1. **A per-second caption-presence measurement, not a sample.** Either instrument the emitted TS
   (count caption-bearing frames per second per channel and record the longest gap), or log a
   per-channel "cues produced" counter and assert *every* 5 s interval has one. Without this, a PASS
   is unfalsifiable — as demonstrated at 18:12.
2. **A load-matched run.** 3 channels on air, ≥1 program conform in flight, the retention sweep
   running, ≥30 min. The 18:12 window is the template: three rollovers inside 95 s is the adversarial
   case, and it should be run *deliberately* rather than waited for.
3. **The gate must still fire.** A run showing zero pauses proves nothing if the gate was simply
   disabled. Instrument the trip count separately and show the tail (>13 s batches) is unchanged while
   the trips drop — i.e. that the gate got smarter, not that the station got faster.
4. **Before/after on the same station.** The counterfactual is already in hand: 182 events, 456 min of
   channel-pause today, 70% of trips at 3 segments. The after-run should be compared against those
   numbers, not against zero.

## Doubts

- **The single largest doubt is section D.** If the verifier *does* check continuity and still passed,
  then either the emitted output is not fed from `active.vtt` the way I read it, or the pauses are not
  producing caption-less output at all — and my whole acceptance-risk framing is wrong. That is worth
  an hour of someone's time before the beta.10 duration rungs are trusted.
- **Recommendation 2 is a tuning change to a safety mechanism, and tuning safety mechanisms is how you
  get a station that looks healthy until it isn't.** The measured 70%-at-3-segments number justifies
  looking at it, but the person who raised the gate should also own proving the gate still catches a
  real collapse. I would want the pre-change trip rate recorded somewhere durable first.
- The backoff design is genuinely well-reasoned and heavily field-hardened (the docstrings cite four
  distinct beta.9 defects it was tuned against). I am recommending against one of its thresholds, not
  against its design, and I may be missing a field case the 120 s base was introduced to fix — its
  own comment says 60 s was doubled to 120 s because "a station that overloads once is likely to still
  be catching up 60 s later". That reasoning assumes an overload means *catching up*, which is true for
  the 8- and 9-segment trips and **not** true for the 128 trips at 3.
