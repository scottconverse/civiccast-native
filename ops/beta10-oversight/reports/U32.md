## Doubts / limits (what would change my mind)

1. **Live throughput here is measured on the *installed* file only.** I did not run the live
   station's workload against the pre-install `tap_worker.py` on real audio (that would require
   touching the station). The A/B is therefore: pre-install = the two historical windows of the
   previously-installed file, post-install = the current window, plus the off-live matrix on the
   exact two files. If someone can produce a post-install window whose `Σ elapsed ÷ wall-clock`
   is ≈1.0 with a rate below its serial-only cap, that would refute finding 2 — I could not
   produce one from any window in this log.
2. **The "~2 min 40 s ASR warm-up" attribution is INFERRED** from the phase emissions (no
   `asr_process_batch` / `runtime_transcribe` records for six emissions). I cannot see inside the
   process to say whether it was model load, a backlog drain, or a deferred first batch. It does
   not affect the conclusion — the independent diagnostic excludes that span by construction —
   but the *rate* correction in §2c rests on it.
3. **The coordinator's "BEFORE" window is 2026-09-24 23:40–23:50, not a window adjacent to the
   07:19 install.** If the intended comparison was "last 10 minutes before the install", the log
   does not contain it: pid 28768's recording had been frozen since 23:50 the previous evening, so
   no pre-install 600 s sample adjacent to 07:19 exists. The nearest pre-install *live* throughput
   evidence is the batch diagnostic (pid 9844 covers 07:30+; pid 28768 covers 23:40–23:55).
4. **One shared GPU is the real ceiling.** `num_workers=3`, `float16`, `medium` model, and a box
   also running coder units: the pre-install numbers were taken with coders running too, so CPU
   contention is *not* the story — but GPU capacity is, and 2.5 s-per-batch × 3 channels is at the
   edge of 3 × 5 s segment streams with 5 s overlap. That is a provisioning question, not a
   regression, and it is the subject of `questions\U32.md`.
