## B. Design (smallest change that satisfies the non-negotiable goal)

> **Superseded in part by "Coordinator fix" at the end of this file.** The design
> below required VIDEO and left audio optional; the shipped design requires every
> kind a sink carries (video AND audio for every sink shipped today) and the names
> below are the pre-audit ones (`_VIDEO_SINK_MAP_ARGS`, `_segment_has_video`,
> `_sink_carries_video`, `maybe_restore_missing_video`). Read this section for the
> mechanism, the audit section for the shipped rule.

Goal: for a sink configured to carry video+audio, the relay never keeps emitting
audio-only HLS — after any (re)start it either produces video+audio or is restarted
again promptly (bounded, logged) until video is present.

Two halves, both in the relay's own layer (no new state machines, no new config):

1. **Require video in the output mapping.** For a video-carrying sink the argv gains
   `-map 0:v:0 -map 0:a:0?` (`hls_relay.py` `_VIDEO_SINK_MAP_ARGS`). A child that
   probes a video-less input now exits immediately (~6.3s, measured) with
   `Stream map '' matches no streams` instead of silently serving audio-only HLS.
   Audio stays optional (`?`) so a video-only input does not kill the relay.
   Whether a sink carries video is declared once, in one place:
   `EgressSink.carries_video: bool = True` (`civiccast/egress/sinks.py:47`). Every
   sink shipped today carries video; an audio-only variant overrides it `False` and
   gets the historical argv byte-for-byte (pinned by a test).
2. **Restart a child that cannot carry video, bounded and backed off.**
   `HlsRelaySupervisor.maybe_restore_missing_video` (`hls_relay.py:531-625`) handles
   two shapes: a child that **exited** (recovered regardless of `producing`, because
   there is no healthy child to protect), and an **alive** child whose newest served
   segment has no video (requires `producing`, the child's own startup grace, a
   video-carrying sink, and a segment name it has not already judged — so a static
   window is not re-probed every tick). The verdict comes from a tri-state probe
   (`_segment_has_video`: real `ffprobe`, `True`/`False`/`None`) so **ignorance never
   restarts anything**. Both paths funnel through `_respawn_locked`, which preserves
   the "one child per (channel, sink)" invariant. Cadence: 3 prompt attempts at
   `5.0s`, then `60.0s` per attempt with an `ERROR` per attempt after the fast ones;
   the attempt count and next-allowed time are carried onto the replacement, so the
   counters belong to the fault episode, not to one child. A sink that does not carry
   video is never judged on video (`_sink_carries_video`).
3. **Wire it into the daemon tick.** `EgressDaemon._restore_relay_video`
   (`daemon.py:2370-2404`) is called from `_poll_hls_relay` on both relay states; the
   dead branch previously only logged and returned. Without this, the supervisor's
   recovery would never run for an ON_AIR channel — the live government relay sat
   audio-only from 18:46:32 until the channel was restarted. `_restore_relay_video`
   uses the same `getattr`/`callable`/`try/except` seam as the neighbouring
   `note_progress`/`progress_stale` calls, so the older supervisor doubles the tests
   inject keep working unchanged.

Not done deliberately: no change to `_UDP_INPUT_ARGS` (the installed 6M probe stays
exactly as it is), no new config surface, no change to the GStreamer graph, and no
retry budget that gives up (see Doubts 1).

## Doubts

1. **A genuinely audio-only program on a video-carrying sink will be restarted once a
   minute, forever.** With `-map 0:v:0`, an input that never carries video makes the
   child exit; the exited shape is recovered regardless of `producing`, so the cadence
   settles at one attempt per 60s with an ERROR each time. That is exactly what the
   brief asks for ("restarted again promptly (bounded, logged) ... until video is
   present") and it is bounded, but it is also an unbounded *episode*: nothing gives
   up. If a station ever legitimately airs an audio-only program on a channel whose
   sink is declared video-carrying, the fix's answer today is "this is a fault".
   Flagging it rather than inventing a give-up rule.
2. **The alive-shape probe is grace-gated for 20s** (`_HLS_RELAY_STARTUP_GRACE_S`), so
   an input that *declares* a video stream but delivers no video packets would be
   served audio-only for up to ~20s before the segment probe restarts the child. The
   argv half is not affected (that child exits only if the stream is absent). I judged
   that acceptable versus restarting children during legitimate startup; a reviewer may
   disagree on the constant.
3. **The segment probe is best-effort by design.** `_segment_has_video` returns `None`
   (claim nothing, never restart) when `ffprobe` is missing or unhappy, so on a host
   with the station's ffmpeg but no `ffprobe` on PATH the second half silently degrades
   to a no-op — the argv half still holds. The station's ffmpeg pack ships both, so
   this is a theoretical gap, not a measured one; I did not test a probe-less host.
4. **Two producers cannot safely share one relay port.** My first end-to-end attempt
   let the audio-only and audio+video producers overlap on the same UDP port; the
   second also re-used PID 0x100 for a different codec, and real ffmpeg answered
   `h264 bitstream malformed, no startcode found`. Both are artefacts of the test
   harness (fixed: one producer at a time, audio mapped first so PID 0x100 stays AAC).
   Recording it because the same PID-reuse shape is plausible in the *product* when a
   slate source and a program source hand over on the same relay port — the live
   symptom would then be a demuxer error rather than an audio-only window. Untested
   here; worth a look if the station ever logs that message.

## Coordinator fix — the rule must cover AUDIO too

Audit finding (coordinator, 2026-09-24): the U12 rule required **video** and left
audio optional (`-map 0:v:0 -map 0:a:0?`), which only moves the lock to the other
side — a child that probes an input carrying video but no audio serves VIDEO-ONLY
HLS forever. Not hypothetical: U13 measured the government relay's post-self-heal
segments at **18:47:44-18:47:56 as video-only (TS PID 256, no PID 257)**.

### What I found about an audio flag (asked for by the audit)

**There was none, and none was expressible.** OBSERVED:

* `EgressSink` (`civiccast/egress/sinks.py`) had `carries_video` only — no audio
  field, and no use of any other audio flag anywhere in `civiccast/egress/`
  (`grep -rn "carries_audio\|audio_only\|has_audio\|-an\b\|mute"` over
  `models.py`, `sinks.py`, `daemon.py`: no matches before this change);
* `EgressSinkSpec` (`civiccast/egress/models.py`) has no audio field, and
  `_ALLOWED_EXTRA_OUTPUT_FLAGS` (`models.py:96-102`) is `-mpegts_flags, -muxrate,
  -pkt_size, -flush_packets, -max_delay` — an operator cannot express `-an`, so a
  half-program sink was not expressible at all before this change.

So no sink today carries video without audio; every shipped sink carries both. I
added `carries_audio: bool = True` next to `carries_video` so the video-only case
has a place to live, and kept that case **optional** rather than fatal
(`-map 0:v:0 -map 0:a:0?`) — it is the one branch of `_relay_map_args` that no
shipped sink takes, and it is pinned by a test.

### The change

`9f1fdc6e fix(egress): require BOTH kinds — a relay must not lock to a half program`

* `sinks.py`: `EgressSink.carries_audio: bool = True` (docstring cites U13's
  measurement and says the flags exist so a one-kind sink can declare itself).
* `hls_relay.py`: `_VIDEO_SINK_MAP_ARGS` becomes a function
  `_relay_map_args(*, carries_video, carries_audio)` — both kinds required for a
  video+audio sink, video required / audio optional for a video-only sink, and the
  historical mapping-less argv for an audio-only sink.
  `_segment_has_video` becomes `_segment_stream_kinds` (the kinds a served segment
  actually carries, `None` = cannot tell), and `_sink_carries_video` becomes
  `_sink_required_kinds` (the kinds a sink must carry; empty = never judged).
  `maybe_restore_missing_video` becomes `maybe_restore_missing_streams`: it
  restarts a child whose newest segment is missing ANY required kind, on the same
  bounded, backed-off cadence (unchanged: 3 fast attempts at 5s, then 60s with an
  ERROR per attempt), and the log names the missing kind. The `_Relay` watch
  fields rename `video_*` -> `streams_verified`/`streams_probed_segment`/
  `stream_fault_attempts`/`stream_retry_not_before`, because "video_verified" on a
  child that must also carry audio would be a lie in the name.
* `daemon.py`: `_restore_relay_video` -> `_restore_relay_streams`, calling the
  renamed supervisor method through the same `getattr`/`callable` seam; the
  relay-death log copy now says "a required stream" instead of "no video".

### Residual doubt, measured down: the mid-write newest segment (Doubt 2)

The check probes the **newest playlist entry**, and the shipped HLS argv does not
pass `-hls_flags temp_file`
(`sinks.py:301-304`: `delete_segments+append_list+program_date_time+independent_segments`),
so the file it probes can be one that ffmpeg is still writing. A partially
written segment that had not yet carried an audio packet would read as
`{"video"}` and trigger a spurious restart — a real harm, since the relay would
be killed on a healthy channel.

**Measured, on a healthy real-ffmpeg relay carrying video+audio** (scratch script
in `%TEMP%\u12-scratch\probe_newest.py`, outside the worktree; the relay argv is
the shipped `-map 0:v:0 -map 0:a:0` tuple plus the real `HlsSink.output_args()`,
and each poll calls the shipped `_segment_stream_kinds` on the newest playlist
entry exactly as the supervisor does):

```
$ python probe_newest.py     # 26 s of polling every 1.5 s, run twice
01 seg000000000.ts   210936 bytes kinds=['audio', 'video']
02 seg000000001.ts    41548 bytes kinds=['audio', 'video']
03 seg000000002.ts    53392 bytes kinds=['audio', 'video']
...
13 seg000000003.ts   838480 bytes kinds=['audio', 'video']

rows=13 one_kind_readings=0
```

OBSERVED: both runs, **0 one-kind readings in 13 probes**, including the
smallest, in-progress entries (41 548 and 84 788 bytes — a segment barely
started). MPEG-TS interleaves both PIDs from the first few kilobytes, so a
newest-entry probe on a channel whose input is carrying both kinds reads both
kinds even mid-write.

Limits of that measurement, stated plainly:

* It is a **26-second local relay**, not a station feed, and the scratch producer
  drives it. The relay's stderr carried 8 decode warnings (`non-existing PPS 0
  referenced` / `no frame!`) because the producer's `libx264` stream is joined
  mid-GOP without repeat-headers — an artifact of the harness, not of the relay;
  it does not affect which PIDs the muxer writes, but it means the harness is not
  a clean feed.
* Doubt 2 is therefore **not eliminated** — a genuine transient gap in the
  *input* that lasts longer than the probe's read window still reads as one-kind
  and restarts the child. At that point the restart is the intended answer to a
  half-program window (the audit's rule), and it is bounded and backed off
  (5 s x3, then 60 s) — but on a feed that flickers, that is a restart per minute,
  which is Doubt 1 wearing a different hat.
