## 3. Item 1 — why was this program not prepared AHEAD of its due time?

### 3.1 What the code path is

**OBSERVED (`file:line`):**

- `civiccast/egress/automation.py:1468` — the exact string `"issued reload for %s: a scheduled
  program is due"` lives in `_check_slate_replan`. **That method's first act is to return unless
  the channel is already in `FALLBACK_SLATE`** (`automation.py:1400-1480`). So the reload that
  eventually carried the next program was issued **only after the channel had already fallen**, by
  the "notice we are on the slate and try again" path — not by any ahead-of-due preparation.
- `civiccast/egress/daemon.py:4544/4556` — `_resolve_schedule_tail` produced the
  `18:06:44,933` line. Its branch condition is `0 < tail_seconds < _SCHEDULE_TAIL_FLOOR_SECONDS`,
  and on a hit it probes `boundary_at = base_at + timedelta(seconds=tail_seconds +
  _SCHEDULE_TAIL_BOUNDARY_MARGIN_S)` and swaps in the plan found there **only if it is strictly
  longer**; if nothing is scheduled it airs the slate (`slate_when_no_next`).
- The ahead-of-due path is the **rollover** (`automation.py:1740-1815` `_maybe_rollover`), which
  is what fired all six times for `government` in this window and **never once for `education`**.
- `automation.py:1487-1520` — `_rollover_lead_seconds` is
  `max(120.0, _ROLLOVER_PREPARATION_PASSES * preparation_timeout + settle_budget + margin)`.
  At the station's shipped 300 s timeout that is `2*300 + 30 + 60 = 690 s` — the docstring states
  it in those numbers.
- `SCHEDULE_GAP_ABSORB_SECONDS = 30.0` (`source_plan.py:110`) is wired in live — `cli.py:1140/1164`
  and `automation.py:2619/2690` pass it, and it is **not** env-gated. So the window U52 changes is
  the one this station runs with.

### 3.2 Why the fall happened at all

**INFERRED (mechanism, named against the code above):** the plan on air before the boundary was
the **0.7 s tail of the closing scheduled item** — that is what the daemon itself resolved from.
A plan with 0.7 s of life cannot carry a **690 s** rollover lead: `plan_end_at - lead` is ~689 s in
the *past*, so the boundary-aligned trigger has nothing to arm on, and the channel reaches EOS with
no prepared replacement. That is the structural reason the "prepare the next item ahead" half of
this brief is not a small change: the daemon has no notion of a *next* plan to prepare until it
asks for one, and it only asks once the channel is due or already dark.

**INFERRED, and the honest boundary of this diagnosis:** the `18:06:44,933` tail-take **succeeded
on the old code**. So this extract does **not** prove that the one-sided-window defect fixed by
U52 was the trigger for *this particular* boundary. What the extract proves is that the reload was
issued post-fall, that no rollover ever fired for education, and that the resulting conform was
224.5 s on air. The two-sided-window fix is demonstrably the fix for the *class* of resolution
failure that the branch's RED tests pin (§5), and it is live-relevant because the 30 s window is
wired — but I will not claim it was THE cause of this incident.

### 3.3 What shipped for item 1

`source_plan.py`'s gap-absorb window is now **two-sided**. The old body (read off the patch's `-`
lines) skipped every item that had already started, so a boundary landing a few seconds *inside*
the next item's slot skipped exactly that item and answered filler — the program's whole
preparation window of slate:

```python
    start_index = 0 if current_index is None else current_index + 1
    for index in range(start_index, len(items)):
        starts_at = _as_utc(items[index].scheduled_at)
        if starts_at < current_time:
            continue                                   # <-- the defect
        if (starts_at - current_time).total_seconds() <= gap_absorb_seconds:
            return index
        return None
```

The new body accepts an item whose slot is currently open, and still refuses one whose own slot has
already closed (a late replay is not a program):

```python
    start_index = 0 if current_index is None else current_index + 1
    for index in range(start_index, len(items)):
        item = items[index]
        starts_at = _as_utc(item.scheduled_at)
        delta = (starts_at - current_time).total_seconds()
        if delta > gap_absorb_seconds:
            return None
        if delta < -gap_absorb_seconds:
            continue
        if delta < 0.0:
            ends_at = starts_at + timedelta(seconds=item.duration_seconds or 0)
            if ends_at <= current_time:
                # Its own slot is closed too: a late replay, not a program.
                continue
        return index
    return None
```

## 4. Item 2 — why did the worker exit 1?

### 4.1 Reproduction on a real GStreamer worker

`staging/U52/scripts/u52_repro_deliberate_kill.py` — raw output in
`staging/U52/evidence/repro-item2.txt`. It launches the **real** worker via the branch's own native
harness (`tests/egress/test_gst_engine_wsl.py` + `test_u41_plan_eos_slate_real_worker.py`) on temp
paths, waits for the slate hold, then tears it down three ways:

**OBSERVED (verbatim from the evidence file):**

```
ffmpeg on PATH : C:\Users\scott\AppData\Local\Microsoft\WinGet\Packages\Gyan.FFmpeg.Essentials_…\ffmpeg-8.1.1-essentials_build\bin\ffmpeg.EXE
worker script  : …\civiccast\egress\gst\worker.py
runtime root   : C:\Program Files\CivicCast (Native)\runtime

## Part A -- deliberate kill (the F3(b) fallback-slate restart's own call)
A1 worker alive on the slate: poll() = None ts_bytes = 328060
A2 calling civiccast.egress.daemon._process_terminate(proc)
A3 deliberate terminate -> returncode = 1 (waited 0.00s)

## Part B -- clean stop (the graceful teardown)
B2 clean stop -> returncode = 0

## Part C -- hard kill (the exit-code shape a crash produces)
C2 Popen.kill() -> returncode = 1

## verdict, from the numbers above
A deliberate == C hard kill on exit code: True (both exit 1)
B clean stop exit code: 0
```

**OBSERVED, and this is the finding:** a deliberate `_process_terminate` and an unconditional
`Popen.kill()` are **indistinguishable by exit code** — both 1. The incident's log line
`worker exited (exit_code=1, state=TRANSITIONING, desired=ACTIVE, pending_reload=True)` is exactly
that shape, which is why it read as a crash.

**Caution on environment:** the ffmpeg on PATH was **Gyan 8.1.1 essentials (WinGet)** — *not* the
station's build, which is `--disable-libx264` by policy. This repro does not encode x264 and the
conclusion is about process exit status, so the difference does not touch the result; it is stated
because it is the kind of thing that silently invalidates a different claim.

### 4.2 Which kill site was it, and what shipped

**INFERRED:** the incident's kill is the **F3(b) fallback-slate restart**,
`daemon.py:_fall_back_to_restart_reload` — the site gated on `state.state == "FALLBACK_SLATE"`
that calls `_process_terminate(process)` rather than the bounded variant. It is the only site whose
precondition (`FALLBACK_SLATE`) matches the incident's state at the exit
(`state=TRANSITIONING (source=CivicCast slate)` 730 ms earlier), and it is the restart path the
`18:10:32,239` "Restarting … onto the plan its interrupted reload already prepared" line narrates.
The other kill site, `_reload_ack_timeout`'s wedged-worker kill, is gated on a live pid that never
acknowledged a reload; the incident's worker was still emitting healthy counters.

Shipped in `daemon.py`:

- `self._reload_kill_reasons: dict[str, str] = {}` beside `_reload_kills`.
- `_note_deliberate_kill(channel_id, reason)` — adds to `_reload_kills` **and** `WARNING`-logs
  `"channel %s: terminating the worker deliberately for a reload (%s); its non-zero exit is this
  kill, not a crash."`
- Both former `self._reload_kills.add(channel_id)` sites now call it with a measured reason string
  (`"reload ack timed out on a live pid…"`, `"reload out of fallback slate…"`).
- The exit line gains `deliberate_kill=%s`, and when true a follow-up line carries the reason:
  `"that non-zero exit was a deliberate kill -- %s -- not an encoder crash; the pending reload is
  honored."`
- Two `self._reload_kill_reasons.pop(channel_id, None)` clears beside the existing drain/stop
  discards, so a stale reason cannot be attached to a later genuine crash.

**One deliberate deviation from the brief's wording, stated so it cannot read as compliance.**
Item 2 says "if an exit remains unavoidable, the worker must log why before exiting." The narration
is **daemon-side, not worker-side** — and that is the only place it *can* be:

- **OBSERVED:** `_process_terminate` returns in **0.00 s** (§4.1 `A3`). The worker gets no window in
  which to run any handler, so a worker-side "why" for this path is not implementable.
- The daemon is also the only party that *knows* the why — the worker is not told it is being
  killed for a reload, it is simply terminated.
- The `WARNING` line therefore fires **before** `_process_terminate` is called, i.e. the reason is
  in the log ahead of the `worker exited` line it explains, and the exit line itself now carries
  `deliberate_kill=True` plus a follow-up reason line.

**This makes the incident's log line self-explanatory on the next occurrence.** It does **not**
make the transition seamless, and it does **not** remove the worker exit or the HLS discontinuity.

### 4.3 The seamlessness half of item 2 — not achieved, and why

The brief asked for "no worker exit, no relay restart". **That is not what shipped, and I am not
claiming it.** Two reasons, both measurable:

1. **The restart is by design.** Issue #157 made filler *interruptible*: a due program must not
   wait out a fill-target plan (up to an hour of slate), so the F3(b) path deliberately tears the
   slate worker down rather than draining it. Removing the exit means changing that design
   decision — a product question, not a bug fix.
2. **The relay cycle is inherent to that restart.** The `18:10:32,225` `HLS relay up for education`
   line is 47 ms before the exit observation, i.e. the restart *did* cycle the relay. That is the
   same surface U51's relay/sinks changes land on (§5).

**Residual question for the owner:** whether the prepared-plan hand-off should be made seamless
(preroll the new leg behind the slate, then switch) — which would remove the exit *and* the
discontinuity, at the cost of reopening #157's interruptibility rule. I did not decide this.
