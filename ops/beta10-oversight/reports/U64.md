## 1. The answer in plain English

A resident watching the 1 August 11 public meeting got a stretch of about four minutes that
sounded roughly **10 LU quieter** than the rest of the meeting. The station's own rung caught
it at 07:18 as loudness check #9. Here is what actually happened.

The ride is a speech-leveling pass: it measures a program second by second and applies a gain
curve, with a hard ceiling of **+18 dB**. That ceiling is not a bug — it is the whole design.
The 1 August 11 asset has, near the start of its aired part, a four-minute passage that is
**low-level speech at about −44.7 LUFS**. To bring that passage up to the −16 LUFS target the
ride would need **~28.7 dB**. It is only allowed 18. So it applies the full 18, every second of
the passage is clamped, and the passage lands at about −26.7 LUFS instead of −16.

Then the gate reads that window and says: this window missed by **10.69 LU**. Which is true,
and useless — the miss is the clamp, and the clamp is the law. The gate is scoring a window it
has forbidden the ride to fix, and printing an operator-visible **WARNING** that reads exactly
like a loudness failure. It has done this **twelve times** across four days, including the
07:53:54 C15 rebuild, which reproduced `10.02 LU / 0.06 LU` to the printed digits.

The fix is the reachability test the owner's own quiet-source rule already specifies: if a
window cannot be brought inside tolerance even at full clamp, that is `EXCLUDED_QUIET_SOURCE`,
not a failure. The candidate adds that test, excludes such windows from the worst-window
number, downgrades the warning to an INFO line naming the excluded starts, and leaves a
reachable miss still a miss.

**It changes no audio byte.** The trim the ride converges on is driven by the whole-program
level, which the window leg never feeds. Curve 2400/2400 points identical, trim 0.4 dB both,
emitted audio identical, max |delta| **0 LU**. What moves is the verdict and the log line.

## 4. Item 3 — the smallest fix, its RED/GREEN, and the no-audio-change proof

**The fix.** The owner's quiet-source rule already defines the test: a second is UNREACHABLE iff
its own centred 45 s ride-window level is below `target − window_tol − g_max`; a window is
`EXCLUDED_QUIET_SOURCE` iff unreachable seconds are at least a quarter of it. The candidate
implements exactly that, and nothing more, in `civiccast/egress/loudness_ride.py`:

- `UNREACHABLE_WINDOW_FRACTION = 0.25`, `unreachable_floor_lufs(...)` = `−16.0 − 0.9 − 18.0` =
  **−34.90 LUFS**, `unreachable_window_starts(...)` walking both tilings at one sample/second.
- `worst_window_deviation_lu(..., unreachable_starts=())` skips excused starts — the exclusion
  is inside the *scoring* function, so an excused window cannot leak into the verdict by any
  other path.
- `LeveledAttempt.unreachable_windows`, `loudness_excused`, and `_loudness_lawful`; the selector
  key becomes `0 if _loudness_lawful(...) else 1`, so a lawful-but-excused attempt still wins.

window starts, and one added `and not kept.loudness_excused(...)` operand on the FAIL warning.

## 5. Item 4 — what `loudness_status: failed` means, and what the station should do

**It is a verdict on the SOURCE asset, not on the ride output.** The verdict is made in
`civiccast/stream/loudness.py:151` — a ±2.0 LU tolerance test applied to a *successful*
measurement of the source. The preparer merely persists it (`preparer.py:709`) and reads it
once, to set `normalized` (`:2810`: `normalized = False if silent_asset else loudness.status != "ok"`).
It is not a statement about whether the conform came out well. **`continuity.py:442`'s
`loudness_status="failed"` is a different artifact entirely** — the offline `EgressContinuityProof`
— and the coordinator's note conflates the two. This report answers the preparer's.

**What the station does today when a conform's own gate fails: nothing but log the warning.**
Both gates that decide a conform's fate ignore `loudness_status`:

- the cache-**HIT** predicate (`:2491`) tests `meta.get("full_asset_conform") is True` — the
  probe verdict is not read;
- the **promotion** predicate (`:3048-3053`) tests duration and method — the probe verdict is
  not read.

So a failing conform promotes and is re-served forever. That is why all four sidecars in the
cache today say `"loudness_status": "failed"` and all four say `"normalized": true` — the status
is decorative. (It is the **cause** of `normalized: true`, which is why the field reads oddly:
`normalized` means "the ride ran", not "the ride succeeded".)

**Why the json was rewritten at 07:24:12** (`evidence/cache-sidecar-forensics.txt`):

```
fixture, captured 09-29 07:21:43 : full_asset_conform true  loudness_method "ride"   168 B
on disk, mtime     09-29 07:24:12 : full_asset_conform false loudness_method null     167 B
```

Both carry identical probe values (`-25.8 LUFS`, `15949.199933 s`, `normalized true`). They
differ in exactly the two conform markers, and the **bytes prove nothing else differs**:
`true→false` is +1 char, `"ride"→null` is −2, net −1, and **168 − 1 = 167**. The writer is the
probe-only call at `preparer.py:2817` — no markers passed, so the `:642-643` defaults apply.

**That rewrite is self-invalidating.** The cache-HIT predicate requires
`full_asset_conform is True`. The key that had been cacheable at 07:21:43 was not cacheable from
07:24:12 on — which is exactly why the 07:53:54 `prepare()` had to run a **fresh full-asset
conform of all 15,949.2 s** rather than serving the cached file, and reproduced `10.02 LU /
0.06 LU` to the printed digits. The rebuild is not a new symptom; it is the deterministic
consequence of a sidecar that invalidated its own cache key.

**Filed as an open question, not guessed at:** why key `757519c3` has no `.ts` in the cache at
all, and why the 07:53:54 rebuild wrote no promotion meta (its mtime is still 07:24:12).
Eviction pressure is excluded — the budget is the 20 GB default (`preparer.py:23`,
`CIVICAST_CONFORM_CACHE_GB`) against the 9.19 GB the cache holds, and there is no eviction line
anywhere in the log set. This evidence does not establish the cause and this report does not
invent one.

### Recommendation: **re-ride the failing stretch, not refuse the cache entry**

Of the three options the brief names:

- **Re-ride that stretch — recommended.** After a conform's own gate fails, re-run the ride
  bound to the failing window(s) with a raised `g_max` (or a longer follow window), keeping the
  result only if the gate then passes. It is the only option that *fixes the sound*, which is
  what the resident actually experienced. Risk: a higher `g_max` on genuinely quiet material
  lifts the noise floor with the speech; the re-ride must keep the existing true-peak guard and
  the `loudness_excused` escape so it cannot loop on an unreachable window. Cost is bounded —
  one extra ride per failing conform, and the mechanism above shows failures are rare and
  deterministic.
- **Fall back to window conforms — rejected.** It sidesteps the full-asset path rather than
  fixing it, and §3 shows the window path hits the same clamp on the same material (`8.42 LU`
  on the one near-stretch window ride). It would trade a loud failure for a quiet one.
- **Refuse the cache entry — rejected as the primary, kept as a safety net.** Refusing the
  entry does not make the audio better; it makes the station re-conform 15,949 s on every
  prepare — the exact cost the 07:53:54 rebuild already paid once, for no change in the two
  printed numbers. It is worth having as a *last* resort for a conform that fails *and* is not
  excused, but it must not be the answer to this finding.

**It does not flip the C15 rung's loudness #9.** The rung's adjudicator reads the **emitted**
air; the ride's exclusion reads the **source**. Applying the same reachability test to the
emitted fixture (`evidence/rung-vs-ride-instrument.txt`) finds:

**0 excused.** This is structural, not incidental: the +18 dB clamp guarantees the emitted
reading can never fall below the floor, so an instrument reading the emitted audio can **never**
fire this exclusion. On the source the same window reads −44.66 LUFS and *is* excused. Same
audio, two instruments, opposite verdicts. **Whoever owns the rung instrument has to point it
at the same signal the ride reads, or the C15 finding stands.** This is a product/oversight
question. It is filed here, not silently patched around.

**The real-asset measurement is on a 480 s fixture, not the full 1,800 s part.** Windows whose
excused start + 240 s runs past 480 s cannot be scored from it. The `[0,240)` window — the one
the rung failed on — is fully covered.
