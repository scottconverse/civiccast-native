### 5.3 Not proven: the Postgres store's one-transaction recovery on a real database

All U06 tests use `InMemoryEgressStore`. What that leaves unproven:

* `PostgresEgressStore.recover_stale_state` (`store.py:487-532`) runs one session and one commit and
  rolls back + re-raises on `IntegrityError`; the in-memory store proves the *contract* (command
  published before state, duplicate id raises, no state-only commit) and `_fake_pg_store` in the
  pre-existing tests proves the rollback path against a fake session, but no test in this unit ever
  executed the real SQL path against a real Postgres/SQLite file.
* The naive-vs-aware `updated_at` question: `DateTime(timezone=True)` returns aware on Postgres but
  naive on SQLite, and `_epoch_seconds` exists for the naive case. Only the aware case is exercised
  in tests (the in-memory store holds the Python datetime it was given). A live test would need to
  read a row back from a real database and assert that `_encoder_is_gone` still classifies a genuinely
  live encoder (created before the row's write) as *ours*, and a reused pid as not-ours — i.e. that
  the epoch comparison survives the round-trip.
* `psutil.create_time()` vs `time.time()`: both are Unix-epoch seconds, but they are different clocks
  in practice (process creation time on Windows vs wall clock) and no test measures a real process.
  A live test would need a real long-running process and a real row to show the comparison is stable
  at the boundary (a row written a fraction of a second after its encoder spawned).

### 5.4 Not proven: the concurrency and cost of the per-pass sweep in production

* The sweep adds one `list_configs()` and one `read_state()` per enabled channel **per pass**
  (`run_once` already reads state per channel through `process_once`, so this roughly doubles those
  reads). With 3 channels at the shipped 2 s poll that is ~1.5 extra reads/s; I did not measure it
  against the real Postgres store.
* Two sweeps can in principle run concurrently if a second `run_once` overlaps a slow one (the loop is
  single-threaded, so today they cannot; a caller invoking `run_once` from two threads could). The
  store's own recovery operation is the atomicity boundary, and a duplicate `command_id` raises
  rather than double-queues — which is fail-closed but would log an exception. Not exercised.

## 6. Product question raised (gap 4)

`questions/U06.md`: reconciliation never recovers a STOPPED row, but the pre-existing `auto_start`
policy starts a stopped `auto_start` channel on the next pass, and an operator's `stop`
(`daemon.py:1345`) is indistinguishable in the stored data from a completed drain or a clean worker
exit (`daemon.py:2640`, `:4092`) — same state, same `pid=None`, same `updated_at`; and the store
exposes only pending commands (`store.py:61-88`), so a consumed operator stop cannot be read back.
Per the brief I stopped rather than inventing semantics; the observed behavior is pinned by
`test_preexisting_auto_start_still_starts_a_stopped_channel` (`d8ea37b1`) and three options with
costs are written up there, with a recommendation (make a human's stop durable by recording its
cause, rather than by freezing STOPPED rows).

## 7. Doubts

1. **The age rule is the weakest link.** `_encoder_is_gone` treats "process created after the row's
   last write" as "not our encoder". It is the best evidence available (the worker's image name is the
   interpreter's, `gst/strategy.py:980`, so a name check cannot work), and it fails closed on every
   unknown — but it depends on the row being re-written while the encoder lives. I traced that
   `_poll_process` writes `pid=` on every live tick (`daemon.py:2508`), so the invariant holds; if a
   future change stops re-writing the row during steady-state ON_AIR, the rule could start clearing a
   live channel's row instead. The `pid exists + identity unreadable → do not touch` branch limits the
   blast radius but does not remove the dependency.
2. **`_reap_orphan` is a different, narrower identity check** and I deliberately did not change it: it
   requires `"ffmpeg"` in the image name and `created_at < boot_epoch`. For a real encoder that
   survives a *service* restart (not a reboot) and is not an ffmpeg-named process, the orphan path
   would not reap it while my sweep would call it "not gone" (its age is older than the row) and leave
   it alone — so a channel could in principle end up with a predecessor encoder still writing while a
   new one starts. This is pre-existing behavior on the orphan side, not something U06 introduces, but
   the two rules are now side by side and should probably be reconciled by whoever owns issue #161.
3. **`questions/U06.md` may change gap 2's usefulness in one respect**: if the coordinator chooses to
   make operator stops durable via a new marker state, that state must not be added to
   `_STALE_RECONCILE_STATES`, or the sweep would fight it.
4. **I did not re-measure the 2026-09-24 incident.** The brief's account (three channels frozen,
   persisted ON_AIR rows with dead pids) is taken as given; my fix is aimed at the mechanism the code
   shows, not at a reproduced live failure.
5. **Report numbers are from the runs quoted**, on the committed tree; the one number I did not
   measure myself (the brief's 1611/40 baseline) is labelled as recorded rather than verified.
