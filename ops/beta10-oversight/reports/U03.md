**How N depends on config (OBSERVED):**

* *Normalized segment, `loudness_target_lufs` set:* **N = 2.** Pass 1 is gated by the guard at

  needed; the probe is skipped when either is false.
* *Segment that needs no normalization, or no loudness target:* **N = 1** (pass 2 only).
* *Cache HIT:* **N = 1** — the stream-copy at `preparer.py:1008`.

2 is therefore the worst case on this path, which is what the lead has to cover.

**`_conform_full_asset_into_cache` is excluded, and here is why (OBSERVED).** It is itself a probe plus an
encode — `preparer.py:581` and `preparer.py:609` — but it cannot run inside a preparation on this engine:

inside a reload's preparation. Counting it would have produced N = 4 and a 990 s lead for work this path
cannot do at that moment. The two call sites of `_conform_full_asset_into_cache` are `preparer.py:1839`

invalidating the ceiling.

## 2. Section A.2/A.3 — the rule, and the upper bound

`_rollover_lead_seconds` (`automation.py:968-981`) now computes:

```python
        override = rollover_lead_seconds_from_env()
        if override is not None:
            self._warn_if_rollover_lead_nears_the_defer_watchdog(
                override, source=f"{ROLLOVER_LEAD_ENV} override"
            )
            return override
        computed = max(
            self._ROLLOVER_MIN_LEAD_SECONDS,
            self._ROLLOVER_PREPARATION_PASSES * preparation_timeout_seconds_from_env()
            + self._ROLLOVER_RELOAD_SETTLE_BUDGET_SECONDS
            + self._ROLLOVER_LEAD_MARGIN_SECONDS,
        )
        self._warn_if_rollover_lead_nears_the_defer_watchdog(computed, source="computed default")
        return computed
```

At the station's shipped values that is `max(120, 2×300 + 30 + 60)` = **690 s**. `_ROLLOVER_MIN_LEAD_SECONDS`
stays 120 s as the floor; the env override (`CIVICCAST_EGRESS_ROLLOVER_LEAD_SECONDS`) is passed through
exactly as before.

**Upper bound.** `ceiling = _ROLLOVER_DEFER_SWITCH_TIMEOUT_SECONDS − _ROLLOVER_LEAD_CEILING_HEADROOM_SECONDS`
= `900 − 60` = **840 s**. A lead **strictly greater than** 840 s logs exactly one `_LOG.warning` per service
lifetime (`_warn_if_rollover_lead_nears_the_defer_watchdog`, `automation.py:983-1030`, latched by
`self._rollover_lead_ceiling_warned`, set in `__init__`) naming the lead, its source, the ceiling, the
headroom and the watchdog. **The value is used as given** — computed or overridden — because clamping an
operator's explicit override would reinstate the failure the lead exists to prevent, and clamping the
computed default would make the lead lie about the worst-case preparation it covers.

The shipped configuration does **not** warn: 690 ≤ 840.

The warning is per *service lifetime*, not per channel or per tick, because the lead is a property of the
deployment's configuration (identical for every channel) while `_check_plan_rollover` calls
`_rollover_lead_seconds()` on every ~2 s poll tick. The latch is a plain per-instance flag, consistent with
`_ROLLOVER_RETRY_WARN_INTERVAL_SECONDS`'s existing treatment of the same repetition problem.

### 3.4 One behavioural consequence that needed its own test (OBSERVED)

Because the gst call site computes `trigger_at = max(last_segment_start_at, plan_end_at − lead)`, a plan
**shorter than the lead** does not "never trigger" — it arms at the plan's own start, on the first tick
after the tick that established the horizon (`_check_plan_rollover` returns immediately after
`_reestablish_plan_horizon`). At 690 s the lead now exceeds a 600 s plan, so this case became reachable in
code paths that previously stayed above it. Pinned by
`test_a_plan_shorter_than_the_lead_arms_at_its_own_start`. The cadence floor
(`_rollover_min_interval_seconds`) and the issued latch still bound how often that can happen for a
channel.
