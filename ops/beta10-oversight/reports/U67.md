## 1. The answer in plain English

At 03:44:10 on 2026-09-30, the education channel's current program was about to end and
automation did exactly the right thing: it resolved the next program (an 1800 s item), recorded
the horizon, and issued a **seamless rollover** — a request to prepare the next program *now* and
hand over to it at the plan's end, with no gap on air.

Four seconds later the channel's state went to `TRANSITIONING`, and stayed there. For 34 hours.
The channel aired black and silent, and **no log line anywhere named the cause.**

Here is what actually happened, and it is the whole of it:

**Automation resolved the boundary one second past the end it recorded. The daemon did not.**

The schedule's item test is the half-open `starts_at <= t < ends_at`. So the instant automation
records as "the plan ends here" — the closing item's own derived end — is *not inside that item*.
Asked at exactly that instant, the schedule answers **no plan at all**. Automation already knows
this and steps one margin past; its own log shows it:

```
03:44:10,575  automation rollover for education resolved to a 0.0s tail of the closing
              scheduled item; using the plan due where that tail ends instead (1800.0s)
03:44:10,578  rollover for education was issued as soon as the previous plan settled:
              the plan on air is 554s long, shorter than the 690s ...
03:44:13,148  channel education: egress state -> TRANSITIONING (pid=24516, last_error=-)
```

The daemon received that rollover, asked the **same instant**, got the **same `None`** — and this:

```python
if source_plan is None or source_plan.channel_id != channel_id:
    return False          # <- no log. none. anywhere.
```

It declined the seamless path **silently**, and fell through to the terminate+restart fallback.
That fallback's only recovery route is **the worker reaching plan EOS and exiting** — and U41's
plan-EOS hold (shipped, live) had removed exactly that: the engine is told to drop the plan-EOS so
the worker never exits at a boundary. So nothing ever exited, nothing ever restarted,
`_poll_process` rewrote `TRANSITIONING` over the channel every ~2 seconds with an unchanged pid
and an empty `last_error`, and it never stopped.

**So: not dropped, not deadlocked, not waiting on a settlement that could never come.** The
rollover was **declined — silently — by a boundary answer the two halves of the system disagree
about, and its only escape hatch had been closed by an earlier, deliberate change.**

The last build before a public release shipped a control plane whose two components ask the same
question at the same instant and give different answers, and whose failure mode is *silent and
permanent*. That is the blocker.

## 2. Root cause, walked against the LIVE bytes

Five steps, each verified by reading the running code, not the repo:

1. **`automation.py:_resolve_rollover_tail`** (LIVE blob `016cf90e`) — resolved the closing item's
   tail, found it 0.0 s / empty at the derived boundary, re-asked one
   `_SCHEDULE_TAIL_BOUNDARY_MARGIN_S` past it, found the 1800 s item genuinely due, and recorded
   `plan_end_at` + `min_plan_seconds=690` on the command. This is U63's **defect A fix**, and it
   works. It is *why* the reload was issued at all.
2. **The daemon drains the command** (`_reload_steps`) and calls
   `boundary_provider(channel_id, max(plan_end_at, now), min_plan_seconds=690)` — the **same
   boundary instant**, because `plan_end_at` is what automation recorded.
3. **The schedule answers `None`** there (half-open item test), so `source_plan is None`, so
   `_reload_steps` returns `False`. The `_resolve_schedule_tail` tail-floor guard
   (`tail_seconds <= 0.0`) is **never reached** — the decline happens before it.
4. **`_request_reload` calls `_fall_back_to_restart_reload(channel_id)`** with
   `failure_reason=None` — again with **no log line**. That arms `_pending_reloads[education]` and
   writes `TRANSITIONING`. State was `ON_AIR`, so the worker was deliberately **not** terminated.
5. **The exit never comes.** Under the live U41 hold (`CIVICAST_WORKER_PERSISTENT=1`) the engine
   drops the plan-EOS, so the worker never exits at a plan boundary. `_poll_process`'s
   "pinned → keep publishing TRANSITIONING" branch is therefore permanent. 34 h.

**Did the evidence settle it?** Yes — completely, and from code plus log, with no gap. There is no
residual "we think". The one extra log line that would have turned this from a 34-hour outage into
a five-minute diagnosis is the `WARNING` this slice adds at step 3 (and a second at step 4).

**Why the two halves disagree, and why the fix belongs in the daemon:** automation's boundary
resolution and the daemon's boundary resolution are two implementations of the same question. U63
repaired one of them. They must give the same answer; the daemon is the one that was wrong.

## 3. The fix

One file, `civiccast/egress/daemon.py`. **+327 / −11**, 15 hunks. Three parts.

**(a) The re-resolve — work item 2.** When the boundary provider answers `None` on the seamless
arm, the daemon re-asks one `_SCHEDULE_TAIL_BOUNDARY_MARGIN_S` (1.0 s) past the boundary with the
**same** `**horizon_kwargs`, and uses that plan rather than declining. It is a **recovery, not a
new selection rule**: it can only turn a decline into the plan the schedule already has due
immediately after the boundary — which is the plan automation recorded the horizon for. The tail
floor and the horizon downstream are unchanged.

```python
if (source_plan is None and not force_fallback and boundary_provider is not None
        and boundary_at is not None and not self.has_manual_override(channel_id)):
    source_plan = boundary_provider(
        channel_id,
        boundary_at + timedelta(seconds=_SCHEDULE_TAIL_BOUNDARY_MARGIN_S),
        **horizon_kwargs,
    )
```

So with the incident's exact inputs — 0.0 s tail resolved to an 1800 s boundary, plan shorter than
the 690 s lead — the next program is **prepared before the plan ends**. If the boundary is
genuinely unplannable, the daemon now says so and then falls back — the "or fall back safely"
clause, with the re-resolve first and the immediate dispatch after.

**(b) End the silence.** Two `WARNING`s: one on the decline (channel, boundary, `force_fallback`,
where the plan was resolved from), one on the un-armed seamless path (state, source, pid) before it
falls through to restart.

**(c) The watchdog — work item 3.** `_poll_reload_stall_watchdog`, appended last in the poll chain
(it judges the settled state row, so `_poll_process`'s write from the same tick must have already
happened).

* **Bound: 1650 s** = `_TRANSITIONING_WATCHDOG_LEAD_SECONDS` (690 s, the deployed rollover lead)
  \+ `_PENDING_RELOAD_SETTLE_DEADLINE_S` (960 s). **Why this shape:** the pin's honest lifetime is
  "the rest of the plan on air, then a restart", so plan length + lead is the right derivation;
  the flat part covers every pin automation itself can dispatch (it never dispatches with more than
  a lead of plan left), and any accepted-but-unsettled reload already in flight gets the full
  settlement deadline. `_reload_stall_bound_seconds(plan_end_at)` **stretches** it from the
  rollover's own recorded horizon when that is further out, so a declined reload against a long
  plan is never judged early; a horizon already in the past leaves the flat bound standing.
* **Stands down entirely** while a preparation or an accepted-but-unsettled reload is genuinely in
  flight — those carry their own deadlines and are not this watchdog's business.
* **Rung 1** (past the bound, nothing in flight): `ERROR` naming state, source, pid, last_error,
  and elapsed; then **re-issue the rollover once** via `_request_reload`.
* **Rung 2** (pin survives the re-issue by a further **300 s**, one preparation timeout): `ERROR`,
  **drop the pin**, `_note_deliberate_kill`, `_process_terminate_bounded` — exactly the Item 85
  wedge branch's shape — so `_poll_process`'s crash-relaunch re-resolves and starts a fresh plan.
  **No human.**
* **It cannot fire on a normal rollover.** Nothing on the healthy path ever writes
  `_pending_reloads`, so the clock only starts on a channel that has already failed a hand-off. A
  200 × 690 s tick loop with a healthy rollover asserts the watchdog's bookkeeping stays empty.

**(d) One honesty edit.** A reload that arms now **pops** any `_pending_reloads` pin a previous
declined attempt left behind; that pin's only meaning was "wait for a worker exit that is not
coming". Left in place it would keep rewriting `TRANSITIONING` over a channel that is already back
on air. All pin writers now go through `_arm_pending_reload`, so the clock and bound are recorded
at the instant the pin appears.

## 6. Risks, and what this slice does not do

**Honest risks.**

1. **Rung 2 terminates a worker.** That is deliberate — a wedged worker that has ignored a
   re-issued reload for 300 s past a 1650 s bound is not going to recover — and it is the same
   shape as the Item 85 wedge branch already shipped. The cost is a channel restart onto a fresh
   plan, which is exactly what the fallback always intended.
2. **The bound is a flat 1650 s with a recorded-horizon stretch.** On a *genuinely* very long plan
   the stretch applies (plan remaining + 1650 s); the flat part is derived from the deployed lead
   and the settlement deadline. The one place a bound can be wrong is if the deployed lead changes
   without this constant; the constant is restated (not imported) on purpose, and the comment
   records the `2*300 + 30 + 60 = 690` derivation so the next reader can re-derive it.
3. **The re-resolve is one margin (1.0 s).** If a schedule ever had two adjacent empty items, one
   margin would not reach the next real program. That case would still be *named in the log* and
   would still be caught by the watchdog — degraded to a restart, not to 34 h of black air.
4. **Two processes still each resolve the boundary.** This fix makes them agree at this boundary;
   it does not unify the implementations. Unifying them is a larger change and is **not** in this
   release-blocker slice.

**What it does not do.** It does not touch the live station, does not install, does not push, does
not change `automation.py`, and does not change any media behaviour. The install step is the
owner's and carries its own gates.

**Known gaps to hand forward.** The 26 pre-existing reds in the affected files are real and
unfixed here — they say the committed tests are stale against the LIVE APIs, which is worth a
separate slice before the public release. And the U41 plan-EOS hold that made this failure
permanent is still live; it is not wrong, but it removes the worker-exit safety net that several
recovery paths in this daemon still assume, which is a class of bug this incident is the first
instance of.
