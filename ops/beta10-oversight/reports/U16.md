### 1.10 The mechanism, stated exactly — and why it is not decidable from here

**OBSERVED.** `switch_running_time` is one value applied to both new-leg pads ⇒ it is *symmetric*
and cannot by itself create a one-sided displacement. The only asymmetric inputs are the two pads'
own observed ends, which are (a) computed in each pad's own cached segment, (b) delivery-timing
dependent (§1.7), and (c) sometimes missing entirely for the throttled stream (§1.8).

**INFERRED, and the blocker.** A per-pad gap has two very different meanings, and the per-pad ends
cannot tell them apart:

- a **delivery lag** — the lagging stream's last *delivered* buffer is behind because its queued
  backlog has not drained: here the shared `max` is *correct*, since that stream's continuation is
  its own end **plus its backlog** (x9: a natural ~0.75 s per-pad spread produced no output step);
- a **genuine divergence** — one branch withheld/stalled (U15's C3): here a per-stream own end or a
  clamp is what avoids a one-sided shift (x8/x10).

**Excluded by evidence in this unit:** the incoming leg's own file (§1.4), the mux's own anchoring of
a constant per-pad offset (§1.5), the relay hop for a constant skew or a backward session jump (§1.6),
and symmetric misbehaviour of the shared offset (§1.10 first line). **Not excluded:** the per-pad
reference inside a real switch, and the hold/preroll release path — neither of which logs its inputs,
and neither of which I could make produce a *one-sided* output step in any deterministic real-engine
configuration I could build (the x8/x10 steps are wedge/stall reproductions whose proximate cause is
visible in the construction itself).

**Consequence for the brief's premise.** The brief's prescribed fix ("ONE offset for all streams") is
already the shipped behaviour, so section B as written is a no-op; the real question is a policy
choice the evidence cannot settle. That is the rule-5 stop: `questions\U16.md`.

## 8. Item B — output A/V guard (daemon)

### 8.1 What shipped (OBSERVED, `grep -n` in `civiccast/egress/daemon.py`)


For a channel whose state row is `ON_AIR`, every ~30 s the daemon reads the newest COMPLETE segment of the
channel's HLS window and measures the first packet PTS of video and of audio, reusing U12's manifest
semantics and its `ffprobe` resolution, timeout and tri-state fail-safe (`hls_relay.py` carries the shared
machinery, +154 lines). A difference over 1.0 s on 3 consecutive probes logs ONE ERROR naming the channel,
each measured offset and each segment, and restarts that channel's **worker** through the ordinary
crashed-encoder relaunch path — a plain non-zero worker exit with no pending reload, so the daemon's own
exit handling owns the replacement (not the relay alone: the offset is created in the engine). Bounded to
3 restarts per channel per rolling hour, then one ERROR every 10 min and no restart. A probe that cannot
measure is "no answer": neither advances nor resets the streak and never restarts anything. The guard is
registered LAST in the daemon's poll tuple so `_poll_process` has already handled any exit this tick; the
streak is voided on a worker pid change.

Tests (15, all in `tests/egress/test_daemon_output_av_guard.py`): bounds match the authorized values, the
newest-COMPLETE-segment selection (3 cases), streak and reset, the ON_AIR gate, the pid-change reset, the
rolling-hour budget with its 10-minute exhausted cadence, the restart riding the dead-encoder path, and two
real-`ffprobe` tests that generate a TS in sync and a TS with a 2 s audio `-itsoffset` and measure them
(both ran here — `ffmpeg`/`ffprobe` are on PATH; they skip with a reason if not).

## 12. Doubts

1. **Item A deviates from the answer's letter, on evidence.** The answer asks the post-offset running time
   to come from a probe on the new-leg **src** pad; measured, that pad reports the pre-offset timeline
   because the offset materialises at the crossing. I shipped the prescribed line *and* a selector-sink
   probe rather than silently dropping the line the answer named. If the coordinator wants only what was
   asked, the selector line is additive and can be removed — but then the post-offset number is not
   observable at all from the seam's tail side.
2. **The guard gates on the state row, not on the ON_AIR confirmation.** It judges a channel the daemon
   models as `ON_AIR`; a channel whose row says ON_AIR while the new leg is still settling could have a
   segment from before the switch judged. Three consecutive probes (~90 s) make this unlikely to produce a
   false restart, but I did not build a test that exercises the settling window.
3. **A guard restart is indistinguishable from an encoder crash in the ordinary accounting.** The restart
   deliberately rides the crashed-encoder relaunch path, so it inherits that path's back-off and escalation
   accounting: a channel desynced by something that is *not* a crash can therefore accumulate escalation.
   With the 3-per-rolling-hour bound this is bounded, but whether that is the desired interaction is an
   ownership question I am flagging, not deciding.
4. **Detection latency is inherent**: 30 s cadence × 3 consecutive probes ≈ 90 s of ON_AIR probing before a
   restart, during which the channel airs a desynced program. That is what was specified, and 109 s of
   desync would have been caught after ~90 s — but it is not a "prevent" mechanism, it is a "notice and
   cure late" mechanism.
5. **Whether a restart is always curative is not established by me.** One live instance (government) was
   cured by a restart. If the engine's rebase produces a step again, the guard will restart again, up to
   the hourly bound; after that it only logs. A step that recurs faster than the budget allows would leave
   the channel airing it, by design.
6. **The real-runtime half of A is only verified when the env var is declared.** The default `-k u16` run
   skips 2 tests, so a reader who runs the suite the ordinary way has not executed the diagnostics against
   a real pipeline. The skip message says how to enable it; I am recording that the gate depends on the
   runner setting it.
7. **Item C's premise is corroborated, not reproduced.** I could not obtain `License=MPL` from the shipped
   CLI because the plugin aborts during registration on this install (§9.4). The corroboration is
   structural (the Rust plugin family and its MPL-2.0 licence), and the abort itself is the more
   consequential observation — it is in the closure/U17 lane, and I have not established why the plugin
   registers at all in U17's probe but aborts here (different environment, different plugin path, or a
   probe that read `get_license()` from the registry rather than running the CLI).
8. **The format-gate miss cost a follow-up commit and is a process doubt, not just a fix.** I reported a
   gate clean using a method that did not apply the project's config; the lesson is that a check run
   outside the repo must carry `--config`, and I have written the checker that does so into a scratch file
   rather than into the repo, so the next agent has no in-repo guard against repeating it.
