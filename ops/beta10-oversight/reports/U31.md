   top of `create_app` under the same `CIVICAST_SUPERVISED` guard the log config uses). Nested jobs
   are supported on Windows 8+; the control plane holds the only handle, so its death by any means
   closes it and the kernel reaps the whole subtree — relay ffmpegs, GStreamer playout workers,

### INFERRED (code path, no live confirmation)

- The control plane is in the supervisor's job (assignment at spawn), therefore its relay ffmpegs
  *inherited* membership in that job. Killing the control plane therefore reaped **nothing**, because
  the supervisor still held the job handle. This is the mechanism the fix targets, and it was

### The mechanism, and why self-assignment

OBSERVED, real processes, `%TEMP%\u31\exp_job.py` ("harness (job A, KILL_ON_JOB_CLOSE) → middle
(control plane) → grandchild (relay ffmpeg)", modes `inherit` / `ownjob`), grandchild spawned through
the **product's own** `civiccast.stream._ffmpeg.start_ffmpeg`:

```
inherit  (middle relies on inherited membership in A only)
    TerminateProcess(middle) -> grandchild ALIVE at +2s; dies only when A's handle closes
ownjob   (middle creates nested kill-on-close job B and self-assigns)
    TerminateProcess(middle) -> grandchild DEAD within 2s
```

Design choices, each with its reason (all in the `child_containment.py` module docstring):

- **Self-assignment, not per-spawn-site assignment.** One call covers every long-lived child the
  control plane will ever have, including ones it does not spawn directly
  (`civiccast.egress.gst.strategy` playout workers, `ts_relay`/`ndi_relay`/`sdi_relay`,
  `civiccast.live.contribution.coprocess`, and their grandchildren). Per-spawn-site assignment would
  have to be repeated at each funnel and would silently miss the next one added.
- **Anonymous, never named.** Two control-plane processes overlap during a restart; a named job would
  let the second join the first's job and hold a handle that prevents kill-on-close from ever firing.
  The empty name is deliberate: pywin32's `CreateJobObject` rejects `None` (measured, pywin32 311).
- **`BREAKAWAY_OK` left set — measured three ways.** `civiccast.native.gstreamer_repair._detached_launch`
  spawns the GStreamer re-stage with `CREATE_BREAKAWAY_FROM_JOB` from the control plane (it must outlive
  its parent). Measured: CP in supervisor's job only → breakaway ok; CP in own job B **without**
  breakaway → `PermissionError winerror=5` (the repair launch fails); CP in own job B **with**
  breakaway → ok. `SILENT_BREAKAWAY_OK` is left clear, so ordinary spawns are captured.
- **Failure is loud but never fatal.** `contain_own_descendants` never raises; `active` is set only
  after `IsProcessInJob` positively confirms membership; an inactive containment is logged at **ERROR**
  (`civiccast/app.py:477-483`) naming the exact consequence. A station whose containment could not be
  established must still air.

### The reclaim defence (second layer)

`civiccast/egress/relay_reclaim.py` (320 lines): `relay_log_shows_bind_failure` (reads the log **tail**,
fails closed on missing/unreadable/non-file), `udp_port_of`, `PortOwner`, `ReclaimVerdict`,
`decide_reclaim` (pure), `PortOwnerApi` Protocol + `PsutilPortOwnerApi` (real OS UDP table; the kill
goes through the package's TOCTOU-safe `verify_and_kill_process`, so a recycled pid is refused).
Wiring in `civiccast/egress/hls_relay.py`: `_live_relay_pids` (never kill our own live relays — two
sinks can hash to one port), `_maybe_reclaim_orphan` (probe **once per child**, latch before acting,
episode counter carried onto the replacement, `_STREAM_FAST_ATTEMPTS = 3` at `hls_relay.py:288`), and
one call at the top of the EXITED branch of `maybe_restore_missing_streams`. A refused holder falls
back to the ordinary 5 s/60 s cadence.

Measurements from `%TEMP%\u31\measure_startup.py` (redirects `PROGRAMDATA`,
`CIVICAST_EGRESS_WORK_DIR`, `CIVICAST_UPLOAD_DIR` into scratch, unsets `CIVICAST_SUPERVISED`,

"Loaded" = 8 below-normal-priority burner processes (`BELOW_NORMAL_PRIORITY_CLASS = 0x00004000`),
stopped after the run. `%TEMP%\u31\startup_measurements.json`, all runs `rc=0`, `created=true`,
python 3.12.13:

| label | wall_ms | import_ms | create_app_ms |
|---|---|---|---|
| idle | **15462.6** | 12669.9 | 1066.8 |
| idle | 10883.3 | 8304.3 | 1302.3 |
| idle | 11207.9 | 8559.3 | 1331.8 |
| loaded | 6873.8 | 5607.7 | 591.1 |
| loaded | 6998.5 | 5704.6 | 642.6 |
| loaded | 7068.6 | 5637.3 | 686.3 |

**Confound, disclosed:** the "loaded" runs are *faster* than the idle runs because they ran after the
page cache was warm — this is a warm/cold confound, not a load effect. The number I sized the budget
from is therefore the **worst cold idle wall, 15462.6 ms** (first run, coldest), and the load series
is reported only as a lower bound.

Chosen, and why:

- `DEFAULT_CONTROL_PLANE_READY_BUDGET_SECONDS = 180.0` (was 30.0). The observed failure was at
  `30.0 s` against a cold start whose *import alone* took 12.7 s on a box also running two coder
  units and three channel preparations. 180 s is ~11.6× the worst cold idle wall on this box, and it
  is now a ceiling on *work*, not on *wall*: a child that keeps spending CPU is never released inside
  it.
- `DEFAULT_CONTROL_PLANE_STALL_SECONDS = 60.0`. 4× the worst cold idle wall (15462.6 ms ≈ 15.5 s),
  so a start that is merely slow on a loaded box can never trip it, while a genuinely frozen child is
  released in 60 s instead of 180 s.
- `progress() → None` means "the sample cannot be taken" → the window **resets**. No evidence is
  never read as a stall: a handle with no process behind it must not be called wedged.
- Only the control-plane spec opts in (`readiness_stall_seconds is not None`); every other child's
  readiness keeps exactly its pre-U31 semantics.
- Known, disclosed behaviour change: the maintenance re-poll
  (`_poll_control_plane_maintenance_ready`) polls the **same** cold Python start and inherits the same
  180 s/60 s, so a held-interlock tick can now wait 60 s where it waited 30 s. F1's stop-chain
  arithmetic is restated in the docstrings: the chain was 60+30+60 = 150 s when F1 was written and is
  300 s now — safe only because `should_abort` (not the budgets) is what bounds the stop path.

**The seam is the OS seam.** The CPU sample is taken by `ChildProcessRunner.cpu_seconds(handle)`
because the runner owns the OS handle; the orchestrator must never read the process table itself.
OBSERVED consequence of getting that wrong: an earlier version of this change sampled `handle.pid`
directly through a module-level helper, a **fake** handle's pid collided with a live process on the
test machine, the real process held its CPU flat, and
`test_g2c_restart_not_ready_warns_once_per_distinct_detail_not_every_attempt` went
`assert 3 == 1` — flaky, 4 runs in 4. Every fake runner now returns `None`.

## Item 3 — Does a control-plane restart discard in-flight preparation?

**Answer: partly — the expensive part survives.** OBSERVED / INFERRED from code (report only, no
change made):

- `civiccast/egress/preparer.py:1440-1481` — each `prepare()` gets a fresh
  `channel_prepared_root / uuid.uuid4().hex[:12]`; a per-plan directory is **never resumed**. A killed
  preparation's partial plan dir is orphaned and reclaimed only by `_gc_prepared_plan_dirs`
  (keep-N = 3, 5 GB budget, 24 h age floor, plus a daemon-supplied live-dir provider).
- `_cache_key` (lines 423-451) hashes `(source_path.resolve(), st_size, st_mtime_ns,
  canonical_profile.model_dump_json(), loudness_target_lufs, loudness_tolerance_lufs,
  _LOUDNORM_METHOD_VERSION)` → sha256[:32]. Keyed on the **source and the profile**, not on the plan.
- The cache-HIT check (`_prepare_segment`, line 1643) requires `cached_ts.is_file() and meta is not
  None and meta.get("full_asset_conform") is True`. Promotion into the cache is an atomic rename
  (`_promote_conform_into_cache`); `_write_cache_meta` is tmp+replace; a partial conform exists only
  as `{key}.ts.tmp` and is never served. So **a partial conform is discarded, a finished one is
  reused** — and under `playout_trim_supported=True` a HIT writes no per-plan file at all.
- OBSERVED live, read-only, `C:\ProgramData\CivicCast\data\egress\conform-cache`: **16 `.ts`, 23
  `.json`, 0 `.ts.tmp`** (39 entries).
- Caveat: a HIT refreshes mtime via `os.utime`, so the 7.2 GB entry's mtime is a last-use time, not a
  creation time.

Net: a control-plane restart during preparation loses *the segment currently being conformed* and the
per-plan trim work, but not any previously promoted conform. That is why the pre-U31 restarts only
cost ~3 minutes each rather than re-conforming everything.

## Doubts

1. **The 4× margin for the stall window rests on a cold-start wall measured while the box was busy
   with my own work.** The worst idle wall (15.5 s) is plausibly pessimistic, which is the safe
   direction, but I have no measurement of a control-plane start under *station* load (three channels
   plus captions plus a real council meeting). If a real start ever burns CPU below one sample tick's
   resolution, the 60 s window is the wrong instrument — CPU seconds are a proxy for progress, not
   progress itself.
2. **The 180 s budget is a number, not a proof.** It bounds a child that keeps working; if the control
   plane can legitimately make progress for longer than 180 s on a cold, loaded station, this change
   converts a 30 s false kill into a 180 s false kill. The measured worst case is 15.5 s, so the
   headroom looks real, but I did not measure the station's worst case.
3. **`BREAKAWAY_OK` is a deliberate hole.** It is measured to be necessary for the tier-5 repair, and
   ordinary spawns still inherit the job, but it means "every long-lived child is reaped" is true only
   for children that do not ask to leave. The one call site that does ask is documented to outlive the
   control plane; a future call site that asks for breakaway without that intent would silently regain
   the orphan defect.
4. **The reclaim kills a process by pid after reading the OS connection table.** The TOCTOU-safe
   `verify_and_kill_process` and the argv gate make a wrong kill very unlikely, but the design does
   accept killing a process on this box if it is an ffmpeg whose argv carries this relay's URI and it
   is not one of our live relays. On a station running unrelated ffmpeg jobs that reuse the relay
   argv shape, this would be wrong; I judged the URI token specific enough (it is derived from the
   sink alone and carries the loopback relay port) but that judgement is mine.
5. **Item 3 is a code reading, not a live experiment.** I did not kill a preparation mid-conform on
   the station (forbidden) and watch what the next start reused. The cache-HIT logic and the atomic
   promotion are clear in the source and the live cache has 0 `.ts.tmp`, which is consistent, but no
   restart was observed consuming a previously promoted conform.
