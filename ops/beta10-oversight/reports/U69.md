## 1. The answer in plain English

The live caption tap listens to a channel's program audio and transcribes it in
~5-second batches. When it cannot keep up, its backlog of settled audio grows;
past a bound (a 15-scan streak, one persistence-window's worth) the tap **sheds** —
it throws away the oldest segments so it can start transcribing the newest, and
the captions for those seconds are gone forever. U68 measured **13 such sheds in
8 hours**, each discarding 10–100 seconds of speech.

U68 changed what the box does when that happens (it drops the foreground
preparation's ffmpeg one scheduling class). But **a shed leaves almost no trace**:
the only two diagnostics that could describe the moment — `phase_timing` and
`tap_batch_diagnostic` — are both **opt-in and self-exhausting**, so **63 of the
87 measured shed windows had no instrumentation attached at all**. Worse, the
survivors point somewhere useful: **46 % of sheds had no preparation running**,
and the transcribe call itself is what stalls (a 5 s batch measured p90 3.7 s,
max 21 s, with queue depth 1 — the stall is *inside* the ASR call, not queueing in
front of it). You cannot chase any of that down from the logs you have.

U69 is not a fix. **It is the missing evidence.** It adds one **always-on** INFO
line that fires when a channel's over-limit streak *starts* and again when a shed
*actually fires*, recording what the tap and the box were doing at that instant:
how deep the queue is and how old its oldest segment is; how long the last few
batches spent waiting for the channel's lock, reading/joining the WAV, inside the
ASR call, and in stabilization; whether the transcribe thread is *inside* the ASR
call right now (and for how long); process CPU, thread count and priority class;
a box-wide ffmpeg census with each child's priority class; and GPU utilization
when a driver is present. It reads no audio, writes no I/O on the hot path, can
never raise into the tap, and can be switched off with one environment variable.

The next shed after this is installed will explain itself.

## 2. The exact log line

One INFO record per event. The message is `Caption tap shed diagnostic <json>` —
a fixed prefix so `findstr`/`Select-String` can pull the family out of a busy log —
followed by a single-line JSON object.

Two `event` values:

| `event` | Fires when |
|---|---|
| `over-limit-streak-start` | the **first** scan on which a channel's settled backlog was over `max_backlog_segments`. The persistence window has not run out yet — this marks the **beginning** of a suspect episode, not a shed |
| `catch-up-shed` | a U23 catch-up shed **fired**: the oldest settled audio was discarded and captioning resumed at the newest segments |

A complete example, wrapped for the page only (on the wire it is one line):

```
Caption tap shed diagnostic {"event": "catch-up-shed", "channel": "education", "pid": 8123,
  "queue_depth": 7, "oldest_queue_age_s": 31.4, "max_backlog_segments": 2,
  "overload_streak": 15, "persistence_scans": 15,
  "shed": {"count": 5, "kept": 2, "skipped_s": 25.0},
  "batches": [{"wait_s": 0.0, "feed_s": 0.012, "asr_s": 5.833, "stabilize_s": 0.041}, ...],
  "batches_total": 412, "batches_retained": 8,
  "asr_in_call": true, "asr_call_s": 3.21,
  "suppressed_since_last": 0,
  "process": {"cpu_s_window": 12.9, "cpu_pct": 21.5, "wall_s": 30.0, "threads": 47,
              "priority_class": "NORMAL_PRIORITY_CLASS"},
  "ffmpeg": {"count": 2, "procs": [{"name": "ffmpeg.exe", "pid": 991,
              "priority_class": "BELOW_NORMAL_PRIORITY_CLASS"}]},
  "gpu": {"available": true, "devices": [{"name": "NVIDIA RTX 4070", "util_pct": 88,
              "mem_used_mb": 4096, "mem_total_mb": 8192}]}}
```

### How to read it

| Field | Meaning |
|---|---|
| `queue_depth` | settled segments the backlog gate **saw** at this instant |
| `oldest_queue_age_s` | age of the oldest settled segment then — a shed's real cost is roughly this minus what was kept |
| `max_backlog_segments` / `overload_streak` / `persistence_scans` | the bound and where in it this line sits |
| `shed.count` / `shed.kept` / `shed.skipped_s` | how many segments were dropped, how many kept, and the wall/audio seconds discarded |
| `batches[].wait_s` | time waiting for the channel's **session lock** |
| `batches[].feed_s` | reading and overlap-joining the WAV |
| `batches[].asr_s` | the **ASR call itself** |
| `batches[].stabilize_s` | the two-window caption stabilization |
| `batches_total` / `batches_retained` | batches seen lifetime vs. the last N kept per channel |
| `asr_in_call` / `asr_call_s` | whether the transcribe thread was *inside* the ASR call when this line was written, and for how long |
| `suppressed_since_last` | how many lines the rate limit dropped for this channel+event since the last line that printed |
| `process.*` | CPU seconds over the observed window, its `%`, wall seconds, thread count, Windows priority class |
| `ffmpeg.*` | **box-wide** ffmpeg census (name, pid, priority class) — not just this process's children |
| `gpu.*` | utilization/memory per device, or `{"available": false, "reason": …}` |

**The diagnosis each supports.** A shed whose `asr_s` is large while
`process.cpu_pct` is low is a **stalled or serialized ASR call** — nothing else
was competing. A shed with a high `cpu_pct`, a thread count in the hundreds and
several ffmpeg children at `NORMAL` priority is the box being **starved by
preparation**. `asr_in_call: true` with an `asr_call_s` that only grows across
consecutive lines is a **hung call**. `process.priority_class` says what the
whole service runs at (`NORMAL` is the shipped default for the tap's process;
playout workers are spawned `ABOVE_NORMAL`, and only the Python ASR *thread* is
dropped to `BELOW_NORMAL`, which the intra-op CTranslate2 pool does not inherit).

## 3. What the tap wiring changed, and what it deliberately did not

All 13 hunks in `tap_worker.py` (+152 / −14) are instrumentation:

* a top-level import of the new module, and one constructor kwarg
  (`shed_diagnostic=…`) defaulting to `shed_diagnostic_from_env(…)`;
* the two `_note_backlog_depth(…)` call sites now also pass the queued segments,
  so the queue age can be measured at the event;
* the streak-start emission (guarded by `streak == 1`), the shed-site emission,
  and the oldest-queue-age measurement;
* timing of the **existing** wait / feed / ASR spans, and a stabilize sink
  threaded through the existing phase-timing object via `PhaseSampleForwarder`;
* the two worker-construction sites re-wired from `self._phase_timing` to the
  forwarding `self._worker_phase_timing`.

**All 14 deleted lines are that re-wiring** (the old `_note_backlog_depth`
signature, the two old call forms, the old `with self._phase_timing.phase(…)`
block, and two `phase_timing=self._phase_timing` kwargs). No ffmpeg argument
list, filter graph, encoder setting, loudness target, queueing policy, shed
decision or caption string is touched. Nothing about **what is transcribed,
queued, shed or captioned** changes.

**Bounds and safety (the work-item-2 contract):**

* **Always on** by default — an opt-in diagnostic is exactly what blinded 63 of
  87 sheds. The escape hatch is `CIVICAST_CAPTION_TAP_SHED_DIAGNOSTIC` set to
  `0`/`false`/`no`/`off` (case- and whitespace-insensitive); anything else, and
  unset, is **on**.
* **Bounded**: at most one line per channel **per event** per 30 s
  (`DEFAULT_MIN_INTERVAL_SECONDS`), at most 8 batch records retained per channel
  (`DEFAULT_MAX_BATCH_RECORDS`), at most 16 channels and 8 ffmpeg entries
  tracked. Nothing grows without a bound; a suppressed event is counted and
  named in the next line rather than lost.
* **Cheap**: no audio is read, no I/O on the ASR/audio hot path; process/ffmpeg/
  GPU probes are coalesced behind a short cache so a station-wide burst never
  rescans the process table more than once per couple of seconds.
* **Failure-proof**: every public collector method suppresses its own errors, the
  tap *additionally* wraps every call (`_note_shed_diagnostic`), and the log write
  itself is suppressed — a broken diagnostic costs one DEBUG line, never a shed.
* **No new dependency**: `psutil` (>= 6.1.0) and `nvidia-ml-py` (`pynvml`) are
  both already declared runtime dependencies. Each probe degrades to a clear
  `"unavailable"` when its library or driver is missing — the line is never
  dropped for want of a probe.
* **Metadata only**: counts, durations, depths, ages, PIDs, process/device names,
  priority classes. No audio, no speech text, no cue text, no credentials.

**The one deliberate deviation from the brief's wording.** The brief asks for
"≤ 1 line per channel per 30 s". The rate limit is keyed on **`(channel, event)`**
— at most two lines per channel per window. This is not an oversight: the
streak start and the shed it leads to are **exactly one persistence window
(30 s) apart by construction**, so a single per-channel budget would
*systematically* suppress the shed line — the one line the whole diagnostic
exists to produce — on every normal episode. `suppressed_since_last` is carried
in the payload so a genuinely suppressed event is still visible as a count. Two
tests pin this: `test_the_line_is_rate_limited_per_channel_per_event` and
`test_the_two_events_are_rate_limited_independently`, and mutation M1 (§8) proves
the second one fails if the key collapses to channel-only.

## 10. Risks, and what is deliberately left out

* **The line is not free.** It fires at most twice per channel per 30 s during a
  sustained episode and once per rare event otherwise; each firing costs one
  process-table census (cached for a couple of seconds across channels), one
  ffmpeg census and one NVML query. On a box with no NVML driver the GPU probe
  returns `unavailable` immediately. The measured cost on the scan path is: two
  `os.stat`-based queue-age reads per over-limit **episode** (not per batch, not
  per scan), and **zero** when the diagnostic is switched off — the tap gates the
  measurement behind `_shed_diagnostic_active`.
* **The queue-age read stats queued files.** `_oldest_queue_age_seconds` reads
  the mtime of the queued segments. That is metadata-only and happens at the
  event, never on the ASR path — but it is real filesystem work, so it is gated
  behind the on/off switch and measured once per event, and
  `test_the_queue_age_is_measured_once_per_event_not_per_batch` pins that.
* **`process.cpu_pct` is a window average**, computed from `time.process_time()`
  (process-wide on Windows) plus psutil's per-process CPU times over the observed
  wall window. It is a coarse signal by design; `threads` and the ffmpeg census
  are the sharper discrimination between "ASR stalled" and "box starved".
* **The ffmpeg census is box-wide, not children-only**, deliberately — the point
  is to see *other* processes competing with the tap, including the station's
  playout ffmpeg processes, not just this worker's.
* **What U69 does not do**: it does not stop a shed, does not change the backlog
  bound, does not touch the ASR call, and does not add a dependency or a daemon.
  It is instrumentation. If the next shed is a stalled ASR call, this line
  says so and the fix is a separate slice; if it is preparation starvation, this
  line says that too.
* **Two leftover temp files, outside the repo.** `/tmp/u69-launch.err` (0 B) and
  `/tmp/u69-launch.out` (94 B, containing `RUN …\runs\U69-1 PID 31660`) are held
  open by a live process and could not be removed (`Device or resource busy`).
  They are not in the worktree and are not U69 evidence; every other temp file
  this slice created was deleted.
