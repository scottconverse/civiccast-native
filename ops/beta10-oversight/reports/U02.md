### 1.4 Step 3 — does arming minutes early cut the current program short? No (OBSERVED)

`engine.py:2597-2603` (`_on_new_leg_ready`):


### 1.5 The rule implemented

```
lead = max(_ROLLOVER_MIN_LEAD_SECONDS,
           preparation_timeout_seconds_from_env()
           + _ROLLOVER_RELOAD_SETTLE_BUDGET_SECONDS
           + _ROLLOVER_LEAD_MARGIN_SECONDS)          # 120 vs (300 + 30 + 60) = 390s
trigger_at = max(last_segment_start_at, plan_end_at - lead)   # unchanged clamp
```

* `CIVICAST_EGRESS_PREPARATION_TIMEOUT_SECONDS` — 300 at the station and by default → **lead 390 s**.
* `_ROLLOVER_RELOAD_SETTLE_BUDGET_SECONDS = 30.0` (new, automation.py:485) — the post-preparation round
  trip: 5 s ack bound (`strategy.py:99`) + a few ~2 s settlement poll ticks + leg build/preroll.
* `_ROLLOVER_LEAD_MARGIN_SECONDS = 60.0` (new, automation.py:486) — command drain to the daemon's next
  tick and clock granularity.
* `max(...)` against `_ROLLOVER_MIN_LEAD_SECONDS` keeps the historic 120 s floor if a deployment has
  shortened the preparation timeout below 120 s.
* Override: `CIVICCAST_EGRESS_ROLLOVER_LEAD_SECONDS` (positive float). Unset/empty → computed default;
  unparseable → `Invalid ...` WARNING then computed default; `<= 0` → `must be positive` WARNING then
  computed default — matching `preparation_timeout_seconds_from_env`'s bad-input handling (§1.2).
  New public helper `rollover_lead_seconds_from_env()` (automation.py:236, :250-278) returns `float | None`.
* Non-gst path: `_rollover_min_lead_seconds` and the `0.5 * planned_seconds` cap are **untouched**.

**Why 390 s is safe against every existing bound (INFERRED, from the constants in §1.3, arithmetic
shown):** preparation finishes at worst at `plan_end - 390 + 300 = plan_end - 90`, so
(a) the arm→EOS wait is ≤ 90 s ≪ 960 s (`_PENDING_RELOAD_SETTLE_DEADLINE_S`) and
(b) the leg-ready→EOS wait is ≤ 90 s ≪ 900 s (`defer_switch_timeout_s`), and with a cache hit the new leg
simply waits ~380 s prerolled, still well under both. **Threshold worth knowing:** the computed formula
crosses the 960 s daemon deadline when `preparation_timeout > 960 - 90 = 870 s`; an operator who sets the
preparation timeout that high (or sets an override above ~960 s) gets a lead that outruns the daemon's
settle deadline, which would fall back to restart instead of arming in time. I did **not** clamp for
that — the brief specifies the rule, and clamping would silently change what the operator asked for. See
§5.2.

## 4. Doubts — where an earlier rollover could misbehave

1. **A schedule edit inside the now-longer pre-boundary window is missed (INFERRED from the code path;
   the trade-off is inherent to the rule).** The reload's plan is built once, when the daemon drains the
   command — `automation.py:1317-1318` calls `boundary_source_plan_provider(channel_id, max(now, plan_end_at))`
   and the daemon calls it again in `_reload_steps` (`daemon.py:3389`) as the preparation starts, i.e.
   ~2 s later. So the boundary item is sampled ~390 s before the boundary instead of ~120 s before it. An
   item **added or moved into the boundary slot** in that window airs only from the *next* rollover. This
   is a real widening of the exposure window (≈6.5 min instead of 2 min at the station's settings) and it
   is not mitigated anywhere in this unit. If that is unacceptable, the fix belongs in the daemon
   (re-sample the boundary plan at settlement) — a different unit.
2. **Override / preparation-timeout values that outrun the daemon's deadlines (OBSERVED arithmetic,
   §1.5).** A lead > ~960 s, or a computed lead > 960 s (preparation timeout > 870 s), means the daemon's
   `_PENDING_RELOAD_SETTLE_DEADLINE_S` can lapse before the deferred switch settles, and the channel
   takes the `_fall_back_to_restart_reload` path instead. The override is honoured verbatim (no clamp),
   and there is no startup validation of it, so a bad value is silent apart from the
   `_PENDING_RELOAD_SETTLE_DEADLINE_S` WARNING at lapse time. U01's §9 records that the relaunch path is
   separately unhealthy, which makes this worth knowing.
3. **A rollover armed while a previous reload is still settling (INFERRED, code paths unchanged).** The
   dispatch latches (`_rollover_issued`, `_rollover_issued_at`) plus `has_pending_reload_settlement`
   (`daemon.py:3271`) already prevent a second dispatch while one is preparing or armed, the daemon
   discards a superseded settlement (`daemon.py:3623-3626`), and an operator takeover supersedes via its
   own `_request_reload` → `_cancel_preparation`. So the *state machine* is unchanged; what my change
   does is hold that state for up to 390 s instead of 120 s, which is a longer window in which a
   concurrent operator action meets an in-flight rollover. I found no path where that is mishandled, but
   I did not test it (see 4.5).
4. **The slate / FALLBACK_SLATE path (NOT TESTED, code path shared).** The gst branch is not gated on
   `state == "ON_AIR"`: `_check_plan_rollover` accepts `{"ON_AIR", "FALLBACK_SLATE"}` (`automation.py:1003`)
   and a finite filler horizon carries its own `plan_end_at`, so a filler rollover now also arms up to
   390 s early, waits (deferred, per `should_defer_switch`'s `FALLBACK_SLATE and plan_end_at is not None`
   clause) for the filler horizon's EOS, and does not cut filler short. Filler preparation is a slate
   render rather than a conform, so the longer lead costs nothing real — but I added **no test for the
   fallback+gst shape**; the gst tests I added are all ON_AIR. Test blind spot, stated deliberately.
5. **What I did not test at all:** any real GStreamer behaviour (no `gi`/bundled runtime here), the
   engine's actual defer-then-commit, the daemon's settle poll, and any live on-air run. My proof is
   unit-level: the automation-side trigger boundary, the override semantics, and the clamp. The
   end-to-end claim "the station no longer goes dark" is **not** proven by this unit — it needs a watched
   run (the brief's own 30 min → 2 h → 4 h → 8 h ladder).
6. **`_rollover_min_interval_seconds` interaction, checked by hand not by test (INFERRED).** The cadence
   floor (`min(300, max(1, 0.5*planned))`, automation.py:856-898) is measured from the last dispatch, while
   the lead moved earlier. For a gst plan the floor is always ≤ half the plan, and consecutive plans are
   contiguous, so a trigger at `plan_end - 390` (or at the last segment's start for a plan shorter than
   390 s) is never further than one plan from the previous dispatch and the floor cannot starve it —
   same conclusion the pre-existing cadence tests (`TestRolloverCadence`) pin for the non-gst path, which
   I left untouched. No new test covers the gst-path floor explicitly.
7. **Comment debt I did not chase:** `automation.py:1516`-region comments and U01's own text describe the
   rollover lead as "up to `_ROLLOVER_MIN_LEAD_SECONDS`" in the deferred-start anchoring logic
   (`_establish_horizon_from_dispatch`, automation.py:1531-1554). That code uses
   `_rollover_min_lead_seconds(previous_planned_seconds)` as its poison bound and is **unchanged** — but
   the *prose* around it now understates the real gst lead (390 s). I left the behaviour alone on purpose
   (it is a bound against a poisoned `previous_end_at`, not a lead) and flag the prose as stale.
