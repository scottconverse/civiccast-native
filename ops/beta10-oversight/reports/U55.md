## Item 1 — the classifier

### 1a. The mapping from a VTT cue time to wall clock (the whole problem)

**OBSERVED — a VTT cue time is a tap-chunk COUNTER, not media time.** The worker
builds each tap chunk as `start = index * self._segment_seconds`
(`civiccast/captions/tap_worker.py:2379`, inside `_read_chunk`), where `index` is
read from the file name by `_SEGMENT_RE` (`tap_worker.py:102`), and the pattern is
`TAP_SEGMENT_PATTERN = "chunk-%06d.wav"` (`civiccast/captions/tap.py:21`). So the
captions the worker emits for chunk *N* carry a counter of `N * segment_seconds`
(5.0 s), and `active.vtt` carries those raw counters — hence the file's own
`126:43:13.850` for a meeting only hours old. There is **no `X-TIMESTAMP-MAP`** in
the file, and `format_webvtt_timestamp` allows 2+ hour digits, so the hour field is
`\d{2,}`, not `\d\d`.

**The mapping chosen, and why:** the newest `chunk-NNNNNN.wav` in
`<tap root>\<channel>\`, with

```
anchor            = mtime(chunk-N.wav) − (N + 1) × duration
epoch(counter)    = anchor + counter
```

A chunk is published only once the segment **before** it is complete, so the file's
mtime is the end of counter `(N+1) × duration`. `duration` is read from the WAV
header (`wave.open(...).getnframes() / getframerate()`), not from
`CIVICAST_CAPTION_TAP_SEGMENT_SECONDS`, so the mapping carries the file actually on
disk. The tap root comes from `CIVICAST_CAPTION_TAP_DIR`
(`tap_worker.py:1852 channel_dir = self._tap_root / channel_id` — the env var is the
ROOT, not the channel dir); the channel's VTT is derived from the receipt's own
`log` path, `<egress>\<ch>`, so no extra configuration is invented.

**OBSERVED — the anchor is stable enough to classify 20-minute-old evidence.**
`anchor_now.py`, every chunk's implied anchor, the live dir and the processed tail
kept separate:

```
LIVE dir (what the tool globs): 2 chunk(s), indices 91498..91499
  implied anchors 1790027649.121 .. 1790027649.294  spread 0.174 s
PROCESSED dir: 14952 chunk(s), indices 0..91471
  its oldest index is 0 at 2026-09-14 23:55:22 -- a previous session, so its counters are a DIFFERENT epoch
  the newest 24 of them (indices 90901..91471, 22:09:19..22:56:49):
  implied anchors 1790027649.133 .. 1790027649.319  spread 0.186 s  (median 1790027649.258)
segment duration from the wav header = 5.0 s
```

Two chunks 5 s apart and twenty-four spanning 47 minutes agree to within 0.19 s, and
the live pair agrees with the processed tail — which is also the **OBSERVED** proof
that `processed/` preserves mtime through the move. (A pre-compaction run of the
same probe over 446 chunks / 37 min gave a 0.099 s spread.)

**OBSERVED — `processed/` is NOT a single epoch, which is why the rule below is
load-bearing.** It holds 14952 chunks and its oldest index is **0**, from
2026-09-14 — a previous session. So its counters restart and its anchors are
meaningless in aggregate (over all 14953 chunks on disk the naive spread is
575931.671 s ≈ 6.7 days). Nothing may ever be read from `processed/`.

**OBSERVED — only the NEWEST chunk may be used**, because the counter restarts at 0
in a new session. That is safe because every chunk visible in the *live dir* **is**
this session's: `_discard_settled_segments` unlinks a channel's leftovers at session
start (`tap_worker.py:1841`), and `_settled_segments` documents that GStreamer
publishes `.wav.partial -> .wav` atomically, so every visible WAV is complete
(`tap_worker.py:2350`). The tool globs the live dir only and picks by highest index.

**OBSERVED — the live dir held just 2 chunks** (91498, 91499) when the probe above
ran, while `processed/` held 14952. That is the whole reason item 2b's retry exists:
a single-shot glob is racing a directory that routinely holds one or two files and is
empty a quarter of the time.

### 1b. What the classifier does

`caption_outage()` is **deliberately unchanged** (rung_check.py, the coordinator's
13:40 tightening — "quiet is excused only on POSITIVE evidence … missing evidence is
not a pass" — is intact). The new hook runs only *after* it has declared an outage,
and can therefore only convert a would-be `BAD` into a listed `OK` note:

```python
outage, why = caption_outage(path, c, v)
if not outage:
    quiet.append(f"{c}:{CAPTION_QUIET}({quiet_detail(v)})")
    continue
# U55: an outage the ASR's OWN output explains is a quiet source, not a broken
# station ...
excuse = no_speech_source(path, c, v)
if excuse is not None:
    quiet.append(f"{c}:{NO_SPEECH_SOURCE}({excuse})")
    continue
bad.append(f"{c}:{k}={st}({why})")
continue
```

`no_speech_source()` returns `None` — i.e. the outage stands — unless **all** of:

* the worker receipt is not `ZERO` (the station's own `received=0` is a positive
  outage sign and is never excused);
* the receipt is not a fresh `OK` (`RECEIPT_FRESH_SECONDS = 150.0`) — a fresh
  receipt says captions WERE injected, so silence is not the source's doing;
* the verify's own `caption_cues(v) == 0`;
* an anchor exists and the window maps into counter space;
* `active.vtt` parses non-empty;
* **no cue overlaps the window** — if the ASR spoke inside the window and none of it
  reached the video, that is a real FAIL and stays one (the case that matters);
* there is a cue **before AND after** the window (an unbounded gap is a dead ASR,
  not a quiet room);
* the gap reaches `ANCHOR_SLACK_SECONDS = 30.0` past **each** end of the window.

## Doubts

1. **The printed gap start wobbles by 1 s** between runs (`22:32:28` vs `22:32:29`)
   because the anchor inherits the chunk mtime's sub-second quantisation. It is
   absorbed by the 30 s slack and does not affect any verdict, but the line is not
   reproducible to the second across invocations.
2. **The excusal applies to any non-fresh receipt that is not `ZERO`**, including a
   status that might one day mean "the worker crashed". The VTT test still has to
   show a *bounded* gap containing the window, and a crashed worker produces no cue
   after the window → fail closed. Residual risk is small but real.
3. **The retry can block the rung up to 6.0 s per channel** on the excusal path.
   That path is only reached after `caption_outage` has already declared an outage,
   and it buys the removal of a ~20–50 % false-FAIL rate, but it is a latency
   trade and should be said out loud.
4. `active.vtt` is read whole — **OBSERVED** 105242 bytes — rather than tailed as
   the brief suggested; at an 11-minute cadence that is irrelevant today, but it is
   not the tail the brief asked for and it will grow with the session.
