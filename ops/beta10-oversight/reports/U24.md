## 1. Why Part A exists

Two incidents this unit found on the live station, both in the beta.10 line, both read off the station's own logs — the station was read, never touched.

**Incident 1 — the relay child's stderr went nowhere.** `_default_starter` (`civiccast/egress/hls_relay.py:1848`) called `start_ffmpeg(args)`, and `start_ffmpeg` (`civiccast/stream/_ffmpeg.py:563`) defaulted `stderr` to `subprocess.DEVNULL`. So the one component that knows why a relay is unhappy — its ffmpeg child — had its entire diagnostic channel discarded. When a relay rebinds, or dies, or is respawned, the supervisor's log line says *that* it happened and nothing about *why*.

**Incident 2 — the two failures that took the longest to diagnose had no child-side evidence at all.** Both were HLS relays that repeatedly rebind, and in both the supervisor's own lines were consistent with several different child-side causes. The distinguishing evidence — ffmpeg's own complaint, one line, in its own words — did not exist on disk. It was in the child's stderr, and the child's stderr was `/dev/null`.

The fix is deliberately small in surface: keep the child's stderr, in a file, per channel, bounded, with the child's argv recorded alongside it, and never let the capture path be a reason a relay stutters.

This is not a new idea in the codebase — it is the idea `civiccast/stream/_ffmpeg.py` already offers via `stderr_path` and that every other ffmpeg caller in the tree already uses. The relay was the caller that didn't.

## 2. Part A design

### 2.1 The path

One file per channel **and per sink label**, at
`<log_root>/<channel_id>/logs/hls-relay.<label>.stderr.log`,
plus one rotated predecessor at `…stderr.log.1`.

- `_relay_log_path` (`hls_relay.py:1290`) builds it. `log_root` comes from the daemon's own work directory: `civiccast/egress/daemon.py:1712` (`log_root=self._work_dir`) and `:4107` (`self._hls_relay.apply(config, log_root=self._work_dir)`). The daemon change is confined to those wiring lines plus the tick (§2.3) — it does not invent a second logging system.
- **No `log_root` means no change in behaviour**: with `log_root=None` the supervisor writes no file and calls the starter with exactly one positional argument, so every existing test double that accepts only `args` keeps working. That back-compat is asserted (`tests/egress/test_hls_relay_stderr_log.py:669`, `:687`).
- The label is sanitized through `_relay_log_component` (`:563`): `re.sub(r"[^A-Za-z0-9._-]+", "_", value).strip("._-")`, then truncated to `HLS_RELAY_LOG_STEM_MAX` (40). A sink label is operator-supplied text, so it must not be able to choose a directory: `sink="../../../../etc"` collapses to a single flat component. Asserted at `:573`.

### 2.2 The header

The first line of every log is one `_relay_log_header` line (`:584`), written **once per spawn**:

```
[hls-relay] pid=---------- utc=2026-09-25T00:00:00.000000Z channel=gov sink=Web spawn=1 reason=start argv=["-hide_banner", …]
```

- `pid` is first because it is the field an operator greps for. It is written as the ten-dash placeholder and **stamped in place** by `_stamp_relay_log_pid` (`:1373`, called at `:1221`) once `Popen` returns the real pid — the header cannot be written before the spawn and the pid does not exist before the spawn. `_LOG_PID_PLACEHOLDER = "-" * _LOG_PID_WIDTH` (`:206`–`:208`).
- `utc` is a zero-padded 10-digit microsecond stamp.
- `reason` is an enum, not free text: `start | rebind | uri-change | respawn-dead | self-heal | stream-restore`. An operator filtering on it gets a stable set; a new reason is a code change, not a spelling.
- `argv` is the child's full argv as JSON — the field that turns "the relay restarted" into "the relay restarted with *these* flags", which is the whole point of Incident 2.
- `_one_line` (`:615`) flattens any value that could contain a newline, so a hostile or merely odd value cannot forge a second header line.
- The header is appended with `newline="\n"` (§2.3) so the separator bytes are the same on this platform as everywhere else, and the file is opened in append mode — `path.open("ab")` for the header write, so the header cannot truncate a predecessor's content.

### 2.3 The cap — and the U24.1 rewrite

**Cap:** `HLS_RELAY_LOG_CAP_BYTES = 5 * 1024 * 1024` (`:194`), with the derivation in the comment block at `:180`–`:193` and the reachability figures in §2.4. **Retained tail:** `HLS_RELAY_LOG_TAIL_BYTES = 1 * 1024 * 1024` (`:199`). **Worst-case retained set:** 30 MiB — a 5 MiB log plus a 1 MiB tail for each of the five channels the station's own configuration declares.

The first cut enforced the cap the obvious way: the child wrote the file directly (a handle inherited from the parent, opened append-mode), and the supervisor rewrote the file in place on its poll tick. That is the architecture U24.1 reversed, for the reason in §3.1. It is described here only so the reader can see what changed.

**The U24.1 architecture — the parent owns the file:**

- ffmpeg's stderr is `subprocess.PIPE`. `start_ffmpeg` grew a keyword: `stderr_pipe: bool = False` (`_ffmpeg.py:568`), used at `:620` (`stderr=subprocess.PIPE if stderr_pipe else (stderr_file or subprocess.DEVNULL)`), with the pipe exposed on the handle as `stderr_pipe: IO[str] | None` (dataclass field `:112`, populated at `:630`). The pre-existing `stderr_path` path is untouched — every other ffmpeg caller in the tree behaves exactly as before.
- **One daemon drain thread per relay child**, `_RelayLogWriter` (`hls_relay.py:649`), constructed at `:1224` and started at `:1229`, held on the relay as `log_writer` (`:962`, set at `:1241`). `_drain` (`:750`) reads the pipe in `readline(_RELAY_LOG_READ_CHARS)` chunks (`:623`, 64 KiB — a chunk-limited read, so a child that emits a megabyte with no newline cannot make the thread allocate a megabyte), writes each chunk to the file **it owns the only handle to**, and exits at EOF. Its blocking calls are exactly two: the read, and a local file write. Nothing else in it can wait.
- **The thread trims its own file.** `_append` (`:769`) tracks a byte estimate and calls `trim_if_over_cap` (`:823`) the moment it crosses the cap; that method `stat`s the real size (the estimate resyncs from `stat` on every check, so a `stat` failure or an external truncation cannot make the estimate drift into a permanent false negative), and if the file is over the cap it closes its **own** handle, calls `_rewrite_to_tail` (`:853`), reopens, and resyncs. Because the thread holds the only handle, the rewrite is safe: no second handle exists with its own file position.
- `_rewrite_to_tail` preserves the header by **reading the first line back out of the file** — `_relay_log_header_line` (`:632`) — rather than from a remembered string, which is what makes the in-place pid stamp (§2.2) survive the rewrite. It seeks `max(0, size - tail_bytes)` from the end, drops the first partial line, and writes header + tail with `path.open("wb")`.
- **Write failures never stall the relay.** `_open_append` (`:785`) sets `_discarding` and warns once if the file cannot be opened; `_append` swallows `OSError`, calls `_note_write_failure` (`:807`) and returns; `_note_write_failure` logs **one WARNING per episode**, not one per line. `_drain` keeps reading in every one of those cases — a relay must never be back-pressured by its own log. Asserted at `:631` and by mutant E (§4).
- **The trim WARNING is one line per trim, not per tick.** This is the operator-facing repair in U24.1 as much as the NUL fix: in the first cut the file grew without bound, so it was over its cap on every tick and the supervisor logged a WARNING *every tick* while the retained content was mostly zero padding. An operator-facing "bounded log" that is unbounded, mostly NULs, and warns continuously is worse than no log.
- **`maybe_trim_logs` (`:1395`) is now a belt to the writer's braces**, and its docstring says so: the writer trims in-thread the moment it crosses, so a tick usually finds nothing to do. It stays because the writer's check can only run when it *appends* — a file left over the cap with the child gone quiet would otherwise sit there until the next spawn. The tick retries it and its return value is the count the daemon reports (`daemon.py:2691`, `:2700`, `:2726`). It takes the writers out under `self._guard` before trimming so it cannot race a writer's own trim.
- **The thread ends with the child, and never outlives it.** `_drain` breaks at EOF; `_close_quietly` (`:900`) and `close` (`:730`) join with `_RELAY_LOG_DRAIN_JOIN_S = 2.0` (`:629`), and if that join times out they **warn and release the handle anyway** — "the log file is released anyway and the relay is NOT affected". `join` (`:722`) is exposed separately. `_terminate_relay` (`:1424`) terminates the child first, so the pipe reaches EOF and the join is short; measured at +0.0004 s (§3.4, proof 3).
- **Unchanged from the first cut, deliberately:** the header format, the path, the cap and tail numbers, rotation-at-spawn (`_begin_relay_log` `:1306`, `_rotate_relay_log` `:1351`), and the no-restart-on-trim property. Rotation still runs at spawn and still needs the predecessor's handles closed, which is why it runs after terminate — asserted at `:698` (`WinError 32` otherwise).
- **The `newline="\n"` detail.** The parent now writes the file, and the parent's text layer would otherwise translate `\n` to `\r\n` on Windows. The child's own handle did not, so a CRLF here would silently double every separator byte and change what line-oriented readers see. `_open_append` passes `newline="\n"` and `errors="replace"` (a non-UTF-8 byte from the child becomes U+FFFD rather than raising inside the drain thread — an exception there would surface as a `PytestUnhandledThreadExceptionWarning` and, under this repo's `filterwarnings = ["error", …]`, as an error).

### 2.5 Windows handle behaviour — what the first cut claimed, and what is actually proven

The first cut's docstring carried this claim:

> measured on Windows: append-mode ffmpeg writes after a rewrite continue from the new size.

**That claim is false, and U24.1 exists because it was false.** The full diagnosis, the test that let it stand, and the fix are §3. The property that replaces it is not a docstring claim at all: in U24.1 there is **no second handle**. The parent owns the file; the child never holds it; the pipe is the child's only output path. The rewrite hazard — two handles, two file positions, one of them stale — cannot arise because the second handle does not exist. That is a code-path property, and it is *also* now backed by a volume measurement through a real child (§3.4, proof 2), which is the part the first cut lacked.

Two Windows behaviours that are real, and are asserted rather than assumed:

- **`WinError 32` on rotation.** Opening or renaming a file that another handle still holds open fails on Windows. Rotation therefore runs at spawn, after the predecessor has been terminated and its handle released (`:698`; mutant D, §4).
- **The drain thread must not be able to stall the child.** A Windows anonymous pipe has a bounded buffer; a full pipe blocks the writer. Since U24.1 the parent drains continuously, so the property to prove is the reverse of the first cut's worry — that the draining keeps up. Proof 2 measures it (§3.4).

## 3. The U24.1 defect, the test that hid it, and the fix

### 3.1 The defect

The coordinator's finding, OBSERVED and reproducible: **`_trim_relay_log`'s docstring said "measured on Windows: append-mode ffmpeg writes after a rewrite continue from the new size". They do not.**

Reproduction with this worktree's venv and the real `civiccast.stream._ffmpeg.start_ffmpeg(args, stderr_path=p)` (ffmpeg 8.1.1, `-loglevel debug`, lavfi sine, 12 s) — `staging/U24/evidence/u24-trim-hole/trimtest.py`. After 5 s the file is rewritten in place (`"wb"`, header + 2000-byte tail), exactly as `_trim_relay_log` did:

```
before 5663 after_trim 2007 1s later 5809 final 5882 NULs 3656 first_nul_at 2007
```

The mechanism: **the child's handle keeps its own file position.** The CRT's `O_APPEND` emulation is per-process state, living in the parent process, not in the OS handle the child inherits. So when the parent rewrites the file, the child's next write lands at its **old** offset, and everything between the new end-of-file and that offset is zero-filled by the filesystem.

Three consequences, all of them operator-visible on the live station:

1. **The cap bounded nothing.** The file's size equals the child's total bytes ever written, because the child keeps extending the same handle at its own offset. A "5 MiB cap" over a child that writes 50 MiB is a 50 MiB file.
2. **The trim fired on every tick.** The file was permanently over the cap, so `maybe_trim_logs` trimmed — and WARNINGed — on every poll. The station's log would fill with the trim warning itself. (That warning is the one recorded in the red run of §3.4: `… passed its 49152-byte cap (69329 bytes); trimmed to the spawn header plus the newest 16384 bytes. The relay child was NOT restarted; if this repeats every tick the child is logging a storm -- read the file.`)
3. **The retained content was mostly NULs.** Rewriting to "the newest 1 MiB" left a tail that the child's next write turned into a hole: the newest bytes *by position* were zeros. So the file that Part A was built to make diagnostic was, past its first trim, mostly unreadable padding — including in precisely the storm case the cap exists for.

### 3.2 The test and the measurement that supported the docstring claim, and why they passed

The brief asks for these to be named. There are three artifacts, and each failed to reach the hazard for its own reason.

**(a) The cap test — `tests/egress/test_hls_relay_stderr_log.py:235` at `3ad288ed`:** `test_the_log_is_trimmed_to_the_cap_keeping_the_header_and_the_newest_lines`. This is the test that "proved" the cap. Its body writes the storm **from the test process itself**, in the same process that then trims and reads back:

```python
noise = "x" * 200 + "\n"
with path.open("a", encoding="utf-8") as handle:
    for _ in range((2 * HLS_RELAY_LOG_CAP_BYTES) // len(noise)):
        handle.write(noise)
    handle.write("THE NEWEST CHILD LINE\n")
assert path.stat().st_size > HLS_RELAY_LOG_CAP_BYTES
trimmed = sup.maybe_trim_logs("gov")
assert trimmed == 1
assert path.stat().st_size <= HLS_RELAY_LOG_CAP_BYTES
assert body[-1] == "THE NEWEST CHILD LINE"
```

**Why it passed:** every assertion reads the file's **quiescent state after the rewrite**. There is no second handle and — decisively — **no writer left running**: the storm handle is closed before `maybe_trim_logs` is called, and the test double's "child" has already stopped. The hazard needs a live writer with a stale position to write *after* the rewrite; this test has nothing writing after the rewrite at all. `assert path.stat().st_size <= HLS_RELAY_LOG_CAP_BYTES` therefore passes trivially, and `body[-1] == "THE NEWEST CHILD LINE"` passes because that line was written *before* the trim and survives as part of the retained tail. The one property the docstring claimed — what a still-running child does on its **next** write — was asserted by nothing in the file.

**(b) The test double — `_LoggingStarter` at `:86`:** it writes its lines into the path *inside the test process* (`stderr_path.open("a")`, then write, then close) and then stops. So even the fake "child" was quiescent, and its appends carried the **parent's** `O_APPEND` semantics, because a Python file object opened by the parent is exactly the case the CRT emulation covers. A double cannot reproduce an inherited-handle file position; that is the whole defect.

**(c) The real-child test — `:366`, `test_a_real_child_appends_its_own_stderr_to_the_file_the_starter_was_given`:** a real ffmpeg, through the real starter, with a real header — but 5 s of `testsrc2` at `-loglevel debug`, which the unit's own measurement puts at **24,233 B**, against a 5 MiB cap. **It never crossed the cap, so it never triggered a rewrite, so it could not see the defect.** Its docstring said so explicitly — "the child exits on its own with no writer draining anything" — and it asserted the no-pipe shape as a *feature*: *"The no-pipe property is a property of the code path instead: `start_ffmpeg` opens `stderr_path` in append mode and passes that handle to `Popen`, never `subprocess.PIPE`."* That is the assertion U24.1 reverses, and it is the reason this test was replaced rather than extended.

**(d) The volume measurement — `evidence/loglevel/` and `summary.json`:** these runs wrote ffmpeg's stderr straight to a file with **no supervisor and no trim**, and their two timed runs are 8.64 s / 6,949 B and 2.09 s / 30,744 B — both far under any cap. They measure *volume*; they never measure a post-rewrite append. Generalizing them into "append-mode writes after a rewrite continue from the new size" was an extrapolation from a trim-free observation, and the docstring's "measured on Windows" is true only of the part that was measured (append-mode writes, uninterrupted).

**Verdict:** the docstring's claim was never tested. The cap test proved the *bookkeeping* (one trim happened, the header survived, the tail was retained, the child was not restarted) and passed because it examined a file nothing was still writing to. The unit's own memory rule was then written from this: **never size a test's write from a constant a mutation can change**, and — the lesson here — **a cap test is only a cap test if a live writer is still writing when the cap is crossed.**

### 3.3 The fix

`c363a4a0` — `fix(egress): let the parent, not the child, own each relay's stderr log`. Architecture in §2.3. In one line: **ffmpeg stderr becomes a `subprocess.PIPE`; one daemon `_RelayLogWriter` thread per relay child owns the only handle to the file, enforces the cap in-thread, discards rather than stalls on write errors, and ends at EOF.** The supervisor's `maybe_trim_logs` is demoted to a belt on the poll tick. `start_ffmpeg` gained `stderr_pipe=`. Header format, path, cap numbers, spawn rotation and the no-restart-on-trim property are unchanged.

The commit is 501 +/98 − in `hls_relay.py` and 30 +/− in `stream/_ffmpeg.py`; it does not touch `daemon.py`.

## 14. A process incident, recorded honestly
