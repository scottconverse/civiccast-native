## 1. In plain English

**Part 1 — a real defect.** The native installer writes the station's environment to the
service registry under a **doubled-C** prefix: `CIVICCAST_` (that is the spelling in
`civiccast/egress/env_vars.py`, the module that documented the bug class). Three switches
shipped by the last three units were read by the code only under the **single-C** spelling
`CIVICAST_`:

| unit | variable | what it does |
|---|---|---|
| U68 | `CIVICAST_EGRESS_PREPARE_LOW_PRIORITY` | demote on-air conform ffmpeg children to below-normal priority |
| U69 | `CIVICAST_CAPTION_TAP_SHED_DIAGNOSTIC` | the always-on shed diagnostic switch |
| U70 | `CIVICAST_WHISPER_LIVE_TEMPERATURE_FALLBACK` | restore the fallback temperature list on the live tap |

An operator who sets them **the way the station sets everything else** sets
`CIVICCAST_…`; the code read only `CIVICAST_…`; the switch was **silently inert**. The two
strings render almost identically in most fonts — that is the whole reason the defect
survived three reviews. Every spelling in this fix was checked by **measurement**
(`len(prefix)`, `str.count`), never by eye.

Each reader now goes through the **existing** `civiccast.egress.env_vars.resolve_renamed_env`
helper (the U03 implementation — reused, not copied). The doubled-C name is primary; the
single-C name keeps working as a documented legacy fallback; when both are set the
doubled-C one wins and both spellings are named in the one-time warning. **No other one-C
variable in the repo was touched** — a repo-wide sweep of the U68/U69/U70 diff
(`git diff release/beta10..beta10-u70 -- '*.py'`) finds exactly three new env-var names,
and all three are fixed.

**Scope finding (a correction to the brief).** The brief also listed
`CIVICAST_CAPTION_TAP_PHASE_TIMING` under U69. That switch was **already** doubled-C in the
code at base (`civiccast/captions/phase_timing.py:60`,
`PHASE_TIMING_ENV_VAR = "CIVICCAST_CAPTION_TAP_PHASE_TIMING"`). Only two *stale comments*
(a docstring in `tap_shed_diagnostic.py` and a comment in `tap_worker.py`) named the
single-C form; those were corrected. Its tests already pin the literal. **No legacy alias
was invented** for a variable that never had a second spelling — inventing one would create
a third spelling for a switch the station has always set correctly.

**Part 2 — diagnostic only, no behaviour change.** U70 established that the diagnostic's
`asr_s` spans `worker.process_batch` = transcribe **+ stabilize + HLS publish +
review_persist**, so a 14 s `asr_s` is not evidence of a 14 s decode. The retained batch
record now carries four more numbers so the *next* live shed says where the seconds went:

- **`transcribe_s`** — wall time inside the model call **plus consuming its lazy segment
  generator**. faster-whisper decodes while you iterate the generator, so timing the call
  alone would report a decode that took no time. The timer wraps the iteration.
- **`persist_s`** — `asr_s − transcribe_s − stabilize_s`, derived by the collector.
  `None` unless **both** terms are known: a residual with a missing term is a wrong number,
  not a smaller one.
- **`duration_after_vad`** — faster-whisper's `info.duration_after_vad`, the audio the VAD
  kept. It is the honest denominator: a long `transcribe_s` over almost no post-VAD audio is
  a stall, not a long file.
- **`max_segment_temperature`** — the highest per-segment decode temperature. U70's finding
  is that a value **above `0.0` is exactly iff the fallback list was walked**; with U70's
  `temperature=0.0` bound the live tap should always report `0.0` (single pass) or `None`
  (no segments). This field proves that bound on the air.

The runtime keeps the numbers in a **`threading.local`** slot, because one runtime instance
serves every channel and each channel decodes on its own executor thread — a plain
attribute would let one channel's numbers land on another channel's batch record. The tap
reads the slot on that same thread immediately after `process_batch` returns and copies
plain numbers out; the record holds **no reference to audio or segment objects**. A runtime
that publishes no metrics, a getter that raises, and a zero-segment decode all yield explicit
nulls. `asr_s` keeps its old meaning and value; the four pre-existing fields are untouched.

## 4. What I could NOT measure

1. **No live observation of the new fields.** Nothing was installed, so `transcribe_s`,
   `persist_s`, `duration_after_vad` and `max_segment_temperature` have **never been
   emitted by the running worker**. The brief's promise — "the next live diagnostic says
   WHERE the 8–15 s go" — is a *design* claim, proven only against fakes. Its live value is
   a prediction.
2. **Same-thread delivery on the real path.** That the tap reads the runtime's thread-local
   slot on the same thread that decoded is proven by construction (the tap consumes the
   generator inline on the channel-executor thread) and by a fake; it is not observed on the
   station. If the real runtime ever moved the decode to a different thread than the tap's
   `process_batch` call, the fields would read `None` — absent-safe, never wrong, but absent.
3. **`duration_after_vad` from the station's actual library version.** The field is read via
   `getattr(info, "duration_after_vad", None)`, so an older faster-whisper yields `None`
   rather than an error — but the real value on the station's pinned version is unobserved.
4. **`persist_s` cannot separate HLS publish from review_persist.** It is defined as
   "everything in `process_batch` that is not transcribe or stabilize" — which is what the
   brief asked for, but it means a publish stall and a persist stall still share one number.
   If the next live evidence needs them apart, that is another slice.
5. **The live incidence of a walked temperature list** — carried forward from U70 §6; this
   unit adds the field that *would* answer it (`max_segment_temperature`) but does not
   answer it, because nothing is on the air.

## 5. Risks / judgement calls

| item | assessment |
|---|---|
| A rename breaks an operator who set the single-C name | The single-C name still works (legacy path in `resolve_renamed_env`) and warns once. Both-set → doubled-C wins, both named in the warning. |
| A second resolver creeping in | None written: all three readers call `civiccast.egress.env_vars.resolve_renamed_env`. The captions modules import it **lazily inside the function**, because importing `civiccast.egress.env_vars` executes the heavy `civiccast.egress` package, which is on the captions import path (precedent: `tap_worker.py` already defers its egress imports). |
| The new fields cost the hot path | Two scalar reads per retained batch; a `dict` per decode. Bounded, and only on the shed-diagnostic path. Never breaks the tap: every hook is wrapped in the same try/except → `_LOG.debug(exc_info=True)` discipline as U69. |
| `persist_s` derived from rounded terms | `_round` clamps at ≥ 0, consistent with its four sibling fields. A physically impossible negative (a fabricated `transcribe_s` larger than the batch's `asr_s`) clamps to `0.0`; this was observed only as a *fake* artifact and cannot occur on the real path, where `transcribe_s ⊆ asr_s` by construction. Kept for consistency rather than special-casing. |
| The "two C's" vocabulary | The phrase is the repo's **existing** term for `CIVICCAST_` (it originates in `civiccast/egress/env_vars.py:10`, before this unit). It is loose — the literal prefix has three C's — so every machine check in this change asserts the **prefix length** (9 vs 8), not a C-count, and the tests are named `..._is_the_two_c_one` in the house style. Deliberately **not** re-worded here: forking the vocabulary in U71 alone would be worse than consistency with the module that owns the concept. |
