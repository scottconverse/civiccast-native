## 1. What was built, and what was deliberately not

While a single channel pass is running, one daemon watcher thread wakes every
`min(threshold, repeat, 5.0)` seconds and asks whether a report of that pass is due: one threshold
after the pass began, then one repeat after each report. A due report dumps the **automation
thread's live Python stack** at WARNING; when a pass that tripped the watchdog ends, one WARNING
line reports its total duration. Every other behaviour of the pass, the loop, the daemon and the
rollover logic is untouched.

coordinator's fixes in §12):

## 7. Doubts and disclosures

The brief asks specifically about two: **could the watchdog itself stall, and could it spam the
log?**

### 7.1 Could the watchdog stall?

- *The dump is the watcher's own work.* `sys._current_frames()` copies the interpreter's frame map
  (bounded by thread count, microseconds); `traceback.format_stack(frame)` walks one stack, bounded
  by its depth, and reads no locks the pass holds. It takes no daemon lock, touches no store, and
  never joins or interrupts the automation thread. The automation thread is therefore never
  *blocked* by the dump — it keeps running while its stack is read, which is the whole point.
- *The one real sharing point is `logging`.* Emission happens on the watcher thread after the
  watchdog's own lock is released, but Python's logging module serialises handler emission behind
  its own module-level lock. If a handler on this logger ever *blocked* (a wedged file share, a
  network handler), the watcher would block inside the handler — reporting would stop silently
  until it returned — and the automation thread's own log calls could queue behind it. This is a
  property of `logging`, not new coupling to the pass, but U04 does add a second thread that emits
  on this logger, so it is a new contributor to that contention. On this host no handler blocks
  (17 tests complete in ~3.7 s). If it ever matters, the fix is a dedicated logger/handler or a
  capped stack depth, not a change to `_run_channel_pass`.
- *`stop()` is bounded and never unbounded-waits.* `stop(timeout=5.0)` sets the stop event and joins
  with a timeout. The watcher's sleep is `Event.wait(interval)`, which is interruptible, so in
  practice it returns immediately. If a join ever timed out, `_thread` is deliberately left set so
  a later `start()` cannot double-spawn — the cost of that choice is that a subsequent
  `run_forever` on the same service object would run **watchless** rather than with two watchers.
  That is a deliberate trade (silent, safe) and is stated here because it is not visible in a test.
- *The pass-side calls cannot stall or fail a pass.* `pass_started`/`pass_finished` take only the
  watchdog's tiny lock and are wrapped in `except Exception` → `DEBUG`; `pass_finished` runs in a
  `finally`, so it cannot swallow or relabel a pass's own exception. Exercised by
  `test_a_failing_clock_never_raises_into_the_pass`.
- *Three ways the watchdog could still raise were found and closed, not just reasoned away.* The
  review in §10 reproduced them: an interval `Event.wait` cannot take (a raise from the loop
  **condition**, not the guarded body); the guard's own fallback log call, when a handler raises
  `RecursionError` while the logger is at DEBUG; and `Thread.start` failing outside `run_forever`'s
  `try`. Each is now fixed and each fix has a test that was red first. The residual, stated plainly:
  a `BaseException` (a `KeyboardInterrupt`) still propagates out of the watchdog's guards, as it
  does from any Python code — that is not the watchdog's to swallow, and `run_forever`'s own
  handling of it is unchanged by this unit.

### 7.2 Could it spam the log?

- *Rate is fixed, not free-running, and now stated as arithmetic.* Exactly one dump per repeat
  interval while a pass is over threshold, and one pass-end line per pass: a stall lasting `D`
  seconds is ≈ `D / repeat` dumps. At defaults (30 s / 60 s) an 8-hour stall is ~480 dumps of ~25
  lines ≈ 12k lines ≈ ~1 MiB; at a mistyped `repeat=0.001` the same stall would be ~29 million
  lines, which is why the reader's docstring now states the arithmetic rather than leaving it to be
  discovered. The live station's control-plane log rotates at ~10 MiB with 6 backups (OBSERVED:
  `control_plane-app.log.1` … `.6` are each 10,485,7xx bytes), so at the shipped defaults one stall
  can at most roll the log once — the diagnostic cannot fill the disk. (The rotation *policy* — cap
  and backup count — is INFERRED from those sizes; I read the files, not the logging config.) No
  floor was added on the repeat value: short repeats are what this unit's own tests use, an operator
  measuring a suspected stall may legitimately want them, and the off switch covers the rest. That
  is a deliberate choice for the coordinator to revisit if the station's log budget says otherwise.
- *Repeat is the operator's dial, and off exists.* `=0` on the threshold disables the watchdog and
  is documented in code and asserted in tests; `0` is returned silently, not nagged about, because
  turning a diagnostic off is a deliberate setting rather than a typo.
- *No re-logging when nothing changed.* The dump is emitted on the tick, so consecutive dumps of an
  unchanged stack are identical apart from the elapsed seconds. The elapsed value is deliberately
  printed with `%.1f` so those lines can be correlated with the station log (U01's evidence had
  second precision).
- *Only one pass is ever watched,* because `run_once` calls the pass serially — so there is one dump
  stream at a time, never one per channel.
- *First-report latency: was up to ~90 s, now bounded by threshold + one tick, and pinned by a
  test.* The original watcher's period was the **repeat** from the second tick on, so a pass that
  began mid-cycle was first reported up to one whole repeat after it crossed the threshold — at the
  shipped 30 s / 60 s that is up to ~90 s elapsed (the correction recorded in §10, R5). U04 review
  fixed the *claim*; the coordinator then fixed the *behaviour* (§12, Fix 2): the watcher now wakes
  every `min(threshold, repeat, 5.0)` and a per-pass due time decides what is reported, so the first
  report lands at threshold + at most one tick — 30–35 s at the shipped defaults, and MEASURED at
  10.01 s for a 6 s threshold against a 60 s repeat (§12). Unlike the old latency, this one is
  pinned: `test_the_report_schedule_is_the_threshold_then_a_repeat_after_each_report` asserts the
  schedule as arithmetic on an injected clock, and
  `test_a_one_second_stall_is_reported_before_it_ends_and_only_once` asserts the end-to-end case.
- *A very small operator value now costs wake-ups.* The tick is whatever `min(threshold, repeat, 5)`
  says, so `repeat=0.001` means ~1000 wake-ups a second — the brief's formula, applied exactly, not
  silently floored. Each tick is a lock acquisition and a comparison; formatting a stack and logging
  happen only when a report is due, and "due" is at most once per repeat. Reported here rather than
  defended against.

### 7.3 One more doubt, and one thing not proven

- *A stall inside a C extension with no Python frames* (e.g. a blocked native call inside ffmpeg or
  GStreamer) would still show the Python frames that led there — enough to name the *entry point*
  the pass entered, not the cause inside the C call. That is the honest ceiling of a
  `sys._current_frames()` dump, and it is still strictly more than the station had on 2026-09-24.
- *This unit does not prove the watchdog would have named the U01 stall's cause.* It proves the
  mechanism names a synchronously blocked Python call (§3). U01's 446 s stall is attributed
  (in U01) to a synchronous `SourcePreparer.prepare` inside the pass; if the real cause is somewhere
  with no Python frame on that thread, the dump would name the caller and not the culprit. That is
  the decoupling fix's problem, and this unit exists to give it evidence — which it will, in the
  first stall that happens with this code installed.

### 7.4 Test blind spots (stated, not hidden)

- 6 of 17 tests were never red (§2.1) — they reference symbols the pre-change code did not have.
- The stall is simulated by a fake daemon blocking inside `process_once`, i.e. the shape "a
  synchronous Python call inside the pass". A stall in the worker-pipe or ffmpeg subprocess path is
  not simulated (that would need the live station, which is out of bounds).
- Timing is real (0.05–0.5 s thresholds with `_wait_for` budgets of 1.0–2.0 s), so a heavily loaded
  machine could in principle make one of the wait-based assertions flake. Not observed: 5 green runs

## 8. Notes on two design decisions worth a reviewer's attention

### 8.1 Why the first check lands one *threshold* after the pass starts

The watch interval starts at the threshold and then becomes the repeat interval. A watcher that
slept the *repeat* interval from the start would miss every stall longer than the threshold but
shorter than the repeat — the band a real stall is most likely to land in at the 30 s/60 s defaults.
Asserted by `test_first_dump_lands_at_the_threshold_not_a_whole_repeat_later`.

### 8.2 Why `0` disables the threshold but is *invalid* for the repeat

The brief specifies threshold `0` as the off switch, so `zero_allowed=True` there. For the repeat,
`0` would make `Event.wait(0)` return immediately and spin the watcher re-checking a pass it just
reported — a busy-loop, not a setting. So the repeat reader rejects `0` and non-finite values,
warns, and uses 60 s. Non-finite values are rejected for both: a `nan` threshold would trip on every
pass (`nan` comparisons are never true in the direction that silences it) and an `inf` repeat would
kill the watcher's loop for the life of the service. Asserted in the parametrized invalid-value
tests (`not-a-number`, `-5`, `nan`, `inf`, `0.0.0`) and the `"0"` repeat test.
