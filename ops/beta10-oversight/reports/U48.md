## 7. Doubts

1. **The predicate is deliberately broad, and it also absorbs the capture's `UNVERIFIED`.** The order's condition is "no loudness measurement (`blocking_reasons` or no `integrated_lufs`)", and that is what is implemented — but a *short capture* and a *continuity-not-proven* window are also measurement-free, so those channels print `INSTRUMENT_ERROR` where the pre-U48 line might have said `UNVERIFIED`. The word `UNVERIFIED` therefore disappears from such a line; the reason text carries the capture's own `detail`, which says which it was. This is what the order's wording asks for, and it reads correctly (no measurement ⇒ no verdict), but it is wider than "never a loudness FAIL" strictly requires, so I am flagging it rather than letting it pass silently.
2. **Two deliveries of the same unit.** The first `bin\` revision (`7195e382` / `aa045912`) was in place for a few minutes before the reason-precedence refinement replaced it. If a rung run had invoked `rung_check.py` in that window and hit a measurement-free channel with a window `detail` but no blocking reasons, it would have printed the generic sentence. No filed evidence has that shape (§3.5), so nothing in the record is affected — but the window existed.
3. **The reason is echoed verbatim, including the doubled backslashes.** `…Permission denied: 'C:\\ProgramData\\…'` is CPython's `OSError.__str__` doubling the filename component's separators; the filed evidence carries the same string. Cosmetic, pre-existing, unchanged by this unit — but a reader may think the line is malformed.
4. **The adjudicator's own `summary` uses the fallback shape** (`public=INSTRUMENT_ERROR <detail>`, unparenthesized) for this classification, because no `summary_line` is set on the new path, while `rung_check.py`'s line is parenthesized. I chose the minimal edit over adding a summary line; if a coordinator-side reader parses the adjudicator's `summary` expecting parens, this will surprise them.
5. **The `integrated is None` branch inside `excusable()` is now unreachable** from the loudness loop (a measurement-free channel returns before it). I kept it, with an in-place comment saying why: it is the one place that says what an excusable window *is*. Dead-ish code that documents a predicate is a deliberate trade, not an oversight.
6. **Retry budget as wall clock.** 20 × 100 ms is a bound on a *reader*, and it is stubbed out of the unit tests except the one test that pins the constants and the recorded delays. If the relay's replace ever takes longer than 2 s under load, the reader still fails closed — with the same reason text as before. That is intended, not verified against a real slow replace.

## 16. Doubts

1. **`CAPTION_QUIET` on the filed verifies rests on absent evidence, not on positive evidence.** `verify-01`/`verify-04` predate the receipt, so their softening says "no worker receipt exists to contradict the FAIL" — a weaker footing than §13.2's "receipt says received=14, and the span carried 2 cues." The reason text (`?s, no cue count; the worker receipt is absent`) says so; the verdict word does not distinguish the two. A reader skimming `OK` should know which kind of quiet they are looking at.
2. **`span_seconds` is media seconds, and after a relay restart the span is not contiguous.** 12 segments × 2.0 s = 24.0 s is reported, while the emitted timestamps spanned 3.7 minutes of wall clock across two runs (§13.1). The name invites a wall-clock reading it does not have. The 900 s staleness floor cannot separate runs when the restart happens inside it.
3. **`HLS_TARGET_SEGMENT_SECONDS` (2.0) is assumed, not measured, for the span.** A relay segment that is not 2.0 s makes `span_seconds` a nominal figure. It is bounded by `CAPTION_WINDOW_MAX_SEGMENTS` (40), so a misreport cannot make the copy unbounded — but the printed span would be wrong, not merely imprecise.
4. **`CAPTION_QUIET` is printed for the whole span's FAIL without saying how many segments were clean.** `0 cue(s)` over a clean span and 30 segments decodable is the signal; the line carries the cue count and span but not the segment count. The full detail is in the JSON.
5. **Two consecutive 0-cue verifies is a *pair* of ad-hoc runs away from an outage verdict.** `previous_verify()` matches `verify-(\d+).json` in the same folder by number, deliberately not by mtime, so an out-of-band verify written beside a rung's does not supply a predecessor and the channel is judged on its receipt alone — which for the filed, receipt-less verifies means quiet. That is the safe direction (a missing predecessor cannot manufacture an outage), but it also means the second sign can be unavailable exactly when the evidence is old.
6. **A caption FAIL could in principle be softened forever.** If a channel were genuinely broken but its worker kept reporting `received>0` (captions reaching the worker, none reaching the mux), and each verify's span happened to decode 0 cues, the second sign would fire on the second verify and fail the run — so the case is covered. What is *not* covered is a worker reporting `received>0` while a decode path silently degrades to 0 cues every *other* verify; the pairing would never line up. I did not find evidence of that shape; it is a gap in the predicate, not a claim about the station.
7. **The `bin\rung.ps1` edit is mine, not the order's** (§12.2), and I am the one who decided the note belongs in the log rather than hidden. A coordinator who wants the verify line to stay exactly `OK` would rather I had suppressed it inside `rung_check.py`; I chose visibility.
