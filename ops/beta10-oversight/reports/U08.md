## 1. Part A — what the sweep actually costs (measured before any change)

**OBSERVED — instruments.** `$TEMP\u08\measure.py` wraps the exact calls `_discover_candidates` makes and
accumulates wall time and call count per phase: `Path.resolve`/`stat`/`is_file` (resolve/stat), `Path.iterdir`/`glob` (listing, drained inside the timed
region — a lazy generator otherwise reports 0 s),
`retention._sha256` (sweep digests), `review_media._sha256` (evidence verification), the WAV probe, and
the review store's `list_with_audio_evidence`/`get_audio_evidence`. It runs the policy's own
`_discover_candidates` through `CaptionEvidenceRetentionPolicy.from_system(...)`.

**OBSERVED — the archive.** Synthetic, in `$TEMP`, shaped from the live numbers in the brief: 4,998 chunks
(5,000 split evenly over `public`/`government`/`education`) at the live measured 160,044 bytes each
(5 s @ 16 kHz mono s16), plus 4,998 matching 320,044-byte evidence WAVs and matching review rows →
**9,996 files on disk**, 9,996 candidates per sweep. Two row models: **1 row per evidence file** (1:1) and
**4 rows per evidence file** (19,992 rows), the latter modelling the live coalescing shape where one ASR
window attaches one WAV to every cue it produced.

**OBSERVED — before, run against a `git archive HEAD` export of `e348bad9` (`--sweeps 2`, back-to-back with
the after run below, same machine state):**

| phase | 1 row/file (4,998 rows) | 4 rows/file (19,992 rows) |
|---|---|---|
| **total sweep 1 / sweep 2** | **25.021 s / 24.571 s** | **35.462 s / 35.083 s** |
| listing | 0.153 / 0.294 s (5 calls) | 0.056 / 0.067 s (5 calls) |
| resolve/stat | 8.855 / 8.229 s (64,983 calls) | 10.079 / 9.866 s (139,953 calls) |
| `_sha256` (sweep: chunks, unclassified evidence) | 6.323 / 6.363 s (4,998) | 3.905 / 3.717 s (4,998) |
| `review_media._sha256` (evidence verification) | 7.195 / 7.156 s (4,998) | 16.880 / 16.845 s (**19,992**) |
| WAV duration (`_wav_duration`) | 2.160 / 2.129 s (9,996) | 3.039 / 3.032 s (24,990) |
| review store lookups | 0.692 / 0.401 s (4,999) | 1.186 / 1.438 s (19,993) |

Two things this pins. (a) Nothing about a warm sweep is cheap: two full reads of the recorded audio per
sweep (`_sha256` + the evidence verification) plus a WAV probe per file, forever, at 60 s intervals.
(b) The evidence verification is the one phase that scales with ROWS, not files — 19,992 reads of 4,998
distinct files in the 4-row model.

**INFERRED — model limits, stated so the numbers are not over-read.** The archive is 1:3 of the live
public channel alone (live: 15,045 processed public chunks; the brief's evidence counts are 4,100 public /
2,771 government / 2,604 education — roughly one review row per 3.7 chunks, where this model has one per
chunk). So the live mix puts relatively MORE weight on the chunk glob loop (raw-chunk candidates) than
this archive does, and relatively LESS on the review-row loop. Absolute live times will therefore be
larger and differently apportioned; the phase identity and the per-file reuse are unaffected. Also, the
same archive measured earlier in this unit on a quieter disk gave 11.3–12.1 s for the 1-row warm sweep —
2× faster than the 24.6 s above, which is this machine's disk load, not the code (see §4's note on the
4-row pair, where the *after* run's resolve/stat cost more than the *before* run's for half the calls).

## 2. Part B — the reuse, and where it is deliberately NOT applied

### B1/B2: `_ReusableFileFacts` — one per policy object

| Line (`retention.py` @ `6b4391b1`) | Symbol | Role |
|---|---|---|
| `128` | `class _ReusableFileFacts` | the cache; docstring records the measurement and its limits |
| `169` / `173` | `begin_pass` / `end_pass` | mark one discovery; on `end_pass`, **every entry whose file the pass did not see is dropped** |
| `186` | `digest(path, stat_result)` | returns the cached digest only when `(st_size, st_mtime_ns)` match the recorded key, else calls `_sha256` |
| `198` | `duration(path, stat_result)` | same key; a probe that returns `None` (unreadable) is **never** cached |
| `238` | `self._facts = _ReusableFileFacts()` | in `__init__` — shared by every caller of the same policy object, cold for a new one |
| `432` / `553` | `begin_pass()` / `finally: end_pass()` | wrap the whole discovery body |
| `588` / `595` | `_file_digest` / `_file_duration` | the two façades the sweep body calls |
| `1001` | `_stat_regular_file` | one `stat` replacing `is_file()` + two `stat()` calls per path (that is where the 64,983 → 54,987 resolve/stat calls went) |
| `985` | `_probe_wav_duration` | replaces `_wav_duration`; returns `None` for unreadable, and `_file_duration` converts that to the historical `0.0` |

**Boundedness, stated precisely.** OBSERVED in tests: a file that vanishes is forgotten by the next pass,
so a *different* file that later reuses its path with the same size and mtime is hashed afresh rather than
inheriting the dead file's digest ([`test_a_vanished_files_entry_is_dropped_not_served`]). A changed mtime
re-reads exactly that one file ([`test_a_changed_mtime_forces_a_rehash`]). A changed size re-reads even
when the mtime is restored ([`test_a_changed_size_forces_a_rehash`]). The cache is per policy object
([`test_the_cache_belongs_to_the_policy_object`]).

**The brief's STOP condition — the finding, and what I did.** The brief said: *"If any caller relies on the
digest to detect tampering of an unchanged-mtime file, say so and STOP (questions\U08.md)."*

OBSERVED: **such a caller exists.** `review_media.verify_caption_review_audio_evidence`
(`civiccast/captions/review_media.py:84`) compares a freshly computed `_sha256(source)` against
`evidence.source_sha256` — the digest recorded when the evidence was written — and raises
`CaptionReviewClipError` on a mismatch. Its caller-facing use is the operator approval path
(`require_low_confidence_approval_evidence`, `civiccast/captions/review.py:147-178`): it is what blocks a
low-confidence cue's approval when the retained audio no longer matches the cue. A cross-sweep
`(size, mtime)`-keyed cache would answer a tampering check out of a stale read, so **the reuse is not
routed there**.

How I read the instruction, and the deviation I am flagging: OBSERVED the literal word is "STOP"; I did
not halt the unit. I read it as *do not put the cache behind that caller* — the safety-critical half of
the instruction — and then to say so with numbers, because stopping the rest of the unit would leave the
station's disk contention unaddressed for a decision that has a safe default. The delivered behaviour is
safe under either reading: the tamper check still reads the **current** bytes at every sweep, once per
sweep per file. The finding, the measured residual and a recommendation are in
`questions\U08.md`; if the coordinator reads "STOP" as "halt", the code as delivered is still the
conservative option and nothing needs reverting.

What the evidence verification *did* get is `_verify_evidence_once` (`retention.py:555`): a memo scoped to
**one sweep**, keyed on the row's recorded `(path, sha256, bytes)` identity. It removes the per-row read
for the coalesced shape (three review rows over one WAV → one read) without ever answering a later sweep
from an earlier read. A row whose recorded digest disagrees with the file is still dropped, and a tamper
performed between two rows of the *same* sweep still fails (both pinned by tests).

### B3: the review-store N+1 — where it is, and why I did not "fix" it

OBSERVED, by reading the actual API rather than assuming:

* `PostgresCaptionReviewStore.list_with_audio_evidence` (`civiccast/captions/persistence.py:237-254`) is
  **one** `select` over `CaptionReviewItem`, with its docstring naming this exact N+1 ("opening a new
  session for every row turns a large review queue into an N+1 round-trip stall").
* `InMemoryCaptionReviewStore.list_with_audio_evidence` (`civiccast/captions/review.py:285-290`) is a
  dict lookup per row with no I/O — measured at 0.692 s for 4,999 rows in the before run and 0.205 s in
  the after run (i.e. it is not a meaningful share of the sweep either way).
* It is **not** declared on the `CaptionReviewStore` protocol (`review.py:181-225` declares create, get,
  get_audio_evidence, list, approve, edit, reject). That is why `_discover_candidates` reaches it with
  `getattr` and falls back to per-row `get_audio_evidence` (`retention.py:419-429`) for a store that does
  not implement it.

So: the N+1 the brief points at is already batched for the durable store. The remaining per-row path is a
compatibility fallback for third-party/test stores only, and it is not where the sweep's time goes. I did
**not** add the method to the protocol: that is a public-contract change for every implementer, it buys
nothing measured, and it is not needed to satisfy this unit's goal. Reported, not done (§5).

## 3. Part C — the verdict refreshes on its own clock

`CaptionRetentionVerdictSource` (`retention.py:696` `__call__`, `762` `_arm_background_refresh`, `776`
`_refresh_loop`, `727` `stop`), with tests in
`tests/captions/test_caption_readiness_verdict.py::TestTheVerdictStaysFreshWithoutAStart`.

* OBSERVED the first `__call__` calls `_arm_background_refresh()` **after** the synchronous divergence
  check and **before** the fresh-verdict read, so the very first start both answers and arms. Building the
  provider starts no thread (`__init__` only creates `self._stopped = threading.Event()`), pinned by
  `test_building_the_provider_starts_no_thread`.
* OBSERVED `_refresh_loop` is `while not self._stopped.wait(self._sweep_interval_seconds)`, i.e. one daemon
  thread named `civiccast-caption-readiness-retention-timer` dispatching a sweep every cadence, with the
  body wrapped so a raising sweep cannot end the loop.
* OBSERVED `_dispatch_sweep` is unchanged: in-flight flag plus the `sweep_interval_seconds` cadence gate,
  so the refresh cannot stack scans — pinned by `test_the_refresh_never_stacks_sweeps` (a blocked sweep
  stays at one call across several cadences). The heavy half stays under `_DISCOVERY_LOCK`, so the tap's
  sweep and this one are still serialized process-wide.
* OBSERVED `stop(timeout)` sets the event and joins both threads; `test_stop_ends_the_refresh_thread` and
  `test_a_stopped_provider_does_not_re_arm` assert on the thread **this** provider armed (identity against
  a pre-start baseline), not on name-membership.
* OBSERVED the gap the coordinator named is closed by test: with `sweep_interval_seconds=0.05`, a second
  sweep runs with **no start to carry it**, and the refusal it publishes gates the **next** start
  (`test_a_sweep_re_runs_without_another_start`, `test_a_background_refusal_gates_the_next_start`).

**Sweeps per minute now (the item the U07 answer asked to be answered in the report).** OBSERVED: there is
exactly **one** provider per process — `build_channel_automation` constructs it once
(`civiccast/egress/automation.py:2710`) and the daemon calls that one object for every channel start
(`civiccast/egress/daemon.py:1576`), so part C adds **one** refresh thread, not one per channel. With a tap
worker present that is up to **2 self-gated sweeps/minute** (tap + provider), and they cannot overlap:
`_DISCOVERY_LOCK` serializes the heavy half, and the provider's own in-flight flag plus cadence gate prevent
self-overlap. INFERRED consequence of §2: in steady state each of those sweeps is now a `stat` pass plus one
evidence read per file, rather than two full reads of the archive. OBSERVED: nothing in the production
wiring calls `stop()` (`grep -rn "readiness_provider\.stop" --include=*.py .` over the worktree, excluding
`.venv`, returns nothing), so the refresh
thread lives as long as the process, which is what U07's design says it should do.

## 6. Doubts

1. **The tamper-gate reading.** I chose "do not route the cache there" over halting the unit, and said so
   in `questions\U08.md`. If the coordinator wants the stronger reading, the answer is "revert nothing,
   decide whether the residual ~2.4 s/sweep of fresh evidence reads is acceptable" — that is the real
   question, and it is a product question (what the station pays for tamper-evidence freshness), not a
   bug.
2. **Wall-clock noise.** The two measurement batches of this unit differ by ~2× on the same archive
   (11.3–12.1 s vs 24.6–25.0 s for the same before-state sweep). I have quoted call counts as the primary
   evidence and both wall-clock sets, but a reviewer should treat any single wall-clock figure here as
   load-dependent.
3. **`_probe_wav_duration` returning `None`.** The rename changed a public-ish private helper's contract
   (unreadable file: `0.0` → `None`, converted back to `0.0` at `_file_duration`). No other user exists,
   but the rename is the kind of change that is invisible until someone imports it.
4. **`unattributed` time in the 4-row after run** (6.3 s of a 40.8 s sweep) is larger than in the before
   run (0.3 s). I did not chase it; the most likely explanation is the instrumented calls now absorb less
   of the sweep and the harness's own accounted-vs-wall gap (plus allocator/GC of ~1.6 GB of hashed
   buffers) shows up outside the wrapped regions. INFERRED, not proven — flagged so nobody reads the phase
   table as complete.
5. **The refresh thread in production is never stopped.** `stop()` exists for tests and orderly shutdown;
   nothing in the daemon wiring calls it. That matches U07's design (the provider lives as long as the
   process) and `daemon=True` means it cannot hold up exit, but it is a deliberate non-call worth naming.
