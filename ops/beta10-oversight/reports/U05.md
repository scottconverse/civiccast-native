### 1.4 The explicit question: how many bounded `_run_ffmpeg`-style calls does ONE installed preparation make?

**Answer: ONE bounded call per distinct segment.** (INFERRED from the code path below, every step cited; not measured on a live station.)

The installed `GStreamer` path is `playout_trim_supported = False`. Walking `_prepare_segment` on that path:

1. `preparer.py:1388` `_check_loudness` is called at `:1642` (and again at `:1726` on the silent-asset resample branch). It delegates to `self._loudness_checker`, whose default is `check_streaming_loudness` (`:317`) and which is special-cased at `:1393`. **`check_streaming_loudness` is not `_run_ffmpeg` and carries no preparation timeout** — the timeout lives inside `_run_ffmpeg` at `:1373`. So the loudness probe consumes no bounded-pass budget.
2. `preparer.py:1779` — the full-asset-cache conform branch is guarded by `if key is not None and not trimmed and self._playout_trim_supported:`. On gst this is **False**, so `_conform_full_asset_into_cache` (`:484`, whose own bounded call is at `:550`) is skipped synchronously.
3. `preparer.py:1839` — the trimmed-MISS conform encode, `result = self._run_ffmpeg(args, cancel_event)`, bounded by `timeout=self._preparation_timeout_seconds` at `:1373`. **This is the one bounded call.**
4. `preparer.py:949` — `_emit_prepared_from_cache`'s stream copy is *also* a bounded `_run_ffmpeg` call, but it is only reachable from the `:1791` return inside the `:1779` branch — i.e. only when `_playout_trim_supported` is True. On gst it is unreachable.
5. `prepare()` (`:1231`) dedupes by `(path, inpoint, outpoint)` at `:1320–1325` and calls `_prepare_segment` at most once per distinct key (`:1328`). A single-item rollover plan therefore makes exactly one such call.

So on the installed base a single-segment preparation spends **1** of the **2** passes budgeted by `_ROLLOVER_PREPARATION_PASSES = 2.0`.

**Decision: keep `2.0`. No `questions/U05.md` was written.** `2.0` is *generous* here (it computes 690s at the shipped 300s timeout where the installed single-segment path needs 300 + 30 + 60 = 390s), and it is *not wrong*: generous is not the failure mode a rollover lead has — a lead that is too short is (that is the 2026-09-24 13:28:25 dark-channel incident this whole unit exists for). The brief's bar was "would be WRONG (not merely generous)"; it is not. Also, `2.0` is the worktree's worst case and a superset of the installed base's, so the *same* computed lead (690s) is correct for both bases — which is what a backport should preserve. See §5.2 for the one pre-existing scaling caveat, which is not introduced by U05.

## 3. Section C — doubts, gaps, and watchlist

### 3.1 Three carried-over one-C spellings in ported comments (upstream text, not introduced here)

`grep -n "CIVICA[SC]*ST_"` on the candidate `automation.py` returns three hits, and **all three are byte-identical to the worktree HEAD file** (candidate 1411/1919 ↔ worktree 1441/1944; line 260 is the U04 comment that deliberately discusses both spellings):

- `automation.py:1411` (candidate) — `_rollover_lead_seconds` docstring: "bounded by ``CIVICAST_EGRESS_PREPARATION_TIMEOUT_SECONDS``".
- `automation.py:1919` (candidate) — `_check_plan_rollover` comment: "a preparation bounded by ``CIVICAST_EGRESS_PREPARATION_TIMEOUT_SECONDS``".

These are the *legacy* spelling being named as if it were primary. They are **inaccurate naming, not incorrect behaviour** — the candidate still honours the one-C name as a legacy fallback with a deprecation warning (§2.3), so a station that sets only the one-C name still gets 300s. Fixing them would touch worktree text outside U02–U04's ported hunks and outside this unit's scope, so they are left exactly as upstream has them and flagged here. **Recommend a one-line follow-up commit in the worktree** to name the two-C spelling in both places.

### 3.2 `_ROLLOVER_PREPARATION_PASSES` does not scale with segment count — pre-existing, unchanged by U05

A rollover preparation of an *N*-segment next plan runs *N* bounded conforms sequentially (one per distinct `(path, inpoint, outpoint)`, `preparer.py:1320–1328`), so *N* ≥ 3 at a 300s timeout can exceed the 690s lead. This is **not** introduced or worsened by U05: the worktree's constant covers exactly one segment's two passes, so the identical caveat exists there at *N* ≥ 2. U05's brief was to port a constant, not to redesign the lead; a segment-count-aware lead is a separate change. Flagging it because the installed base makes it slightly *easier* to reach (3 installed segments vs 2 worktree segments before the bound is exceeded) — but on a single-item rollover plan, which is the shape `_check_plan_rollover` documents ("One scheduled item per plan"), the candidate's one-bounded-call path is comfortably inside the lead.

### 3.3 The candidate is *not* a worktree mirror, by design — and the live trial should expect that

The overlay is the installed package with U02–U04 ported in. It deliberately does **not** gain anything else the worktree has, notably the two-pass loudnorm conform (`build_loudnorm_probe_args`, `measured_loudness`). Nine `test_preparer.py` tests exercise that feature and fail on the candidate for exactly that reason. If the live trial is judged against the worktree's test suite it will look like "U05 broke nine preparer tests"; it did not — those nine fail on the pristine installed base too, for the same reason. They are drift the installed package already had.
