## 2. The "pending" semantics: quoted, and where WAV retention is enforced

`CaptionRetentionResult` (`retention.py:31-40`) has no pending field — six fields, `ready |
refusal_reason | requires_fallback_slate | deleted_paths | protected_paths | audit_records` (`questions/U07.md`
§1). The pending state that exists lives entirely in the caption tap worker, and **the egress provider never
reads it and never overrides it**. It is enforced at three points:

**(a) The tap's own pending refusal literal** — `tap_worker.py:544`:
```python
        self._retention_refusal: str | None = "retention-verification-pending"
```
with `_retention_ready = False` (`:543`). Set from the real verdict only when a sweep finishes
(`:1650-1651`: `self._retention_ready = bool(retention.ready)`).

**(b) The persistence mode that gates audio evidence** — `tap_worker.py:1884-1901`:
```python
    def _review_persistence_guard(self) -> Iterator[ReviewPersistenceMode]:
        with self._retention_lock:
            if not self._retention_ready and not self._retention_in_flight:
                yield "refused"
            elif self._retention_in_flight:
                yield "text-only"
            else:
                yield "audio"
```
consumed at `civiccast/captions/worker.py:205-217`, where the evidence WAV factory is attached only
`if mode == "audio"`; in `text-only` the review row is persisted as `payload = item` **without**
`audio_evidence`.

**(c) The raw-chunk write boundary** — `tap_worker.py:1222-1228`, where the decision is made before the WAV
is parked in `processed/`:
```python
                    if self._retention_in_flight:
                        # Captions/review text continue while periodic audio
                        # retention verification is pending. Never keep raw WAVs
                        # under yesterday's verdict or defer them into a backlog.
                        segment.unlink(missing_ok=True)
```
So while pending, the chunk is **deleted**, not retained — captions and text-only review continue, no WAV is
kept. The tap also states this in prose at `tap_worker.py:1578-1581`: *"`_retention_ready` stays False and
`_retention_refusal` stays 'retention-verification-pending', so no ASR is transcribed into an unverified
store and no WAV is retained."*

**Why that makes Option B safe:** the safety property the brief cares about ("pending captions but no
retained WAVs") is a property of the tap's state machine, never of the value the egress provider returns.
When the provider answers `_PENDING_VERDICT`, the tap is — by its own rule — in exactly the state it is
already in whenever its own sweep is in flight, which is the same state the live station has been running
in. **The provider's pending answer grants no capability the tap does not already grant itself.**

## 4. Sweeps per minute, and whether they can overlap (the coordinator's Q3 ask)

**INFERRED from code (all cadences read from the constants, none measured on a live station):**

| Sweeper | Cadence gate | Rate |
|---------|--------------|------|
| The tap worker's own sweep (`tap_worker.py:1518`, gate at `:1553` `now - self._last_retention_sweep < _RETENTION_SWEEP_SECONDS`, in-flight latch at `:916`) | 60 s, plus not-in-flight | **≤ 1.0/min**; on this archive a 60.5 s scan pushes the effective interval to ~120 s → **~0.5/min** |
| The provider's sweep (this unit, `retention.py:561`) | only when a start finds no verdict fresher than 180 s, **and** nothing in flight, **and** ≥ 60 s since the last dispatch | **≤ 0.33/min** with continuous starts; **0/min** on a station that never starts a channel |
| Both present (the lab station runs the tap inline) | — | **≤ ~1.33 dispatches/min** |

**Can they overlap? Yes — and they are therefore serialized.** They are two independent threads
(`civiccast-caption-retention` and `civiccast-caption-readiness-retention`), so nothing but
`_DISCOVERY_LOCK` (`retention.py:68`) stops both from being inside `_discover_candidates` at once. Both
callers reach discovery through `enforce_discovered` (`retention.py:272`, `with _DISCOVERY_LOCK:`), so **at
most one full scan of the archive is in progress at any instant in the process**; the second waits. The
divergence check runs *before* the lock (`retention.py:512` → `:220`), so a start's cheap refusal never
queues behind somebody else's scan.

**One consequence worth your attention (INFERRED):** because the two sweeps serialize, on today's archive
the provider's sweep can queue behind a ~60 s tap scan. With a 180 s freshness bound, a station whose archive
takes ~60 s to scan will often still find a *stale* verdict at a start — which is handled correctly (the
start proceeds pending, one INFO line per start, no stall) but means **the pending path will be the normal
path on the current archive until the archive shrinks.** That is the §6 leak, not a defect in this unit.

**OBSERVED — under what retention condition.** `_is_eligible` for `kind == "raw-chunk"`

```python

            return False
        return now - _utc(candidate.created_at) >= _RAW_CHUNK_MAX_AGE
```
So a chunk is deletable under exactly two conditions: **(i)** a verified evidence window covers it **and** it
is ≥ 24 h old (pruned with reason `raw-chunk-expired-after-derived-evidence`, `retention.py:457-460`); or
**(ii)** the channel has **no** evidence window at all (`evidence_pending` False) **and** it is ≥ 24 h old.

**OBSERVED — the asymmetry that causes the pile-up** (`retention.py:318-329, 351`):
```python
                windows = verified_windows.get(channel_dir.name, ())
                covering = tuple(... if evidence_start <= start and start + duration <= evidence_end)
                verified = bool(covering)
                ...
                        "evidence_pending": bool(windows),
```
`evidence_pending` is **channel-level** ("does this channel have any resolvable evidence window anywhere?");
`derived_evidence_verified` is **chunk-level** ("does a window cover *this* chunk?"). One evidence-bearing
review row anywhere in public's history makes `evidence_pending` True for **every** public chunk — closing
condition (ii) for the whole channel — so any chunk that is not itself covered is pinned at any age, forever.

**INFERRED — how a chunk ends up uncovered while the channel stays window-positive.** Two code-supported
routes:

1. **The chunk produced no committed cue.** The evidence WAV is written per committed review item —
   `tap_worker.py:1910-1920`'s `write_once(_cue)`, called from `civiccast/captions/worker.py:214` inside
   `for item in caption_result.review_items:`. A chunk whose ASR produced no committed cue creates no review
   row and therefore no evidence, ever.
2. **The chunk was consumed during a text-only window.** `worker.py:207-217` attaches audio evidence only
   `if mode == "audio"`; in `text-only` (the pending rule quoted in §2b) the row is persisted without
   evidence. Also, evidence WAVs are themselves subject to the 90-day resolved-evidence cap
   (`_RESOLVED_EVIDENCE_MAX_AGE`, `retention.py:26`), so a row whose WAV was pruned contributes no window
   while other rows still do — coverage can be **lost after the fact** while `evidence_pending` stays True.

Both routes are the leak the code already documents in two places — `retention.py:341-350` (*"MEASURED LIVE
2026-09-17 (Blackwell station): public/processed reached 12,980 files / 1,980.8 MB … 12,737 permanently
unprunable chunks"*) and `retention.py:436-446`. Commit `75ac6754` added condition (ii) to bound it — but
(ii) only fires when the channel is **window-free**, so "channel has windows, this chunk is not covered" is
the surviving case, and it is the one that matches public's size.

**What would settle the split (not done, needs your say-so and the load):** a read-only census over the live
archive classifying each public chunk as *covered-and-aged* (deletable now) / *uncovered-but-channel-has-windows*
(suspected majority) / *channel-window-free* (deletable now). A diagnosis, not a fix.

## 9. Doubts

1. **A failed sweep degrades to "permanently pending", not to a refusal** (`retention.py:597-611`: exception →
   log, clear in-flight, publish nothing, previous verdict stands until it ages out). That is deliberate
   (fail-safe toward airing the program, fail-closed toward evidence, and never take a station off the air
   over a transient DB fault) but it means a *permanently* broken review store is invisible in the egress gate
   except as one INFO line per start plus whatever the tap's own refusal path reports. If you want a
   consecutive-failure escalation, that is a follow-on design decision, not something I invented here.
2. **Lazy dispatch vs a self-scheduling loop.** I gate dispatch on starts so a station that never starts a
   channel never scans — the disk-contention story that motivates U07 argues against a free-running loop on
   the very volume under repair. Consequence: a verdict can be cold when the first start after a long idle
   arrives. If you prefer a warm verdict, dispatching once more from `_run_sweep`'s tail is a one-line change
   (at the cost of a continuous scan duty cycle). Flagging rather than choosing for you.
3. **A background refusal publishes for every channel already publishing status** (`retention.py:623-624` via
   `_published_channel_ids`), whereas the synchronous path publishes for the starting channel only. My reading
   of Q4's "per channel"; justified because the only refusing verdict is `caption-storage-volumes-diverge`,
   which is station-wide by construction, and because it matches the channel-set semantics of
   `reset_existing_live_sidecars` (`live_sidecar.py:105-110`). It does mean a divergent station blanks all
   channels' live captions at once (`publish_caption_runtime_status` resets `active.vtt`) — the same thing the
   tap does at its own refusal boundary, but earlier. Tell me if you want the narrower behavior.
4. **`_published_channel_ids` globs the storage root.** If a station sets `storage_root` somewhere other than
   the directory its channels publish `runtime-status.json` into, the *background* refusal publish silently
   finds nothing. Safety is unaffected (the started channel is still refused synchronously by
   `check_storage_divergence`), but the sidecar would then only be corrected by the tap's next refusal pass. I
   did not verify on a live station which directory that is.
5. **The freshness window is tested only with an injected clock** (`_Clock` in the new test file), never in
   real time; a production regression from `time.monotonic` to a wall clock would not be caught by these
   tests.
6. **No new daemon-level test asserts that a *fresh refused* verdict actually refuses a start** — the unit
