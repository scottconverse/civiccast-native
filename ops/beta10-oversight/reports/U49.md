### 3.3 No filter in the station's ffmpeg is a *true-peak* limiter

```
$ "/c/Program Files/CivicCast (Native)/dependencies/ffmpeg/bin/ffmpeg.exe" -h filter=alimiter
   level_in          <double>   set input level (from 0.015625 to 64) (default 1)
   level_out         <double>   set output level (from 0.015625 to 64) (default 1)
   limit             <double>   set limit (from 0.0625 to 1) (default 1)

   level             <boolean>  auto level (default true)
   latency           <boolean>  compensate delay (default false)
```

No oversampling option: `alimiter` is a **sample-domain** limiter, so a true-peak limiter can only be the
composition the ride already uses (`loudness_ride.py:706-715`, `aresample→4×, alimiter, aresample→1×`).

Two traps in that option list matter, and I hit the first one:

- **`level` defaults to true** ("auto level … normalizes audio back to 0dB"). My first A/B left it at the
  default and the limiter made things **worse**: emitted concat TPK **+0.3 dBTP** (from −0.8 unfixed) and
  loudness **−15.1 LUFS** (from −16.1) — an illegal +1.0 LU shift. Every case in §4 pins `level=0`.
- **`latency` defaults to false**, so `alimiter` does not compensate its lookahead delay. Dropped into the
  live relay as-is it shifts audio against video. (Read from the option list; I did **not** measure the A/V
  offset — §7.)

### 3.4 A pre-encode ceiling cannot bound a post-encode overshoot

The live event started from a prepared artifact whose own guard is `TP_GUARD_MAX_PEAK_DBFS = 0.1`
(`loudness_ride.py:1816` — "no decoded sample above +0.1 dBFS") and still reached **+1.16 dBFS** emitted,
after two AAC generations. A ceiling in front of an encoder constrains the encoder's *input*; it does not
constrain what the encoder *emits*, and AAC overshoot is content-dependent. Any fixed pre-encode ceiling
leaves a residual. Work 3's test as literally specified — "asserting emitted true peak <= +0.1 dBTP" — is
therefore not satisfiable by the mechanism the brief prescribes, and writing it first would be writing a test
to fail.

## 6. A finding about the acceptance statistic itself

This is the second substantive result and it **corrects** what I filed first. It is the reason every number in
§2 and §4 is a per-segment measurement rather than a window maximum.

**OBSERVED — the mechanism.** `scripts/capture_emitted_hls_audio_proof.py` builds its loudness/peak figure by
**concatenating** the captured segments and running `ebur128=peak=true` over the joined window
(`:1081-1088`), then takes the last `Peak:` line (`:1012`, `"true_peak_dbfs": last(_LOUDNESS_PEAK_RE)`). The
brief's OBSERVED table is a column of those window maxima. A window maximum is not the maximum over the
window's segments — **in either direction.**

**(i) It under-reports.** `emitted3/education/seg000000598.ts` measures **+1.2 dBFS on its own** (§5). As the
117th file of a concat list, the window reports a cumulative maximum of **+0.8**, and +0.8 is where it sits
for every longer prefix tried:

```
prefix= 60  Peak=-0.0 dBFS      prefix=117  Peak=0.8 dBFS
prefix=116  Peak=-0.0 dBFS      prefix=130  Peak=0.8 dBFS
                                prefix=180  Peak=0.8 dBFS
                                prefix=243  Peak=0.8 dBFS
```

A true-peak estimate cannot fall below the largest sample decoded (0.97 dBFS here), so the joined window is
not decoding the same signal the member file decodes.

**(ii) It over-reports.** Case B2's window reports `Peak: 0.3 dBFS` while all 91 member segments measure
≤ −1.5 dBFS and the window's own decoded samples top out below full scale:

```
$ ffmpeg -i ab2/B2/all.ts -vn -af ebur128=peak=true -f null -   ->  Peak: 0.3 dBFS
$ python where2.py ab2/B2/all.ts  ->  max |sample| = 0.919989 (-0.7244 dBFS), samples with |v| > 1.0: 0
```

**(iii) The cause, measured.** Re-encoding the same audio into longer joins progressively changes it. The
*same* excursion, decoded four ways:

| joined as | decoded position | max \|sample\| | ebur128 window Peak |
|---|---|---|---|
| `seg000000598.ts` alone | 1.3486 s into the segment | 1.118059 (**+0.97 dBFS**) | **+1.2** |
| `597`+`598` remuxed | 3.3540 s | 1.109590 (+0.90) | +1.1 |
| `597`+`598`+`599` remuxed | 3.3540 s | 1.109590 (+0.90) | +1.1 |
| all 243 remuxed (`sweep3/edu-all.ts`) | 233.3486 s | 1.068281 (+0.57) | **+0.8** |

The 243-segment join shifts the timeline by **~0.58 s** and the excursion's amplitude falls from +0.97 to
+0.57 dBFS along the way. Frame counts show the join both adds and loses audio: the 243-segment window
decodes **23 405 568** frames where its members sum to **23 386 320**; the pair and trio decode 192 512 /
287 744 where 2 × 96 256 and 3 × 96 256 are expected.

**INFERRED (labelled as inference — I did not instrument the concat demuxer):** joining independently encoded
HLS segments produces a stream whose decode is not the concatenation of the members' decodes; timestamps
overlap at the joins, so each boundary's AAC overlap-add is reconstructed from the wrong neighbour and the
demuxer shifts or drops frames. One mechanism, which is why (i) and (ii) point in opposite directions.

**Consequence for this unit:** the brief's table cannot be read as per-segment maxima — some of its cells may
be join artifacts and some real events may be damped below the limit by the join. **Nothing in this report
depends on a window maximum.** I did not modify `scripts/capture_emitted_hls_audio_proof.py` or
`bin\rung_check.py`; whether the statistic should change is Q4.
