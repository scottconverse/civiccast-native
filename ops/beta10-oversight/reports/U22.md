## 0. Headline

**OBSERVED — the ~3 s is one greedy 10-second decoder pass, and the batch is
twice the audio the brief assumed.**

- One `asr_process_batch` is **one 10 s window** (the shipped 5 s segment plus the
  shipped 5 s overlap), not ~5.4 s of audio. The brief's "~900 segments/600 s →
  ~2.7 segments (~5.4 s audio)/batch" does not match the station:
  `asr_process_batch count=335` over a 600 s window (§1.3) with ~112 settled
  segments per channel per 600 s — i.e. ~1 window per batch, 10 s each, **3350 s
  of audio decoded per 600 s of wall time**.
- **OBSERVED — 82–88 % of that time is `ctranslate2 ... .generate`**, the
  autoregressive decoder loop. Decode, VAD, mel filterbank and the encoder are
  each ≤ 6 %. Stabilization is 0.38 ms — 0.013 %.
- **OBSERVED — the retry-ladder hypothesis is REFUTED.** Every window cost
  exactly **one** `generate` call (12/12, `retry_fraction` 0.0). The multi-second
  tail is not faster-whisper's temperature fallback.
- **OBSERVED — no transcribe kwarg, no `compute_type`, and no `num_workers`
  change is a usable lever.** All measured at ≤ 8 % (several negative); the one
  large lever (`without_timestamps`) loses 9.5 % of words and 39.8 % WER.
- **OBSERVED — the brief's target (p95 < 2.0 s for 3 concurrent channels) is not
  reachable by configuration.** At n=90 per arm: shipped overlap 5.0 s → p95
  2590.0 ms; overlap 2.5 s → p95 2200.2 ms. Both fail. The nearest legal arm
  costs 41 % of on-air words.
- **OBSERVED / INFERRED — the pauses are a tail problem, not a mean problem.**
  Mean per channel is 2.8–3.4 s against a 5 s cadence (the tap keeps up), yet the
  station logged **19 overload events in 67.5 min**, often tripping two or three
  channels within seconds of each other, and a 3-channel concurrent run
  reproduced it twice: a **10 568 ms** worst window at n=90 and a **15 999 ms**
  worst window at n=180, with round-wall p95 **5.43 s then 12.28 s** against a
  5.0 s cadence. The p95 is reproducible (2590 → 2619 ms); the tail's size varies
  but its existence does not. A shared-resource stall is the shape (INFERRED);
  the temperature ladder is not the cause (OBSERVED, refuted).

### 1.4 The call itself, with the exact arguments

**OBSERVED** — `civiccast/captions/runtime.py:888` (`_transcribe_chunk`), the
`transcribe` call at `:898`:

```python
with TemporaryDirectory(prefix="civiccast-caption-") as temp_dir:
    wav_path = Path(temp_dir) / "chunk.wav"
    _write_pcm_chunk_wav(chunk, wav_path)

    segments, _info = self._model_instance().transcribe(
        str(wav_path),
        beam_size=self.beam_size,
        language=self.language,
        task=self.task,
        vad_filter=self.vad_filter,
        initial_prompt=initial_prompt,
        **({"word_timestamps": True} if self._live else {}),
    )
```

- `word_timestamps=True` **is** set on the live path. It is load-bearing: the
  live stabilizer's word path (§1.6) reads `hypothesis.words`.
- `initial_prompt` is `None` on the live path — `_build_initial_prompt`
  (`runtime.py:978`) returns `None` when vocabulary is `None`, and the live tap
  passes none. **There is no prompt conditioning in live.**
- Words are made absolute against the chunk: `chunk.start_seconds +
  float(word.start)`; one merged live `CaptionHypothesis` per chunk carries
  `audio_window_start_seconds=chunk.start_seconds`,
  `audio_window_end_seconds=chunk.end_seconds`, `words=live_words`.
- `_segment_confidence` (`runtime.py:994`) = `exp(avg_logprob) * (1 -
  no_speech_prob)`, rounded to 4 dp.

### 1.5 How the 3 workers are used, and the batch geometry

**OBSERVED** — `civiccast/captions/tap_worker.py:165` `default_max_channel_workers`
returns `min(3, max(1, runtime.num_workers))` → **3** on this box. One
`LiveCaptionWorker` per channel; **all three call ONE shared `WhisperModel`**
(the runtime caches a single instance behind `self._model_lock`,
`runtime.py`). There is no per-channel model and no batching across channels.

The docstring states the design assumption, verbatim:

> serial 2.75-second GPU calls take roughly 8.25 seconds per cycle and inevitably
> build backlog, while three GPU calls in flight stay inside the segment interval.

**OBSERVED** — the window is built by `_with_overlap` (`tap_worker.py:2145`
*HEAD*, `:2086` *installed*): with a usable previous segment it returns
`AudioChunk(start_seconds=current.start_seconds - actual_overlap, ...,
pcm_s16le=previous.pcm_s16le[-overlap_bytes:] + current.pcm_s16le)`. So the
default 5 s overlap makes every ASR window **10 s of audio advancing 5 s**.

**OBSERVED** — `tap_worker.py:299` `max_backlog_segments: int = 2`; `:514`
(HEAD) raises `ValueError("Caption tap overlap_seconds must be greater than
zero.")`, so **overlap 0 is not a legal configuration**.

### 1.6 The stabilization path (why `word_timestamps` cannot be dropped)

**OBSERVED** — `civiccast/captions/pipeline.py:88-95`:

```python
with self._phase("runtime_transcribe"):
    ...
with self._phase("caption_stabilize"):
    ...
    expired_before = self._stabilizer.expired_unconfirmed_count
    for hypothesis in hypotheses:
        committed_cues.extend(self._stabilizer.observe(hypothesis))
    expired_unconfirmed_cues = self._stabilizer.expired_unconfirmed()[expired_before:]
```

**OBSERVED** — `civiccast/captions/stabilize.py:124` `_observe_live_words`:

- `if self._last_word_window is not None and window <= self._last_word_window:
  return []` — the *same* window observed twice is not a vote. **A word can only
  be confirmed by a later, advancing window that overlaps it.**
- `compatible(i, j)` (`:153`) needs exact casefolded token equality **and** a
  non-empty intersection of four intervals (prev word span, cur word span, prev
  audio window, cur audio window).
- An accepted run needs `len(run) >= 2 or len(incoming) == len(old) == 1`.
- Words that never get a second confirming window go to `_expired_unconfirmed`
  via `_review_words` (`:251`) and **never reach air**.

**Therefore (INFERRED from those OBSERVED facts):** the overlap is not a
performance knob that happens to be 5 s — it *is* the confirmation mechanism. It
is the only reason a second window exists to re-observe a word. Lowering it
mechanically lowers caption yield, which §4 measures.

`_build_cue` (`:510-515`) sets `low_confidence = hypothesis.confidence <
low_confidence_threshold` (0.75, `:40`) **when not explicitly passed**, so a
*confirmed* cue can still be flagged low-confidence.

## 6. Recommendation

**No code change follows from this diagnosis; the brief's target is not reachable
by configuration.** Stated with the numbers:

1. **Do not ship any transcribe-kwarg, `compute_type` or `num_workers` change.**
   Every measured lever is ≤ 8 % or negative (§3.1, §3.1 table 2), and several
   are within run-to-run noise (`language="en"` measured 0.985 and 0.801 in two
   harnesses). Cost: zero. Benefit: ~zero.
2. **The only configuration lever is the tap overlap, and it is a word-dropping
   speedup.** Window = 5 s + overlap and RTF ≈ 0.20 under 3-way concurrency, so
   the overlap is the cost. Moving 5.0 → 2.5 s buys **p95 2590 → 2200 ms (−15 %,
   ratio 0.849)** and round-wall p95 **5.43 → 2.27 s**, at a measured cost of
   **41 % of on-air words (51 vs 87 over 12 windows)** and **no** change in cue
   count (10 vs 10). **This must be said plainly: it drops words.** I do not
   recommend it without the owner's call (doubt D1).
3. **The brief's p95 < 2.0 s target is unreachable on this box by configuration.**
   Both the shipped 5.0 s arm (p95 2590.0) and the 2.5 s arm (p95 2200.2) fail at
   n=90. To reach < 2.0 s p95 you must decode less audio: overlap ≈ 1.0 s (on-air
   words 7 vs 87, −92 %) **or a smaller model** — and only
   `packs\captions-floor\models\faster-whisper-medium` is installed, with
   first-use download forbidden (`runtime.py:660-666`), so a model swap is a new
   pack, not a configuration change.
4. **The smallest change that is actually justified is a fix to the tail, not the
   mean.** Per-channel mean is 2.8–3.4 s against a 5 s cadence — the tap keeps up
   on average. The pauses come from the tail (19 events / 67.5 min; reproduced
   twice — 10 568 ms worst window and 5.43 s round-wall p95 at n=90, 15 999 ms
   and 12.28 s at n=180; simultaneous multi-channel trips). Two named next units,
   in order:
   - **U-next-A (cheap, no code):** establish whether the station's ASR may share
     the adapter with ~25 desktop GPU clients. `nvidia-smi` at sample time lists
     browsers, overlays, an Epic launcher and two AI desktop apps. The docstring
     at `tap_worker.py:165` assumes "three GPU calls in flight stay inside the
     segment interval" — measured true for the mean (2.614 s round wall) and
     **false for the p95** (5.426 s). If the station is meant to be real-time,
     this is a deployment requirement, not a tuning problem.
   - **U-next-B (the only measured ≥ 1.4× lever):** a `BatchedInferencePipeline`
     prototype that **preserves `word_timestamps=True`** and the per-window audio
     bounds the stabilizer needs. `final-batched.txt` shows 0.562 on a 10 s window
     and 0.445 on 30 s audio — but that measurement is confounded with
     `without_timestamps=True`, which is disqualified, so it is a hypothesis, not
     a result (§7, doubt D5).

**Answer to the brief's literal ask** ("smallest change bringing mean batch time
well under the audio duration with margin"): the mean is *already* well under the
audio duration — 2203 ms against 10 s (RTF 0.204) at 3-way concurrency, 1.86×
throughput headroom station-wide (§1.3). The mean is not the defect. Under the
brief's *stricter* p95 < 2.0 s target, the honest answer is: **not reachable by
configuration; nearest reachable is overlap 2.5 s at p95 2200 ms and −41 %
on-air words.**

## 7. Doubts and open questions

- **D1 (product decision — blocking the only speed lever):** what is the minimum
  tap overlap that still produces acceptable live captions? The bench cannot
  answer this: overlap 2.5 s costs 41 % of on-air words, 1.0 s costs 92 %, 0.0 s
  costs 100 % of cues. **Filed in `questions/U22.md`.**
- **D2:** may `language` be pinned to `"en"`? It measured 0.985 and 0.801 in two
  harnesses (not reproducible), WER 0.015, but the spec's translation feature
  (Spanish) means a pinned source language is a product decision, not a bench
  result.
- **D3 (drift finding):** `station-set.json`'s `runtime` block
  (`caption_device: cpu`, `caption_compute_type: int8`,
  `caption_model_root: components/captions-large-v3/...`) is **stale and
  misleading** — none of it is in force and the named model is not installed
  (§1.1, §1.2). It is not a U22 deliverable but it is exactly the kind of record
  that costs the next engineer an hour.
- **D4:** is it intended that **every** committed live cue is flagged
  `low_confidence` (100 % at every tested overlap, threshold 0.75) and that
  roughly half the transcribed words expire unconfirmed? If the station is
  emitting low-confidence cues on air continuously, the 3 s latency is not the
  first caption problem. **Filed in `questions/U22.md`.**
- **D5:** the batched pipeline's 0.562 is confounded with
  `without_timestamps=True`; whether it can keep `word_timestamps=True` **and**
  the per-window absolute word timestamps at a useful batch size is unmeasured.
- **D6 (measurement environment):** every number here was taken on a **shared
  desktop GPU** with the live station running and my own harness competing for
  the same adapter. §3.2's pairing cancels ambient *drift* between arms but not
  absolute contention; all absolute milliseconds are therefore upper-bound-ish
  for an exclusive station GPU, and the *ratios* are the durable results.
- **D7:** the tail's cause is **INFERRED, not measured**. I refuted the retry
  ladder and reproduced the stall, but I did not instrument the stall itself.
  Naming it as GPU preemption is a hypothesis with supporting observations, not a
  proof.
- **D8 (brief premise):** the brief's "~900 segments/600 s → ~2.7 segments (~5.4 s
  audio)/batch" is wrong on both counts — the station runs ~335 batches of ~10 s
  each per 600 s. Every conclusion in this report is computed from the observed
  figures, not the brief's. **Noted in `questions/U22.md`.**
