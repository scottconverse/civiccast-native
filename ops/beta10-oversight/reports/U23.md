## 2. What it does now

### 2.1 The catch-up (work item 2)

The trigger is **unchanged** — the U11 persistence window. What changed is the action at
the trigger, in `run_once` (`civiccast/captions/tap_worker.py:1438`, inside the
over-limit branch that opens at `:1401`):

```python
                    if not self._catch_up_must_pause(channel_id):
                        kept, shed_count = self._shed_backlog_to_catch_up(
                            channel_id, queued_segments
                        )
                        dropped += shed_count
                        batch_id = self._begin_batch(...)
                        pending.append((..., kept, ..., batch_id, True))
                        self._reset_overload_persistence(channel_id)
                        continue
```

`_shed_backlog_to_catch_up` (`:1017`): `keep = self._max_backlog_segments` (`:1052`),
`shed = queued_segments[:-keep]`, `kept = queued_segments[-keep:]`; pop
`_previous_segments` under the session lock (`:1058`); record the discard
(`reason="max-backlog-catch-up-shed"`, `queue_depth=len(queued_segments)` — the depth the
gate saw, `:1059-1066`); measure the skipped seconds **before** unlinking (`:1072`);
unlink; append the shed to `_catch_up_sheds`; **one** WARNING (§5); return the kept batch,
which is submitted on that same scan with `deferred=True`.

No pause, no generation bump, no caption clear, no `paused` status, no drain. The episode
ends when the shed resolves it (`_reset_overload_persistence`, `:1465`), so a later
overshoot starts a fresh streak; the **shed history survives**, because it is the
escalation evidence.

**Why keep `max_backlog_segments` (2) rather than 1.** (a) It is exactly the size of the
legal deferred batch this tap already submits, so catching up never issues a *larger* ASR
call than the station was already making — the shed cannot make the backlog worse.
(b) The stabilizer's confirmation mechanism is the 5 s overlap between consecutive windows
(U22 §4: dropping it drops words). Keeping 1 would resume on half a window with no overlap
partner, *and* would discard the newest audio's context exactly when the model is already
behind. Keeping 2 resumes with a normal, fully-overlapped pair.

### 2.2 The seam guarantee

A window handed to ASR must be contiguous audio; the batch after a shed must not
overlap-join across the gap. Three independent layers, in order of directness:

1. **Belt.** `_shed_backlog_to_catch_up:1058` pops `_previous_segments` for the
   channel, so `_with_overlap` has nothing to join to on the first window after the gap.
2. **Suspenders.** `_with_overlap` (`:2458`) independently refuses the join —
   `previous_index + 1 != index` and the sample-rate check, then
   `abs(previous.end_seconds - current.start_seconds) > sample_tolerance`. A shed leaves at
   least one whole segment between the last transcribed and first kept segment, so both
   guards fail across the gap.
3. **The existing read-failure pop.** Windows are built **per segment** (`:1693-1706`), and
   an unreadable segment already pops `_previous_segments` (`:1698`) — the same
   "no join across missing audio" rule the shed relies on, already in the code.

The pop can never cost a legitimate overlap: a shed by construction leaves ≥1 whole segment
between the last transcribed segment and the first kept one, so the join it discards was
never legal.

The stabilizer needs no help: `_observe_live_words` expires every pending word whose
`min(word.end, window_end) <= new_window_start` into the review-only `_expired_unconfirmed`
track, so a forward jump ages pre-gap words **out**, and an on-air cue requires word-time
overlap across two windows. A discarded second therefore cannot air.

### 2.3 The retained ladder, redefined

The pause is now for a channel that is **not** a transient: it has shed
`catch_up_shed_limit` times (default **3**) inside `catch_up_shed_window_seconds` (default
**300 s**). `_catch_up_must_pause` (`:1002-1015`) is
`self._catch_up_sheds_in_window(channel_id) >= self._catch_up_shed_limit`.

Justified from U22's numbers, in the code (`DEFAULT_CATCH_UP_SHED_LIMIT`, `:184`, derivation
comment `:164-183`): the
U11 window is 15 scans = 30 s, already 1.57× the worst transient ever measured (U10 max
per-batch ASR 19.08 s; U22 observed 19.5 s) — so **one** GPU stall cannot produce even one
shed; the over-limit stretch must persist a whole window first. Three sheds inside five
minutes therefore needs ≥ ~90 s of over-limit scans in that span (three whole windows),
which no transient produces. A channel that genuinely cannot keep up sheds about once per
persistence window (~30–40 s, since a shed leaves exactly a legal batch of work) and
escalates after ~105 s instead of limping at a growing loss. `1` escalates on the second
episode; `0` is the documented escape hatch back to the pre-U23 rule (pause on the first
persistent overshoot) — the history is then always empty and `0 >= 0` is true on the first
episode (`:1009-1015`).

The shed history is cleared at a session boundary/reset (`:1220`, `:1261`), a flush, and
when the ladder takes over (`:1487`) — deliberately **not** on a healthy scan: a shed
leaves exactly a legal batch in flight, so the very next scan would erase the history that
tells a transient from a box that cannot keep up. It also expires on its own window
(`_catch_up_sheds_in_window`, `:985`), so a station that recovers returns to catch-up
behaviour rather than carrying a stale verdict.

A shed is **not** an overload: `overloaded_channels`/`paused_channels` stay empty and the
published state stays `within-capacity` with `consecutive_overloads` 0, so the state file
keeps meaning what it always meant.

### 2.4 CPU-only runtimes (1 caller)

The shed is a **filesystem/queue decision, not a worker-pool one** — it does not touch
`default_max_channel_workers` or the executor bound. A CPU-only station (one caller,
station-wide, `:232-234`) behaves identically: a channel whose settled backlog persists
past the window sheds its oldest audio and resumes on the newest. Because a CPU station can
only work one channel at a time, a three-channel CPU station that is genuinely short of
cycle sheds regularly and escalates to the retained pause — which is the correct answer for
it, since the pause is the only thing that actually stops the work. INFERRED (from the code
path, not measured on a CPU station): no CPU-station run of the catch-up was performed in
this unit. What the shed *cannot* do on any hardware is change concurrency, so the CPU
behaviour differs from CUDA only in how often the trigger is reached.
