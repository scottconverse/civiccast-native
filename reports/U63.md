## 1. Plain English

### A — education: about five minutes of filler where a programme was due (00:37:22 → 00:42:07)

At **00:28:38.238** the channel automation asked the schedule what was due at the boundary where the
live 554 s plan ended. It got **no answer at all** — its own lead line says *"no asset duration
available for the boundary"*. The code read "no answer" as "nothing is scheduled": it set
`force_fallback` and put the fallback slate on air. A programme *was* due at that boundary. The
slate stayed up for about five minutes, until the daemon noticed on its own and did a cold 276.9 s
conform to get the programme on air at ~00:42:07.

**Why the answer was empty.** The automation asks about `plan_end_at`, which is a **derived**
instant — `starts_at + sum(durations)`, never measured — so the question lands exactly on the
closing item's own slot end, and the scheduler's half-open item test (`starts_at <= t < ends_at`)
excludes that instant. The daemon asks from its own `now` instead, which is why the daemon got an
answer and the automation did not.

**The incident doc's hypothesis is refuted.** The doc says the automation was handed a 23.5 s tail of
the closing item and chose filler. It cannot have been: the "use the answer as-is" branch needs
`fresh_end <= plan_end_at` with `fresh_start = max(now, plan_end_at) = plan_end_at`, which forces
`fresh_seconds <= 0` — and 23.5 s is not ≤ 0. The 23.5 s is the **daemon's own** measurement on its
own clock at its own reload: its line is stamped 00:37:28.275 against a plan whose declared end was
00:37:52, and 00:37:52 − 00:37:28 = 23.5 s to the tenth. Two processes, two instants, five minutes
apart. The arithmetic is in `evidence/live-edu-0028-0042-window.txt`.

**The fix.** `_resolve_rollover_tail` re-asks the provider **where the answer's own tail ends**
(`boundary + tail_seconds + 1.0 s`) and adopts that plan **only when it is strictly longer than the
tail**. It returns the original plan by identity whenever the answer is at or above the floor,
whenever the second look finds nothing to air or no improvement, and on `SourcePrepareError`. This is
the rule the daemon already applies at reload time (`EgressDaemon._resolve_schedule_tail`), so the
two processes now give the same answer at the same boundary. Filler stays correct for a real gap.

### B — government: a 155 s plan on air with a cold 1800 s item behind it (slate ~00:37:30 → ~00:40:30)

The 155 s plan itself rolled over cleanly at 00:23:53 (prepared in 2.4 s). The item due behind it was
a **cold 1800 s asset**: its preparation was queued at 00:35:22 and finished at 00:40:25 — **302.8 s**
— so the channel sat on the in-worker slate for about three minutes while the horizon went past due
by 2 s, then 63 s, then 124 s.

**Where the 155 s plan came from.** From the boundary provider — the 00:23:48.598 lead line names
`Senior Citizens Advisory Board - June 2026.mp4 (155s at 12x + 120s)` and the 00:23:53.450 prep line
confirms `1 segment(s)`. The rollover was correct. What failed is the **look-ahead**, the mechanism
that exists precisely for this regime (a plan shorter than the lead). On the 00:23:48 tick:

```
lead = 690 s;  now = 00:23:48.598  ->  savable_at = 00:35:18.6
boundary = fresh_end = 00:38:53 (00:35:18 + 155 s);  previous_start = 00:35:18

STEP 1  boundary 00:38:53:  dispatch_at = max(00:35:18, 00:38:53 - 690s) = 00:35:18
        OLD test  dispatch_at >= savable_at  ->  00:35:18 >= 00:35:18.6  ->  FALSE
        -> falls through. The boundary that needed warming is skipped.
STEP 2  boundary 01:08:53:  dispatch_at = max(00:38:53, 01:08:53 - 690s) = 00:57:23
        OLD test  TRUE  ->  warmer wakes here and the walk RETURNS.
        -> the item warmed is the one AFTER the one that needed it.
```

The two numbers in step 1 are **0.6 s apart**, and `savable_at` is `now + lead` off the tick's clock
while `dispatch_at` derives from the plan's declared end — so the comparison lands on whichever side
that declared end happens to fall. Here it fell on the wrong side. The 1800 s item first appears in
the log at **00:35:19.484**, printed by the tick that *dispatched* it, not by the 00:23:48 tick that
could have warmed it.

**The fix.** One added clause:

```python
if dispatch_at >= savable_at or dispatch_at <= previous_start:
```

`dispatch_at <= previous_start` means this boundary's own dispatch has collapsed onto the instant we
are dispatching from — the horizon is already inside the lead — which the `now + lead` test alone
rejects by the poll overshoot. That collapse is exactly what a plan shorter than the lead does to
every boundary after it. Only the first step can reach it, so later steps are unchanged. Warm is
fire-and-forget on one background thread with a single conform thread, so it cannot delay the
reload's synchronous prepare, and the shared cache key is deduped by `_warming`, so there is no
double encode.

## 5. Risks

1. **A re-asks the schedule provider.** One extra call per degenerate boundary (answer below 30 s),
   on the same thread that already calls it. It cannot fire when the answer is ≥ 30 s, and it returns
   the original plan on any error — so the worst case is a duplicate query, not a bad plan.
2. **The 30 s floor is a policy number.** It matches the daemon's `SCHEDULE_GAP_ABSORB_SECONDS` tail
   rule, so the two processes agree — but if that daemon constant is retuned, this one does not follow
   (see the divergence note in §6). A tail between 0 and 30 s now resolves to the next programme; a
   genuine gap still resolves to filler.
3. **B widens when the warm starts.** It starts the conform at the dispatch instant instead of one
   plan later. The cache key is shared and `_warming`-deduped, so it cannot double-encode; but it does
   mean more conform work can overlap a reload's own synchronous prepare on the single conform thread.
   The alternative — not warming — is what produced the 302.8 s cold conform on air.
4. **Neither fix addresses the ~28–30 s base offset** (A1's open sub-piece, §7) or the engine's
   EOS timing. A fixes the *empty answer*; on its own that is enough to stop the filler in this shape,
   but the engine reaching EOS ~28–30 s before the declared horizon is untouched and will move when
   the changeover happens.
5. **The fix is validated by replay, not by a live run.** No station action was permitted, so the
   proof is: RED/GREEN on frozen bytes, a whole-tree differential, and the live log arithmetic. The
   next real boundary of each shape is the first live observation.

## 6. Deliberate divergences from the brief (stated loudly)

- **The floor is 30 s, not "shorter than the rollover lead."** The brief asks for the next programme
  when the answer is *shorter than the rollover lead*. The deployed lead on C14 is **690 s**; using it
  as the threshold would cut any legitimate short item under 11.5 minutes and skip to the programme
  after it. The floor is instead `_ROLLOVER_TAIL_FLOOR_SECONDS = 30.0`, matching the daemon's
  `SCHEDULE_GAP_ABSORB_SECONDS` tail rule. This is a change to the letter of the brief in service of
  its intent.
- **One divergence from the daemon is deliberate and documented**: the daemon also bails on
  `tail_seconds <= 0.0`, while an empty answer is precisely the case this rule exists for at the
  automation. The daemon never sees a 0.0 tail (its `source_plan` is always a plan it resolved for
  some instant), so its guard is defensive only.
- **The constants are restated, not imported.** The comment in the code gives the real reason —
  policy ownership — and not an import-direction rationale, which would have been false.

## 7. What is not proven, and what is disclosed

**Open, recorded as open rather than settled:**

1. **A1's ~28–30 s base offset is OPEN.** The engine reached EOS at the 00:37:22 changeover while the
   plan's declared end was ~00:37:52, so the slate came up ~28–30 s before the horizon the automation
   computed against. The leading candidate is the deferred-start anchor rule in
   `_establish_horizon_from_dispatch`; it is reported as a **candidate, not a finding**, and no code
   was changed for it. Work A addresses the *empty answer*, which is a separate and independently
   sufficient cause.
2. **B's warm side cannot be read off the logs.** `warm_source_plan` and `SourcePreparer.warm_plan`
   log on **FAILURE only**, and the window shows no warm, look-ahead, or conform-cache line for the
   1800 s item at any tick. Because a successful warm is silent, that absence proves nothing by
   itself: "the 00:23:48 walk warmed nothing" rests on the **walk arithmetic**, not on a log line.
3. **The 107 reds in `tests/egress` are undiagnosed** (§4). The delta is the claim.

**Disclosed:**

- **Install path.** The brief spells it `C:\Program Files (x86)\CivicCast (Native)\…`; that path
  **does not exist** on C14. The install tree is `C:\Program Files\CivicCast (Native)\` — the same
  non-`(x86)` spelling U62b's install note used. Exactly one copy of the module.
- **Uncommitted overlay.** The worktree carries the station's installed `civiccast` package as an
  uncommitted overlay: **30 modified + 5 untracked paths** (35), measured at the slice commit. None
